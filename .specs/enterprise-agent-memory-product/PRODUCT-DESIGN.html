1.4 这个产品不做什么（边界）

边界即需求。以下每一条都是明确的产品承诺，越界即视为缺陷。

不做理由 / 替代做法
不做新的 Agent Harness 或编排运行时执行属于 Codex / Claude Code / DSH 等外部 Harness；平台只治理证据与记忆，不接管执行循环。
不提供 public Memory长期 MemorySpace 的 owner 只有 user | team | project | agent 四类。需要跨边界复用时走「分诊 → 脱敏 → 审核 → 发布为 Wiki / Skill / Template」。
不用一张泛化 Asset 表替代专业资源Wiki、Code、Skill、Template、Memory 各有来源、版本、编辑与阅读语义；资源库只做授权后的发现与跳转，不编辑。
不把「关联 / 可见」当作「可写 / 可执行」owner ≠ visibility ≠ ACL ≠ execution authority；发布或检索不授予执行权。
不在原型里执行真实副作用不真实删除、不擦除终端、不迁移、不发送通知、不跑生产 Run、不暴露凭据明文。
不把阶段性方案写成最终结论Schema、阈值、算法、SLA、责任矩阵、合同与法域模板一律标注待确认，实现前另开 change。

2.1 五个不能混淆的维度

产品中最常见的误用，是把下面五个维度当成一件事。它们各自有独立的权威来源，任何一个都不能推导出另一个。

维度回答的问题权威来源不可推导的结论
Identity
身份		谁在发起这次请求？认证出的 Principal；无法识别真人时为 actor_unknownKey 的登记人不等于实际操作者。
Relation
关系		两个对象之间是否有关联？成员关系、归属边、Agent 关联、资源挂载有关联不等于可以修改这个关系本身。
Ownership
归属		内容由哪个边界负责？Project 的 owning Team；资源 owner 与 ACL创建者不等于 owner。
Context
工作上下文		本次工作在哪里发生、读哪里、写哪里？ContextBinding最近访问的项目或仓库路径只是提示，不是绑定。
Authorization
权限		当前主体能执行什么动作？凭据 scope ∩ 成员/绑定授权 ∩ 资源 ACL ∩ 继承策略 ∩ 动作策略 ∩ 委托与 RunGate可查看不等于可写；可使用不等于可管理。
被明确禁止的权限推导
  • Team 成员 不等于 该 Team 关联 Project 的成员。
  • Team↔Project 的关联 不等于 项目读写授权。
  • Agent 被列入 Team / Project 不等于 Agent 可写、可调用工具或可审批。
  • 当前 Team / Project 的筛选范围 不等于 授权或执行绑定。
  • Agent 的 mounted 资源 不等于 某次 Run 的 effective 资源。
  • 服务凭据的创建者 不等于 服务主体的权限来源。
  • 历史 Snapshot 不等于 可以绕过当前撤权。
  • Agent 提出候选 不等于 Agent 可以审批或发布。

对象定义

2.5 执行与人工闸门

产品里有两个不同的「批准」，它们解决不同的问题，不能互相替代，也不能共用一个状态字段。

ChangeSet Review —— 内容批准

  • 对象：记忆、Wiki、Skill、RCA、Template、策略变更候选。
  • 问题：这份内容能不能发布、给谁用。
  • 结果：candidate → triage → staged → changeset → review → published / withdrawn / superseded。
  • 注意：approved ≠ published，审核通过与真正发布是两步。

RunGate —— 运行副作用批准

  • 对象：会改变外部状态的高风险工具调用。
  • 问题：此刻、以这个身份、为了这个 Purpose，能不能真的执行。
  • 结果：approved / executing / verified，或 blocked / expired / revoked / unknown。
  • 注意：默认 blocked；执行中权限被撤回会逐工具处置。

动作风险分层与人工介入

级别典型动作人工介入
R0只读浏览、检索、查看证据无需审批，但受授权与 Purpose 过滤。
R1写入候选记忆、创建草稿、提交 ChangeSet进入分诊 / 审核队列；不直接改变已发布内容。
R2发布知识资产、修改成员与关联、导出受控内容需要对应治理角色审批；审批绑定不可变的计划版本。
R3跨空间 / 跨租户复用、清理与删除、外部通知、不可逆副作用默认阻断；需要独立复核、职责分离与 Break-Glass 边界约束。

审批的粒度为「某一份不可变计划版本」。计划一旦变更，原审批失效，必须重新走门禁——这是防止「批了 A 执行了 B」的唯一可靠方式。

2.6 核心不变量

下面八条是整个产品的硬约束。任何页面、接口或自动化流程与它们冲突时，以不变量为准。

#不变量含义与后果
1owner ≠ visibility ≠ ACL ≠ execution authority归属、可见、访问控制与执行权是四件事，任何一件都不能推导出另外一件。
2发布或检索不授予执行权能读到某个知识资产，不等于能用它去改生产；读取目标空间不等于能修改其中的资源。
3权限过滤先于召回、图分析、投影与模板渲染防止候选集、侧信道与模板泄露；渲染后裁剪不合格。
4requested ≠ executed ≠ verified；retained ≠ service-visible；unknown ≠ zero请求、执行、验证是三种不同事实；保留不等于服务可见；未知不等于没有。
5恢复、重建、迁移、重试会产生新副本 / 新 revision旧的清理证明不自动继承到恢复后的新资产；必须重新盘点与门禁。
6外部副本无法证明时，停止高敏复用、导出与全量清理声明fail-closed：收窄、隔离、阻断、升级，而不是乐观放行。
7技术阻断先于法务判断，报告事实与法律决定分离平台报告「已处置 / 未处置 / 未知」，不代替法务作出法律结论。
8补偿、回滚、重试与替代 Provider 都是新的受授权动作它们不是「撤销」，同样要过 RunGate 与审批，同样产生新证据。

  4. 不可变保留与法律保全判定：命中保全或不可变保留时标记 retained，service_blocked 与 retained 可同时存在；保留不等于可继续检索或执行。解除保全、缩短不可变保留或提前删除都是独立高风险动作。
  5. 独立验证：按证据等级分层声明——E0 未确认、E1 传播或访问已阻断、E2 逻辑处置已执行、E3 范围内验证、E4 受控介质或责任方证明。证据等级不跨副本继承，抽样结果不得表述为数学意义上的全量证明。
  6. 逐消费者确认与闭包验证：每个消费者必须证明已应用所需版本（applied_and_verified），再进入 closure_verified；stale / pending / failed / unknown 不得伪装为 current。

  8. 投递与修订：一个报告共享 Delivery Intent，各渠道独立 Attempt；记录生成、批准、排队、发送尝试、渠道接受、传输完成、接收确认、阅读或下载、撤回请求与修订发布。渠道接受不等于人已接收，接收不等于已阅读，新事实不静默改写已发送报告。
  9. 恢复轨道：备份恢复、灾备切换、索引或 Embedding 重建、缓存回填、Manifest 重生成、Provider 重试、跨区域复制、迁移导入与恢复演练都可能重新生成已撤回内容；恢复前检查撤回与保全状态，恢复后生成新 inventory 并重新执行传播阻断与验证，不继承旧证明。

5.1 登录与全局导航

入口路径

#/login（壳外页面，不进入侧栏）。登录成功后落地 #/home。侧栏四级分组与全部入口以构建契约第 3 节为准，本章各节只重复与本节相关的 hash。

操作步骤

  1. 打开 #/login。平台不提供自助注册：账号与凭据由 platform-admin 在 #/settings（Users / Keys）维护。
  2. 输入账号与口令登录。登录成功与失败都写审计，可由 governance / auditor 在 #/audit 按“操作者 + 动作”筛选。
  3. 登录后按当前角色渲染侧栏：契约矩阵中标为 — 的模块不出现；标为 ○ 的模块只呈现只读入口。
  4. 确认顶栏当前 scope 与角色标识（日常演示身份为 林工（lin.gong）· member；平台账号 admin 显示 platform-admin · 管理员）。
  5. 切换 Team / Project scope 或直接输入 hash 深链；内容按当前授权重新解析，不沿用上一个 scope 的可见结果。
  6. 左下角「退出登录」结束会话。

结果反馈

落地 #/home；侧栏 active 项与当前路由一致；顶栏面包屑前两段可点（回上一级），叶子段为纯文本。登录、退出、失败尝试、scope 切换均产生审计事件。

边界情况

  • 无权限：直接输入矩阵中为 — 的模块 hash 时显示 denied；拒绝信息不回显无权对象的名称或数量。
  • 身份不可确认：无法确认实际操作者时记为 actor_unknown；Key 或凭据的登记人不等于实际操作者（createdBy ≠ owner ≠ actor）。
  • 禁用与过期：账号被禁用时口令正确也拒绝；会话过期后重新登录回到当前路由，但不自动重放未完成动作。
  • 离线：本地打开原型时为合成数据，页面标注「演示数据」，任何授权与投递结论都不成立。

入口路径

#/home。工作台是登录后的默认落点，也是“我的项目们现在需要我做什么”的唯一入口。

操作步骤

  1. 用顶部 scope switcher 选择 Team 或 Project 范围（需要该范围的成员关系或 ACL）；工作台只显示当前 scope 内可行动的事项。
  2. 在「我的 Task」查看处于 active / paused / blocked 的 Task，点行进入 #/task/t-104；paused ≠ blocked。
  3. 在「等待分诊」查看 #/ingestion/triage 中处于 staged / assigned 的候选数量与范围；需要 knowledge-owner 才能进入处理，其他角色只见计数。
  4. 在「等待审核」查看 #/changes 中 review_required 的 ChangeSet（演示对象 cs-4410）；处理需要 knowledge-owner。
  5. 在「失败 Run」查看 r-81 这类失败 Run，下钻到 #/task/t-104/run/r-81 看失败原因、缺口与下一门槛。
  6. 从「最近证据」或清理 unknown / RunGate blocked 卡片进入 #/governance/cleanup、#/governance/lineage；工作台自身不提供执行按钮。

结果反馈

每张卡片同屏显示范围 + 证据时间 + 责任边界 + 下一门槛；计数是当前授权范围内的实测值，点击后跳转到对应专业页并由该页承担操作与授权判定。

边界情况

  • 无权限：矩阵为 — 的模块不出现；为 ○ 的角色只看到计数与范围，看不到候选内容与证据正文。
  • unknown：清理 unknown 与外部副本状态显示为 unknown，不显示为 0（unknown ≠ zero）。
  • 高风险动作：RunGate blocked 卡片显示阻断原因、下一门槛与责任角色，不提供「一键执行」。
  • 部分成功与离线：Connector 离线或事件缺口时显示 partial / stale 与最后证据时间；loading / empty / filtered-empty 分开表达，不用一个「暂无数据」覆盖。
  • 待确认 首页卡片集合在两处来源中列举不同：redesign-v3/DOMAIN-MODEL-AND-IA.md §6 只列「我的 Task、等待分诊、等待审核、失败 Run」；CONCEPTS.md §7 另列 scope switcher、待分流、待审核、清理 unknown、RunGate blocked、最近证据。本节按并集描述，最终卡片集合未收敛。

5.3 项目与项目导航

入口路径

#/projects（列表）→ #/project/p-db/overview。项目内二级导航（概览 / Tasks / Agents / Runs / Resources / Access / Activity）由项目页内的水平页签承载，不进入全局侧栏。

操作步骤

  1. 在 #/projects 按可见范围浏览 Project 卡片（member 只看到自己参与的 Project）；点击卡片进入概览，不直跳 Task。
  2. 在概览页确认 owning Team、可见性（open / restricted）、当前 revision 与最近活动时间。
  3. 用二级导航进入 Tasks / Agents / Runs / Resources / Access；切换页签只改变视图，不改写对象归属或授权。
  4. 在 Tasks 中新建或认领 Task（需要 project-admin 或 Project 内写权限）；写操作写审计。
  5. 需要引用其他 Project 的只读来源时，在 Task 的 ContextBinding 中登记 referenceProjectIds[]，逐项单独授权，不复制来源内容。
  6. 成员与访问在 #/project/p-db/access 由 project-admin 维护；Team 级成员在 #/team 由 team-owner 维护。

结果反馈

进入 Project 后立即显示 scope、可见性与当前角色；open 只放宽日常协作入口，不放宽 Memory / Wiki / Code / Skill / Template 的 CRUD，也不放宽成员、ACL、visibility、Agent 配置与 Project 删除转移（这些仅 Team Owner / Project Admin 可做）。

边界情况

  • 无权限：restricted Project 需要显式读权限，否则 denied，且不泄露 Project 内的对象名称或数量。
  • 关系不等于权限：Team 成员身份不等于关联 Project 的成员身份；TeamProject 关联不等于项目读写授权。
  • 绑定冲突：显式无权目标直接拒绝；context_conflict 时不得回退到最近 Project、个人空间或相似 Project。
  • 归档：Project 归档后其 MemorySpace 转只读或归档，保留历史 owner 与来源，不自动删除或转移记忆，也不静默改变 ACL。
  • 待确认 Team ↔ Project 关系口径未收敛：final-v1/DOMAIN-MODEL.md §3 写「Team → Project 是一对多归属关系，每个 Project 必须且只能有一个 owning Team」；redesign-v3/DOMAIN-MODEL-AND-IA.md §3 写「多对多协作关联」。两处并存，本手册不自行裁决，只按“必须有唯一 owning Team + 协作关系不授予权限”执行操作口径。
  • 过期与筛选：revision 变化或关系命中过期时标 stale；筛选为空与真为空分开。

5.4 任务

入口路径

#/task/t-104（从 #/project/p-db/tasks 或工作台进入）。

操作步骤

  1. 打开 t-104「修复 DB-Proxy 连接池耗尽」，确认目标、验收标准与交付物（状态：进行中）。
  2. 读 planning snapshot：任务计划与资源配置在确认时被锁定为不可变快照，之后 latest 配置变化不回填、不改写该快照。
  3. 读 ContextBinding：primaryProjectId（主要工作现场）、referenceProjectIds[]（逐项单独授权的只读来源）、writeTargetSpaceId（本次唯一写入目标）；三者都不授予对其他项目的读或写。
  4. 逐个查看关联 Runs（r-83 verified、r-81 failed）；Run 成功不改变 Task 的验收状态。
  5. 交付与验收：确认交付物与验证证据后由有权主体验收（需要 project-admin 或 Task 验收权限）；无权限时只能提议，不能自行置为已验收。
  6. 需要重启工作或派生后续任务时创建 Reopen / Follow-up / Derived，而不是就地改写历史 Run 或历史快照。

结果反馈

Task 保持「进行中」直到验收被独立确认；每次状态转移记录 from / to / reason / evidence_refs / actor / timestamp 并写审计。planning snapshot 与 Binding 以只读方式展示 revision 与时间。

边界情况

  • 状态分离：Run succeeded ≠ Task accepted；完成 ≠ 验证完成，完成 ≠ 发布或可执行；「最后一次 Run 成功」「Harness 返回完成」「Owner 点击完成」都不能单独决定完成。
  • 历史快照：历史 Snapshot 保存事实，不能绕过当前撤权；verification_expired / approval_invalidated / manifest_stale 显示为需重新确认。
  • 绑定冲突：弱证据或多候选进入 Triage，不自动选定一个目标。
  • 无权限：member / team-owner / project-admin 可操作；knowledge-owner / agent-admin / governance / auditor / platform-admin 只可见（矩阵口径）；无权读取时显示受限状态而非伪造确定归属。

5.5 运行

入口路径

#/task/t-104/run/r-83；Run 列表在 #/project/p-db/runs。Run 不作为常规顶层资源出现，只从 Task 或所属 Project 下钻。

操作步骤

  1. 从 Task 详情或工作台的失败 Run 卡片进入 Run 详情。
  2. 读树形事件：按事件层级展开当前 Harness / Agent、工具调用、输入证据、输出与审计；事件是追加式记录，缺失、乱序、采样分别标注，不补造顺序。
  3. 读实际上下文：本次 Run 实际解析出的不可变 ContextManifest，含 memory_id、source_revision、owner_scope、inclusion_reason、authorization_context、policy_version、sensitivity_decision、redaction_state；它与 Agent 的默认装配（mounted）不是同一件事。
  4. 读工具证据：逐条 Tool Call 的计划与实际调用、结果与 External Effect；计划外差异单列，工具调用成功不代表返回内容可信。
  5. 读 RunGate：状态 approved / executing / verified / blocked / expired / revoked / unknown，同屏显示当前策略、下一门槛与责任角色；RunGate 不能放宽 ToolPolicy。
  6. 读交付与验证：Verification Result 与交付物；外部效果 unknown 时冻结扩大副作用并进入对账。

结果反馈

Run 状态、证据时间与范围同屏；requested ≠ executed ≠ verified。RunGate 判定、审批失效、撤回与恢复都产生新的状态记录或新 revision，不覆盖历史事实。

边界情况

  • unknown：结果未知时不自动重试有副作用的动作，也不扩大副作用；unknown 不得视为成功或失败。
  • 审批失效：资源、revision、工具参数、范围扩大、环境、风险升级、权限变化、来源撤回或回滚方案变化都会使审批失效 → RunGate=blocked → 重新生成计划并重新审批；审批超时不等于批准。
  • 工具被拒：超出 Tool Policy 时显示拒绝原因与可行动作，不用摘要、改写或工具结果绕过。
  • 离线与缺口：missing_event / out_of_order / duplicate / lease_expired 标为 partial / unknown，不显示为 complete；Trace 缺失不等于动作未发生。
  • 撤权：权限撤销、敏感暴露、归属撤销或高风险 owner 变化可暂停受影响的 Run 并要求重新解析上下文。

5.6 Agent

入口路径

#/agent/a-retriever（演示对象另有 a-coder「代码修复 Agent」、a-reviewer「变更评审 Agent」）。

操作步骤

  1. 打开 Agent 详情，确认基本信息：name / description / type / visibility / owner / status / version 与关联范围。
  2. 读关联范围：AgentTeam / AgentProject 关系只授予明确的 view / use 能力，不授予写、工具调用、审批或成员管理能力。
  3. 读装配三层：accessible（当前主体可用的候选）、mounted（Agent 默认装配）、effective（某个 Run 实际解析出的不可变集合）；三者不可互换。
  4. 修改行为配置（系统提示词、运行参数、模型配置引用、工具、Skill、Hooks）：需要 agent-admin 角色；模型与工具仍受上级 policy 限制。
  5. 查看 Vault reference 与 Policy：只显示引用、指纹、scope、轮换与撤销状态，不回显秘密内容。
  6. 查看实际运行：从 Agent 下钻到使用它的 Run 与运行证据；不要用 mounted 资源替代 Run 的 effective 资源。

结果反馈

配置修改生成新 version 并写审计；visibility 只控制发现与查看元数据，不会让私有资源公开；关联变更不改变被关联资源的 owner 与 ACL。

边界情况

  • 角色口径：仅 agent-admin 可操作（矩阵为 ●）；member / team-owner / project-admin / governance / auditor / platform-admin 只可见（○）；knowledge-owner 不可见（—）。
  • 秘密与拒绝：API Key 只在创建时展示一次，系统只保存哈希/指纹与撤销状态；拒绝信息不泄露无权对象的名称或数量。
  • 不能自我审批：Agent proposal ≠ approval / publish；治理 Agent 只能 detect / explain / propose / open_review / request_revalidation，不能 reopen、change_owner、export、publish、delete 或 grant_permission。
  • 写入受控：write 必须按资源类型拆分——对 Memory 是按 MemorySpace 写策略写入候选；对 Wiki / Code / Skill 是创建或修改候选并进入 #/changes。
  • 能力不等于授权：Harness / Agent 声称支持某工具、结构化输出或长上下文，不代表可访问该工具、字段或 scope；能力未知不得自动视为可用。
  • 退役与撤权：Agent 退役后其 MemorySpace 停止新增或转只读，产生的业务记忆不随 Agent 自动删除；历史 Snapshot 不能绕过当前撤权。

5.7 记忆与空间策略

入口路径

#/memory（浏览、来源、版本、纠错）与 #/memory/spaces（空间与策略，作为记忆的管理视图）。

操作步骤

  1. 选择 MemorySpace：ms-proj-db（project/p-db）、ms-team-pay（team/team-pay）、ms-user-lin（user）、ms-agent-retriever（agent）；长期 owner 只有这四类，平台不提供 public Memory。
  2. 打开单条记忆（如 m-9031 L1 原子「DB-Proxy 连接池上限 200」、m-9044 L2 场景、m-9102 L3 事实）：查看层级、canonical_owner_scope、来源与 revision、Purpose、敏感性、生命周期与可见范围。
  3. 读来源与版本：真源是规范对象与不可变 revision；Index、Projection、Snapshot 都是绑定 revision 的派生物（Index ≠ Canonical Truth）。
  4. 纠错：提交 correction 或 transfer；纠正以追加 correction_record 的方式展示历史链，不覆盖原归属事实；只有显式 Transfer 才改变 owner。
  5. 空间策略：在 #/memory/spaces 查看四类空间的写策略、ACL 与生命周期；归档或只读状态只影响新写入，不改历史归属。
  6. 跨空间复用时走受控形态（reference / promotion_candidate / derived_asset / published_asset / transfer），默认 reference_status=available、retrieval_status=restricted、action_status=blocked。

结果反馈

归属或内容变化生成指向有效历史版本的新规范 Revision，并沿血缘覆盖主存储、检索索引、缓存、派生摘要、Context Manifest 与知识化候选；传播失败时暂停扩大传播。撤回显示「访问已撤销、停止传播、平台已处置、索引失效中、外部清除未知、受法律保留阻断」，不只显示「已删除」。

边界情况

  • 归属不等于权限：属于 Team ≠ 所有 Team 成员都可读；属于 Project ≠ Project 内所有主体都可改；由 Agent 产生 ≠ 记忆属于 Agent；被某 Project 引用 ≠ 归属该 Project。
  • 状态表达：当前有效 / 待确认 / 已更新 / 存在争议 / 已失效或已撤回 / 部分可用 / 未知；unknown 表示「系统无法安全判断」，不等于成功或失败；模型不可用或输入缺失不默认通过。
  • 冲突：显示冲突是什么、影响什么、依据是什么、为何需要人工审核；冲突不得由最后写入者、单一置信度或模型相似度裁决。
  • fail-closed：权限检查、归属解析、敏感性判断、审计记录或撤回传播失败时默认拒绝写入或隔离；隔离内容不得进入普通检索、摘要、Context Manifest、自动执行或默认训练链路。
  • 纠错不可回退权限：回滚生成新的规范 Revision，不恢复旧权限或旧审批；「纠正不能只修改 owner 字段」。
  • 角色口径：member / team-owner / project-admin / knowledge-owner 可操作；agent-admin / governance / auditor / platform-admin 只可见；无权用户不得通过归属解释推断隐藏 Space、Owner 或资源存在性。

5.8 资源库

入口路径

#/library。资源库是授权后的跨类型发现页，只做发现与跳转，不编辑任何资源。

操作步骤

  1. 进入 #/library：系统先按当前主体、Purpose、租户与 scope 完成授权过滤，再做筛选（先授权再筛选，不能先全库召回再隐藏结果）。
  2. 选择 Team 维度（relatedTeamId）、Project 维度（relatedProjectId）、User 维度（ownerUserId）。
  3. 选择 Agent 维度时必须明确关系类型：mountedByAgentId（默认装配）或 usedInRunByAgentId（实际运行使用）。
  4. 组合筛选：同维内取 OR，维间取 AND；actor 是独立维度，不能与 owner 混用。
  5. 点击结果行跳转到对应专业页：记忆 #/memory、知识资产 #/knowledge/wiki/k-wiki-connpool、代码场景 #/scenario/cs-2201。
  6. 需要编辑、发布、撤回或执行时，回到对应专业页并按其角色与门槛操作；资源库不提供这些入口。

结果反馈

结果行显示命中的关系类型与对象类型，用于解释「为什么看到它」；跳转保留 hash 深链，返回时筛选条件不丢失。命中只表示关系存在，不表示获得读取、注入、执行或导出权限。

边界情况

  • 关系图不等于权限图：关联不等于共享，引用不等于所有权，组织关系不等于权限继承；用户应能区分所属、参与、引用、影响与派生。
  • 无权限：无权对象不进入结果集，也不体现为计数差；关系查询本身可能泄露组织结构与资源存在性，需最小权限。
  • 空态区分：loading / empty / filtered-empty 分别表达；筛选条件过窄导致的空结果与确实没有对象不同。
  • 过期：对象 revision 变化或来源撤回后，原关系命中标 stale，并可下钻到血缘页确认传播状态。
  • 角色口径：契约矩阵未单列「资源库」行，本页不新增任何角色能力；可见性由被查对象的 owner、ACL 与上方矩阵对应模块共同决定。

5.9 知识资产

入口路径

#/knowledge（目录）→ 专业页：#/knowledge/wiki/k-wiki-connpool、#/knowledge/skill/k-skill-pg-triage、#/knowledge/rca/k-rca-2201、#/knowledge/template/k-tpl-scene-db、#/knowledge/code-context/k-ctx-dbproxy。

操作步骤

  1. 按类型进入专业页：Wiki 回答「这是什么 / 为什么」，Skill 回答「怎么做」，RCA 回答「为什么失败 / 如何避免复发」，Template 回答「从什么结构产出」，Code Context 回答「代码意味着什么 / 改动边界」。
  2. 读版本：asset_version / parent_version / content_revision 与来源 revision、policy 版本、脱敏版本；版本不可原地覆盖。
  3. 读适用范围与消费者状态：valid_from / valid_until、applies_to / does_not_apply_to，以及分离的 reference_status / retrieval_status / action_status。
  4. 发布或修订走 #/changes 的 Queue → Review → Publish（需要 knowledge-owner）；approved ≠ published。
  5. 复核与处置：按 keep / narrow / revise / suspend / deprecate / revoke / archive 处理，必要时 recompute / rollback；高影响变化同步阻断新使用并级联撤回或复核。
  6. 消费反馈走 feedback → classify → impact assessment → review candidate → 人工或策略决定 → 新版本 / 收窄 / 暂停 / 撤回，反馈不能直接改写资产。

结果反馈

published 只表示在当前范围内可见、可参考；published ≠ actionable，可执行仍需独立授权（action_status 默认 blocked）。撤回优先于自动巩固、同步、发布与缓存刷新；逻辑撤回（立即不可检索、不可注入、不可执行）与物理删除分离，失败时 fail-closed。

边界情况

  • 类型不等价：Wiki ≠ Skill；RCA ≠ 普通 Wiki；Template ≠ 历史产物复制品；Code Context ≠ 单纯代码索引；Skill ≠ Prompt 收藏。
  • 发布门槛：Wiki 需来源可追溯；Skill 需演练或测试验证，且工具调用仍由独立 Tool Policy 与 RunGate 授权；RCA 必须区分确认根因、假设与待补证据；Template 需真实复用记录；Code Context 必须绑定 repo、revision、路径、符号或模块。
  • 反馈与使用率：一次负反馈不能自动删除稳定知识，一次成功也不能自动提升为团队规范；长期未使用不等于错误，高使用率也不等于正确。
  • 影响评估：内容、源内容、代码 revision、权限归属、敏感性脱敏、消费者投影六类变化必须触发影响评估；impact_pending 不能直接进入 current。
  • 无 Target Owner：只能保留候选，不得正式发布；脱敏验证或血缘缺失时隔离。
  • 角色口径：team-owner / project-admin / knowledge-owner / platform-admin 可操作；member / agent-admin / governance / auditor 只可见。
  • 超时：复核超时标 review_overdue / escalated / blocked，不自动通过。

5.10 代码场景

入口路径

操作步骤

  1. 打开场景，先确认 repo + revision 硬锚点（如 sha256:9f3c7a2 短码）；branch 是可移动引用，不能替代 revision。
  2. 按 Identity → Code Anchor → Scope → Evidence → Paths → RCA → Change → Verification → Resume 逐段读；Code Context、RCA 与 Work Thread 边界分离，不合并为一条记忆。
  3. 读 RCA：默认展示「症状 → 关键证据 → 当前结论」，按需展开候选假设、冲突、未知与验证门槛；明确区分「确认根因」与「问题已解决」。

结果反馈

边界情况

  • 硬锚点缺失：缺 repo 或 revision 时不得发布稳定 Code Context、确定性 RCA、可执行 Patch 或 Skill。
  • 完整性：时间线是带完整性状态的派生视图，缺失显示 partial / unknown，不补造顺序；只有一条可读时间线时也必须显示 sampled / gapped / redacted / unknown。
  • 三不变量：修复有效 ≠ 根因完整；未复现 ≠ 问题不存在；测试通过 ≠ 生产风险消失。
  • 未知不重试：恢复不得盲目重放有副作用的写操作；Run 状态未知不得自动重试；Patch Candidate 默认 action_status=blocked。
  • 旁路状态：blocked / paused / needs_human_confirmation / abandoned / reopened 均需给出下一门槛与责任角色。
  • 角色口径：member / team-owner / project-admin / knowledge-owner 可操作；agent-admin / governance / auditor / platform-admin 只可见。

5.12 分诊 Triage

入口路径

操作步骤

  1. 在队列中打开分诊项，确认当前状态为 staged 或 assigned，并确认受理人（需要 knowledge-owner 角色）。
  2. 读候选归属与理由：信号分解包括 explicit_user_selection / work_thread_owner / project_or_team_context / resource_path_and_revision / producer_identity / connector_metadata / participant_membership / recent_activity / content_semantics / historical_assignment；置信度以「依据充分 / 有限 / 存在争议 / 尚未确认」表达，不显示虚假精确百分比。

边界情况

  • 低置信度与冲突：停在 staged，不自动写入更宽 scope；宁可暂时留在较窄的原始边界。冲突类型 multiple_owner / owner_vs_participant / space_scope_conflict / temporal_conflict / source_conflict / revision_conflict / producer_binding_conflict / permission_conflict / transfer_conflict 分别显示。

  • 批量迁移：planned → validated → approved → running → partially_succeeded / paused / rolled_back_candidate / completed / failed / unknown；需预览、影响范围、成功/失败/未知分项与恢复入口。回滚不恢复旧权限或旧审批。
  • 队列纪律：治理队列必须有 reviewer、due_at、升级路径与最终决定，不能成为无期限暂存区。
  • 角色口径：knowledge-owner 可操作；member / team-owner / project-admin / governance / auditor 只可见；agent-admin / platform-admin 不可见（—）。

5.13 变更与发布

入口路径

#/changes，含 Queue / Review / Publish 三个视图；演示对象 cs-4410（ChangeSet，待 Review）。这是唯一的内容审核入口，发布构建状态也在这里显示。

操作步骤

  1. 在 Queue 打开 cs-4410，确认变更来源（人工编辑或 Agent 候选）、目标对象与目标 scope。
  2. 确认三方合并前提：变更处于 locked、基线版本已固定，且审核针对 mergedHash + headRevision；发布按 CAS 语义执行，基线漂移即拒绝发布。
  3. 执行 Pre-check：来源可追溯、血缘与 revision 一致、无权限扩大、无敏感性扩大；预检失败默认隔离、补证、退回或拒绝，不允许「带警告继续」。
  4. 按对象类型走专项审核门槛（Wiki 来源可追溯；Skill 需演练或测试验证；RCA 区分确认根因与假设；Template 需真实复用记录；Code Context 绑定 repo / revision / 路径 / 符号）。
  5. 高风险或跨域变更追加安全、隐私与治理审核；author / content_reviewer / policy_reviewer / release_approver / consumer_owner 分离，执行者不能自审、自批、自发布。
  6. Publish：生成不可变新版本与消费者投影；撤回优先于发布与缓存刷新，逻辑撤回立即不可检索、不可注入、不可执行。

结果反馈

状态在 source / candidate / review_required / approved / published / suspended / deprecated / revoked 之间流转，approved ≠ published；每次决定写审计（主体、Purpose、策略版本、理由、义务）。审核超时保持 Review 或暂停，不自动批准。

边界情况

  • 预检失败：进入隔离或补证，不进入审核；预检通过只表示允许进入审核，不表示会被批准。
  • 无 Target Owner：只能保留候选，不得正式发布；目标空间管理员不能绕过来源 ACL。
  • 状态语义：review_required 表示需要重审但不一定错；suspended 停止新使用；deprecated 不再推荐但可保留受控历史引用；revoked 不得进入普通检索、投影或执行；candidate 只对授权审核者可见。
  • 影响评估：impact_pending 不能直接进入 current；低影响异步出新版本，中影响暂停并重审，高影响同步阻断新使用并级联撤回或复核。
  • 撤回传播：发布后源权限收窄 → 立即阻断并重新评估；外部副本状态未知时保持阻断，不伪造「已清除」。
  • 角色口径：knowledge-owner 可操作；member / team-owner / project-admin / agent-admin / governance / auditor / platform-admin 只可见。

5.14 血缘

入口路径

#/governance/lineage。

操作步骤

  1. 选择起点对象（记忆 m-9031、知识资产、代码场景 cs-2201 或某个 Run）并携带 source revision 发起查询。
  2. 读当前关系：LineageAssertion → 验证与冲突处理 → CurrentLineageRelation；同屏显示覆盖范围、缺口、过期与 partial。
  3. 查看影响分析：只产出 Impact Report、Impact Candidate、Recommended Review、Blocking Recommendation 四类结论，不是执行动作。
  4. 处理隐藏节点：对被当前主体无权访问的节点只显示「存在关系但不可见」与风险级别，不显示对象名称、数量或内容。

  6. 需要进一步处置时跳转到 #/changes 或 #/governance/cleanup；血缘页自身不改对象、不扩大权限。

结果反馈

撤回场景显示阻断原因类别、范围、时间、缺口与下一门槛，不暴露受限源细节；长任务显示进度、缺口、取消与重提；异步状态取 requested → authorized_snapshot → queued → running → partial / paused / awaiting_recheck → completed / failed / cancelled / expired / stale。截断或超时不得标 complete。

边界情况

  • 可见性分层：普通用户只看本 Project 的直接关系；Project Owner 可看本项目多跳；Security / Privacy 可看授权内跨边界；治理与审计可看全局闭包但仍受内容 ACL 过滤；跨租户完整闭包默认禁止。
  • 不得当作反向索引：血缘不扩大权限，也不得用于绕过 ACL 推断无权对象的存在性。
  • 缺口与超时：超时、无权、缺口、未扫描不得伪装成「无影响」；完整性状态取 complete / partial / unknown / stale / failed / cancelled。
  • 缓存与检查点：checkpoint 只恢复计算位置、不恢复权限；缓存命中必须重检当前授权。
  • fail-closed：过滤先于召回；无法完成授权过滤时阻断而不是返回部分闭包。
  • 角色口径：knowledge-owner / governance / auditor 可操作；member / team-owner / project-admin / agent-admin / platform-admin 只可见。

5.15 清理证据

入口路径

#/governance/cleanup；演示对象 ci-8812（CopyInventory）。

操作步骤

  1. 打开 ci-8812 的 CopyInventory 快照，确认清理证明的范围基线：source_revision、副本类别（源资产及 revision、热缓存、检索索引、Embedding、Context Manifest、工作目录与临时文件、离线导出、下载与再分享文件、快照、备份、灾备与异地副本、恢复介质、日志与审计投影、第三方与再处理者副本）。
  2. 读传播状态：revoke_committed → deny_path_active → impact_event_enqueued → traversing → consumer_update_pending → applied_and_verified → closure_verified；失败分支 missing_event / out_of_order / duplicate / lease_expired / consumer_unavailable / version_conflict / dead_letter / reconciliation_failed / external_unknown 逐条列出。
  3. 派发处置任务（需要 governance 角色）：范围快照 → 传播闸门 → 处置动作 → 验证 → 对账 → 关闭；每步绑定 source_revision、inventory snapshot、policy version、purpose、scope、idempotency key、attempt、deadline、stop condition 与证据引用。
  4. 读验证证据等级：E0 未确认（默认不可声明完成）/ E1 传播或访问已阻断 / E2 逻辑处置已执行（留回执）/ E3 范围内验证 / E4 受控介质或责任方证明；等级不跨副本继承。
  5. 读保留与保全四轨：服务轨道（立即阻断检索、投影、导出与执行）、生命周期轨道、保全轨道（法律保全与法定留存冻结指定范围与版本，须有责任人、依据、范围与解除条件）、恢复轨道（恢复前检查撤回与保全，恢复后生成新 inventory 并重跑阻断与验证）。
  6. 读 Claim Boundary 五类：在线可控范围已验证 / 备份待生命周期到期 / 第三方已回执但未独立验证 / 离线或外部副本未知 / 依法保留。

结果反馈

处置状态取 not_scoped / planned / requested / blocked / executed / verified / partial / unknown / retained / expired；报告取值只允许 retained 或 unknown。service_blocked 与 retained 可以同时存在。每张证据卡同屏显示范围 + 证据时间 + 责任边界 + 下一门槛。

边界情况

  • 状态不可混用：requested ≠ executed ≠ verified；retained ≠ service-visible；unknown ≠ zero；超时不是成功。
  • 未知边界：未发现、不可访问或未接入的副本不得默认不存在；第三方证据不足默认 unknown / blocked 或收窄交付，不伪造全量删除证明；非受管与外部终端只允许 requested / not_confirmed / external_unknown，禁止升级为 verified。
  • 不得自动重试：未知结果不得自动重试不可逆动作；抽样不得表述为数学意义上的全量证明；verified_scope ≠ 全局 verified。
  • 高风险动作默认 blocked：解除保全、缩短不可变保留、提前删除、恢复高敏内容都是独立高风险动作，页面显示阻断原因、下一门槛与责任角色，不提供「一键执行」。

入口路径

操作步骤

  1. 打开 rpt-3301，先读事实内核：事件与请求 ID、源与目标空间、资产与 revision、inventory snapshot、时间线、动作、证据、范围、未知、保留、责任链与版本。
  2. 选择受众投影（内部 / 客户 / Provider / 监管）：字段披露、脱敏、未知与禁止外发规则在渲染之前执行；模板不能自行决定权限。
  3. 确认 unknown / retained / not_scoped / external_copy 的语义在投影中未被省略或改写。
  4. 批准：draft → approved；批准与执行分离，执行者不能自批高影响外发（需要 governance）；无责任人、角色冲突、跨租户责任不明或事实不足时先阻断并升级。
  5. 生成 Delivery Intent 并逐渠道尝试：多渠道共享同一 delivery intent、每个渠道独立 Attempt（dlv-902 已送达、dlv-903 投递未知）；不得以一个渠道成功冒充全局送达。
  6. 修订或撤回：新证据、回执冲突、恢复或范围变化时生成新版本并标 supersedes / revokes，旧版本标记过期；不静默改写已发送的报告。

结果反馈

报告状态取 draft / approved / superseded / restricted / stale / revoked；投递状态取 accepted / delivered / acknowledged / failed / delivery_unknown / revoked。渠道接受不等于人已接收，接收不等于已阅读，阅读不等于已理解或已采取行动。每次投递绑定报告快照、接收者、Purpose、渠道、有效期与允许动作。

边界情况

  • 事实与法律分离：触发事件只启动评估，不自动等于法定数据泄露或必须通知；技术阻断先于法务判断；「无法判断是否需通知」本身是需要升级的状态。
  • 最小披露：一租户的通知不得泄露其他租户的名称、数量、关系、资产、攻击路径或副本存在性；内部全量血缘、秘密与凭据不得以「透明」为名外发。
  • 投递失败：通知失败时继续阻断并保存证据，升级到备用责任人、法务或合规；delivery_unknown 既不得当作已送达，也不得直接当作失败。
  • 撤回边界：撤回不等于外部副本已删除；撤回、删除与高影响声明不得因超时盲目重复；新版本触发当前状态重检与必要的重新审批。
  • 角色口径：governance / auditor 可操作；team-owner / project-admin / knowledge-owner / platform-admin 只可见；member / agent-admin 不可见（—）。

5.18 设置与权限矩阵 / 审计

入口路径

#/settings（Users / Keys / Models / Integrations）、#/permissions（只读说明页）、#/audit（追加式审计）。

操作步骤

  1. #/settings：由 platform-admin 维护 Users、Keys、Models 与 Integrations；公共模型配置提供 Provider / Model 与 Vault 凭据引用，各 Agent 不复制密钥。
  2. 凭据操作：API Key 只在创建时展示一次，系统保存哈希或指纹、scope、期限、最后使用与撤销状态；任何页面、日志或 Agent 配置都不回显密钥内容（需要 platform-admin）。
  3. #/permissions：只读查看「角色 → 权限与作用」；本页不做授权变更。授权输出包含 decision / obligations / required_approvals / redactions / allowed_scope / expiry / policy_version / audit_level，不是单一布尔值。
  4. 判定顺序：租户隔离与安全禁令 → 法规与敏感性 → 来源 ACL 与血缘 → Organization → Team → Project → Resource ACL → Purpose → Harness Capability → Tool Policy → RunGate → 时间与条件检查；上游硬拒绝不能被下游解除，下游只能进一步收紧，unknown 不转换成允许。
  5. 审批与执行：高风险动作按 R0–R3 分层处理，审批绑定不可变计划版本；资源、revision、工具参数、范围、环境、风险、权限、来源状态或回滚方案变化都会使审批失效并回到 RunGate=blocked。
  6. #/audit：按事件类型、敏感性、用途、保全与生命周期分层查看 Decision / Execution / Impact / Identity·Policy / Lineage·Retention 五类审计；审计读取同样按当前主体、Purpose、敏感性与最小必要授权。

结果反馈

权限状态取 requested / approved / active / suspended / expired / revoked / denied；授权决策取 allow / deny / isolate / needs_review；审批状态取 requested / under_review / approved / rejected / expired / revoked / superseded；执行状态取 queued / gated / running / partially_executed / succeeded / failed / rolled_back / cancelled / blocked。审批超时不等于批准，absence / timeout ≠ consent。审计生命周期取 captured → integrity_checked → retained → accessed / audited → hold_or_due → deletion_pending → deleted / retain_minimal / failed / unknown。

边界情况

  • 门槛分层：R0 只读可逆低影响，可按策略自动并审计；R1 受限工作区变更需明确授权与 ToolPolicy；R2 受控资源变更需独立审批、RunGate、回滚与验证；R3 高影响或不可逆禁止仅凭策略自动放行。影响或闭包未知时不得默认 R0。
  • 职责分离：proposer / approver / executor / verifier 至少区分，默认禁止同一主体提议并审批、审批并执行、执行并完成最终验证；替代只允许命名替代人、值班代理、Break-Glass approver 与法定人数兜底，且在原授权子集内。
  • fail-closed：审计或策略不可用时高风险动作默认阻断；审计不可静默修改。反例：hash ≠ author proof、signature ≠ content truth、retained ≠ retrievable、expired ≠ all copies deleted。
  • 删除语义：deleted 只表示声明范围与方法的删除验证通过；备份、第三方副本或加密擦除无法证明时保留 unknown / external_unknown；过期清理需覆盖正文、附件、索引、缓存、备份与派生副本。
  • 最小披露：凭据、客户数据、完整生产请求体与无关 Trace 不因「审计」名义复制；审计读取不授予修改业务资产或批准执行的权力。
  • 角色口径：设置页仅 platform-admin 可操作，auditor 不可见（—），其余只可见；权限矩阵页 governance / auditor / platform-admin 可操作，其余只可见；审计页 governance / auditor / platform-admin 可操作，member / agent-admin 不可见（—），其余只可见。
  • 未覆盖：公共模型配置项、通知配置与审计界面的具体形态在现有事实来源中未明确，按暂缓处理。

9 · 常见问题

本章回答：第一次接触这个产品最容易误解的地方。问题主要来自第 1.4 节的边界和第 2.6 节的不变量。

Q1 · 这不就是又一个 Agent 框架 / Harness 吗？

不是。Harness 负责「干活」——规划、调工具、改代码、跑测试；本平台负责「记住、理解、授权、复用、撤回并审计这些活干过什么」。平台不接管执行循环，也不提供编排引擎。所以它不会和 Codex / Claude Code / DSH 竞争，而是它们共同的记忆与治理底座。

Q2 · 为什么不能像网盘一样，把一条记忆直接共享给别的项目？

因为记忆里混着来源、Purpose、敏感性和责任边界。直接复制会让来源链断裂、责任无法追溯、也无法在源变化时级联撤回。正确路径是：分诊 → 脱敏 → 审核 → 发布为受控的 Wiki / Skill / Template，接收方引用锁定版本；升级或派生是显式变更，不会静默同步。此外，长期 MemorySpace 没有 public 类型——这是刻意的。

Q3 · 我能看到这条记忆，为什么不能用它去改生产配置？

因为 owner ≠ visibility ≠ ACL ≠ execution authority：看得到不等于有权执行。执行要单独过 RunGate，按当前时刻的主体、目标、Purpose、资产版本、血缘、脱敏状态、Tool Policy 与审批状态重新判定，而且默认是 blocked。发布知识资产也不会顺带授予执行权。

Q4 · 清理任务显示「已执行」，是不是说明数据已经彻底删除了？

不是。产品严格区分 requested / executed / verified。「已执行」只代表处置请求已下发；只有独立验证通过才是 verified，而且要绑定范围与证据时间。备份、离线介质、终端和外部 Provider 副本常常只能得到 retained 或 unknown。所以页面永远不会显示「全量已清理」——未知就是未知，不等于零。

Q5 · Agent 已经关联了这个项目，为什么还是不能改里面的东西？

关联只授予明确的 view / use 能力：可以在范围内查看已获准对象、使用已获准的模型、工具、Skill、Memory 与 Template。它不授予写权限、工具调用权或审批权，也不能修改 Team、Project、成员、关联、策略与配置。写入必须逐项按资源 owner、ACL、写策略和关联范围另行授予，并且对 Wiki / Skill 类资源是以「候选 + ChangeSet」的形式进入审核。

Q6 · 为什么无权限时只显示「无权访问」，不告诉我那个对象叫什么？

这是有意的最小投影：拒绝信息如果暴露了对象名称、类型或总数，本身就是一次信息泄露——攻击者可以靠枚举推断出私有资源的存在与规模。因此无权对象一律不披露其存在、名称与数量，只说明「当前身份 / 用途 / 范围」不足以访问，并给出申请路径。

Q7 · Run 都成功了，为什么 Task 还没完成？

因为 Run succeeded ≠ Task accepted。Run 是「一次执行尝试」，Task 是「有验收标准的工作目标」。执行成功只说明这次尝试跑通了，验收还需要人工或规则确认交付物、证据完整性和验收标准。失败重试也会创建新的 Run，而不是覆盖旧记录。

Q8 · 审核都通过了，内容怎么还没发布？

因为 approved ≠ published。审批绑定的是某一份不可变的计划版本；审批通过后仍要执行发布构建、处理下游索引与派生资产、写入发布状态。中间任何一步失败或计划被修改，原审批即失效，需要重新走门禁。

Q9 · 一条记忆已经撤回了，为什么清理报告里还有「未知」？

撤回能保证的是传播阻断：新检索、新投影、新下载、新执行和再分享立即停止。但已经落到外部 Provider、备份介质、离线导出或终端的历史副本，平台无法单方面证明其状态。此时正确做法是记录 unknown 并附范围、证据时间与责任方，按 fail-closed 收窄高敏复用，而不是把它写成「已完成」。

Q10 · 原型里的按钮点了为什么没反应？

因为第 6 章是只读静态原型：数据全部是虚构的演示数据，页面不连接任何后端，也不产生真实副作用。可以点开页签、切换视图、阅读证据，但「删除 / 发送 / 迁移 / 执行 Run」这类动作在本 change 中不实现——原型展示的是形态、状态与门槛，不是可运行能力。

Q11 · 文档里为什么有内容标着「待确认」？

因为那些内容还没有足够的真实输入可以冻结：具体 Schema、阈值、算法、性能与 SLA、组织责任矩阵、供应商合同与法域模板都属于这一类。把阶段性方案写成最终结论，会让后来的实现被一份没有依据的文档绑死。所以本文档明确标注待确认，并在 §10.2 集中列出。

Q12 · 我的对话内容会被自动送到外部 Provider 吗？

不会自动发生。跨边界复用和导出都是受授权动作：需要 Purpose、目标 ACL、敏感性判定、脱敏与审批，高风险动作默认阻断。一旦确实发生外部处理，该 Provider 副本会进入 CopyInventory 作为独立副本面管理，并有范围绑定证明、审计权和撤回后的对账要求。凭据与密钥只保存引用和状态，任何页面都不回显明文。
