4 · 核心时序

本章按六条主链描述平台的关键时序：谁参与、按什么顺序发生、以及当条件不成立时系统默认收窄、隔离、阻断或升级，而不是继续执行。链路骨架来自 CONCEPTS.md 第 5 节与 ARCHITECTURE.md 第 2、3 节；每一步的状态取值、字段与反例约束指回议题 01–10 的蒸馏事实。序号表示逻辑顺序，不表示同步调用或单次事务。

统一不变量（贯穿全部链路）：requested ≠ executed ≠ verified、retained ≠ service-visible、unknown ≠ zero、approved ≠ published、Run succeeded ≠ Task accepted、owner ≠ visibility ≠ ACL ≠ execution authority。高风险动作默认 blocked，页面必须同屏给出「阻断原因 + 下一门槛 + 责任角色」。

4.2 记忆自动归属与分诊（Triage → ChangeSet）

Connector / Harness→ Ingestion & Triage→ 归属解析（规则事实 + 模型信号 + 风险门禁）→ 治理队列 / 隔离→ MemorySpace Owner

依据：议题 3 第 1–3 轮、补充专题、子议题深化 2、3、7；议题 4 深化 7。待确认 本链路末端的变更对象名称存在两种口径：议题 03 / 05 / 06 的蒸馏稿未出现 ChangeSet 作为归属或变更对象（议题 05 明确「两份文档均未出现 ChangeSet」），其链路写作 Triage → Knowledge Candidate；.specs/final-v1/DOMAIN-MODEL.md §2 与 .specs/redesign-v3/DOMAIN-MODEL-AND-IA.md §2 把 ChangeSet 定义为内容变更审核发布的统一对象。不自行裁决。

编号步骤

  1. 接收候选：Connector 或 Harness 提交候选内容，携带来源、观测时间、绑定资源与有效时间版本；四个判断面（Identity / Provenance / Binding / Temporal State）任一不成立都不能由其他面补齐成正式 Owner。
  2. 归属信号聚合：按「规则事实优先 → 模型信号辅助 → 风险门禁约束」聚合，输出 candidate_space、signal_breakdown、confidence_band、contradictions、freshness、scope_and_purpose、automation_eligibility；不使用全局固定权重。
  3. 候选与裁决：采用「候选 + 规则裁决」，顺序为显式授权声明 → 已确认 Work Thread / Project / Team → Connector 验证绑定 → 稳定历史关联 → 内容语义推断 → 保守默认落点；保留 Ownership Decision 审计。
  4. 风险六维评估：影响范围、敏感性、证据强度、可逆性、冲突程度、执行影响；不采用单一总分自动放行。
  5. 四种处置：自动落位（低影响、非敏感、归属唯一、来源可信、无冲突、可撤回）；自动暂存 / 候选；人工确认或治理队列；隔离。自动暂存与治理队列必须区分。
  6. 自动处理等级：A0 显式选择或规范 Owner 关联（记录事实但仍查权限）；A1 低风险可自动生成候选或受限更新；A2 跨空间、Owner 变化、敏感高影响或冲突时只生成候选并进入审核。
  7. 落位与状态迁移：ownership_pending → confirmed，进入目标空间正常治理并保留 L0 来源与确认记录；owner_scope → narrowed_scope / promoted_scope / derived_scope / rejected / isolated / withdrawn 四类事件分别处理，不统一改一个 owner 字段。
  8. 下游传播：检索、Context Manifest 与知识化候选按当前 owner、ACL、用途、敏感性和有效性重新判断；旧 Manifest 与正在运行的 Run Context Snapshot 不因新归属事件被静默改写。

  1. 权威撤回与同步最小阻断：源撤回、权限收窄或策略变化形成权威撤回版本；立即阻断新的检索、投影、下载、执行与再分享（deny_path_active）。检测信号不等于权威撤回，阻断先于证明，阻断也不冒充删除。
  2. Copy Inventory 版本化快照：记录逻辑副本身份与来源 revision、边界与责任方（owner / controller / provider / recipient）、用途与分类与保留保全、生命周期与访问与处置、发现观测与覆盖率与新鲜度、证明快照与声明范围。快照是清理证明的范围基线，每个观测、处置与验证保留自己的时间、版本与来源。
  3. 分层处置：在线对象、缓存、索引与 Embedding、Manifest 走在线分支；备份、灾备与恢复介质走备份生命周期轨道；导出、下载、再分享与终端走外部轨道；Provider 与再处理者走合同与证明包轨道。四轨并行：服务阻断、备份生命周期、法律保全、恢复重建。
  4. 不可变保留与法律保全判定：命中保全或不可变保留时标记 retained，service_blocked 与 retained 可同时存在；保留不等于可继续检索或执行。解除保全、缩短不可变保留或提前删除都是独立高风险动作。
  5. 独立验证：按证据等级分层声明——E0 未确认、E1 传播或访问已阻断、E2 逻辑处置已执行、E3 范围内验证、E4 受控介质或责任方证明。证据等级不跨副本继承，抽样结果不得表述为数学意义上的全量证明。
  6. 逐消费者确认与闭包验证：每个消费者必须证明已应用所需版本（applied_and_verified），再进入 closure_verified；stale / pending / failed / unknown 不得伪装为 current。
  7. 分层报告：先生成不可变事实内核，再做受众投影（平台操作人员、客户与数据主体、Provider、监管与执法）；字段分五类（必须披露、条件披露、仅内部、禁止外发、由法务批准），字段披露、脱敏、未知与禁止外发规则在渲染前执行。
  8. 投递与修订：一个报告共享 Delivery Intent，各渠道独立 Attempt；记录生成、批准、排队、发送尝试、渠道接受、传输完成、接收确认、阅读或下载、撤回请求与修订发布。渠道接受不等于人已接收，接收不等于已阅读，新事实不静默改写已发送报告。
  9. 恢复轨道：备份恢复、灾备切换、索引或 Embedding 重建、缓存回填、Manifest 重生成、Provider 重试、跨区域复制、迁移导入与恢复演练都可能重新生成已撤回内容；恢复前检查撤回与保全状态，恢复后生成新 inventory 并重新执行传播阻断与验证，不继承旧证明。
