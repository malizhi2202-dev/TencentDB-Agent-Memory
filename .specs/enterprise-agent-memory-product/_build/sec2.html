2 · 核心概念

本章回答：这个产品由哪些对象构成、它们之间是什么关系、以及哪些推论是被明确禁止的。读完之后，你应该能解释为什么「我看到了它」不等于「我能改它」。

2.1 五个不能混淆的维度

产品中最常见的误用，是把下面五个维度当成一件事。它们各自有独立的权威来源，任何一个都不能推导出另一个。

维度回答的问题权威来源不可推导的结论
Identity
身份		谁在发起这次请求？认证出的 Principal；无法识别真人时为 actor_unknownKey 的登记人不等于实际操作者。
Relation
关系		两个对象之间是否有关联？成员关系、归属边、Agent 关联、资源挂载有关联不等于可以修改这个关系本身。
Ownership
归属		内容由哪个边界负责？Project 的 owning Team；资源 owner 与 ACL创建者不等于 owner。
Context
工作上下文		本次工作在哪里发生、读哪里、写哪里？ContextBinding最近访问的项目或仓库路径只是提示，不是绑定。
Authorization
权限		当前主体能执行什么动作？凭据 scope ∩ 成员/绑定授权 ∩ 资源 ACL ∩ 继承策略 ∩ 动作策略 ∩ 委托与 RunGate可查看不等于可写；可使用不等于可管理。
被明确禁止的权限推导
  • Team 成员 不等于 该 Team 关联 Project 的成员。
  • Team↔Project 的关联 不等于 项目读写授权。
  • Agent 被列入 Team / Project 不等于 Agent 可写、可调用工具或可审批。
  • 当前 Team / Project 的筛选范围 不等于 授权或执行绑定。
  • Agent 的 mounted 资源 不等于 某次 Run 的 effective 资源。
  • 服务凭据的创建者 不等于 服务主体的权限来源。
  • 历史 Snapshot 不等于 可以绕过当前撤权。
  • Agent 提出候选 不等于 Agent 可以审批或发布。

2.2 组织与工作对象

组织层

对象定义明确不是什么
User可独立创建的身份主体；可选在创建时或之后加入 Team。不是必须隶属于某个 Team 的对象。

Harness外部执行环境（Codex / Claude Code / DSH 等）；能力、身份与租约独立记录。不是平台内部组件，平台不接管其执行循环。

待确认 Team 与 Project 的基数口径存在两份来源，尚未收敛：本 change 与 .specs/final-v1/DOMAIN-MODEL.md 采用「每个 Project 必须且仅有一个 owning Team（1:N 归属）」；.specs/redesign-v3/DOMAIN-MODEL-AND-IA.md 采用「Team↔Project 多对多协作关联」。本文档第 3、5、7 章按 1:N owning Team 描述，实现前必须由架构 change 裁决。

工作层

对象定义边界

记忆分层

层级形态说明

2.4 安全与副本

对象定义
Purpose本次读取、复用、导出或执行的用途。它参与权限判定，不是可选的备注字段。
VisibilityContext一次判定的完整可见上下文：主体、委托、源 / 目标空间、Purpose、ACL、敏感性、revision、环境与策略版本。

RunGate针对当前主体、目标、Purpose、资产版本、风险、审批与能力的动态执行准入；执行中持续重检。

权限过滤发生的顺序（不可颠倒）

先做授权、Purpose、敏感性与撤回过滤，再做召回、图分析、投影与模板渲染。任何在渲染之后才裁剪字段的做法都视为缺陷——它会让无权内容先进入进程、缓存或日志。

2.5 执行与人工闸门

产品里有两个不同的「批准」，它们解决不同的问题，不能互相替代，也不能共用一个状态字段。

ChangeSet Review —— 内容批准

  • 对象：记忆、Wiki、Skill、RCA、Template、策略变更候选。
  • 问题：这份内容能不能发布、给谁用。
  • 结果：candidate → triage → staged → changeset → review → published / withdrawn / superseded。
  • 注意：approved ≠ published，审核通过与真正发布是两步。

RunGate —— 运行副作用批准

  • 对象：会改变外部状态的高风险工具调用。
  • 问题：此刻、以这个身份、为了这个 Purpose，能不能真的执行。
  • 结果：approved / executing / verified，或 blocked / expired / revoked / unknown。
  • 注意：默认 blocked；执行中权限被撤回会逐工具处置。

动作风险分层与人工介入

级别典型动作人工介入
R0只读浏览、检索、查看证据无需审批，但受授权与 Purpose 过滤。
R1写入候选记忆、创建草稿、提交 ChangeSet进入分诊 / 审核队列；不直接改变已发布内容。
R2发布知识资产、修改成员与关联、导出受控内容需要对应治理角色审批；审批绑定不可变的计划版本。
R3跨空间 / 跨租户复用、清理与删除、外部通知、不可逆副作用默认阻断；需要独立复核、职责分离与 Break-Glass 边界约束。

审批的粒度为「某一份不可变计划版本」。计划一旦变更，原审批失效，必须重新走门禁——这是防止「批了 A 执行了 B」的唯一可靠方式。

2.6 核心不变量

下面八条是整个产品的硬约束。任何页面、接口或自动化流程与它们冲突时，以不变量为准。

#不变量含义与后果
1owner ≠ visibility ≠ ACL ≠ execution authority归属、可见、访问控制与执行权是四件事，任何一件都不能推导出另外一件。
2发布或检索不授予执行权能读到某个知识资产，不等于能用它去改生产；读取目标空间不等于能修改其中的资源。
3权限过滤先于召回、图分析、投影与模板渲染防止候选集、侧信道与模板泄露；渲染后裁剪不合格。
4requested ≠ executed ≠ verified；retained ≠ service-visible；unknown ≠ zero请求、执行、验证是三种不同事实；保留不等于服务可见；未知不等于没有。
5恢复、重建、迁移、重试会产生新副本 / 新 revision旧的清理证明不自动继承到恢复后的新资产；必须重新盘点与门禁。
6外部副本无法证明时，停止高敏复用、导出与全量清理声明fail-closed：收窄、隔离、阻断、升级，而不是乐观放行。
7技术阻断先于法务判断，报告事实与法律决定分离平台报告「已处置 / 未处置 / 未知」，不代替法务作出法律结论。
8补偿、回滚、重试与替代 Provider 都是新的受授权动作它们不是「撤销」，同样要过 RunGate 与审批，同样产生新证据。
