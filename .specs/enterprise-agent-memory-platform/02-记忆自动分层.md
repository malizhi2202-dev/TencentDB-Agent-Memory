## 子议题深化 1：L1 具体数据库 Schema、索引和事件存储实现

**状态：已完成（第 1 轮，自动审核通过）**

### 主题与成功标准

本主题严格承接议题 2 原暂缓项的原文：**“L1 具体数据库 Schema、索引和事件存储实现”**。本轮只讨论 L1 原子记忆的最小持久化边界、不可变版本/追加事件、查询索引和一致性原则，不固化具体厂商、表名、字段全集、分片参数或生产部署方案。

成功标准：形成可支持当前已确认 L1 语义的最小存储分层，明确规范对象、事件、Evidence、Snapshot、Projection 和索引的边界；保证版本、权限、敏感性、来源和撤回状态可追踪，不把索引或事件日志误当作业务真源。

### 阶段 1：头脑风暴

#### 需要持久化的对象

```text
L1 Memory Item
L1 Version / Revision
Evidence Reference
Memory Event
Immutable Snapshot
Derived Projection
Index Entry
Policy / Retention Reference
```

建议保持：

```text
Canonical Memory Object + Append-only Events + Immutable Snapshot + Derived Projections
```

其中：

- **Canonical Memory Object**：当前规范状态、归属、敏感性、生命周期和当前版本引用；
- **Version / Revision**：不可变内容和状态版本；
- **Evidence Reference**：来源、观察时间、置信度、生成者和证据定位；
- **Memory Event**：创建、修正、确认、争议、撤回、失效和归属变化等追加事实；
- **Snapshot**：用于恢复和查询优化的不可变状态快照；
- **Projection**：面向检索、统计或 UI 的派生视图；
- **Index Entry**：关键词、结构化过滤、向量或关系查询的索引投影。

#### Schema 设计方向

候选方案：

1. **单表 JSON 文档**：接入快，但版本、事件、证据和字段级权限容易混杂；
2. **完全规范化关系表**：边界清晰，但早期演进和多类型记忆成本高；
3. **规范元数据 + 版本内容 JSON + 独立事件/证据表**：在稳定边界和演进能力之间平衡；
4. **事件源为唯一真源**：审计和重放强，但查询、权限过滤和运营复杂度高。

建议采用第 3 种，并保留事件与快照的一致性边界：

```text
Canonical Metadata
+ Immutable Version Content
+ Append-only Event Log
+ Evidence References
+ Derived Index / Projection
```

#### 索引候选

```text
identity / scope index
state / lifecycle index
owner / subject index
sensitivity / purpose index
source / revision index
time / retention index
keyword index
vector index (optional)
relation / evidence index
```

索引只用于定位候选，必须在返回、注入、导出或决策前重新执行当前权限、Purpose、敏感性、撤回和有效性检查。

#### 事件候选

事件至少需要：

```text
event_id
memory_id
memory_revision
aggregate_type
aggregate_id
event_type
occurred_at
recorded_at
actor / producer
source_reference
idempotency_key
causation_id
correlation_id
schema_version
policy_context
payload_reference
```

事件 Payload 是否内嵌、引用、加密或脱敏，本轮不固化。

### 阶段 3：总结、结论与建议

#### 建议的最小存储边界

```text
L1Memory
├── identity / ownership / scope metadata
├── current_revision_ref
├── lifecycle / sensitivity / retention metadata
└── created_at / updated_at

L1Revision
├── immutable semantic content
├── parent_revision
├── evidence_refs
├── schema_version
└── content_integrity

MemoryEvent
├── event identity and causality
├── actor / producer
├── source and policy context
├── revision transition
└── payload reference

Snapshot / Projection / Index
└── derived from a canonical revision or event position
```

#### 建议的一致性原则

1. 规范对象、当前 Revision、追加事件和 Outbox/事件发布需要明确原子边界；
2. Snapshot、Projection 和 Index 可最终一致，但必须绑定来源 Revision、事件位置、生成状态和生成时间；
3. 索引命中不能直接授权读取、注入或执行；
4. 迟到、重复、乱序和未知事件必须隔离、幂等或生成校正候选；
5. 事件和版本不可静默覆盖，纠正采用追加式记录；
6. 处置、撤回和权限收窄必须使受影响投影进入失效/重算路径。

#### 建议的查询边界

```text
Index Candidate Retrieval
→ Canonical Revision Fetch
→ Current Validity Check
→ Permission / Purpose / Sensitivity Check
→ Evidence and Conflict Check
→ Consumer Projection
```

不能因为结构化索引、向量索引或缓存命中就跳过规范状态和权限校验。

#### 核心不变量

```text
Index ≠ Canonical Truth
Projection ≠ Source Object
Snapshot ≠ Mutable Current State
Event Append ≠ Business Authorization
Schema Valid ≠ Content Valid
History Replay ≠ Current Permission
```

### 阶段 4：专家团讨论

- **产品/UX**：存储设计应服务于可解释状态、来源、纠正和撤回，不应让用户看到数据库技术细节。
- **架构**：支持“规范元数据 + 不可变版本 + 追加事件 + 证据引用 + 派生索引/投影”；要求原子边界和来源 Revision 明确。
- **可靠性**：要求事件幂等、Snapshot 可重建、Projection 可重算、索引落后可观测；不能因索引故障丢失规范状态。
- **安全/隐私**：要求字段级敏感性、Purpose、保留和撤回元数据不只存在于索引；索引和向量不得扩大原对象权限，事件 Payload 需最小化。

专家团综合建议：采用规范对象与版本为真源、事件用于追加审计和重建、Snapshot/Projection/Index 为绑定 Revision 的派生物；具体数据库选型和 Schema 细节留待后续架构阶段。

## 子议题深化 2：各类状态的自动判定阈值与模型

**状态：已完成（第 1 轮，自动审核通过）**

### 主题与成功标准

本主题严格承接议题 2 原暂缓项原文：**“各类状态的自动判定阈值与模型”**。本轮讨论 L1/L2/L3 状态判定如何结合证据、时间、冲突、风险、使用反馈和人工确认，明确自动判定与发布/执行门禁的边界；不固化具体阈值数值。

### 阶段 1：头脑风暴

状态判定不应由单一置信度决定，至少区分：

```text
observed
inferred
human_confirmed
current
stale
disputed
retracted
invalidated
unknown
```

候选输入包括：证据来源可信度、直接/间接观察、时间新鲜度、重复出现、跨场景一致性、反例、来源撤回、主体确认、实际采纳反馈、影响范围、敏感性和风险。

建议将“状态评估”与“状态转换”分开：

```text
Evidence Assessment
→ State Candidate
→ Policy / Risk Gate
→ Automatic Transition or Review Queue
```

低影响、可逆、证据充分的状态可自动推进；涉及安全、权限、生产、隐私、跨 Project、可执行知识或高影响结论时，自动模型只能生成候选或隔离，不能自动发布。

阈值应有：适用对象、模型版本、输入窗口、置信度/证据区间、降级规则、过期规则、人工覆盖、解释依据和回滚/撤回路径。模型输出还必须允许 `unknown`，不能强制二分类。

### 阶段 2：官方/权威机制调研

- scikit-learn Probability Calibration：<https://scikit-learn.org/stable/modules/calibration.html>（访问：2026-09-19）。参考概率校准、验证集和校准误差；模型分数不自动等于业务置信度。
- NIST AI Risk Management Framework：<https://airc.nist.gov/airmf-resources/airmf/>（访问：2026-09-19）。参考风险识别、测量、管理和持续监测；风险分级不能被单一模型分数替代。
- JSON Schema Specification：<https://json-schema.org/specification>（访问：2026-09-19）。参考结构化状态输出和校验；格式合法不等于判定正确。

共同规律：模型分数需要校准和持续监测；状态判定需保留输入、版本、适用范围和不确定性；高风险结果需要治理门禁与人工/受控审核。

### 阶段 3：总结、结论与建议

建议采用多信号、分层、可解释的判定模型：

```text
Evidence Quality
+ Freshness
+ Repetition / Cross-context Stability
+ Contradiction / Counterexample
+ Human Confirmation
+ Adoption Feedback
+ Impact / Risk
→ State Assessment
```

建议输出：

```text
state_candidate
confidence_band
evidence_summary
model_version
input_window
expiry
contradictions
recommended_action
review_required
```

不建议把数值阈值直接写成全局常数。阈值应按状态类型、风险级别、Scope、数据分布和模型校准结果配置，并保留策略版本。状态变化应采用迟滞/防抖，避免小幅波动导致频繁晋升和降级。

自动判定边界：

- 低风险、低影响、证据充分：可自动更新候选状态；
- 过期、冲突、来源撤回或证据不足：降为 `unknown`、`stale` 或 `disputed`；
- 高影响、安全、权限、隐私、生产和跨空间：自动生成候选，进入审核或隔离；
- 自动模型不可用或输入缺失：不默认通过，进入 `unknown`。

### 阶段 4：专家团讨论

- **产品/UX**：用户需要看到判定依据、有效期、冲突和下一步，不应只看到一个置信度百分比。
- **架构**：要求模型版本、策略版本、输入窗口和阈值配置可复现；状态候选与规范状态转换分开。
- **可靠性**：要求漂移监测、校准、回放评估和异常告警；模型不可用时必须有安全降级。
- **安全/隐私**：高风险内容 fail-closed；模型输入、特征和解释也受敏感性、Purpose 和访问控制。

专家团综合建议：采用多信号状态评估、校准后的置信区间、迟滞/防抖、显式 unknown 和风险门禁；不固化全局数值阈值，不允许模型分数直接授予发布、注入或执行权限。

## 子议题深化 3：全量冲突识别与自动裁决算法

### 主题与成功标准

本主题严格承接议题 2 原暂缓项原文：**“全量冲突识别与自动裁决算法”**。本轮只确认冲突识别、分级、证据比较、自动处理边界和人工升级原则，不固化具体算法、阈值或模型。

### 阶段 1：头脑风暴

```text
value_conflict
scope_conflict
temporal_conflict
source_conflict
revision_conflict

```

冲突识别对象分层：

```text

```

处理候选：

```text

```

不能使用“最新时间”“最高置信度”“多数投票”“模型信心”单独裁决高影响冲突。需要共同基线、证据来源、时间有效性、适用 Scope、权限、敏感性、血缘、版本和业务约束。

自动裁决应满足：低影响、规则明确、证据充分、差异可逆、无高风险副作用；否则只能生成候选或进入治理队列。冲突解决必须追加新 Revision/Decision，不覆盖分支和原始证据。

### 阶段 2：官方/权威机制调研

- CRDT 官方资料：<https://crdt.tech/>（访问：2026-09-19）。参考在特定数据类型和操作假设下的可收敛合并；CRDT 不能替代语义、权限和业务约束判断。
- Martin Fowler Event Sourcing：<https://martinfowler.com/eaaDev/EventSourcing.html>（访问：2026-09-19）。参考保留历史事件和追加式重建；事件重放不自动决定业务真值。
- Protocol Buffers：<https://protobuf.dev/programming-guides/proto3/>（访问：2026-09-19）。参考字段兼容和版本演进；Schema 兼容不等于语义无冲突。

共同规律：结构层可合并不等于语义层可接受；冲突需要版本、来源、约束和风险上下文；高影响结果保留历史并进入显式治理。

### 阶段 3：总结、结论与建议

建议采用分层冲突管线：

```text
Detect
→ Classify
→ Compare Common Baseline
→ Evaluate Evidence / Scope / Time / Policy
→ Validate Cross-unit Constraints
→ Auto-resolve or Candidate
→ Verify
→ Append Decision / New Revision
```

建议输出：

```text
conflict_id
conflict_type
affected_units
common_baseline
candidate_resolutions
evidence_comparison
policy_context
risk_level
automation_eligibility
chosen_action
verification_result
```

自动处理分级：

- M0：格式、重复、明显同义且无语义差异，可自动规范化；
- M1：低风险、规则明确、证据充分、可回退，可自动生成并验证新 Revision；
- M2：事实、权限、Scope、敏感性、生产、安全、合规、跨空间或外部副作用冲突，只生成候选并要求审核/隔离。

保持：

```text
自动解决 ≠ 自动发布
自动发布 ≠ 自动执行
候选建议 ≠ 规范结论
```

### 阶段 4：专家团讨论

- **产品/UX**：用户需要看到冲突是什么、影响什么、依据是什么、自动处理为何可行或为何需审核；不能只显示“冲突已解决”。
- **架构**：要求共同基线、语义单元和跨单元约束验证分开；保留冲突历史、决策和新 Revision。
- **可靠性**：要求冲突重算幂等、版本绑定、队列限流和失败隔离；规则变化后可重算但不能覆盖历史决定。
- **安全/隐私**：权限、敏感性、撤回和跨空间冲突默认高风险；不向无权主体泄露冲突两侧的敏感内容。

专家团综合建议：采用语义单元为主、字段和对象为辅助的分层冲突识别；M0/M1 受限自动处理，M2 进入治理；任何自动决策都需证据、策略、版本和验证记录。

## 子议题深化 5：普通成员主状态的具体界面与交互

**状态：已完成（第 1 轮，自动审核通过）**

### 主题与成功标准

本主题严格承接议题 2 原暂缓项原文：**“普通成员主状态的具体界面与交互”**。本轮只讨论如何把复杂的 L1/L2/L3 状态、证据、权限、争议、失效和下一步转化为普通成员可理解、可操作且不泄露敏感信息的主状态体验；不固化具体视觉稿或前端组件实现。

### 阶段 1：头脑风暴

普通成员需要先知道：

```text
当前是什么状态
我能否使用
为什么是这个状态
下一步是什么
何时需要重新确认
```

不应直接暴露完整状态组合、内部模型分数、权限图、全部事件或敏感证据。建议采用：

```text
主状态
+ 简短原因
+ 影响范围
+ 下一步
+ 有效期/更新时间
+ 可展开依据
```

候选主状态：

```text
当前有效
待确认
已更新
存在争议
已失效
已撤回
部分可用
暂时不可用
无权访问
未知
```

主状态与动作必须分离：查看、纠正、申请确认、查看来源、请求新版本、发起恢复、提交治理申请不应由状态颜色隐式授权。

不同角色需要不同投影：Member 看能否继续和下一步；Owner 看责任和影响；Approver 看风险、依据和门禁；Operator 看运行/失败；Auditor 看版本、证据、决定和访问记录。

### 阶段 2：官方/权威机制调研

- WCAG 2.2 Status Messages：<https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html>（访问：2026-09-19）。参考状态变化应能被辅助技术感知；不定义 Memory 状态语义。
- Nielsen Norman Group Progressive Disclosure：<https://www.nngroup.com/articles/progressive-disclosure/>（访问：2026-09-19）。参考先展示核心信息、按需展开细节；不替代权限和敏感性治理。
- Material Design Progress Indicators：<https://m3.material.io/components/progress-indicators/overview>（访问：2026-09-19）。参考进度、等待和不确定状态表达；视觉指示不等于业务完成。

共同规律：主界面提供可理解的当前状态和下一步，复杂依据渐进披露；状态通知需可访问；不使用颜色或单一成功/失败替代语义。

### 阶段 3：总结、结论与建议

建议采用：

```text
Member Projection
├── primary_status
├── can_use / can_continue
├── concise_reason
├── impact_scope
├── next_action
├── last_verified_at / valid_until
└── expandable_evidence_and_history
```

建议状态卡至少明确：

- **当前有效**：在当前 Scope、Purpose 和有效期内可使用；
- **待确认**：事实或权限尚不足，下一步为确认、Probe 或审批；
- **已更新**：已有新版本，需要查看差异或重新确认；
- **存在争议**：不同证据或主体结论冲突，不自动作为高置信使用；
- **已失效/已撤回**：不可作为当前有效记忆使用；
- **部分可用**：仅部分 Scope、字段或场景可用；
- **未知**：系统无法安全判断，不等于成功或失败。

主状态计算不能泄露无权对象存在性。对于无权主体，可返回统一的“不可用或无权访问”投影，不展示敏感原因。

建议采用渐进披露：第一层是状态、能否继续和下一步；第二层是更新时间、适用范围、缺口和阻断原因；第三层是来源、证据、版本差异、治理决定和访问审计。详情仍按主体、Purpose、Scope、敏感性和血缘授权。

可访问性边界：状态不能只依赖颜色、图标或动画；文本、语义角色、键盘操作、辅助技术状态通知和错误解释必须同时存在。异步刷新不应打断正在编辑的内容。

### 阶段 4：专家团讨论

- **产品/UX**：支持“状态 + 能否继续 + 下一步 + 依据”的结构；要求状态文案面向任务，不直接暴露数据库、模型或策略术语。

## 子议题深化 6：复杂概率置信度和通用事件溯源平台

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题严格承接议题 2 原暂缓项原文：**“复杂概率置信度和通用事件溯源平台”**。本轮讨论概率置信度和事件溯源的适用边界、最小可行表达、审计/重放价值与过度复杂风险，不建设通用平台，也不固化概率模型和基础设施选型。

### 阶段 1：头脑风暴

概率置信度可能帮助表达：

```text
证据支持强度
状态判定不确定性
冲突风险
来源可信度
时效衰减
模型校准误差
```

但它不能替代：

```text
来源引用
人工确认
权限判断
政策决定
验证结果
业务责任
```

应区分：

```text
model_score
calibrated_probability
confidence_band
evidence_quality
policy_risk
human_confirmation
```

概率输出必须允许 `unknown`、`not_applicable` 和 `insufficient_evidence`，不能强行转换成精确百分比。不同记忆类型、不同风险和不同数据分布不应共享未经校准的全局分数。

事件溯源的价值包括追加审计、状态重建、历史解释和派生投影重算；风险包括存储/查询复杂度、敏感事件长期保留、重放副作用、版本兼容和把事件系统误当作全部业务真源。

### 阶段 2：官方/权威机制调研

- scikit-learn Probability Calibration：<https://scikit-learn.org/stable/modules/calibration.html>（访问：2026-09-19）。参考概率校准、可靠性和校准误差；模型分数不等于业务置信度。
- Martin Fowler Event Sourcing：<https://martinfowler.com/eaaDev/EventSourcing.html>（访问：2026-09-19）。参考事件作为状态变化记录、重放和快照；事件重放不等于重新执行外部副作用。
- OpenTelemetry Trace Data Model：<https://opentelemetry.io/docs/specs/otel/trace/>（访问：2026-09-19）。参考关联与事件事实分离；Trace 不替代业务事件和审计。

共同规律：概率需要校准、适用范围和不确定性；事件历史与当前状态分离；重放、快照和投影需要版本、权限和副作用边界；通用平台只有在真实规模和稳定需求下才值得建设。

### 阶段 3：总结、结论与建议

建议采用轻量分层，不建设通用概率/事件溯源平台：

```text
Evidence References + Qualitative Bands
+ Optional Calibrated Score by Memory Type
+ Append-only Domain Events where needed
+ Immutable Snapshots / Derived Projections
```

概率只作为决策输入之一，输出应绑定：

```text
model_version
calibration_version
training_or_validation_window
applicable_memory_type
scope
evidence_refs
confidence_band
uncertainty_reason
expiry
```

事件溯源只用于已有明确事件边界的领域对象；事件 Payload 最小化，敏感内容引用或脱敏；状态重建和投影重算不能重新触发原始外部副作用；当前规范对象、权限和生命周期仍是平台真源。

自动化边界：低风险内部评估可使用定性置信区间或已校准模型；高风险、安全、权限、生产、跨空间和可执行知识不得由概率分数直接通过；事件历史缺口或 Schema 不兼容时进入 unknown/隔离，而不是假设重建成功。

### 阶段 4：专家团讨论

- **产品/UX**：普通用户应看到“依据充分/有限/存在争议/尚未确认”，而不是虚假的精确百分比；专家用户可查看校准和版本依据。
