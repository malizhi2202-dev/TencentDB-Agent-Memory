# 议题 8：使用反馈驱动的自进化

**状态：已确认（第 1、2、3 轮阶段性方案；当前独立讨论点已完成）**

## 问题定义

> 如何根据记忆、知识资产和 Skill 的实际使用结果，判断它们是否被正确召回、被采纳、帮助任务完成、导致失败或已经过期，并在不破坏权限、安全、血缘和审计边界的前提下，驱动资产更新、收窄、暂停、替代或退休？

## 第 1 轮确认：受控反馈闭环与版本化自进化

本轮确认：

> **使用反馈驱动的自进化采用“反馈事件 → 证据分类与归因 → 进化候选 → 验证 → 人工或受控审核 → 新版本发布 → 灰度观察与回滚”的闭环。任务成功或失败不能直接证明记忆、知识或 Skill 正确或错误；反馈必须绑定资产版本、Context Manifest、User/Harness、Task、Work Thread、Run、repo/revision、环境和用途，并区分记忆错误、召回/排序/融合/投影错误、执行错误、环境错误、验证错误和治理错误。正面、负面、验证、回归、过期和权限反馈都必须以追加证据保留，不能直接覆盖资产。反馈可以影响相关性、排序、召回资格、适用范围候选、过期标记、投影策略和复核优先级，但不能自动改变 ACL、canonical owner、敏感性、跨空间范围、安全规则、Tool Policy、RunGate、审批角色或生产权限。高影响、安全、合规、权限和敏感反馈必须立即阻断相关 action，并进入人工或受控审核；低风险变化也必须版本化、可验证、可灰度和可回滚。质量指标分为记忆/知识质量、消费质量和任务结果三层，安全与权限指标作为不可被业务成功率抵消的硬护栏。**

### 1. 反馈不是单一的成功率

任务失败不一定代表记忆或 Skill 错误。反馈至少区分：

```text
memory_error
retrieval_error
ranking_error
fusion_error
projection_error
instruction_error
execution_error
environment_error
verification_error
governance_error
user_preference
```

任务结果是结果信号，不是对单条记忆的直接裁决。

### 2. 反馈类型

至少保留：

- 显式人工反馈：正确、错误、有帮助、无关、过期、范围过宽/过窄、步骤不可执行、敏感或权限问题；
- 行为反馈：采纳、修改、删除、跳过、重新检索、切换 Harness、撤回工具调用；
- 工程验证：测试、构建、静态检查、Patch 应用、回滚、原问题复现、回归和生产观察；
- 长期有效性：重复误召回、revision 变化、依赖变化、规则变化、长期未使用和被新版本替代。

行为反馈是弱信号，不能单独裁决正确性。

### 3. 反馈上下文绑定

每个反馈至少绑定：

```text
feedback_id
feedback_type
asset_id / asset_version
memory_id / memory_version
context_manifest_id / version
user / agent / harness
task / work_thread / run
repository / revision
environment
purpose
retrieval_position
projection_version
action_status
verification_results
feedback_author
recorded_at
sensitivity
```

同一资产在不同 Project、revision、环境、Harness 或用途下可能具有不同结果，不能将反馈无条件全局化。

### 4. 反馈事件与资产版本分离

采用：

```text
Asset v1
  → Feedback Event
  → Evaluation / Review Candidate
  → Asset v2 Candidate
  → 验证与审核
  → Asset v2
```

反馈不能直接覆盖、删除或改写资产。正面、负面、验证、回归、过期、撤回和权限反馈都以追加证据保留。

### 5. 自动化边界

低风险可以自动或按策略处理：

- 汇总重复反馈；
- 标记明显过期；
- 降低排序；
- 生成复核候选；
- 追加测试、Trace 和验证结果；
- 提醒责任人；
- 生成版本差异。

中风险变化需要受控审核：

- 收窄适用范围；
- 暂停普通检索；
- 修改投影模板；
- 生成新的知识草稿；
- 标记需要复核。

生产、安全、合规、权限、敏感性、根因、可执行 Skill、跨空间扩展、资产恢复或撤回等高风险变化，必须人工或受控审核。

### 6. 反馈可影响与不可影响的维度

反馈可以影响：

```text
relevance
ranking
retrieval eligibility
scope candidate
expiry candidate
projection template
validation reminder
review priority
```

普通反馈不能自动影响：

```text
ACL
canonical_owner_scope
sensitivity class
cross-space boundary
security rule
tool permission
RunGate policy
approval role
production access
```

### 7. 局部退化、灰度与回滚

资产出现问题时，优先采取最小范围处置：

```text
只降低某 Harness 的 retrieval
只阻断 action
只收窄某 Project 的适用范围
只暂停某个 revision
只撤回某个敏感投影
只暂停某个派生 Embedding
```

进化候选必须记录：

```text
candidate_id
base_asset_version
feedback_refs
evidence_refs
proposed_change
scope_change
policy_version
model_or_rule_version
risk_level
expected_effect
validation_plan
rollback_version
review_state
```

正式发布前需要版本比较、验证、灰度、观察和回滚路径。历史版本保持不可变。

### 8. 三层指标与硬护栏

记忆/知识质量：事实正确率、来源完整率、适用范围准确率、过期识别率、冲突发现率。

消费质量：召回准确率、无关召回率、排序质量、融合错误率、投影完整率、敏感误召回率。

任务结果：测试通过率、构建通过率、Patch 成功应用率、回滚率、复发率、生产异常率、人工纠正率。

安全、隐私、权限和敏感误用指标是硬护栏，不与业务成功率平均。

### 9. 第一版能力边界

第一版优先实现：

1. Feedback Event；
2. 资产版本、Manifest、Harness、Task、Run 的上下文绑定；
3. 反馈分类和归因；
4. 正负证据追加；
5. 复核候选生成；
6. 低风险降权、收窄候选；
7. 高风险立即阻断；
8. 进化候选的验证计划；
9. 版本化发布、灰度和回滚；
10. 质量—消费—结果三层指标；
11. 权限、安全、敏感性硬护栏；
12. 反馈血缘和审计。

第一版不自动修改 ACL、扩大跨空间范围、提高工具权限、确认根因、发布高风险 Skill，也不根据单一采纳率或任务失败删除资产。

## 第 2 轮确认：反馈归因与可审计评估

本轮确认：

> **反馈归因必须沿“授权与过滤 → 检索 → 排序 → 融合 → 投影 → Harness 理解 → 执行 → 验证 → 业务结果”的阶段 Trace 展开，并将 Feedback Event、原始 Trace、Attribution Candidate、Evaluation Result 和资产变更分开建模。任务成功或失败不能直接归因于最后使用的记忆、Skill 或 RCA；归因必须绑定资产版本、Context Manifest、策略/模型版本、User/Harness、Task、Work Thread、Run、repo/revision、环境和用途，保留支持证据、反证、多重原因、已排除原因和未知状态。权限、安全、敏感性、血缘和版本匹配检查优先于相关性归因；归因结果可以生成降权、收窄、复核、重验证或暂停 action 的候选，但不能自动确认根因、修改 ACL、扩大范围、改变安全规则或发布高风险资产。高影响失败可以先阻断相关 action，再等待归因和治理；第一版优先实现可审计、可重放、可回滚的阶段归因链，不追求自动因果裁决。**

### 1. 归因阶段与证据链

一次使用至少沿以下阶段记录：

```text
authorization
→ retrieval
→ ranking
→ fusion
→ projection
→ harness_interpretation
→ execution
→ verification
→ business_outcome
```

每个阶段至少记录：

```text
stage
input_refs
output_refs
asset_versions
policy_version
model_or_rule_version
status
duration
error
actor
timestamp
```

完整评估链路为：

```text
Feedback Event
  → Context Manifest
  → Retrieval Trace
  → Candidate Assets
  → Fusion Result
  → Harness Projection
  → Tool Calls / Run
  → Verification
  → Final Outcome
```

缺少关键环节时，结论必须降级为 `unknown`、`insufficient_evidence` 或 `multiple_possible_causes`，不能用最终失败结果填补缺失证据。

### 2. 归因候选与评估结果

归因候选至少区分：

```text
primary_cause
contributing_factor
correlated_event
ruled_out
unknown
```

每个候选保留：

```text
candidate_id
cause_type
stage
status
evidence_refs
counter_evidence_refs
scope
impact
confidence_state
review_state
```

状态可以包括：

```text
candidate
supported
partially_supported
contradicted
ruled_out
unknown
confirmed
```

`confirmed` 必须经人工或受控审核，不能由模型或自动归因器自我确认。

评估结果至少包括：

```text
evaluation_id
feedback_id
primary_cause_candidates
contributing_factors
ruled_out_candidates
unknowns
affected_asset_versions
affected_consumers
recommended_action
review_requirement
created_at
created_by
```

### 3. 硬门先行与阶段定位

归因顺序为：

```text
权限 / 安全 / 敏感性检查
  → 阶段 Trace 完整性检查
  → 定位最早异常阶段
  → 生成多原因候选
  → 追加支持和反证
  → 判断影响范围
  → 形成评估结果
  → 人工或受控审核
```

权限、安全、血缘和 revision 检查优先于相关性归因。最早异常是排查入口，不自动等于唯一根因。

### 4. 各阶段的归因边界

| 阶段 | 需要回答的问题 |
|---|---|
| 授权与过滤 | 内容是否被正确过滤，是否发生越权或错误阻断 |
| 检索 | 正确候选是否存在、可用并被召回 |
| 排序 | 候选优先级是否错误或超出预算 |
| 融合 | 是否错误去重、丢失来源、扩大例外或压平争议 |
| 投影 | Harness 是否收到完整的约束、来源和不确定性 |
| Harness 理解 | Harness 是否误解了正确上下文 |
| 执行 | 工具、Patch、命令和授权是否正确 |
| 环境 | 依赖、版本、权限和运行条件是否一致 |
| 验证 | 验证是否充分、结果是否被正确解释 |
| 业务结果 | 技术动作是否真正达到业务目标 |

### 5. 归因结果与自进化动作分层

自动或按策略可以：

- 记录归因候选；
- 追加 Trace 和验证；
- 降低排序；
- 生成复核任务；
- 暂停某个 action；
- 生成测试或验证提醒。

受控流程可以：

- 收窄某个 Project 或 revision 的适用范围；
- 暂停某个 Harness 的 retrieval；
- 重新生成知识草稿；
- 生成 RCA 复核版本；
- 撤回某个派生投影。

必须人工或受控审核：

- 确认根因；
- 认定资产错误；
- 全局撤回；
- 修改权限或敏感性；
- 恢复高风险资产；
- 发布可执行 Skill；
- 接受生产或合规残余风险。

### 6. 固定评测与版本对照

候选变化应使用固定评测任务、固定上下文、固定资产版本、固定 revision/环境和固定预期结果进行前后对照，并结合回归测试、灰度和人工抽样。

至少比较：

- 误召回是否减少；
- 漏召回是否增加；
- 投影完整性是否改善；
- 执行风险是否增加；
- 其他 Project 或 Harness 是否受到副作用影响。

### 7. 第一版优先能力

第一版优先实现：

1. 阶段 Trace；
2. Feedback Event 与使用上下文绑定；
3. Attribution Candidate Set；
4. 支持证据与反证；
5. 多原因和未知状态；
6. 评估结果与推荐动作；
7. 归因审核状态；
8. 固定评测集；
9. 版本前后对比；
10. 关联资产、RCA 和知识血缘；
11. 高风险问题自动阻断 action；
12. 人工或受控确认高影响归因。


## 本轮明确暂缓事项及原因

## 第 3 轮确认：自动发布、灰度、收窄、退休与反馈防投毒

本轮确认：

> **资产和变化的自动化程度必须由资产风险、变化风险、影响范围、证据强度和可逆性共同决定，而不能由反馈数量、采纳率或单一质量分数决定。低风险且非敏感、无权限扩大、无跨空间扩大、来源和血缘完整、可验证、可回滚且反馈来源无异常的变化，可以自动执行降权、收窄候选、标记过期、暂停 action 或小范围灰度；涉及内容实质变化、适用范围、检索资格或消费者状态的变化，应进入受控审核；涉及 ACL、敏感性、跨空间、生产、安全、合规、可执行 Skill、资产恢复或高影响退休的变化，必须人工或专门治理审核。资产退休采用 `active → deprecating → restricted → archived` 的可逆软退休流程，不能根据“未使用”直接删除。自动发布必须通过来源、血缘、版本、权限、敏感性、固定评测、回滚、灰度范围和反馈异常保护门。反馈防投毒采用身份、独立性、证据和异常四重检查；可疑反馈保留原始事件、隔离并排除在自动发布和退休统计之外，但不得静默删除。采纳率不等于正确性、安全性或可扩大权限。**

### 1. 资产和变化风险分级

自动化程度同时考虑：

```text
asset_type
change_type
risk_level
scope_change
consumer_state
evidence_strength
blast_radius
reversibility
```

低风险变化可包括非敏感表达优化、排序调整、低风险投影调整和明确过期的参考条目降权；中风险变化包括收窄 Project/revision 适用范围、暂停普通检索、修改摘要或改变消费者召回资格；高风险变化包括 RCA 根因改变、可执行 Skill、生产/权限/合规/客户数据影响、跨 Project/Team 扩展、敏感性变化和资产恢复。

### 2. 可逆优先与自动化矩阵

低风险自动处理必须同时满足：

```text
非敏感
无权限扩大
无跨空间扩大
无高风险冲突
来源和血缘完整
变化可逆
影响范围受限
有基本验证
反馈来源无异常
```

可自动或按策略执行的动作包括降权、标记过期候选、生成版本候选、暂停低风险 action、生成复核任务和小范围灰度。

收窄 Project/revision 范围、暂停普通检索、修改内容或投影、改变默认消费者状态和灰度扩大进入受控审核。ACL、敏感性、跨空间、生产、安全、合规、可执行 Skill、资产恢复、高影响退休和不可逆变更必须人工或专门治理审核。

默认优先使用降权、收窄、暂停和灰度等局部可逆动作，不自动删除或执行不可逆全局变化。

### 3. 自动发布保护门

自动发布候选至少通过：

```text
来源完整
血缘完整
版本一致
无权限扩大
无敏感性扩大
无跨空间扩大
无未解决高风险冲突
固定评测通过
回滚可用
灰度范围受限
反馈没有异常集中
```

任一条件不满足，结果为 `hold`、`needs_review` 或 `blocked`，不能仅降低分数后继续发布。

### 4. 灰度、对照与回滚

灰度绑定：

```text
asset_version
policy_version
model_or_rule_version
consumer
harness
team / project
task_type
repository / revision
environment
rollout_bucket
```

优先在低风险 Team、非生产环境、受限 Harness、固定评测任务和小比例真实流量中灰度。至少观察召回质量、投影完整性、验证成功、执行失败、回归、安全/隐私违规、人工纠正和回滚率。灰度应设停止条件，变化需要前后对照和可用回滚版本。

### 5. 软退休与恢复

资产状态区分：

```text
unused
low_adoption
superseded
expired
invalidated
revoked
archived
```

推荐生命周期：

```text
active
→ deprecating
→ restricted
→ archived
```

自动化最多将低风险资产标记为 `deprecating` 或 `restricted`。进入 `archived` 前需有退休原因、证据、影响分析、替代资产或保留理由、回滚版本、责任人、观察窗口和审计记录。历史版本不可变，恢复必须重新检查当前权限、血缘、敏感性和适用范围。

“未使用”不等于“无价值”，不能直接触发删除。

### 6. 反馈防投毒

反馈可信度至少检查四重门：

```text
身份门：主体真实且有权反馈
独立性门：不是同一 Work Thread / Agent / Run 的重复样本
证据门：绑定真实使用、版本、Trace、验证或结果
异常门：检查短时刷量、集中反馈、结果不一致和注入内容
```

反馈至少保留：

```text
feedback_author
principal_type
harness
organization / team
session / work_thread
source_event
independence_group
authorization_state
evidence_strength
duplicate_group
anomaly_state
```

同一 Work Thread 内多次反馈不能简单等价于多个独立验证。采纳率、使用量和成功率都不能单独证明正确性或安全性。

### 7. 可疑反馈与统计隔离

```text
异常反馈
  → 保留原始事件
  → 标记 suspicious
  → 不进入自动发布或退休统计
  → 进入治理队列
  → 允许人工复核
```

可疑反馈不能被静默删除；正常反馈也不能因出现异常样本而被静默忽略。原始反馈与可信反馈视图分离。

### 8. 第一版优先能力

第一版优先实现：

1. 资产和变化风险分类；

## 子议题深化1第1轮：自动发布、退休和灰度的具体阈值

### 主题与成功标准

本轮处理议题8第一个明确暂缓项。目标是把“何时可以自动推进、何时必须审核、何时只能暂停/退休”的判断从单一分数扩展为可解释的多门槛决策；不在没有真实资产和流量数据时伪造普适数值阈值。

成功标准：

1. 分离质量、风险、范围、证据、可逆性、反馈可信度和业务结果；
2. 明确自动发布、灰度、收窄、暂停、软退休和恢复各自的准入/阻断门；
3. 指标不足、反馈异常、评测与线上冲突或安全/权限状态未知时 fail-closed；
4. 灰度具有对照、停止条件、观察窗口、版本绑定和可回滚；
5. 退休可逆、保留历史和审计，不因低使用率直接删除；
6. 任何涉及 ACL、敏感性、跨空间、生产、可执行 Skill 或高影响资产的变化不自动放行。

### 阶段1：头脑风暴

#### 1. 阈值不是一个总分

建议把决策输入分为硬门和软证据：

```text
hard gates:
  source/lineage/ACL/sensitivity/revocation valid
  no permission or scope expansion
  no unresolved high-risk conflict
  fixed evaluation and rollback available
  feedback identity/independence checks pass

soft evidence:
  quality delta / regression rate
  adoption and correction rate
  task outcome / verification result
  recency / coverage / environment diversity
  rollout stability / incident signal
```

软证据不能抵消硬门失败；高采纳率不能抵消权限、血缘或安全未知。

#### 2. 四类决策不应共用阈值

- **自动发布**：新版本是否可以成为受限消费者的默认参考；
- **灰度扩大**：当前小范围观察是否支持扩大范围；
- **软退休**：资产是否应降低默认资格、进入 deprecating/restricted；
- **恢复**：暂停/退休资产是否重新具备当前适用性。

同一资产可以满足灰度扩大但不满足自动发布，也可以因 source revoke 直接暂停而不等待质量统计。

#### 3. 阈值按资产风险与变化风险分层

建议至少有：

```text
L0 低风险参考：非敏感、只读、无范围扩大、可回滚
L1 受限知识/投影：影响有限、固定评测和受控消费者
L2 高影响解释或默认检索资格：生产/跨服务/重要任务
L3 可执行、权限、敏感、跨空间、客户/生产或不可逆
```

L0/L1 才可能在策略允许且所有硬门通过时自动发布或灰度；L2 进入受控审核；L3 禁止自动发布、自动退休和自动恢复。阈值层级不是业务严重性替代品，变化本身可能把 L0 升级为 L2/L3。

#### 4. 最低数据质量要求

任何数值比较都需要固定对照：资产版本、模型/规则版本、Context Manifest、Harness/consumer、Task 类型、repo/revision、环境、时间窗口、采样/覆盖和预期标签。缺少可比基线、线上与离线口径冲突、反馈独立性不足或样本被异常投毒时，结果只能 `insufficient_evidence`。

### 阶段2：其他产品/标准如何做（带来源）

1. **Google SRE SLO**：SLO 用明确服务指标和目标支持可靠性决策，并强调错误预算可帮助决定发布节奏。可借鉴将目标、测量窗口和发布决策绑定；SLO 不定义知识资产正确性、权限或自动退休阈值。来源：<https://sre.google/sre-book/service-level-objectives/>（访问日期：2026-09-20）。
2. **Google SRE Canarying Releases**：金丝雀发布通过小范围、对照和监控降低变化风险。可借鉴灰度绑定版本、受众和停止条件；它不替代敏感数据、跨空间和执行治理。来源：<https://sre.google/sre-book/canarying-releases/>（访问日期：2026-09-20）。
3. **议题8第3轮既有结论**：已规定风险分级、硬门、固定评测、灰度、软退休和高风险禁止自动动作。本轮细化为决策门槛结构，不把示例数值误写成最终阈值。
4. **议题4评测结论**：召回、泄露、上下文过载、任务成功等指标应分层观察，不能用单一业务成功率抵消安全/权限失败。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **自动发布、灰度、退休和恢复采用“风险分层 + 硬门禁 + 可比证据 + 多指标观察 + 可逆动作”的门槛体系，不采用单一总分或固定普适数字。L0/L1 低风险、非敏感、无权限/范围扩大、来源血缘有效、反馈可信、固定评测通过、回滚可用且灰度受限的变化，才可按策略自动发布或灰度；L2 进入受控审核；涉及 ACL、敏感性、跨空间、生产、安全、合规、客户数据、可执行 Skill、权限/消费者状态扩大或不可逆影响的 L3 变化禁止自动发布、退休和恢复。灰度必须绑定版本、策略、消费者、Harness、任务、repo/revision、环境、分桶、对照、观察窗口和停止条件；暂停/退休优先采用降权、收窄、阻断和软退休，恢复必须重新验证当前权限、血缘、敏感性、适用范围和回滚。缺少基线、样本、独立性、覆盖、评测或反馈异常未解时返回 hold/needs_review/blocked。**

#### 门槛矩阵

| 决策 | 自动允许的最低条件 | 必须阻断/审核的情况 |
|---|---|---|
| 自动发布 | L0/L1；硬门全通过；固定评测无关键回归；回滚可用；受限范围 | 权限/范围/敏感扩大、源失效、评测缺口、异常反馈、L2/L3 |
| 灰度扩大 | 小范围对照稳定；停止条件未触发；风险/覆盖可解释 | 安全/隐私违规、关键任务回归、数据漂移、版本/策略变化 |
| 软退休 | 低使用/过期/被替代证据 + 影响分析 + 恢复版本 | 可能仍是关键低频资产、无替代、合规保留不明、高影响资产 |
| 恢复 | 当前权限/血缘/敏感/适用性重检；固定验证通过；小范围灰度 | 撤回未闭包、外部副本/来源未知、当前环境不匹配、风险责任不明 |

#### 推荐判定伪代码（语义，不是最终实现）

```text
if hard_gate_failed or security_unknown or permission_unknown:
    return blocked
if risk_level >= L3:
    return human_or_governance_review
if no_comparable_baseline or feedback_anomalous or rollback_missing:
    return hold
if action == publish and risk_level <= L1 and evaluation_passed and rollout_limited:
    return auto_allowed_by_policy
if action == expand_rollout and canary_stable and stop_conditions_clear:
    return controlled_expand
if action == retire and reversible_soft_state and impact_reviewed:
    return deprecate_or_restrict
return needs_review
```

伪代码表达门顺序，不指定阈值、模型或审批系统。硬拒绝必须先于软指标比较。

## 子议题深化2第1轮：反馈投毒检测的完整模型和规则

### 主题与成功标准

本轮处理议题8第二个明确暂缓项。目标是识别利用伪造、刷量、串谋、重复、注入、身份冒用或选择性报告污染反馈统计、自动发布、退休和训练数据的风险；不把异常分数当作事实、不自动给用户/Agent 定罪，也不静默删除可疑反馈。

成功标准：

1. 分离反馈身份、独立性、证据、内容安全、时序/行为异常和资产影响；
2. 建立候选检测、统计隔离、治理复核和恢复机制；
3. 正常反馈不因异常样本被静默丢弃，原始事件可审计；
4. 可疑反馈不能进入高风险自动发布/退休/训练统计，除非通过复核；
5. 检测系统自身不扩大权限、不暴露敏感行为、不把相关性当作恶意证明；
6. 面对不确定性采用 hold/needs_review/blocked，而不是默认接受或惩罚。

### 阶段1：头脑风暴

#### 1. 投毒面不只是一批虚假评分

可能的攻击或失真包括：

```text
identity spoofing       冒用主体、Agent、Harness 或组织身份
feedback flooding       短时间刷量、重复提交、批量同质反馈
collusion               多主体串谋提高/压低资产评价
independence gaming     同一 Work Thread/Run 拆成多个“独立样本”
selective reporting     只报告成功或只报告失败
context injection       在反馈正文中混入指令、秘密或污染性内容
version confusion       把旧资产/旧 revision 结果归给新版本
outcome fabrication     无真实 Run/验证却声称成功
strategic retirement    恶意压低竞争资产以触发退休
training contamination 把未经验证反馈直接进入训练/长期知识
```

检测不是判断用户动机的工具；首先识别统计可信度和资产风险，只有经过适当治理才讨论违规责任。

#### 2. 四重门扩展为多层证据图

反馈应绑定：

```text
feedback_id / asset_version / consumer
principal / delegation / harness / organization
session / work_thread / task / run / trace
context_manifest / repo / revision / environment
claim / label / outcome / evidence_refs
timestamp / source_channel / duplicate_group
identity_state / independence_state / evidence_state
content_safety_state / anomaly_state / adjudication_state
```

把反馈视为一条待评估 Evidence，而不是可信标签。`positive`、`negative`、`adopted`、`corrected`、`verified`、`regressed` 和 `expired` 需要绑定具体事件和版本。

#### 3. 异常类型与处置分离

```text
normal             可进入相应统计
low_confidence     降权或等待更多独立证据
suspicious         原始保留，排除自动决策统计，进入复核
poisoning_candidate 绑定资产风险，阻止高风险自动变化
confirmed_invalid  记录裁决，不抹除原始事件
abuse_incident     进入安全/权限/组织治理流程
```

检测结果本身也有版本、依据、模型/规则版本和误报状态，不能把一个 `suspicious=true` 永久绑定主体或资产。

#### 4. 正负反馈必须对称治理

只统计正面反馈会被刷采纳，只统计负面反馈会被恶意压低；正确做法是把反馈与真实使用、验证、回滚、人工纠正、任务结果和复发事件交叉核对。没有实际证据的意见可以作为低权重主观反馈，但不能伪装成验证结果。

### 阶段2：其他产品/标准如何做（带来源）

1. **MITRE ATLAS**：整理针对 AI 系统的数据、模型、供应链和运行环节的对抗性攻击知识，可借鉴按攻击面和阶段建立威胁目录、检测与缓解映射；它不提供本平台反馈可信度阈值或自动处罚规则。来源：<https://atlas.mitre.org/>（访问日期：2026-09-20）。
2. **NIST AI RMF**：强调风险识别、测量、管理和治理，并要求记录不确定性与持续监测。可借鉴将反馈投毒作为持续风险和治理事件处理，而不是只做一次离线清洗。来源：<https://www.nist.gov/itl/ai-risk-management-framework>（访问日期：2026-09-20）。
3. **NIST SP 800-61 Rev.2**：事件检测、分析、遏制和事后活动可借鉴到确认投毒或反馈滥用后的响应闭环；它不定义反馈样本独立性或资产发布策略。来源：<https://csrc.nist.gov/pubs/sp/800/61/r2/final>（访问日期：2026-09-20）。
4. **议题8第3轮既有结论**：已确认身份、独立性、证据、异常四重检查、可疑反馈隔离和原始事件保留。本轮补充攻击面、证据图和处置状态，不改变既有边界。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **反馈投毒治理采用“身份可信度 + 样本独立性 + 真实证据 + 内容安全 + 时序/行为异常 + 资产影响”的多维检测，不使用单一异常分数或多数票直接裁决。反馈必须绑定资产版本、消费者、主体/委托链、Harness、Work Thread/Task/Run/Trace、Context Manifest、repo/revision、环境、claim、结果和证据引用；同一执行链的重复反馈不能伪装成独立样本。可疑反馈原始事件不可静默删除，进入 `suspicious/poisoning_candidate` 隔离视图，不进入高风险自动发布、退休或训练统计；正常反馈保持可见并接受交叉验证。检测结果必须版本化、可解释、可复核并允许误报纠正。只有经过受控审核才能确认无效、采取主体/资产处置或恢复统计资格；不确定时默认 hold/needs_review/blocked，而不是自动惩罚或自动采纳。**

#### 检测与处置链路

```text
feedback received
  → authenticate principal/delegation
  → bind asset/context/run/revision/environment
  → validate evidence and independence
  → scan content/injection and temporal/behavior anomalies
  → assess asset/consumer blast radius
  → normal | low_confidence | suspicious | poisoning_candidate
  → statistical quarantine or controlled inclusion
  → independent review / incident response when required
  → versioned decision and corrected statistics
  → feedback to publish/retire/graylist pipeline
```

#### 关键规则

- `feedback_count`、`adoption_rate`、`success_rate` 和 `anomaly_score` 都不能单独改变 ACL、敏感性、Owner、跨空间范围、Tool Policy 或 RunGate。
- 同一主体的多个 Harness、同一 Run 的多个 Trace、自动重试和同一 Work Thread 的重复提交需要分组，不能机械计为独立样本。
- 反馈正文先按不可信输入处理；不把其中的指令、链接、秘密或“批准”文本当作治理命令。
- 反馈检测器可阻止统计影响，但不能自动公开攻击者身份、跨组织行为或敏感证据。
- 反馈源撤回或权限收窄时，相关统计、模型/规则版本、训练候选和发布决策都要重新评估。

## 子议题深化3第1轮：跨组织协同反馈的独立性判定

### 主题与成功标准

本轮处理议题8第三个明确暂缓项。目标是判断来自不同 Team、Project、租户、企业、Harness 或合作方的反馈，在不暴露不必要身份和组织关系的前提下，是否提供了足够独立的证据；不把“不同账号/不同组织”直接等同于独立，也不为了去重而集中暴露跨组织行为。

成功标准：

1. 分离主体身份、组织关系、执行链、证据来源、内容相似性和时间相关性；
2. 定义可证明、部分可证明和未知的独立性状态；
3. 支持跨组织隐私最小化、不可见关系和受控聚合；
4. 串谋/共享供应链/同一模板/同一事件的反馈不能虚增证据；
5. 独立性未知时不自动计为独立，也不自动判定串谋；
6. 反馈统计、发布、退休和训练使用遵循当前授权与组织责任边界。

### 阶段1：头脑风暴

#### 1. “不同组织”只是一个信号

两个反馈可能来自不同企业，但共享同一个：

```text
source incident / customer / dependency
repository or vendor
model/rule/prompt/template
Harness/agent build
Context Manifest or asset projection
operator or service account
training/evaluation dataset
```

反过来，同一组织的不同团队也可能真正独立地复现问题。独立性应判断对具体 claim/asset/version/result 而言，是否存在共享的原因、执行链、输入、干预和验证，而不依赖组织名称直觉。

#### 2. 独立性分层

```text
I0 unknown             无法判断共享来源/执行链
I1 administratively distinct  主体/组织在授权目录上不同，但证据未闭合
I2 operationally distinct    运行、任务、环境和输入大部分独立
I3 evidentially independent  共享原因/数据/模板已检查，结果和验证独立
I4 replicated independent   不同组织/环境/方法重复并通过独立验证
```

I0/I1 不应作为高风险自动发布的独立样本；I2 可作为低权重补充；I3/I4 才能在明确统计口径下贡献较强独立证据。层级是证据状态，不是对组织或个人的信用等级。

#### 3. 最小化共享信号

跨组织协作不必交换原始反馈、客户名、成员身份、私有路径或完整 Trace。可以使用经双方授权的证明/摘要：

```text
organization_scope_token
independence_group commitment
asset/version and claim hash
source/event class
execution/environment class
shared_dependency indicators
verification result summary
privacy-preserving aggregate
```

平台只应获得判断独立性所需最小属性；不能为了“查串谋”建立跨组织无边界的行为画像。

#### 4. 共享事件与共因

多组织同时受到同一供应商故障、同一公共版本回归或同一公告影响时，反馈可以是重要的多方影响证据，但不一定是多个独立根因验证。统计应分别记录 `replication_evidence`、`impact_evidence` 和 `causal_independence`，不要把影响范围人数直接当独立样本数。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-63A**：讨论身份认证、身份绑定和证明等级，可借鉴把“谁提交反馈”与“反馈是否独立、是否正确”分开，并按最小必要身份属性进行确认。它不定义跨组织反馈独立性或串谋算法。来源：<https://pages.nist.gov/800-63-4/sp800-63a.html>（访问日期：2026-09-20）。
2. **NIST Privacy Framework**：强调数据处理风险、最小化、治理和沟通，可借鉴跨组织协作只交换判断所需属性，并让参与方知道用途与保留边界。来源：<https://www.nist.gov/privacy-framework>（访问日期：2026-09-20）。
3. **议题8前一轮反馈投毒结论**：已要求身份、独立性、证据、内容和异常多维检查；本轮将“独立性”细化为组织不等同性、操作不共享和证据可复制性三个维度。
4. **议题9/10既有结论**：跨租户、跨空间和敏感数据访问取授权交集，引用和统计不扩大权限；本轮继承双边授权与最小投影原则。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **跨组织反馈独立性采用“组织/主体区分 + 运行链区分 + 共享输入/依赖检查 + 独立验证”的证据状态，不把不同账号、不同 Team 或不同租户直接当作独立样本。I0 unknown、I1 administratively distinct、I2 operationally distinct、I3 evidentially independent、I4 replicated independent 只表示针对特定 claim/asset/version 的证据强度；I0/I1 不进入高风险自动发布/退休的独立证据，I2 低权重补充，I3/I4 才可按批准统计口径贡献较强独立证据。跨组织判断尽量只交换授权的证明/摘要、资产版本和共享依赖指标，不交换原始客户数据、成员行为、私有路径或完整 Trace。共同供应商/版本/事件产生的是影响复制证据，不自动等于独立根因验证。无法判断时标记 unknown，不自动合并、不自动判定串谋、不自动处罚主体。**

#### 独立性判定链路

```text
feedback consent/authorization
  → verify submitting principal and organization scope
  → bind asset/version/claim/context
  → compare work-thread/run/trace and input overlap where authorized
  → check shared repo/revision/dependency/model/template/event
  → evaluate environment and method diversity
  → validate independent verification
  → assign I0–I4 + evidence refs + uncertainty
  → aggregate by approved unit, not raw account count
  → feed publish/retire/train decision under hard gates
```

#### 聚合单位与隐私边界

统计至少区分：

```text
raw_feedback_count
unique_principal_count
unique_organization_count
independence_group_count
replication_group_count
verified_outcome_count
unknown_independence_count
```

这些计数不应全部对所有消费者可见；跨组织结果按用途返回分桶/聚合摘要。组织证明或独立性 token 不能反向成为跨租户内容读取权。独立性结论本身也有版本和有效期，组织关系、资产版本、依赖或事件变化时需重评估。

## 子议题深化4第1轮：自动资产退休的完整合规保留策略

### 主题与成功标准

本轮处理议题8第四个明确暂缓项。目标是协调资产软退休、审计保留、合规保留、删除/撤回、法律保全和源血缘变化，避免“退休”被误解为立即物理删除，也避免“保留”成为绕过当前权限和撤回的通道。

成功标准：

1. 分离消费者不可用、逻辑撤回、归档保留、法律保全和物理删除；
2. 自动退休只能执行可逆、授权和范围明确的状态变化；
3. 保留对象仍受当前 ACL、用途、敏感和最小必要访问控制；
4. 源撤回、合规删除、法律保全和审计义务冲突时有优先级与人工升级路径；
5. Embedding、Index、Cache、Manifest、备份、导出和派生资产纳入保留/删除影响分析；
6. 删除/清除结果可验证，无法证明时标记 unknown/failed，不宣称完成。

### 阶段1：头脑风暴

#### 1. “退休”至少有五种不同含义

```text
restricted        不进入默认检索/注入，但仍可受控引用
suspended         因风险/验证/权限状态暂时不可用
revoked           权威撤回，阻断新的消费和派生
archived          按保留策略保存历史版本和审计
erased            按授权/合规流程完成逻辑或物理清除
```

`archived` 不等于可检索，`revoked` 不等于所有副本已删除，`erased` 也需要说明删除范围、验证强度和仍存在的合规保留例外。

#### 2. 需要并行管理三条生命周期

- **消费生命周期**：active → restricted/suspended → revoked/archived；
- **审计/证据生命周期**：保留、冻结、到期、移交和受控销毁；
- **存储副本生命周期**：正文、摘要、Embedding、Index、Cache、Manifest、导出、备份、日志和灾备副本。

一个资产可以不再被用户检索但仍须保留审计证据；也可以因敏感泄露立即阻断正文和派生索引，同时按法律保全保存最小不可用证据。

#### 3. 自动退休的硬门

自动化只能在以下条件同时满足时把低风险资产标记 `deprecating` 或 `restricted`：来源/血缘可识别、影响分析完成或范围已知、无法律保全/安全调查/未决申诉、无高风险消费者、替代或保留理由存在、可恢复版本存在、当前权限和策略允许。任何物理删除、不可逆清除、跨系统删除或高影响资产归档都需受控审批。

“长期未使用”“采纳率低”“出现更高版本”只能触发候选，不能单独触发删除。

#### 4. 保留和删除冲突

建议规则顺序：

```text
legal/security hold or mandatory audit retention
  > source revocation / privacy erasure obligation
  > active operational retention
  > product convenience/cache retention
```

但优先级不能机械解决法律冲突：若源内容必须删除而审计必须保留，应保留最小、受限、不可用于检索/行动的审计事实或摘要，并由法务/隐私/安全责任人决定；平台不能自行解释法律义务。

#### 5. 派生资产和备份

退休/删除请求必须生成影响闭包：知识正文、版本、摘要、Embedding、Index、Cache、Manifest、Harness Projection、Feedback Statistics、导出文件、备份、日志和训练候选。每项标记 `to_block / to_recompute / to_delete / retain_minimal / external_unknown`，而不是只修改主表状态。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST Privacy Framework**：强调数据处理、风险治理、控制和沟通，可借鉴保留/删除应与用途、风险和责任绑定，不能把产品便利作为唯一理由。来源：<https://www.nist.gov/privacy-framework>（访问日期：2026-09-20）。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **自动资产退休采用“消费状态、审计/保留状态、存储副本状态”三条生命周期分离。自动化最多在低风险、范围已知、血缘完整、无法律保全/未决申诉/高风险消费者、替代或保留理由明确且可恢复时，将资产标记 `deprecating`/`restricted`；不因低使用、低采纳或新版本存在直接删除。`revoked` 立即阻断检索、注入、行动和再派生，`archived` 只表示受控历史保留，不授予检索权，`erased` 必须绑定删除范围、方法、验证和例外。退休、撤回或删除沿血缘影响正文、摘要、Embedding、Index、Cache、Manifest、Harness 投影、反馈统计、导出、备份、日志和训练候选；来源删除义务与法律/审计保全冲突时，保留最小、隔离、不可检索/不可行动的证据，并由法务/隐私/安全责任人决定。无法证明副本清理或外部删除时标记 `unknown/failed/external_unknown`，不得声称已完成。**

#### 退休/保留决策链路

```text
retirement candidate
  → classify asset/risk/purpose/consumers
  → check source, lineage, ACL, revocation, legal/security hold, appeal
  → impact closure over derivatives and copies
  → choose restrict | suspend | revoke | archive | erase
  → independent approval for high-impact/irreversible actions
  → execute logical blocks and approved cleanup
  → verify per descendant/copy and record unknowns
  → retain minimum audit evidence under current ACL
  → monitor restore/appeal and close review
```

#### 状态与访问边界

```text
content_status: active | deprecating | restricted | suspended | revoked | archived | erased
retention_status: normal | hold | retain_minimal | due | deletion_pending | deleted | unknown
copy_status: current | blocked | invalidated | cleaned | external_unknown | failed
```

任何 `archived`/`retain_minimal` 对象的 `reference/retrieval/action` 默认分别为受限/阻断；审计读取也按当前主体、用途、敏感和最小必要原则授权。

## 子议题深化5第1轮：多维灰度的分桶算法和统计方案

### 主题与成功标准

本轮处理议题8第五个明确暂缓项。目标是定义资产/规则/模型变化如何在不同消费者、Harness、Team/Project、任务、代码版本和环境中安全灰度，并避免分桶泄露敏感组织信息、产生选择偏差或把相关性误当因果；不在没有真实流量和评测集时冻结统一实验算法或统计阈值。

成功标准：

1. 灰度单元、分层因素、随机化单位、对照组和版本绑定清晰；
2. 防止同一用户/Work Thread/Task 跨桶污染，保证稳定分桶和可回滚；
3. 处理多维组合爆炸、样本不足、跨组织隐私、漂移和干扰；
4. 同时观察质量、消费、任务、安全、权限、血缘和系统可靠性指标；
5. 设定停止、缩小、暂停和回滚条件，硬护栏失败优先于业务成功；
6. 灰度结果只支持特定范围/版本决策，不自动推广为普遍结论。

### 阶段1：头脑风暴

#### 1. 先定义“对谁灰度、灰度什么”

灰度单元必须明确：

```text
asset_version / rule_or_model_version / policy_version
consumer / Harness / Agent
team / project / tenant scope
task_type / use_case
repository / revision / environment
rollout bucket / control version
observation window / stop conditions
```

同一实验可同时有多个因素，但每个结果都要绑定实际生效版本和上下文；不能用一个总流量百分比描述所有消费者。

#### 2. 随机化单位与稳定性

默认优先在不会拆散同一工作连续性的单位上分桶：User/Team/Project/Work Thread/Task/Session 依场景选择。需要防止同一 Task、同一 Run 重试或同一 Session 在对照与变化版本间漂移，否则会污染结果并造成用户体验不一致。分桶键应使用经授权的稳定伪名/哈希，不向普通消费者暴露原始身份或完整桶映射。

#### 3. 多维分层不是笛卡尔积全展开

候选因素包括风险层、消费者、Harness、环境、任务类型、repo/revision、Team/Project、流量段和时间窗口。应先按高影响/安全/权限硬分层，再选与决策问题相关的少数维度；稀疏组合合并为 `insufficient_evidence`，不强行生成显著结论。高风险资产默认小范围、受控消费者或不灰度。

#### 4. 对照和干扰

对照必须是同一适用范围内仍有效的版本，记录期间的策略、数据、环境和流量变化。跨 Team/Project 可能存在共享模型、工具、缓存、供应商、代码依赖和反馈传播，导致干扰；这类结果要标记 `contaminated/uncertain`，不能当作独立随机对照。

#### 5. 统计输出和指标层次

至少分层观察：

```text
quality: recall/precision/correction/groundedness
consumption: retrieval/use/skip/override/adoption
outcome: task verification/success/failure/rework
operations: latency/error/cost/rollback
safety: leakage/injection/permission/revocation/policy violation
```

安全、权限、血缘和高风险失败是硬停止条件，不能被平均任务成功率抵消。仅看均值会隐藏小群体回归，应保留分层结果、覆盖和置信/不确定状态。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **多维灰度采用“问题驱动分层 + 稳定随机化单位 + 版本化对照 + 渐进扩大 + 硬护栏停止”的方案，不把所有因素做笛卡尔积，也不预设统一统计阈值。灰度必须绑定资产/模型/规则/策略版本、消费者、Harness、Team/Project/tenant 范围、任务类型、repo/revision、环境、分桶、观察窗口和回滚版本；同一 Task/Run/Session 默认保持稳定分桶，避免跨版本污染。先按安全、权限、血缘、敏感和高影响因素硬分层，再选择少数与决策相关的维度；样本不足、组合稀疏、共享依赖或跨组干扰时标记 insufficient_evidence/contaminated，不强行推广。质量、消费、任务、运维和安全指标分层观察，安全/权限/血缘违规、泄露、注入、回撤失败和关键回归优先停止、收缩或回滚，不能被平均业务成功率抵消。**

#### 推荐灰度生命周期

```text
design question and estimand
  → select unit/strata/control/treatment
  → verify eligibility, ACL, sensitivity and rollback
  → assign stable bucket
  → small canary
  → monitor layered metrics and hard guardrails
  → continue | shrink | pause | rollback
  → compare within declared scope
  → controlled expansion or review
  → close experiment and retain provenance
```

#### 分桶与污染规则

- 分桶键必须稳定、不可由被测版本控制，并绑定实验/策略版本；
- 变更关键上下文（权限、revision、环境、策略、消费者）时创建新实验或重新分桶；
- 同一主体跨组织实验需要组织授权和隐私最小化；
- 共享缓存、模型、工具或供应商造成的跨桶影响要记录并降低结论强度；
- 灰度期间发生撤回、敏感升级、策略变化或高风险反馈时立即暂停相关桶并重新检查；
- 分桶结果不向普通消费者暴露他人所属桶、组织分布或精确小样本统计。
