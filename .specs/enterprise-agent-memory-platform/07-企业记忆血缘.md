# 议题 7：企业记忆血缘

**状态：已确认（第 1、2、3 轮阶段性方案；当前独立讨论点已完成）**

## 问题定义

> 如何让 Wiki、Skill、RCA、L3 事实、Code Context、Embedding、Context Manifest 和执行结果能够回溯来源、解释派生过程、支持影响分析，并在源变化、撤回、权限收窄或 revision 变化时安全传播？

## 第 1 轮确认：结构化血缘、事件传播与受控影响分析

本轮确认：

> **企业记忆血缘不是单一的来源字段或展示型关系图，而是围绕不可变对象版本、类型化关系、运行事件和派生状态建立的可追溯体系。第一版采用结构化血缘引用集合、追加式事件和可查询的来源/影响视图，不立即建设完整图数据库。血缘至少区分事实来源、推理结论、派生资产和消费执行四类关系，并明确区分 `derived_from`、`supports`、`verified_by`、`applies_to`、`used_by`、`invalidated_by` 等语义。血缘不能扩大权限；来源 ACL、用途、敏感性、脱敏、发布状态和当前有效性共同约束消费。源撤回、权限收窄、revision 变化或证据失效时，必须优先阻断新的检索和执行，再异步重算受影响的索引、Embedding、Manifest 和派生资产；历史版本和已完成 Run 不被静默改写。**

### 1. 血缘对象范围

血缘至少覆盖以下对象：

```text
工作来源
├── User / Harness
├── Work Thread / Task / Run
├── Tool Call / Conversation / Evidence

工程对象
├── Repository / Revision
├── File / Symbol / Environment
├── Test / Trace / Log / Verification

记忆与知识对象
├── L0 Evidence
├── L1 Atomic Memory
├── L2 Context View
├── L3 Long-Term Memory
├── RCA / Wiki / Skill / Template / Code Context

派生与消费对象
├── Embedding / Index Entry
├── Context Manifest / Harness Projection
├── Action Proposal / Run Plan
└── Execution Result
```

这些对象不等价于同一种“来源”：Evidence 是事实证据，RCA 是解释性结论，Skill 是知识化资产，Embedding 是索引派生物，Context Manifest 是一次请求的投影，Run Plan 是执行计划，Execution Result 是消费和验证反馈。

### 2. 血缘关系语义

第一版至少支持以下关系：

```text
captured_from     从某来源采集
observed_in       证据出现于某次 Run / Tool Call
anchored_to       锚定到 Repository / Revision
derived_from      由某对象加工生成
supports          支持某个假设或结论
contradicts       反驳某个假设或结论
verified_by       由某验证结果支持
applies_to        适用于某 Project / Revision / Environment
projected_to      投影给某 Harness / Consumer
used_by           被某次请求或 Run 使用
invalidated_by    因某事件失效
supersedes        新版本替代旧版本
revoked_by        因权限、合规或来源撤回而撤回
```

关系不能全部简化为 `source_id`：

- `derived_from` 不等于 `verified_by`；
- `used_by` 不等于“该 Run 证明资产正确”；
- `applies_to` 不等于归属；
- 引用源对象不等于可以查看源对象全部内容。

### 3. 不可变版本与血缘记录

每条重要血缘关系至少绑定：

```text
source_object_id
source_version
target_object_id
target_version
relation_type
created_at
created_by
derivation_policy_version
redaction_policy_version
authorization_context
valid_time
recorded_at
status
```

代码和 RCA 场景还需保留：

```text
repository
revision / revision_range
file / symbol scope
environment
dependency range
```

这样可以区分不同来源版本、脱敏策略、模型/规则版本和面向不同 Harness 的投影，避免新版本静默覆盖旧版本。

### 4. 来源闭包与影响闭包

必须同时支持向上追溯和向下影响分析。

来源闭包：

```text
Skill v3
  ← derived_from RCA v2
  ← derived_from Evidence Set v5
  ← observed_in Run 123
  ← produced_by Harness X
  ← started_by User Y
  ← anchored_to repo revision R
```

影响闭包：

```text
Source Evidence revoked
  → RCA v2
  → Skill v3
  → Embedding / Index Entry
  → Context Manifest
  → Action Proposal
  → pending Run
```

影响闭包用于撤回、权限收窄、revision 变化、证据失效和策略变更后的重新评估。

### 5. 血缘与权限边界

血缘存在不等于可以访问，能够访问源对象也不等于可以访问全部派生对象。有效消费至少同时检查：

```text
当前主体权限
∩ 来源对象 ACL
∩ 目标空间策略
∩ 用途策略
∩ 敏感性与脱敏策略
∩ 资产发布状态
∩ 当前有效性
```

血缘不得成为绕过 ACL 的反向索引。摘要、Embedding、缓存、Context Manifest 和 Skill 都不能因为更抽象就自动脱离来源治理。

### 6. 血缘粒度

第一版按风险分级：

| 粒度 | 第一版策略 |
|---|---|
| 对象级 | 必须支持，例如 Skill 来源于 RCA |
| 版本级 | 必须支持，用于发布、撤回和审计 |
| 证据集级 | RCA 和知识化优先支持 |
| 字段级 | 高风险、高敏感资产按需支持 |
| 片段级 | 高风险、高敏感结论按需支持 |
| Token 级 | 不在第一版支持，留待以后讨论 |

不要求每个自然语言 token 都有精确来源。

### 7. 血缘状态、事件与传播

血缘或派生状态至少区分：

```text
active
partially_valid
needs_review
invalidated
revoked
orphaned
redacted
blocked
archived
```

推荐采用：

```text
权威当前状态
+
追加式血缘事件
+
可重建的派生视图
```

事件示例：

```text
LineageCreated
LineagePolicyChanged
SourceVersionChanged
SourcePermissionChanged
SourceRevoked
DerivedAssetRecomputed
ConsumerProjectionInvalidated
RunUsageRecorded
```

事件至少一次投递，消费端幂等；权威状态决定当前是否允许消费，事件负责传播和重建。源权限撤回、记忆失效、revision 不再适用或证据失效时：

```text
立即阻断新的 action
→ 阻断不满足条件的 retrieval
→ 标记受影响资产 needs_review / blocked
→ 异步重算索引、Embedding、Manifest 和派生资产
→ 审核后恢复、收窄、替代或撤回
```

失效要快，恢复可以慢。历史版本和已完成 Run 不被静默改写，但保留 `used_version`、`source_version_at_time`、`current_status` 和必要的事后失效标记。

### 8. 第一版能力边界

第一版优先实现：

1. 核心对象不可变版本；
2. 统一对象 ID 和版本 ID；
3. 类型化血缘引用；
4. `derived_from`、`supports`、`verified_by`、`used_by` 等关键关系；
5. 来源闭包和影响闭包查询；
6. 权限、敏感性、用途和发布状态检查；
7. 源撤回或失效后的新消费阻断；
8. Embedding、Index、Manifest 和消费者投影的派生血缘；
9. Run 使用记录；
10. 至少一次事件投递、消费幂等和状态收敛。

第一版不建设完整图数据库、自动因果裁决、Token 级溯源或无人工确认的高风险影响处置。

## 第 2 轮确认：血缘断言、权威性与冲突处理

本轮确认：

> **血缘不应由外部系统或模型直接写入最终权威关系，而应采用“Lineage Assertion → 验证与冲突处理 → Current Lineage Relation”的三段式模型。血缘声明必须记录声明者、采集方式、证据、版本、授权上下文和策略版本，并区分 observed、declared、derived、inferred、human_confirmed 和 imported。运行系统负责声明其直接观察到的事实，平台负责技术验证、去重、版本和权限检查，资源 Owner 或领域治理责任人负责确认高影响的解释关系、适用范围和跨边界关系。声明者、验证者、审批者、消费者和修正者必须分开建模。冲突不得由最后写入者、单一置信度分数或模型相似度自动裁决；应保留冲突断言，按风险暂停高风险检索和执行，并通过受控审核形成 accepted、rejected、superseded 或 unresolved 状态。血缘缺失或不可信时，低风险内容可以暂存为不可执行候选，高风险内容必须隔离或阻断。**

### 1. 血缘声明与当前关系分离

任何 Connector、Harness、治理 Agent 或人工操作者先提交 `LineageAssertion`，不能直接覆盖平台权威关系：

```text
LineageAssertion
├── assertion_id
├── source_object_id / version
├── target_object_id / version
├── relation_type
├── asserted_by
├── assertion_source
├── observation_or_declaration
├── evidence_refs
├── captured_at
├── authorization_context
├── policy_version
└── status
```

平台经过验证、去重、权限和版本检查后，才形成 `CurrentLineageRelation`。原始断言必须保留，当前关系不能取代断言历史。

### 2. 血缘来源类型

至少区分：

```text
observed          由运行、连接器或工具直接观察
declared          由 Owner、Harness 或外部系统显式声明
derived           由已确认关系推导
inferred          由模型、规则或相似性推断
human_confirmed   经授权人员确认
imported          从外部目录或血缘系统导入
```

事实血缘与解释血缘分开处理：运行系统产生的 `observed_in`、`used_by` 等关系偏向事实；RCA 的 `supports`、知识资产的 `applies_to` 等关系可能包含解释和判断，不能使用同一可信度语义。

### 3. 采集责任与审核责任

| 血缘关系 | 首要声明者 | 技术验证者 | 业务/治理批准者 |
|---|---|---|---|
| `observed_in` | Run / Connector | 平台采集服务 | 通常无需人工 |
| `anchored_to` | Connector / Harness | 代码或资源目录 | 高风险时由 Repo/Project Owner 确认 |
| `derived_from` | 知识化服务 | 派生服务 | 知识资产 Owner |
| `supports` | RCA 服务 / 分析者 | 证据校验服务 | RCA Owner |
| `verified_by` | 测试、CI、验证系统 | 验证系统 | 高影响时由领域 Owner 确认 |
| `applies_to` | Owner / 分析服务 | revision 和环境检查 | 领域 Owner |
| `projected_to` | Manifest 服务 | 权限和用途检查 | 策略系统控制 |
| `used_by` | Run / Harness | 执行记录系统 | 通常无需人工 |
| `revoked_by` | Owner / Security / Policy | 权限或状态系统 | 按撤回类型审批 |

产生过程证据的系统负责声明；拥有业务解释责任的主体负责确认；平台负责校验、传播和审计。

### 4. 关系状态与冲突处理

关系级状态应正交记录：

```text
provenance_state
observation_state
authorization_state
completeness_state
consistency_state
review_state
freshness_state
propagation_state
```

不使用单一 `lineage_confidence` 替代硬门禁。发现冲突时：

```text
保留所有断言
→ 标记冲突类型和影响范围
→ 计算当前消费风险
→ 高风险：阻断 retrieval / action
→ 请求责任主体补充证据
→ 形成 accepted / rejected / superseded / unresolved
→ 记录决策、责任人和影响
```

不得使用最后写入者、最高置信度、模型相似度或 Owner 级别单独裁决关系。

### 5. 缺失、不可信与传播延迟

区分血缘缺失和血缘不可信：

- 血缘缺失：没有来源引用、使用版本或派生版本记录；
- 血缘不可信：声明者无权、关系与运行记录冲突、revision 不匹配、源已撤回或仅有未经审核的推断。

处置原则：

```text
低风险 + 血缘缺失
  → 可暂存为不可执行候选
高风险 + 血缘缺失
  → 隔离或阻断
低风险 + 推断关系
  → 可作为候选，不进入执行链
高风险 + 关系冲突
  → 阻断相关 retrieval / action，进入治理队列
权限或来源不可信
  → 默认拒绝
传播尚未完成
  → 以权威状态为准，不因事件延迟恢复已撤回消费
```

### 6. 第一版优先能力

第一版优先实现：

1. `LineageAssertion` 独立对象；
2. 声明者、采集方式、证据、策略版本和授权上下文；
3. 关系类型白名单；
4. 关系级责任矩阵；
5. 断言去重、版本校验、权限校验和状态验证；
6. 冲突保留和治理队列；
7. 当前有效关系与原始断言分离；
8. 高风险关系人工或受控审核；
9. 缺失或不可信关系的 fail-closed；
10. 关系修正、撤回和审核记录不可变。


## 第 3 轮确认：血缘可见性与影响分析的治理边界

本轮确认：

> **血缘可见性必须与源内容可见性、知识检索权限和执行权限分离建模，至少区分关系存在性、关系元数据、源内容和影响分析四类能力。任意血缘查询都必须结合当前主体、用途、MemorySpace、目标对象、敏感性、查询范围和深度生成最小必要投影；能看到关系不等于能读取源内容，能看到派生摘要不等于能回溯原始日志。跨 Project、跨租户、全局影响闭包、血缘导出和撤回影响分析属于单独的高权限能力。无权节点可以隐藏或以不泄露敏感信息的抽象占位返回，但不得通过名称、数量、路径、错误信息、缓存或 Embedding 侧信道泄露其存在。影响分析只能生成复核、阻断或处置候选，不能直接授予删除、修改 ACL、恢复资产或执行工具的权限；紧急撤回可以先阻断新的检索和执行，再完成异步影响确认和正式治理。血缘查询和高风险影响分析必须可审计，缓存和投影也必须服从当前权限和策略版本。**

### 1. 血缘可见性的四类能力

至少区分：

```text
lineage_presence
  是否知道关系或节点存在

lineage_metadata
  是否查看类型、版本、状态、Owner 和时间

lineage_content
  是否读取源对象或派生对象内容

impact_analysis
  是否查询上下游影响闭包
```

跨空间和治理操作另行控制：

```text
cross_scope_impact
impact_export
lineage_revoke
lineage_recompute
```

这些能力不能压缩成单一的 `lineage:read`。

### 2. 最小必要血缘投影

同一血缘关系面向不同主体、用途和范围，可以生成不同投影。投影至少考虑：

```text
principal
purpose
tenant / organization
MemorySpace
target object
risk level
sensitivity
requested depth
```

建议返回：

```text
LineageProjection
├── visible_nodes
├── visible_relations
├── redacted_nodes
├── withheld_reasons
├── impact_summary
├── current_validity
├── allowed_actions
└── audit_context
```

投影是派生数据，必须绑定主体、用途、策略版本和过期条件；不能把一个主体生成的血缘投影直接复用于另一个主体。

### 3. 血缘可见性与源内容 ACL 分离

有效可见性至少取：

```text
主体对目标对象的权限
∩ 主体对源对象元数据的权限
∩ 主体对关系本身的权限
∩ Purpose Policy
∩ 敏感性 / 脱敏策略
∩ 跨空间策略
```

源内容读取还必须满足源对象 Content ACL。由此：

- 能看 Skill，不一定能看 RCA 原文；
- 能看 RCA 标题，不一定能看日志；
- 能看资产不可重新验证，不一定能看撤回源内容；
- 能查看当前 Project 影响，不一定能查看其他 Project 名称。

### 4. 影响分析的范围与权限

影响分析至少受以下参数限制：

```text
scope: User / Team / Project / Organization
depth: 直接下游 / 多跳下游 / 完整闭包
object_types: Memory / Knowledge / Index / Manifest / Run
time_range: 当前有效 / 历史版本 / 全历史
purpose: 调试 / 事故处理 / 安全 / 合规 / 重算
export: 禁止 / 脱敏导出 / 审批后导出
```

默认策略：普通用户限于当前 Project 和直接关系；Project Owner 可查看当前 Project 的多跳影响；Security/Privacy 在授权范围内查看跨边界影响；企业治理/审计可查看全局闭包但仍受内容 ACL 过滤；跨租户完整闭包默认禁止。

### 5. 隐藏节点与抽象占位

当用户无权查看节点或关系时：

- 节点存在本身敏感，完全隐藏；
- 用户需要理解阻断原因但不能看源对象，返回抽象占位；
- 同一 Project 的低敏感源，可显示有限元数据；
- 跨 Project、客户、凭据和生产数据默认隐藏源内容；
- Security/Privacy 事故处理须经授权后扩大元数据可见性。

抽象占位不得泄露原始名称、精确 Project、用户身份、文件路径、客户标识或未经授权的精确影响数量。

### 6. 影响分析与处置动作分离

影响分析只能生成：

```text
Impact Report
Impact Candidate
Recommended Review
Blocking Recommendation
```

不能直接授予删除、修改 ACL、跨空间导出、终止 Run、自动发布或自动恢复权限。紧急安全场景可以：

```text
Source revoked
  → 立即阻断新 retrieval / action
  → 记录临时阻断事件
  → 异步完成影响确认和正式处置
```

### 7. 查询审计与侧信道防护

血缘查询至少记录：

```text
query_id
principal
purpose
target_object
requested_scope
requested_depth
visible_scope
redacted_scope
result_count_bucket
decision
policy_version
timestamp
exported
follow_up_action
```

应限制对象枚举、查询深度、频率、导出和错误差异；隐藏节点不得通过名称、数量、响应时间、缓存、搜索排序、Embedding 或错误信息泄露。

### 8. 第一版优先能力

第一版优先实现：

1. 关系存在性、元数据、内容和影响分析四类能力分离；
2. 基于主体、用途、范围、深度和敏感性的最小投影；
3. 当前 Project 内对象级来源摘要和直接上下游；
4. 受限节点的隐藏或抽象占位；
5. 影响分析单独授权；
6. 血缘查询和高风险影响分析审计；
7. 导出默认关闭；
8. 影响分析与撤回、删除、ACL 修改、执行分离；

## 子议题深化1第1轮：血缘可见性权限的完整 RBAC/ABAC 策略矩阵

### 主题与成功标准

本轮处理议题7的第一个明确暂缓项：血缘可见性权限的完整 RBAC/ABAC 策略矩阵。目标是定义不同主体在不同用途、对象、关系、深度和敏感级别下能看到什么，而不是把“能看血缘”误当成“能看源内容”或把角色名称冻结为最终企业组织模型。

成功标准：

1. 分离关系存在性、关系元数据、节点摘要、节点内容和影响分析权限；
2. 同时表达 RBAC 的职责基线与 ABAC 的主体、资源、用途、范围、敏感性、来源 ACL、状态和环境条件；
3. 明确隐藏节点、聚合结果和错误响应不能泄露受限信息；
4. 影响分析、导出、跨 Project/租户和撤回传播属于额外高风险动作；
5. 权限变化、撤回和策略版本变化使缓存/投影失效；
6. 缺少主体、用途、ACL、敏感性、血缘或当前策略时 fail-closed。

### 阶段1：头脑风暴

#### 1. 血缘查询不是单一 read

至少分为：

```text
existence       是否存在关系/对象
metadata        类型、版本、时间、状态、方向和关系语义
summary         脱敏标题、范围、责任人摘要和风险标签
content         节点正文、日志摘录、代码片段或参数
impact          受影响下游/上游闭包与传播范围
export          导出、共享、跨空间或跨租户交付
admin           修改策略、撤回、恢复、重算和审计查询
```

能看 `derived_from` 关系不代表能看 source 内容；能看摘要不代表能展开日志；能看直接上下游不代表有全局影响分析权；能做影响分析不代表能导出结果或执行撤回。

#### 2. RBAC 只提供职责基线，ABAC 决定实际范围

建议角色基线包括：普通成员、Project Owner、Source Owner、Knowledge/Asset Owner、Reviewer、Security/Privacy、Operations/Incident、Auditor、Governance Admin 和 Service/Connector。角色不能单独放行访问，实际决策至少计算：

```text
current_subject
∩ role/action grant
∩ resource ACL
∩ source ACL and lineage
∩ purpose
∩ tenant/project/space scope
∩ sensitivity/redaction policy
∩ asset publication/current state
∩ environment and time condition
∩ break-glass / approval condition
```

组织成员关系、资源 Owner、参与过 Run、创建过资产和 Agent 身份不能自动等价于全部血缘读取权。

#### 3. 推荐 ABAC 属性

```text
subject: identity, roles, clearance, project/team, delegated_by
resource: object_type, object_id, source_space, target_space, sensitivity
relation: relation_type, source_version, target_version, direction, depth
purpose: observe | diagnose | verify | audit | impact | export | administer
scope: tenant/project/team/space/repository/revision/environment
state: published | candidate | suspended | revoked | restricted
condition: time, incident, approval, policy_version, break_glass
```

未声明用途、深度、范围或目标对象时，默认使用最小投影而不是推断最大权限；`audit` 也不自动解锁原始凭据或客户数据。

### 阶段2：其他产品/标准如何做（带来源）

1. **OpenLineage Facets**：以可扩展 facets 表达作业、数据集和运行的 lineage 元数据，可借鉴对象/运行/关系元数据分层和扩展能力；它不定义本平台的细粒度内容 ACL、跨空间授权或影响分析审批。来源：<https://openlineage.io/docs/spec/facets/>（访问日期：2026-09-20）。
2. **Microsoft Purview Data Lineage**：提供数据来源、转换和上下游可视化；可借鉴按对象和链路展示来源/影响，但产品可见范围依赖组织治理，不能直接移植为 Agent Memory 的授权矩阵。来源：<https://learn.microsoft.com/en-us/purview/concept-data-lineage>（访问日期：2026-09-20）。
3. **Databricks Unity Catalog Lineage**：强调按权限查看 lineage、列级/对象级治理和审计；可借鉴“查询 lineage 不等于读取底层数据”的隔离思想。它不定义本平台跨 Harness、RCA、Manifest、Tool Policy 或撤回闭包。来源：<https://docs.databricks.com/en/data-governance/unity-catalog/data-lineage.html>（访问日期：2026-09-20）。
4. **议题9既有结论**：权限采用主体—资源—动作—用途—作用域—条件—风险—状态模型，硬拒绝优先，未知默认拒绝/隔离；本轮直接将其展开到血缘关系和影响分析。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **血缘可见性采用 RBAC 基线 + ABAC 条件决策，并把 existence、metadata、summary、content、impact、export、admin 分成不同动作。实际可见范围取当前主体、角色动作授权、对象/来源 ACL、血缘、用途、租户/Project/Space、敏感/脱敏、发布状态、环境、时间和审批条件的交集；硬拒绝优先，未知或冲突默认拒绝、隔离或最小投影。血缘关系不扩大源内容权限，看到派生对象不自动看到原文，审计和影响分析也不自动解锁凭据、客户数据或跨租户内容。影响闭包、导出、跨边界查询、撤回/恢复和策略管理需要额外授权并审计。查询缓存、投影和错误响应必须绑定主体、用途、范围、策略版本、敏感策略和过期条件；权限/撤回/策略变化先阻断并使其失效。**

#### 原则级策略矩阵

| 主体/用途 | existence | metadata/summary | content | impact | export/admin |
|---|---:|---:|---:|---:|---:|
| Project member / observe | 当前 Project 内、已发布对象 | 当前范围内脱敏摘要 | 仅对象/来源 ACL 允许的内容 | 默认直接上下游；深度受限 | 否 |
| Project owner / diagnose | Project 管理范围 | 可看更多关系与版本 | 需 source ACL、用途和敏感策略通过 | 需单独 impact 授权 | 不自动允许 |
| Source/Asset owner / verify | 所属源/资产范围 | 可见验证所需元数据 | 仅当前负责范围，不能越过跨空间边界 | 需目标范围明确 | 不自动允许 |
| Security/Privacy / audit | 授权审查范围 | 可看策略、阻断、撤回状态 | 原文按最小必要，凭据仍隔离 | 可审查影响闭包 | 导出需专门审批 |
| Operations/Incident / diagnose | 绑定 Incident/Environment | 受限运行和版本信息 | 生产原文需应急授权 | 可看事故影响范围 | Break-Glass 限时限域 |
| Auditor / audit | 审计和决策记录范围 | 可见策略版本和职责链 | 默认不看业务原文/秘密 | 需单独授权 | 导出受控、不可改策略 |
| Governance admin / administer | 策略和状态元数据 | 管理范围内 | 不因管理权自动看内容 | 需审计且按范围 | 策略修改/撤回需职责分离 |
| Service/Connector | 仅绑定任务和字段 | 最小运行元数据 | 只读必要字段，禁止横向枚举 | 否，除非明确任务授权 | 不得导出/自授 |

矩阵是最低原则，不替代企业组织和客户合同。任一 `source_acl`、敏感性、用途、目标范围或撤回状态无法证明时，结果不得升级。

#### 查询决策与隐藏规则

```text
authenticate subject
  → resolve purpose and tenant/project/space
  → check action + relation type + requested depth
  → evaluate source/target ACL, sensitivity, state and policy
  → return minimum projection
  → audit decision and policy version
```

不存在、无权和被隐藏对象应尽量使用一致响应；禁止通过数量、名称、排序、错误差异、响应时间、缓存命中、Embedding 或深度探测推断隐藏节点。`result_count` 只在策略允许时返回分桶/近似值。影响分析失败或血缘不完整时返回 `unknown/partial`，不能返回“无影响”。

```text
historical cache        ≠ current authorization
```

## 子议题深化2第1轮：跨租户影响分析和导出协议

### 主题与成功标准

本轮处理议题7的第二个明确暂缓项“跨租户影响分析和导出协议”。目标是明确跨租户查询、影响闭包和导出如何在租户边界、来源 ACL、目标用途、脱敏、审批和审计下运行；不把管理员身份、血缘关系或事故上下文视为自动跨租户授权，也不冻结具体租户目录、法务例外、传输系统或密码学实现。

成功标准：

1. 跨租户影响分析与普通血缘查询、内容读取、导出、撤回和执行分离；
2. 明确跨租户最小投影、源/目标双边授权和用途绑定；
3. 导出默认关闭，导出物自身携带范围、敏感、血缘、有效期和接收者限制；
4. 隐藏节点、聚合、计数和失败响应不能泄露跨租户信息；
5. 导出前后均有脱敏、审批、完整性、审计、过期和撤回处置；
6. 无法证明边界、权限、血缘或清理状态时 fail-closed。

### 阶段1：头脑风暴

#### 1. 跨租户影响分析不是“把全图给管理员”

跨租户分析可回答受控问题，例如“某源版本撤回影响了哪些已授权派生资产”“某租户可见资产是否投影到另一个租户”，但必须按用途、范围、深度和最小结果回答。输出优先使用脱敏类型、数量分桶、状态和责任方引用，不默认暴露租户名称、项目路径、客户身份、原文、内部拓扑或隐藏节点。

#### 2. 跨租户动作分级

```text
T0 当前租户内直接/多跳查询
T1 经双方授权的跨租户关系存在性或粗粒度影响摘要
T2 经审批的脱敏影响闭包/审计报告
T3 原文或高敏导出、跨租户撤回/恢复、可执行或生产相关交付
```

T0 不得升级为 T1；T1 的关系摘要不自动允许 T2 导出；T2 不自动允许 T3 原文、执行或修改。任何跨租户动作还需满足当前主体、源租户、目标租户、用途、最小范围、敏感策略、血缘和有效期。

#### 3. 源租户与目标租户双边责任

源侧确认对象可被发现/派生、来源 ACL 允许指定目的、revision/血缘/敏感性完整、没有禁止外发内容；目标侧确认接收用途、目标 Owner、消费者范围、保存期、再分享策略和撤回能力。中介平台不能用自己的存储权限替代双方授权。没有明确目标 Owner 的跨租户结果只能作为隔离候选，不得交付。

#### 4. 导出物是新的受控资产

每个导出包或报告至少带：export_id/version、source/target tenant、requester/delegator、purpose、scope/depth、object/relation types、redaction policy/version、lineage refs、sensitivity、recipient、created/expires/revoked_at、integrity digest、allowed actions、no_reshare 条件和审计引用。导出物不能只是一份脱离控制的 JSON/CSV；即使下载成功，接收者也不能据此获得源内容、检索、发布或执行权。

#### 5. 影响分析与处置动作分离

影响分析只能产生摘要、候选阻断、复核任务、通知和影响列表引用；撤回、删除、ACL 修改、跨租户通知、终止 Run 或恢复资产另走各自授权。跨租户紧急泄露处置可以先同步阻断受影响新 retrieval/projection/action，再异步完成闭包和双边治理，不能以导出一份全量图作为紧急捷径。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-207 Zero Trust Architecture**：强调不应基于网络位置或隐含信任放行，访问应按主体、资源、策略和动态条件决策。可借鉴跨租户每次请求重新授权、最小权限和持续评估；它不定义血缘关系、导出格式或租户法务边界。来源：<https://csrc.nist.gov/pubs/sp/800/207/final>（访问日期：2026-09-20）。
2. **NIST SP 800-53 Rev.5**：提供访问控制、审计、信息流执行、数据最小化和边界保护等控制族。可借鉴跨边界传输前后的策略检查、审计和责任分离；控制目录不是本平台最终 RBAC/ABAC 或导出协议。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-20）。
3. **议题10跨空间复用与脱敏**：已确认受控引用/派生而非原文复制、源/目标双边责任、脱敏验证、发布与可执行分离以及撤回传播。本轮将租户作为更强隔离边界应用这些原则。
4. **议题9企业级权限与治理**：已确认跨租户、客户数据、凭据、不可逆和生产动作触发高风险流程；本轮明确跨租户影响分析与导出不得绕过独立审批和 RunGate 边界。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **跨租户影响分析采用最小投影、用途绑定、源/目标双边授权和按风险分级的受控协议。关系存在性/脱敏摘要、影响闭包、原文导出、撤回/恢复和执行是不同动作；跨租户关系摘要不授予内容访问，影响分析不授予处置或执行。T0–T3 只作为原则性风险层：T0 当前租户查询，T1 双方授权的粗粒度摘要，T2 审批后的脱敏影响报告，T3 原文/高敏/可执行/生产相关交付。导出物是带版本、范围、深度、敏感性、脱敏策略、血缘、接收者、有效期、完整性和禁止再分享条件的新受控资产；默认导出关闭，源撤回/权限收窄/目标策略变化时先阻断新的使用，再级联暂停、撤回、通知和复核。无法证明租户边界、来源 ACL、目标用途、血缘、脱敏或清理状态时默认隔离/阻断。**

#### 跨租户请求协议（语义层）

```text
request
  → authenticate subject/delegation
  → resolve source tenant + target tenant + purpose + scope/depth
  → classify action T0–T3
  → evaluate source ACL, target policy, sensitivity and lineage
  → source-owner / target-owner approval where required
  → minimize and redact
  → independent validation (content, re-identification, applicability)
  → issue time-bound export/analysis asset
  → recipient authorization and no-reshare enforcement
  → audit delivery, access, use, revoke and expiry
```

请求必须绑定不可变 request/plan 版本；租户、对象范围、用途、参数、脱敏策略、接收者、revision、环境或风险变化使授权失效。导出失败、校验失败、接收者无法认证或撤回传播不明时不得降级为裸文件交付。

#### 最小输出层级

| 输出 | 默认可见内容 | 不应包含 |
|---|---|---|
| T1 关系摘要 | 关系类型、方向、版本状态、粗粒度影响桶、策略状态 | 租户内路径、客户身份、原文、隐藏节点细节 |
| T2 脱敏报告 | 受控对象类型、影响范围、脱敏摘要、责任引用、验证和不确定性 | 凭据、客户明细、完整源码/日志、未授权拓扑 |
| T3 高敏交付 | 仅在专门审批、最小范围和强审计下提供必要内容 | 与用途无关的全量图、可执行权限、永久复制权 |

T1/T2 结果应支持 `partial/unknown/blocked`，不能把不可见节点当作不存在，也不能用精确零值掩盖未分析范围。

## 子议题深化3第1轮：血缘查询的精确差分隐私、数量隐藏和侧信道防护参数

### 主题与成功标准

本轮处理议题7第三个明确暂缓项。目标是确定血缘存在性、数量、影响范围和查询行为可能泄露信息时的防护语义；不直接冻结统一 epsilon、噪声分布、查询预算、延迟填充或所有行业阈值。成功标准是：先识别泄露面，再按用途和风险选择精确、分桶、近似、拒绝或差分隐私结果；查询预算、组合攻击、缓存和错误响应纳入治理；无法证明安全时默认收紧或阻断。

### 阶段1：头脑风暴

#### 1. 需要保护的并不只有节点内容

血缘查询可能泄露：

- 某租户、Project、客户、服务或代码组件是否存在；
- 某敏感资产有多少下游消费者、某事故影响了多少对象；
- 对象名称、路径、时间、版本、团队、Owner 或关系类型；
- 查询耗时、错误差异、分页/排序、缓存命中、召回分数、Embedding 相似度；
- 重复查询后由多个结果拼出的隐藏集合、变化趋势或单个成员信息。

因此“结果已脱敏”不代表查询接口安全；元数据、计数、存在性、状态和行为反馈也应按敏感级别控制。

#### 2. 先进行查询风险分类

```text
Q0 已授权低敏当前范围：可返回精确直接关系
Q1 受限摘要：分桶/泛化/近似数量与抽象关系
Q2 敏感影响或跨边界：审批、预算、审计、限频和专门投影
Q3 高敏存在性/个体可推断：默认拒绝或只返回统一阻断结果
```

Q0–Q3 是语义层风险，而非统一数值。是否进入 Q2/Q3 取决于对象、主体、用途、范围、历史查询、目标租户、组合风险和当前策略。

#### 3. 精确结果与差分隐私不是二选一的万能开关

- 精确结果适用于主体已被授权、低敏、范围小且不存在显著成员推断的查询；
- 分桶、区间、泛化和最小阈值适用于需要趋势但不需精确成员的摘要；
- 差分隐私适用于定义清晰的统计查询，需要明确邻接关系、epsilon/delta、组合预算、贡献上限和误差接受标准；
- 对关系存在性、单个高敏节点和复杂图路径，噪声可能无法提供可用或安全的语义，默认应拒绝、抽象占位或返回统一结果，而不是强行套用 DP。

差分隐私只约束特定输出机制的统计泄露，不自动解决源 ACL、身份授权、内容泄露、侧信道、缓存隔离、成员定义或跨租户审批。

#### 4. 查询预算与组合攻击

每个主体、用途、租户、资源范围、时间窗口和策略版本都应有可审计的查询预算/限频上下文。预算消耗和结果质量必须可解释；同一数据集的多次计数、不同过滤器、边界查询、错误重试、分页、排序和导出组合起来可能降低保护，不能只按单次请求评估。

预算不足、历史查询未知、数据集邻接关系不明或跨租户组合风险不可评估时，返回低精度/抽象结果或阻断。预算状态本身也不能泄露精确剩余量。

#### 5. 侧信道统一防护

一致性规则至少覆盖：

```text
无权对象 / 不存在对象 / 已撤回对象
  → 统一授权失败或抽象结果
查询错误、分页边界、排序、延迟、缓存命中、数量和频率
  → 不得成为隐藏信息的稳定信号
```

不要求所有请求机械使用相同延迟，而是按风险对高敏路径采用统一错误、响应大小/分页策略、缓存隔离、限频和必要的延迟扰动；具体技术措施必须通过攻击测试验证，不以“加随机延迟”宣称解决侧信道。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST Privacy Framework**：提供识别、治理、控制、沟通和保护隐私风险的框架；可借鉴先识别数据处理和风险，再选择控制与持续评估。它不规定血缘查询 epsilon、噪声机制或侧信道实现。来源：<https://www.nist.gov/privacy-framework>（访问日期：2026-09-20）。
2. **NIST Privacy Engineering Program**：强调可预测性、可管理性和解耦等隐私工程目标；可借鉴将查询用途、可见性、控制和验证纳入设计，而不是把脱敏当作一次性过滤。它不替代租户策略和风险阈值。来源：<https://www.nist.gov/itl/applied-cybersecurity/privacy-engineering>（访问日期：2026-09-20）。
3. **Dwork et al. Differential Privacy / Concentrated Differential Privacy**：差分隐私通过相邻数据集输出分布约束来降低单个参与者影响，集中式变体支持组合分析。可借鉴邻接关系、预算、组合和误差必须显式定义；论文不解决 ACL、图关系语义、缓存/错误侧信道或企业审批。来源：<https://arxiv.org/abs/1603.01887>（访问日期：2026-09-20）。
4. **议题7既有查询审计结论**：已要求限制枚举、深度、频率、导出和错误差异，并记录 result_count_bucket、策略版本和 follow_up_action；本轮将其扩展为风险分类和查询组合治理。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **血缘查询隐私采用“风险分类 → 最小输出 → 组合预算与限频 → 侧信道验证”的分层方案，而不是对所有查询统一添加噪声。Q0 可在已授权低敏范围返回精确直接关系；Q1 返回分桶、区间、泛化或抽象摘要；Q2 对敏感影响/跨边界查询要求审批、预算、审计和专门投影；Q3 对高敏存在性或个体可推断默认拒绝或统一阻断。只有在邻接关系、贡献上限、epsilon/delta、组合预算、误差和用途明确且通过攻击评估时，才可使用差分隐私统计；DP 不替代 ACL、用途授权、跨租户审批、撤回、缓存隔离或侧信道防护。隐藏节点、错误、分页、排序、延迟、缓存、Embedding、频率和导出都必须纳入泄露评估；预算/历史查询未知或风险不可评估时默认降低精度、隔离或阻断。**

#### 语义级查询决策

```text
authenticate and authorize
  → classify object/relation/purpose/scope risk
  → check source/target ACL and historical query context
  → choose exact | bucketed | generalized | DP | abstract | deny
  → apply depth, frequency, export and composition controls
  → validate result/side-channel risk
  → return minimum projection with uncertainty
  → audit decision, policy version, budget and follow-up
```

推荐记录：query_id、主体/用途、对象和关系类型、scope/depth、输出机制、数据集/邻接定义引用、预算桶、历史组合上下文、精度/误差状态、redaction、decision、策略版本和验证状态。不得向普通消费者暴露可用于反推的精确预算或内部噪声参数。

#### 最小防护矩阵

| 风险 | 默认输出 | 额外控制 | 失败处理 |
|---|---|---|---|
| Q0 低敏当前 Project | 精确直接关系 | 当前 ACL、审计、深度限制 | 降为摘要或拒绝 |
| Q1 受限统计 | 分桶/区间/泛化 | 最小计数阈值、限频、缓存隔离 | 返回 unknown/partial |
| Q2 敏感/跨边界影响 | 脱敏或 DP 统计、抽象关系 | 双边/独立审批、预算、组合检查、攻击评估 | 隔离/阻断 |
| Q3 高敏存在性/个体推断 | 统一拒绝或无细节占位 | 强审计、异常检测、必要应急授权 | 不返回可区分结果 |

这不是最终数值策略；阈值、预算和噪声应按数据集、用途、风险和真实攻击样本校准。

## 子议题深化4第1轮：血缘可见性与搜索、Embedding、Context Manifest 的统一过滤协议

### 主题与成功标准

本轮处理议题7第四个明确暂缓项。目标是确保血缘查询、关键词/向量/关系检索、Embedding/Index、缓存和 Context Manifest 对同一主体、用途、范围和策略产生一致的可见性结果；不把过滤器名称、数据库实现或某一搜索引擎 DSL 冻结为最终方案。

成功标准：

1. 统一定义当前身份、用途、tenant/Project/Space、source ACL、敏感、撤回、revision、环境和消费者能力等过滤上下文；
2. 确保过滤在检索召回前或至少在任何可泄露候选返回前生效，而不是只在 UI 隐藏；
3. 约束关键词、向量、图/血缘和缓存的结果交集，防止旁路召回和 Embedding 泄露；
4. Context Manifest 只包含当前授权且能证明来源与适用范围的投影；
5. 权限、撤回、策略、revision 或环境变化能够使 Index/Embedding/Cache/Manifest 失效或重算；
6. 缺少过滤上下文、来源血缘或一致性证明时 fail-closed。

### 阶段1：头脑风暴

#### 1. 统一的是授权上下文，不是强行统一物理索引

建议所有入口先解析一个不可变、带版本的 `Visibility Context`：

```text
subject / delegated_by
purpose / consumer
tenant / project / space
resource and allowed actions
source ACL / target policy
sensitivity / redaction policy
asset state / revocation state
repository / revision / environment
requested depth / token budget / expiry
policy_version / context_version
```

关键词、向量、图关系和 Manifest 可以使用不同索引和查询机制，但都必须引用同一授权上下文与过滤结果版本。统一协议不等于所有数据进入一个表，也不等于调用者可以自带一个更宽松的 filter。

#### 2. 过滤必须早于可能泄露的检索阶段

安全顺序优先为：

```text
authenticate
  → resolve Visibility Context
  → policy/ACL/sensitivity/revocation filter
  → candidate search (keyword/vector/graph)
  → applicability and revision filter
  → ranking/fusion
  → redaction and budget projection
  → Context Manifest
```

若底层向量或全文系统无法在召回前表达租户、来源 ACL、撤回和用途过滤，则只能用于已隔离的低敏分区、先取得安全候选或完全放弃该路径；不能先召回全库再让应用层隐藏结果。过滤后候选数量、分数、排序和错误也不能泄露被过滤对象。

#### 3. Embedding 是派生数据，不是权限边界

Embedding、倒排索引、图索引、近邻缓存、查询缓存和 rerank 特征都可能泄露源信息或保留撤回内容。每个派生对象需要 source refs、策略版本、可见范围、模型/索引版本、生成时间、失效状态和删除/重算能力。不能因为 Embedding 不可读、内容不完整或只返回相似度，就跳过 ACL、敏感和撤回检查。

#### 4. Context Manifest 是一次受控投影

Manifest 只能由当前 Visibility Context 生成，记录被选对象、版本、来源、适用范围、过滤结果、脱敏状态、预算、过期时间和策略版本。它不是权限本身；Harness/Agent 取得 Manifest 后仍不能通过自然语言扩大范围或将其内容当作工具授权。权限或源状态变化时，旧 Manifest 只作历史审计，不得继续用于新的检索、注入或行动。

#### 5. 缓存隔离和一致性

缓存键至少绑定主体/委托链、用途、tenant/Project/Space、过滤上下文版本、策略/敏感版本、revision/environment、查询形态和过期时间。无法证明不同主体/用途不会共享缓存时，禁用共享缓存。撤回或权限收窄先同步阻断命中，再异步清理/重算；清理失败不能返回旧内容。

### 阶段2：其他产品/标准如何做（带来源）

1. **Elastic Document/Field Level Security**：支持按文档和字段控制访问，说明过滤应成为搜索安全边界而非只由展示层裁剪；其具体角色和查询语法不能直接作为本平台跨源 ACL、撤回和 Manifest 契约。来源：<https://www.elastic.co/guide/en/elasticsearch/reference/current/document-level-security.html>（访问日期：2026-09-20）。
2. **OpenSearch Security 文档/机制**：搜索系统通常将索引、文档/字段过滤和角色策略组合；可借鉴查询层授权和最小字段返回，但本轮不依赖某厂商 DSL 或假定所有 Connector 都支持同等过滤能力。来源：<https://opensearch.org/docs/latest/security/access-control/>（访问日期：2026-09-20；当前页面可用性受站点路径变化影响）。
3. **OpenTelemetry Context Propagation**：跨服务传播关联上下文可支持把请求身份/trace 上下文传给采集和检索边界，但 Trace Context 不是授权凭证。来源：<https://opentelemetry.io/docs/concepts/context-propagation/>（访问日期：2026-09-20）。
4. **议题4/5/9/10既有结论**：按需融合要求早期权限过滤、知识化要求派生资产继承来源治理、议题9要求当前授权交集、议题10要求跨空间派生和撤回阻断；本轮把这些边界合并到检索—投影路径。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **血缘、关键词、向量、图关系、缓存和 Context Manifest 共享同一版本化 Visibility Context，但保持信号和物理存储分离。身份、委托链、用途、tenant/Project/Space、主体动作、来源 ACL、敏感/脱敏、资产/撤回状态、repo/revision、环境、消费者能力、预算和有效期必须在候选可能泄露前确定；过滤优先于召回，不能先召回全库再由 UI 隐藏。Embedding/Index/Cache 是派生数据，必须保留来源、策略、模型/索引版本和失效状态；Manifest 是当前授权的一次投影，不是权限本身。权限、撤回、策略、revision 或环境变化先同步阻断受影响检索/注入/行动，再异步清理、重算和审计；缺少上下文、血缘或过滤一致性证明时默认隔离/阻断。**

#### 推荐过滤协议

```text
request + authenticated principal
  → Visibility Context Resolver
  → authoritative policy decision
  → source/revocation/sensitivity/applicability filter
  → isolated keyword/vector/graph search
  → result-level lineage and permission recheck
  → rank/fuse only visible candidates
  → redact, deduplicate, budget and explain
  → issue Context Manifest with context/version/expiry
  → consumer-specific retrieval/injection/action checks
```

每个检索结果至少带内部不可见于普通消费者的 source refs、source version、policy/context version、visibility decision、redaction and completeness state。查询结果被复用到缓存、Embedding 或 Manifest 时，必须沿血缘记录派生关系；任何一层无法验证当前可见性，都不能用旧结果补全。

#### 一致性与失败矩阵

| 变化/失败 | 立即动作 | 后续动作 | 禁止行为 |
|---|---|---|---|
| ACL/用途收窄 | 阻断新检索、注入和 action | 清理/重算索引、缓存、Manifest | 返回旧缓存 |
| 源撤回/敏感升级 | 标记派生失效并阻断命中 | 影响闭包、通知、复核 | 以摘要/Embedding 继续使用 |
| revision/环境变化 | 降级候选或暂停适用性 | 重算 Code Context/Manifest | 默认当作当前事实 |
| 过滤服务不可用 | fail-closed 高风险路径 | 恢复后重新解析上下文 | 回退全库检索/默认 Project |
| Connector 不支持前置过滤 | 隔离数据源或拒绝该路径 | 建立安全适配/重新索引 | 先全量召回后 UI 隐藏 |
| 缓存版本不明/跨主体命中 | 丢弃命中 | 重新生成并审计 | 以命中成功证明权限 |

## 子议题深化5第1轮：全局影响分析的性能、缓存和异步任务模型

### 主题与成功标准

本轮处理议题7第五个明确暂缓项。目标是在高权限、跨项目/租户和大规模血缘闭包场景下，明确同步查询、异步任务、缓存和降级的安全语义；不承诺未经负载数据验证的延迟 SLA、图数据库或队列品牌。

成功标准：

1. 按范围、深度、风险、数据规模和用途选择同步或异步模式；
2. 结果可表达 complete、partial、unknown、stale、failed、cancelled 等状态，超时不能伪装成无影响；
3. 异步任务重新验证主体、用途、策略、血缘和撤回状态，不能沿用创建时的永久授权；
4. 缓存绑定 Visibility Context、策略/敏感版本、图/索引版本和过期条件；
5. 重试、取消、重复投影和失效清理具备幂等性；
6. 过载、队列积压、权限服务故障和闭包不完整时 fail-closed 或安全降级。

### 阶段1：头脑风暴

#### 1. 影响分析是长任务，不是普通列表请求

全局闭包可能跨多个租户、数百万节点、不同权限域和异步派生链，查询期间源权限、撤回状态和图版本也可能变化。因此应区分：

```text
sync_preview       小范围、低深度、低风险的即时摘要
async_analysis     大范围、多跳、跨边界或高风险闭包
snapshot_analysis  绑定明确图/策略版本的可复现分析
streaming_update   对长任务的进度、缺口和状态通知
```

结果必须携带分析开始/结束时间、图/策略版本、可见范围、扫描范围、缺口、状态和完整性；“返回空列表”不能同时表示无影响、无权、未完成和扫描失败。

#### 2. 同步/异步选择原则

可按以下因素选择模式：范围和深度、节点/边估计、跨租户/敏感级别、影响动作风险、实时性要求、当前负载、是否需要完整闭包和是否允许近似。超过安全预算时转异步或拒绝，不通过截断结果冒充完整结果。

异步任务必须保存请求版本而非永久授权，并在开始、每个敏感分区、分页/续跑和交付前重新检查当前权限、源撤回、策略、目标范围和接收者。

#### 3. 缓存的三种语义

- **Exact cache**：只可在相同 Visibility Context、图/策略/敏感版本、用途和有效期内复用；
- **Redacted aggregate cache**：只保存经过验证的分桶/聚合，仍需检查组合风险和当前政策；
- **Computation checkpoint**：只保存可恢复进度和源版本，不代表结果可见或授权仍有效。

缓存命中必须重新做当前授权检查；缓存不能作为绕过撤回、ACL 或预算的依据。缓存失效优先于提高命中率。

#### 4. 进度与部分结果

异步分析可报告已扫描范围、待扫描范围、隐藏/不可见范围、失败分区、版本冲突和预计剩余工作，但不暴露受限对象名称和精确隐藏数量。部分结果必须标记 `partial`，并区分“尚未扫描”“无权查看”“源缺失”“任务失败”和“确实没有下游”。

#### 5. 过载和资源保护

应采用范围/深度上限、租户和主体配额、优先级、并发限制、客户端退避、队列隔离、取消和死信/人工接管。高风险影响分析不能无限占用系统，也不能在过载时降级成全库无过滤扫描。策略/审计服务故障时，敏感和跨边界任务暂停；低风险任务也只能返回明确失败或过期结果。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **全局影响分析采用“同步预览 + 版本化异步任务 + 安全缓存/检查点”的分层模型。小范围、低深度、低风险查询可同步返回；跨项目/租户、多跳、敏感或完整闭包默认异步，并以 request/plan 版本、图/策略/敏感版本、Visibility Context、游标和当前权限重检贯穿任务生命周期。结果必须明确 complete/partial/unknown/stale/failed/cancelled，超时、无权、缺口和未扫描不能伪装成无影响。缓存只在主体、用途、范围、策略/敏感、图/索引版本和有效期匹配且当前授权通过时命中；checkpoint 只恢复计算位置，不恢复权限。撤回、ACL/策略变化、版本漂移、过滤服务故障或缓存失效时先阻断交付和下游动作，再取消/重算/清理并审计。过载采用限流、配额、退避、优先级、取消和隔离，不能回退到无过滤全库扫描。**

#### 异步任务状态和检查点

```text
requested
  → authorized_snapshot
  → queued
  → running
  → partial / paused / awaiting_recheck
  → completed | failed | cancelled | expired | stale
```

每次状态变化追加事件并记录：request/plan version、principal/delegation、purpose、scope/depth、Visibility Context、graph/index/policy versions、cursor/checkpoint、scanned/hidden/failed ranges、redaction、result completeness、expiry、decision 和 audit refs。恢复任务前重新解析当前上下文；版本或权限变化时只能新建分析版本或从安全检查点重算，不能沿用旧结果直接交付。

#### 结果交付规则

```text
analysis complete + current authorization + unchanged relevant versions
  → deliver minimum projection
analysis partial/unknown/stale or context changed
  → deliver only explicitly allowed status/summary, block impact/action use
analysis high-risk and approval/validation missing
  → block delivery and all downstream action
```

`completed` 表示本次声明范围在某个版本快照下完成计算，不表示永久没有影响、源内容当前可见或可以执行处置。

## 子议题深化6第1轮：紧急撤回、自动阻断与事后审批的完整流程

### 主题与成功标准

本轮处理议题7第六个明确暂缓项。目标是明确源撤回、敏感泄露、权限收窄、血缘断裂、revision 失效或策略违规发生时，平台如何立即降低继续传播和执行风险，并在事后完成影响闭包、责任确认、恢复/收窄/替代/撤回和审计；不把自动阻断误写成自动批准删除、恢复或生产变更。

成功标准：

1. 区分检测、权威撤回决策、自动阻断、影响分析、处置审批、恢复和事后复核；
2. 明确高风险路径的同步阻断范围与允许的最小止损动作；
3. 阻断和异步闭包具备幂等、可重试、可观测和 fail-closed 语义；
4. 正在运行的 Run、缓存、Manifest、Embedding、Index、导出物和离线副本有明确处置状态；
5. 恢复/收窄/替代/重新发布必须重新验证当前权限、血缘、敏感、revision 和适用性；
6. 事后审批不追认未经授权的高风险副作用，也不删除历史审计。

### 阶段1：头脑风暴

#### 1. 触发源与权威状态分离

撤回事件可能来自 Source Owner、Security/Privacy、Policy Engine、Connector、用户举报、异常检测、合规请求、revision 变化或下游验证失败。检测信号只是候选；只有可信的授权主体/策略状态才能将资产标记为权威 revoked/suspended。检测到明显高风险泄露时，可以先执行预定义的最小自动阻断，再等待正式撤回决策。

#### 2. 两阶段闭环

```text
Phase A — synchronous containment
  detect/receive signal
    → authenticate source and incident
    → write immutable control event
    → change authoritative block state
    → stop new retrieval / projection / injection / action
    → pause or gate pending high-risk Run
    → isolate affected cache/index/Manifest/export

Phase B — asynchronous governance
  enumerate lineage impact
    → classify confirmed/possible/unknown descendants
    → notify owners/consumers/security/operations
    → revoke/withdraw/retain/replace/narrow by decision
    → handle running/finished Run and external copies
    → revalidate before restore
    → post-incident approval, review and lessons
```

Phase A 只执行已预授权、可逆或最小止损动作；Phase B 的删除、恢复、跨租户通知、生产变更、长期 ACL 修改、知识替代和责任/风险接受必须走对应审批。

#### 3. 自动阻断的边界

可以自动阻断：新 retrieval、new projection、Context Manifest 生成/刷新、受影响 action proposal、pending high-risk Run、缓存命中、索引投影、跨空间发布队列和未交付导出。对已运行副作用动作，自动化只能按工具幂等/停止能力和既定 RunGate 策略暂停、取消或标记 `containment_pending`，不能盲目杀进程、回滚数据库或伪造成功。

#### 4. 状态和证据

至少区分：

```text
signal: detected / unverified / confirmed / rejected
control: active / blocked / isolated / restored / expired
propagation: pending / partial / complete / failed / unknown
asset: usable / suspended / revoked / superseded / retained_for_audit
run: not_started / gated / paused / running / partially_executed / completed / requires_review
review: requested / under_review / approved / rejected / superseded
```

每次状态变化记录主体、来源、原因、scope、策略版本、对象/版本、时间、影响分析版本、自动动作、人工决策、例外和审计引用。`propagation=complete` 只能说明声明范围的控制传播完成，不能证明外部离线副本不存在。

#### 5. 失败安全和重复处理

重复撤回、乱序恢复、撤回后迟到事件、传播消费者故障、权限服务不可用、影响闭包超时和外部系统无响应必须幂等处理。撤回优先级高于普通恢复和缓存刷新；恢复事件不能因为到达较晚而自动解除已生效阻断。无法验证影响范围或外部清理时，维持 blocked/unknown，并限制新的使用。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **紧急撤回采用“权威状态先行、同步最小阻断、异步影响闭包、独立处置审批、重新验证恢复、事后复核”的两阶段流程。检测信号不等于权威撤回；但对预定义高风险信号可先写入不可变事件并阻断新的 retrieval、projection、injection、action、Manifest 刷新、缓存命中、索引投影、发布队列和 pending 高风险 Run。自动阻断不自动批准删除、生产回滚、长期 ACL 修改、跨租户通知或恢复。影响闭包必须表达 complete/partial/failed/unknown，并枚举 RCA、Knowledge、Embedding、Index、Cache、Manifest、Harness 投影、导出物和 Run 的影响状态。恢复、收窄、替代、重新发布或解除阻断必须重新验证当前主体、用途、ACL、敏感、血缘、revision、环境、策略和适用性；无法证明传播/清理/外部副本状态时维持 blocked/unknown。事后审批补充责任和治理，不追认未经授权的高风险副作用，也不删除历史审计。**

#### 事件与控制状态机

```text
signal detected
  → authenticated/authorized decision
  → containment event appended
  → authoritative block active
  → propagation task queued
  → descendants classified and owners notified
  → disposition: revoke | suspend | narrow | replace | retain | restore
  → independent approval where required
  → current context revalidation
  → controlled restore or continued block
  → post-review and lessons
```

每个消费者应有独立状态，不用一个主资产字段假设传播已完成：

```text
source / asset / embedding / index / cache / manifest / export / run_projection
blocked | pending_review | invalidated | cleaned | unknown | restored
```

#### 自动阻断优先级

```text
P0 confirmed credential leak / cross-tenant exposure / active unsafe action
  → block all affected new consumption and pending high-risk actions
P1 source revoke / permission loss / severe sensitivity or lineage break
  → block retrieval/projection/action and isolate descendants
P2 revision/applicability/validation drift
  → suspend affected current use; allow only explicitly marked historical audit
P3 low-confidence signal
  → create review/monitoring candidate; no broad block unless policy requires
```

P0–P3 是原则性优先级，不是数值阈值。P3 也不能让不可信候选进入高风险执行；P0 的自动动作仍应是预授权的最小止损。

## 子议题深化7第1轮：血缘导出文件的水印、加密和外发控制

### 主题与成功标准

本轮处理议题7第七个明确暂缓项。目标是定义血缘报告、影响分析、审计摘要和跨租户导出在生成、传输、存储、打开、再分享、撤回和过期时的控制边界；不将某个 DRM、DLP、密钥服务或文件格式冻结为平台最终实现。

成功标准：

1. 导出内容、元数据、接收者、用途、范围和有效期绑定为新的受控资产；
2. 按敏感性和风险选择水印、加密、密钥、访问和外发策略；
3. 水印支持责任追踪但不被当作加密或授权替代；
4. 导出前后都有审批、脱敏、完整性、审计、过期和撤回状态；
5. 下载、缓存、备份、离线副本和再分享的控制边界明确；
6. 无法证明接收者、密钥、范围、血缘或撤回能力时默认不交付高敏内容。

### 阶段1：头脑风暴

#### 1. 导出不是“把查询结果保存成文件”

导出文件是一个独立的 `Export Asset`，至少记录：

```text
export_id/version
source/target tenant/project/space
requester/delegator/approver/recipient
purpose / allowed_actions
scope / depth / object and relation types
source versions / lineage refs / redaction policy
sensitivity / classification
created_at / expires_at / revoked_at
integrity digest / key reference / watermark reference
reshare policy / download and access events
```

文件正文、索引、附件、预览图、压缩包目录、元数据、文件名和错误响应都可能泄露信息，不能只保护正文。

#### 2. 三类控制目标不能互相替代

- **加密**保护未经授权者读取内容，依赖密钥、身份和生命周期；
- **水印/指纹**帮助追踪来源、接收者和泄露路径，不能阻止复制或授权；
- **DLP/外发策略**在生成、下载、分享和接收边界识别/阻断违规传输，不能取代内容加密和来源 ACL。

有效控制是组合而非单项万能：加密失败不能用水印补偿，缺少接收者约束不能用“no-reshare”文字宣告解决。

#### 3. 按风险分级导出

```text
E0 低敏、当前范围、内部短期摘要：平台内受控查看，必要时轻量水印
E1 脱敏跨空间/跨租户摘要：加密传输、接收者绑定、有效期、审计和水印
E2 敏感影响/审计报告：独立审批、强身份、密钥隔离、内容/元数据水印、禁止再分享或专门交付
E3 原文、凭据痕迹、客户/生产数据、可执行或高影响导出：默认禁止；仅专门人工/合规批准的最小必要交付
```

E0–E3 只是原则层级。任何高风险导出还需满足源/目标授权、用途、脱敏、血缘、接收方能力和撤回条件。

#### 4. 关键生命周期

```text
requested
  → classified/redacted
  → approved
  → generated and integrity-checked
  → encrypted and watermarked
  → delivered to authenticated recipient
  → accessed/used/audited
  → expired or revoked
  → retained/deleted under policy
```

审批绑定导出版本、内容范围、接收者、用途、密钥策略、有效期和允许动作；内容、范围、接收者、目的、策略或敏感性变化使批准失效。

#### 5. 外发和离线副本边界

平台可控制生成、下载、访问、分享链接、密钥发放、撤回通知和在线副本；对已下载到个人设备、截图、复制文本、邮件转发、备份、打印和第三方系统副本，可能只能记录未知/待接收方处置，不能声称已物理清除。高敏内容无法执行接收者绑定、有效期、加密和审计时，默认留在平台内或阻断导出。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-57 Part 1**：强调密钥材料生命周期、保护、使用、轮换、撤销和销毁。可借鉴导出加密不能只选择算法，还要绑定密钥责任、用途、有效期和失效流程。来源：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问日期：2026-09-20）。
2. **NIST SP 800-111**：讨论存储加密技术、威胁和密钥管理；可借鉴静态数据与终端存储都需保护，导出到用户设备后风险边界会变化。它不规定血缘导出审批、水印语义或接收方撤回。来源：<https://csrc.nist.gov/pubs/sp/800/111/final>（访问日期：2026-09-20）。
3. **NIST Privacy Framework**：强调数据处理、隐私风险、控制和持续沟通；可借鉴导出前目的/最小化、接收者、透明性和撤回评估。它不提供文件 DRM 或具体水印实现。来源：<https://www.nist.gov/privacy-framework>（访问日期：2026-09-20）。
4. **议题7/9/10既有结论**：导出默认关闭，跨租户需双边授权，派生资产权限不扩大，撤回先阻断新使用并异步处置；本轮把导出文件生命周期进一步具体化。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **血缘导出文件作为独立 Export Asset 治理，正文、元数据、附件、预览和文件名一并受控。导出按 E0–E3 原则风险分级：低敏内部摘要可平台内受控查看；脱敏跨边界摘要需强身份、加密传输、接收者绑定、有效期、水印和审计；敏感影响/审计报告需独立审批、密钥隔离和禁止再分享控制；原文、凭据、客户/生产数据、可执行或高影响内容默认禁止，仅在专门最小必要审批下交付。加密保护机密性，水印/指纹支持责任追踪，DLP/外发策略识别和阻断传输，三者不能互相替代。审批绑定导出版本、范围、用途、接收者、密钥策略、有效期和允许动作；内容、范围、策略、权限、接收者或敏感性变化使批准失效。撤回/过期先阻断在线访问、下载、链接、密钥发放和后续投影，再异步通知、吊销密钥/访问、处理在线副本和记录外部副本 unknown；无法证明外发控制、接收者或清理能力时默认不交付高敏结果。**

#### 推荐导出控制链路

```text
request + current Visibility Context
  → classify sensitivity/risk/purpose
  → source/target ACL and lineage check
  → minimize/redact and independent validation
  → approval and immutable export plan
  → generate versioned asset + integrity digest
  → apply encryption/key policy + watermark/fingerprint
  → authenticated delivery and recipient acknowledgement
  → access/download/reshare audit
  → expiry/revoke: block access + revoke key/link + notify + impact review
```

水印字段应只包含必要的追踪信息，避免把接收者个人数据、内部秘密或原始血缘再次写入文件；公开可见水印和不可见指纹都必须接受重识别、移除和误归因评估。

#### 导出状态

```text
candidate → redaction_review → approval_pending → approved
→ generated → delivered → access_monitored
→ expired | revoked | delivery_failed | external_unknown
```

`delivered` 不等于已阅读或可再分享，`revoked` 不等于外部设备已删除，`external_unknown` 不能降级为 `cleared`。

### 阶段4：专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| 密钥管理 | 文件加密了是否就安全？ | 不够。密钥用途、主体、生命周期、撤销、终端和备份同样受控。 |
| 隐私 | 水印会不会增加个人信息泄露？ | 只写最小追踪字段，区分可见水印/指纹并做再识别评估。 |
| 安全响应 | 已下载文件如何紧急撤回？ | 先撤销在线访问、链接和密钥，通知接收者并标记外部副本 unknown；不宣称可控制个人设备。 |
| 合规 | E3 内容能否通过特批导出？ | 只有专门人工/合规批准的最小必要交付；默认禁止且不能用普通审批替代。 |
| 产品 | 水印、加密和确认流程会不会影响使用？ | 对低风险提供平台内预览和分级简化；高风险以安全和可审计为先。 |
| 运营 | DLP 或密钥服务不可用怎么办？ | 高敏导出阻断；不回退裸文件、永久链接或默认密钥。 |

反例约束：

```text
encrypted              ≠ authorized
watermarked             ≠ confidential
DLP passed              ≠ source ACL passed
link expiry             ≠ downloaded copy deleted
recipient authenticated ≠ recipient may reshare
export delivered        ≠ external cleanup complete
key revoked             ≠ screenshots erased
checksum valid          ≠ content safe to disclose
```

### 自动审核与推进

自动化可以分类导出风险、核对源/目标授权、执行字段最小化/脱敏候选、生成版本化 Export Asset、校验完整性、应用已批准的加密/水印策略、记录交付和访问、在过期/撤回时阻断链接和密钥、生成外部副本 unknown 与复核任务。不能自动批准 E2/E3、选择绕过密钥治理的 fallback、把水印当授权、删除接收方设备、解除跨租户审批或宣称离线清理完成。

### 自动审核：当前方案无明显歧义，已确认通过，准备进入下一轮/下一个议题。

本轮阶段性批准记录：在用户授权自动继续范围内，采用“Export Asset + E0–E3 分级 + 加密/水印/DLP 分工 + 接收者/有效期/撤回控制”的方案。该方案承接议题7、9、10的授权、脱敏、撤回边界，明确外部副本不可控时的 unknown 状态，暂无材料性歧义。

### 明确暂缓事项及原因

| 暂缓内容 | 暂缓原因 |
|---|---|
| E0–E3 完整内容目录、阈值和法务例外 | 需要企业数据分类、客户合同和合规校准 |
| 加密算法、密钥服务、轮换/吊销和终端密钥交付实现 | 依赖企业安全架构、KMS 和客户端环境 |
| 水印/指纹格式、抗移除、误归因和取证规则 | 依赖取证、隐私和实际文件/媒体类型 |
| DLP、DRM、CASB 和外发通道集成 | 依赖企业外发系统和接收方能力 |
| 下载、备份、离线副本和接收方撤回/删除的技术协议 | 依赖跨组织系统、合规保留和责任矩阵 |
| 导出体验、性能、审计保留和运营 SLA | 依赖产品、存储和运营验证 |
