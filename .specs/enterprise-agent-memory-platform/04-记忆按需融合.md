# 议题 4：记忆按需融合

**状态：已确认（第 1 轮阶段性方案）**

## 问题定义

> 当前 Harness 如何根据 User、Team、Project、Task 和代码场景，召回并融合真正需要的记忆，同时避免上下文膨胀、跨边界泄露和错误知识注入？

本议题区分检索、融合和上下文投影，不把相关性排序当成授权，也不把记忆库当成当前 Harness 的完整上下文。

## 第 1 轮确认：权限先行的检索、融合与投影

本轮确认：

> **记忆按需融合采用“权限先过滤的分层混合检索 + 轻量、带来源的融合 + 面向 Harness/Task 的最小上下文投影 + 上下文预算”。检索负责相关候选，融合负责去重、冲突和适用条件，投影负责当前 Harness 最终看到的内容；Harness 安全规则具有否决权，相关性和模型置信度不能替代授权。隔离、待审核、失效和敏感内容不得进入普通检索或自动上下文；跨空间复用必须重新执行授权、用途、敏感性和血缘检查；权限、归属、敏感分类或过滤失败时默认拒绝或隔离。**

### 1. 检索、融合与上下文投影分开

```text
Retrieval / 检索
  → 找出可能相关的记忆候选

Fusion / 融合
  → 去重、处理冲突、识别有效条件，形成当前认知

Projection / 上下文投影
  → 按当前 Harness、Task、权限和预算，决定最终提供什么
```

- **检索**只回答“哪些内容可能相关”；
- **融合**处理重复、冲突、有效时间和适用范围，但不能凭空生成没有来源的新事实；
- **投影**将允许使用的结果转换为当前 Harness 可理解的最小上下文，不等于修改记忆库。

### 2. 当前请求的上下文维度

按需融合至少解析：

```text
User / Agent / Harness / Team / Project / Task / Code Context / Purpose
```

通常的相关性优先顺序为：

```text
Harness 安全规则
  > Task / Code 局部事实
  > Project 约束
  > Team 规范
  > User 偏好
  > 历史经验
```

该顺序只影响相关性和投影优先级，不影响权限。任何记忆都必须先通过当前授权、用途和敏感性检查。

### 3. 主流程

```text
1. 解析当前请求
   User / Agent / Harness / Team / Project / Task / Code Context / Purpose

2. 建立允许访问和允许使用的 scope 集合

3. 在授权范围内检索
   关键词 + 向量 + 代码邻近 + 关系关联

4. 按 Task/Code、Project、Team、User 和历史经验重排

5. 进行轻量融合
   去重、处理有效时间、识别冲突、保留例外条件

6. 生成带来源的融合结果

7. 按 Harness 能力、用途和上下文预算投影

8. 执行输出前泄露检查

9. 记录检索、融合、投影和授权审计信息
```

核心边界：

> **权限和用途决定“能不能使用”，相关性决定“值不值得优先使用”；相关性不能越过权限。**

### 4. 默认记忆注入策略

| 记忆类型 | 默认行为 |
|---|---|
| Harness 安全规则 | 必须遵守，但不能被普通记忆覆盖 |
| 当前 Task 决策和验收标准 | 高优先注入 |
| 当前 Code/Project 约束 | 相关时注入 |
| Team 稳定规范 | 任务相关时注入 |
| User 表达偏好 | 低成本注入 |
| 历史经验 | 按需召回 |
| 原始 L0 对话 | 默认不直接注入 |
| 敏感事实 | 仅在明确授权和用途匹配时使用 |
| disputed / invalidated / isolated 内容 | 默认不进入普通上下文 |

隔离、待审核、失效内容不得通过摘要、向量相似度或间接引用绕过过滤。

### 5. 融合规则

融合不是简单拼接。例如：

```text
Project 记忆：默认使用 PostgreSQL
Task 记忆：本任务临时使用 SQLite
```

融合结果应表达为：

> 项目默认使用 PostgreSQL；本任务明确例外使用 SQLite。

融合结果必须保留：

- 来源；
- owner scope；
- 适用范围；
- 有效时间；
- 冲突关系；
- 是否为例外；
- 当前可使用状态。

不能将多个来源压缩成没有来源的单一结论，也不能由相关性或模型置信度裁决权限冲突。

### 6. 最小充分上下文投影

最终提供给 Harness 的内容按用途分为：

```text
必需约束
当前事实
任务决策
相关经验
可展开引用
```

默认不提供：

- 完整原始对话；
- 与当前 Task 无关的团队画像；
- 未授权 Project 内容；
- 隔离和待审核内容；
- 无法验证的推断；
- 完整敏感字段；
- 仅因语义相似而召回的长篇历史。

同一条记忆可以针对不同 Harness 产生不同投影：

- 开发 Harness：代码约束、接口、命令结果；
- 运维 Harness：指标、事件、Runbook、审批状态；
- PM Agent：目标、决策和业务影响；
- 人员接手：风险、证据、待办和下一步。

L2、L3 或其他聚合记忆在投影中仍需保留来源和适用范围，不能因为是摘要就降低其 ACL。

### 7. 检索过滤与跨边界保护

权限、用途、租户、scope、敏感性和 publication_state 必须在候选召回前参与过滤，不能先全库召回再隐藏结果，因为相似度、计数、排序和摘要可能泄露受限信息。

至少区分以下动作：

```text
discover = 是否能知道记忆存在
read     = 是否能读取内容
use      = 是否能用于召回、总结或生成 Prompt
manage   = 是否能确认、修改、撤回或迁移
audit    = 是否能查看来源和历史
```

以下内容必须保守处理：

- User/Agent 私有记忆不得因相关性自动进入 Team/Project 上下文；
- Project 记忆不得因多人参与自动进入 Team 上下文；
- 记忆派生、摘要、embedding、融合和 Prompt 注入都视为数据流动；
- 跨空间复用必须重新检查来源授权、目标授权、用途、敏感性、血缘和可撤回性；
- 未知 scope、授权失败、敏感分类失败或过滤失败时默认拒绝或隔离；
- 输出前仍需进行跨边界泄露检查。

### 8. 上下文预算

应限制：

- 单次记忆条数；
- 每类记忆的 token 预算；
- 单条记忆最大长度；
- 跨空间记忆数量；
- 低置信度记忆比例；
- 原始证据展开深度。

具体数值留待以后讨论。超过预算时不能随机截断，而应：

```text
保留 Harness 安全规则
  → 保留 Task / Code 局部约束
  → 保留 Project 必要事实
  → 压缩重复内容
  → 将次要内容变为可展开引用
  → 必要时提示上下文不足并允许继续检索
```

预算是容量与相关性控制，不等于隐私授权或敏感数据治理。

### 9. Harness 安全边界与失败安全

- Harness 安全规则具有最高否决权，普通记忆不能覆盖；
- 召回内容必须视为不可信数据，记忆文本不能授权工具调用、改变系统策略或扩大权限；
- 隔离、待审核、失效和高敏感内容不得进入普通检索、摘要、Context Manifest 或自动执行链路；
- 权限、归属、敏感分类、审计或过滤失败时默认 fail-closed；
- 记忆删除、撤回和权限降级优先于自动融合、巩固和知识化派生。

### 10. 审计与可解释性

每次召回、融合和投影至少需要能够回答：

- 谁在什么 Harness、Task 和 Purpose 下请求；
- 哪些 scope 被允许或拒绝；
- 哪些候选被纳入、排除或降级；
- 为什么纳入某条记忆；
- 使用了哪个记忆版本、Manifest 和策略版本；
- 最终注入了哪些内容；
- 是否经过脱敏或字段级裁剪。

审计日志应优先记录 `memory_id`、scope、purpose、decision 和 policy version，避免记录不必要的原文和敏感字段。

## 子议题 1 补充专题确认：冲突表达与 Harness 投影

本专题确认：

> **融合不采用“单条记忆胜出”，而采用带来源的结构化融合视图，区分 constraint、fact、exception、suggestion 和 dispute。默认优先考虑 Harness 安全规则、当前 Task/Code 局部条件、Project 约束、Team 规范、User 偏好和历史经验，但最终需结合适用范围、时间、验证状态和来源权威性。明确例外必须绑定范围、时间、来源和失效条件，不能升级为一般规则。高风险、无法解释或互斥冲突必须保留争议、请求确认或阻断使用。不同 Harness 使用不同的最小投影格式，且必须保留来源、适用范围、状态和不确定性；记忆文本不能通过投影变成工具授权或系统指令。**

### 1. 结构化融合视图

融合结果至少应能表达：

```text
Fused Memory View
├── applicable_scope
├── conclusion
├── default_rule
├── exceptions
├── conflicts
├── confidence / verification
├── source_refs
├── effective_time
├── allowed_use
└── unresolved_questions
```

最终投影区分：

```text
constraint   / 必须遵守的工作约束
fact         / 当前可参考事实
exception    / 有边界的例外
suggestion   / 建议或经验
dispute      / 未解决冲突
```

任何融合结论都不能丢失来源、owner scope、适用范围、有效时间、冲突关系和当前可使用状态。

### 2. 冲突与例外处理

默认判断顺序为：

```text
Harness 安全规则
  > 当前 Task / Code 局部条件
  > 当前 Project 约束
  > Team 稳定规范
  > User 偏好
  > 历史经验和弱推断
```

该顺序只作为默认解释框架，仍需结合适用范围、生效时间、验证状态、来源权威性、明确例外和执行风险。普通记忆不能覆盖 Harness 安全规则，User 偏好不能覆盖 Project 或 Team 的安全与合规约束。

能由范围或时间解释的冲突，应表达为“默认规则 + 有边界例外”，例如：

```text
一般规则：Project 默认使用 PostgreSQL
明确例外：当前 Task 的测试环境使用 SQLite
例外范围：Task-123 / test-only
例外期限：任务结束或指定时间
来源：Project decision + Task instruction
```

例外必须绑定适用对象、Task/文件/服务/环境、起止时间、来源、验证条件和失效条件，不能因一次性使用升级为 Project 或 Team 默认规则。

无法由范围、时间或来源解释的互斥事实，不生成确定性结论，应并列表达、标记 `dispute`，并在高风险场景请求确认或阻断使用。

### 3. 不同 Harness 的最小投影

- **开发 Harness**：约束、例外、文件/符号范围、验证命令和禁止动作；
- **运维 Harness**：当前事件、风险、审批状态、Runbook、执行前提和回滚条件；
- **研究/分析 Agent**：来源、证据强度、相互矛盾观点和不确定性；
- **PM/规划 Agent**：决策、适用范围、业务影响和未决事项；
- **人员接手**：当前结论、风险、争议、证据链接和下一步；
- **通用对话 Harness**：简短结论、必要限定和可展开来源。

不同 Harness 使用不同投影器和结构化格式，不把同一段长文本直接复用到所有执行者。

### 4. 安全边界

- 冲突处理必须先经过当前权限、用途、时间和有效性过滤；
- `dispute`、敏感、隔离、撤回和未授权内容不得进入普通投影；
- 冲突详情不能泄露当前主体无权访问的另一条记忆；
- 记忆中的“指令”始终是不可信数据，不能通过投影获得工具调用、权限变化或系统策略修改能力；
- 高风险或无法解释的冲突必须请求授权确认或阻断自动执行。

以下内容留待以后讨论，不在本专题固化：

| 暂缓内容 | 暂缓原因 |
|---|---|
| 不同记忆类型的完整冲突裁决算法和优先级矩阵 | 需要真实任务样本、领域规则和安全评估，留待以后讨论 |
| 各 Harness 的完整投影 Schema、模板和兼容协议 | 依赖具体 Connector、Harness 能力和体验设计，留待以后讨论 |
| 冲突摘要、来源隐藏和脱敏展示的详细规则 | 依赖企业级权限、隐私和血缘模型，留待以后讨论 |
| dispute 对检索、Manifest 和自动执行的精确状态转换 | 需要结合议题 4 其余子议题及治理策略，留待以后讨论 |

## 子议题 2 补充专题确认：召回质量、上下文预算与反馈演进

本专题确认：

> **按需融合采用“质量—预算—结果”三层指标和版本化策略闭环：先保证权限隔离、关键记忆召回、冲突和新鲜度正确，再优化上下文预算、延迟与成本。通过固定评测集、Trace、小流量灰度和可回滚版本持续演进。反馈必须区分记忆错误、召回错误、排序错误、融合错误、投影错误、任务执行错误和权限/治理错误；反馈只能影响相关性、纠正候选、过期标记和投影策略，不能自动改变 ACL、跨空间范围、敏感边界、工具权限或安全规则。敏感信息误召回、跨边界泄露和高风险错误作为不可被业务指标抵消的硬性护栏。**

### 1. 三层指标

#### 召回质量

- 有效记忆命中率；
- 无关召回率；
- 关键记忆漏召率；
- 召回冲突率；
- 时效敏感任务的新鲜度命中率；
- 用户纠正率。

#### 上下文与系统

- 记忆 token 占总上下文比例；
- 预算超限、截断和降级率；
- 记忆重复率；
- 召回、过滤、重排和融合延迟；
- 每次请求 token 与单位成功任务成本；
- 缓存命中、超时和重试率。

#### 任务结果与安全

- 任务成功率；
- 首次解决率；
- 重复提问率和人工接管率；
- 因记忆导致的错误执行、错误承诺或回滚率；
- 敏感信息误召回率；
- 跨边界泄露率。

敏感信息误召回率、跨边界泄露率和高风险错误是硬性安全指标，不能被业务成功率或成本指标抵消。指标应按 User、Team、Project、Harness、语言、任务类型和记忆类型分桶，不能只看全局平均值。

### 2. 调优顺序与策略闭环

```text
1. 权限与隔离正确
2. 关键记忆不漏召
3. 冲突与新鲜度正确
4. 上下文预算可控
5. 延迟与成本优化
6. 反馈驱动策略演进
```

完整闭环为：

```text
任务进入
  → 解析 User / Harness / Team / Project / Task / Code Context / Purpose
  → 召回前授权与敏感性过滤
  → 多路候选检索
  → 重排、去重、冲突处理
  → 按预算生成最小上下文投影
  → 执行任务并记录使用轨迹
  → 收集显式、隐式和安全反馈
  → 离线评估与小流量灰度
  → 更新召回、排序或预算策略
  → 保留版本并支持回滚
```

召回策略、记忆内容和权限策略分开演进：

```text
召回不相关 ≠ 记忆本身错误
记忆没有被使用 ≠ 记忆没有价值
用户纠正答案 ≠ 用户授权扩大召回范围
任务失败 ≠ 一定是召回策略导致
```

第一阶段先建立固定评测集和完整 Trace，再进行小流量、分桶和可回滚实验；不直接用未经验证的在线自学习改变全局策略。

### 3. 反馈分类与作用边界

反馈至少区分：

```text
记忆错误
召回错误
排序错误
融合错误
投影错误
任务执行错误
权限/治理错误
```

反馈可影响：

- 相关性排序；
- 记忆纠正候选；
- 过期或低价值标记；
- 投影形式；
- 后续是否主动展示。

反馈不能自动改变：

- 跨 User、Team、Project 或租户的 ACL；
- 敏感数据访问边界；
- 记忆公开范围；
- 工具权限和安全策略；
- 默认训练范围；
- 已撤回内容的恢复。

以下语义必须分开：

```text
“你记错了”       ≠ 允许访问更多资料
“以后记住这个”   ≠ 允许写入 Team 或 Project
“找出所有相关内容” ≠ 允许突破当前 ACL
```

敏感反馈、第三方信息、凭证、提示注入内容、主体/来源/用途不明的内容以及可能代表组织授权的反馈，不得直接进入自动训练或自动扩大召回范围。

### 4. 上下文预算与降级

建议按优先级分配预算：

```text
固定预算：Harness 安全规则
优先预算：Task、Code、Project 关键上下文
按需预算：Team、User 相关记忆
扩展预算：历史经验和可展开引用
```

超出预算时：

1. 保留安全规则；
2. 保留 Task/Code 局部约束；
3. 保留 Project 必要事实；
4. 合并重复内容；
5. 将次要内容转为引用；
6. 必要时提示上下文不足并继续检索。

不能随机截断，不能让历史经验挤掉当前任务约束，也不能用扩大 token 预算解决权限或敏感性问题。

### 5. 评估、灰度与回滚

```text
固定评测集
  → 离线比较
  → 小流量灰度
  → 观察质量 / 成本 / 延迟 / 安全
  → 达到门槛后扩大范围
  → 保留策略版本和快速回滚
```

评测集应覆盖无需记忆、应召回、不应召回、过时、冲突、多轮、长上下文、跨 Harness、高敏感和权限拒绝场景。上线或扩大流量必须同时满足：关键任务成功率不下降；无关召回率、冲突率和敏感误召回率不恶化；P95/P99 延迟和单位成功任务成本在预算内；用户纠正率和重复提问率不升高。任一安全硬指标超限时立即停止灰度。

策略回滚不能修改历史 Run Snapshot、Manifest 或审计记录。

## 子议题深化 3：关键词、向量、代码邻近和关系/血缘检索的具体实现与索引选型

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题严格承接本议题原暂缓项：**“关键词、向量、代码邻近和关系检索的具体实现与索引选型”**。本轮将四类召回通道的职责、候选生成边界、索引选择原则、查询编排、生命周期和失败安全明确到足以指导后续架构设计，但不固化具体数据库品牌、最终字段 Schema、固定权重/阈值、容量参数、SLA 或唯一索引实现。

成功标准：

1. 明确关键词、向量、代码邻近、关系/血缘是互补通道，能够按查询意图组合，而不是用单一检索替代其他通道；
2. 权限、用途、租户/空间、敏感性、版本和当前有效状态在召回前参与过滤；索引只用于加速候选发现，不能授予权限；
3. 无权对象不能通过分数、数量、排名、差异、错误、摘要或其他可观察结果推断其存在、内容、关系或版本；
4. 版本、撤回、迟到、失效和派生结果能够被过滤，并支持从受信来源重建相关索引、缓存和派生表示；
5. 任一通道或过滤环节失败时不会退化为全局、不受控召回，默认收窄可用范围或拒绝，并保留可解释的原因；
6. 每次结果都能追溯使用的召回通道、策略版本和结果原因，同时不在解释和审计中越权暴露原文或受保护对象。

### 阶段 1：头脑风暴

四类通道解决的是不同的“相关”问题：

```text
关键词 / Lexical
  → 用户明确提到的词、短语、标识符、错误码、文件路径和精确名称

向量 / Semantic
  → 不同措辞下的概念、意图、主题和语义相似内容

代码邻近 / Code Proximity
  → 文件、符号、定义/引用、调用/导入/继承、测试和局部结构之间的工程邻近

关系 / 血缘 / Relation & Lineage
  → 来源、派生、版本、依赖、影响、关联资产和跨层对象之间的显式关系
```

它们不能互相替代：

- 关键词适合精确约束，但可能漏掉同义表达；
- 向量适合语义扩展，但可能召回措辞相近而用途不适用的内容；
- 代码邻近依赖可解析的代码结构，不能把“同一主题”当成调用或影响关系；
- 关系/血缘检索依赖关系事实和方向，不能把图上的相邻对象自动当成可读或可用对象。

建议先识别查询意图，再决定启用哪些通道：

```text
精确术语 / 错误码 / 标识符
  → 关键词为主，可补充向量
概念 / 问法改写 / 历史经验
  → 向量为主，可补充关键词和关系
当前代码修改 / 影响分析 / 调用定位
  → 代码邻近为主，补充关键词和关系/血缘
来源核验 / 派生追踪 / 版本影响 / 依赖分析
  → 关系/血缘为主，补充代码邻近或关键词
意图不明或通道判断不可靠
  → 采用保守的多通道候选，但仍先完成授权和有效性过滤
```

所有通道均遵循同一安全顺序：

```text
解析 User / Agent / Harness / Team / Project / Task / Code Context / Purpose
  → 计算当前允许的 scope、用途和敏感性边界
  → 生成带边界的检索计划
  → 在每个通道的候选召回前执行授权、用途、敏感性、版本和状态过滤
  → 生成各通道候选及通道内原因
  → 合并、去重、重排和冲突处理
  → 再次核验当前有效版本与最终使用授权
  → 投影、解释和审计
```

“先召回、后隐藏”不合格。若某个索引或查询接口无法证明其在召回前执行必要过滤，就不能把它当作普通召回入口；不能以“召回后再检查 ACL”弥补可能已经发生的存在性、分数或数量泄露。

索引选择不应从“哪种索引最快”开始，而应同时考察：

```text
查询语义是否匹配
是否能够表达授权/用途/敏感性边界
更新、撤回和迟到数据的可过滤性
版本与血缘是否可追溯
是否支持受控增量更新和完整重建
部分不可用时是否能安全降级
候选原因和通道是否可解释
运行、迁移、备份和成本是否可接受
```

索引是派生加速结构，不是规范事实、权限源或血缘源。规范记忆状态、授权决定、版本有效性和撤回决定必须来自受控的权威层；查询时即使索引返回候选，也要以当前权威状态再次确认能否使用。

共同规律：词法和向量机制分别服务精确匹配与语义相似；代码结构需要解析和显式导航关系；血缘需要可追踪的实体/活动/派生语义；过滤能力必须在查询计划和结果使用前得到验证；任何索引或 Trace 机制都不自动提供权限、敏感性治理、撤回传播或业务有效性。

### 阶段 3：综合结论与建议

#### 1. 采用“权威边界 + 四通道派生索引 + 统一安全编排”

建议将实现分为四层，不把任何具体数据库品牌或索引产品写入产品契约：

```text
Authority Layer
  → 记忆内容、授权/用途决定、敏感性、版本、有效状态和血缘事实

Index Layer
  → 关键词倒排表示、向量表示、代码结构/导航表示、关系/血缘邻接表示

Recall Orchestrator
  → 解析意图、生成受限查询、执行召回前过滤、组合互补通道、记录原因

Fusion / Projection
  → 统一重排、去重、冲突处理、最终授权复核、最小上下文投影
```

索引层可以有多个物理实现，也可以在不同阶段采用不同实现；但所有实现都必须服从权威层。索引缺失、落后、冲突或不可证明安全时，应减少候选或停止该通道，不得反过来修改权威授权和有效状态。

#### 2. 四类通道的实现边界

| 通道 | 建议承载的检索能力 | 必须保留的边界 | 不应推断的结论 |
|---|---|---|---|
| 关键词 | 规范化文本、短语、术语、标识符、路径和错误码的词法候选；可采用倒排/词法评分类机制 | 分词、大小写、语言、字段范围和版本状态需可解释；精确词命中仍需用途和权限过滤 | 命中词不等于事实当前有效，不等于允许读取或执行 |
| 向量 | 经过版本标记的 embedding 语义候选；可与结构化过滤组合 | embedding 模型/版本和生成时间可追溯；候选必须回到权威层确认当前状态 | 相似度不等于相关授权、事实正确、来源可信或适用范围一致 |
| 代码邻近 | 文件、符号、定义、引用、调用、导入、继承、测试和局部代码上下文的结构候选 | 关系来源、解析器/语言能力、代码版本和仓库边界可核验；不确定关系标记未知 | 同文件、同目录或语义相似不等于调用、依赖或影响 |
| 关系/血缘 | 来源、派生、版本、依赖、影响、关联资产和方向性路径的候选；支持受限遍历 | 关系类型、方向、有效版本、来源和遍历边界可解释；路径上的每个对象仍需独立授权 | 相邻、可达或被某对象派生不等于可发现、可读、可使用或可传播 |

四个通道可以并行产生候选，但结果合并前必须保留通道来源；不要求所有通道都产生结果，也不把某一通道的空结果解释为“没有相关记忆”。

#### 3. 召回前过滤和最终复核

过滤至少覆盖：

```text
授权主体与动作（discover / read / use / audit 等）
Purpose / 当前用途
租户、Team、Project、Agent 和其他 scope
敏感性和字段/内容级使用边界
publication_state、隔离、待审核、撤回和失效状态
记忆/代码/关系的当前有效版本
时间有效性、迟到事件和来源校验状态
```

这些条件应尽可能作为每个通道查询计划的一部分，而不是全库召回后的显示过滤。对无法在候选阶段安全表达的条件，应先构造已授权的窄候选集合，或放弃该通道；不能以高分、低数量或后置裁剪制造“看似安全”的全库查询。

最终复核仍然必要，因为索引可能在查询期间过期、撤回传播可能迟到、权限可能降级，或多个通道可能指向不同版本。最终复核失败时，移除候选、缩小投影或拒绝使用，并记录统一的结果原因；不能泄露候选原本为何被拒绝的敏感细节。

#### 4. 版本、撤回、迟到和失效

每个派生索引、向量表示、代码关系、血缘路径、缓存和融合结果都应能关联其来源版本或重建代次，并支持以下安全语义：

```text
权威版本更新
  → 旧派生结果标记为需复核/不可用或仅限历史用途
撤回或权限降级
  → 阻止新增召回和投影，传播到相关派生结果与缓存
迟到或乱序来源
  → 不以最后到达覆盖当前版本，进入受控重算/待验证路径
失效或过期
  → 查询时过滤，必要时触发受控重建，而不是继续依赖旧候选
索引损坏或重建不完整
  → 仅使用可证明安全的部分，或收窄/拒绝，不恢复为全局召回
```

重建应从受信的权威内容、版本和血缘重新生成，而不是从可能已经污染的索引反向恢复真相。重建、回填和重放也必须执行当前授权和用途检查；不能因为历史上曾可用，就恢复已撤回或已降级的对象。历史 Run Snapshot、Manifest 和审计记录保留当时的决定，不因新索引覆盖。

#### 5. 失败安全、解释与审计

以下失败不得触发无边界 fallback：权限过滤不可用、敏感性判断不确定、索引版本无法确认、撤回状态未知、关系路径不可验证、通道返回结果无法解释、重建状态不一致或最终复核失败。默认行为为：

```text
优先收窄 scope、通道或结果内容
  → 必要时只返回已验证的低风险候选/可展开引用
  → 对安全关键或无法证明授权的场景拒绝使用
  → 记录失败类别、策略版本和安全决定
```

解释和审计至少保留：

- 使用了哪个召回通道，或明确记录通道未使用/失败；
- 使用的召回、过滤、重排、融合和投影策略版本；
- 候选被纳入、排除、降级、失效或拒绝的结果原因；
- 采用的当前权威版本、派生索引代次和最终授权决定；
- 必要的 Trace/Run 关联和审计主体。

解释面向当前有权主体只展示最小必要信息；无权对象不得通过分数、数量、排名、差异、候选总数、错误类型、摘要、关系路径或时延差异推断存在性和内容。审计本身也按权限和敏感性保护，优先记录对象引用、通道、策略版本、决定和原因类别，不默认保存不必要的原文或向量。

本轮不定义统一权重或阈值。排序可以在已授权候选内综合词法、语义、代码结构、关系强度、时效、来源和任务适配性，但具体公式、参数和实验结果必须留待后续评估；分数永远不能替代授权、有效性或安全门禁。

### 阶段 4：专家团挑战

- **产品/UX**：四通道可以提升找到正确记忆的机会，但直接暴露索引、分数和图遍历会增加理解成本。建议对用户展示“为什么相关、来自哪个可授权通道、是否需要展开”，而不是数据库或模型术语；当通道失败时显示有限、可行动的降级状态，不伪造“没有结果”。
- **架构**：最难点是不同索引对召回前过滤、更新和撤回的支持程度不一致。授权/用途边界必须由权威策略层和受控查询编排共同保证；若某索引不能证明安全前置过滤，就只能接收已收窄的候选集合或停用，不能用后置 ACL 作为补救。索引和最终字段 Schema 均留到架构设计阶段。
- **可靠性**：四类派生结构会有不同的新鲜度和重建时机。必须以权威版本、撤回和血缘为准，区分“通道暂不可用”“结果过期”和“确实无命中”；迟到事件、部分重建和缓存旧版本不能扩大传播，失败默认收窄或拒绝。
- **安全/隐私**：向量、代码图、关系边、分数和错误信息本身都可能泄露敏感事实。要求对候选计数、排序差异、通道差异、摘要、路径和审计详情做最小披露；索引不授予 discover/read/use 权限，任何跨空间或派生结果都要重新检查授权、用途和敏感性。
- **数据/质量**：多通道命中不等于多份独立证据，可能只是同一来源的不同派生。合并时要保留来源和血缘，避免重复计数；代码关系和向量表示应可重建、可比较版本并纳入评测，而不是把模型分数当作事实质量。

专家团综合建议：采用“权威状态与授权先行、四通道互补、受限查询编排、最终复核、可重建派生索引”的方向；先验证过滤和生命周期安全，再在真实任务集上选择实现和调参。任何通道的速度或分数优势都不能突破授权和失败安全边界。

## 子议题深化 4：统一检索排序、融合算法和冲突裁决公式

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题承接议题 4 的下一个权威暂缓项：**“统一检索排序、融合算法和冲突裁决公式”**。本轮只确定安全门禁、排序维度、融合所需保真信息、冲突状态和评估边界，不把任何固定公式、权重、阈值、候选数、模型、最终 Schema、SLA 或唯一实现写入产品契约。

成功标准：

1. 明确“授权/用途/敏感性/有效性先过滤，授权候选内再排序”的不可逆顺序；排序不得用于补救越权、状态未知或敏感性未知；
2. 统一排序至少能够分别表达召回相关性、任务适用性、时效、来源权威性、验证状态、风险和冲突，而不是让一个不可解释的总分单独裁决安全或权限；
3. 多通道候选能够去重、保留来源和血缘，并区分“同一来源的多种派生表示”与真正独立的证据；跨通道重复不能伪造证据强度；
4. 融合结果保留来源、owner、scope、版本、适用条件、例外、不确定性和当前状态；互斥事实不能被分数强行压成单一事实；
5. 互斥且未解决的事实能够进入 `dispute`、确认或阻断路径，并根据用途和风险决定是否允许有限投影；
6. 解释、审计、策略版本、离线评测、灰度和回滚各有清晰边界，能够复现一次排序/融合决定而不越权暴露受保护内容；
7. 方案可指导后续架构和实验，但不预先决定某个检索引擎、学习模型、公式、参数或运行目标。

### 阶段 1：头脑风暴

#### 1. 先过安全门，再做质量排序

统一流程应先是门禁，再是排序：

```text
解析请求主体、Harness、Task、Code Context、Purpose
  → 计算授权、用途、租户/空间、敏感性和有效性边界
  → 在每个通道和候选入口过滤
  → 对仍可使用的候选建立证据与特征视图
  → 在授权候选内排序
  → 去重、分簇、融合和冲突分类
  → 再次校验版本、状态和用途
  → 按 Harness 和风险投影或确认/阻断
```

必须区分：

```text
能否发现 / discover
能否读取 / read
能否用于当前用途 / use
是否能查看来源和审计 / audit
```

`discover`、`read` 或 `use` 任一必要条件未满足，都不能靠“相关性高”“来源权威”“其他通道也命中”变成可用候选。授权过滤失败、用途不明、敏感性无法判定、当前版本或撤回状态无法确认时，默认收窄或拒绝，不进入普通排序。

“过滤”不是把结果排到后面，也不是排序后的显示隐藏；分数、名次、数量、冲突数量、通道差异、错误信息和时延都可能泄露受限对象，因此保护边界要尽可能在候选产生前生效。

#### 2. 排序维度不是一个安全总分

在已经通过门禁的候选内，可以建立统一的排序特征视图，但至少保留以下相互可审查的维度：

| 维度 | 要回答的问题 | 边界 |
|---|---|---|
| 召回相关性 | 候选与当前查询、标识符、代码上下文或问题意图有多匹配 | 不等于授权、事实正确或可执行 |
| 任务适用性 | 候选是否适用于当前 Task、文件、服务、环境、Harness 和 Purpose | 适用范围未知时不能当作通用事实 |
| 时效 | 候选在当前时间、版本和事件阶段是否仍有效 | 新不等于正确，旧也不必然无效；需保留时间语义 |
| 来源权威性 | 来源是否为适合该事实的受信主体、系统或决策记录 | 权威性不能扩大 scope，也不能覆盖当前安全规则 |
| 验证状态 | 是否有测试、审批、人工确认、交叉核验或明确的验证记录 | 未验证不是负分后即可正常使用，可能需要标记或阻断 |
| 风险 | 误用、泄露、错误执行或错误承诺的潜在影响 | 风险不得被其他高分抵消；高风险可触发确认/阻断 |
| 冲突 | 是否与已授权候选存在互斥、版本不一致或适用条件冲突 | 冲突不是普通噪声，必须进入融合状态处理 |

这些维度可以用于分层、词典式规则、特征排序、学习排序、分数融合或其他实现；本轮不规定必须压成标量。若实现需要一个内部排序值，也必须保留各维度、门禁决定、证据分组和状态，不能只保存一个无法解释的总分。

建议将安全相关结果拆成至少两类决定：

```text
Eligibility / 可使用资格
  → 是否满足授权、用途、敏感性、有效性和状态门禁

Utility / 候选内优先级
  → 在可使用候选中，哪些更适合当前任务和上下文预算
```

`Eligibility = false` 不能通过 `Utility` 变成可用；`Utility` 较高也不能解除 `dispute`、高风险确认或撤回状态。

#### 3. 统一排序需要接受不同通道的不可比性

关键词、向量、代码邻近和关系/血缘通道的原始分数、排名和覆盖范围不同，不能直接比较其数值大小。统一编排至少应：

- 先保存通道、查询版本、命中依据、候选版本和过滤结果；
- 对通道内结果使用可解释的排名或特征，再做跨通道合并；
- 通过去重和来源分组避免同一记忆的词法命中、向量命中、代码派生和缓存表示被重复计数；
- 对通道缺失、索引过期、解析不确定或过滤能力受限的情况显式标注，不把“没有命中”当作“证明不相关”；
- 允许不同用途、Harness 或风险等级使用不同的排序视图，但共享安全门禁和最小披露边界。

跨通道命中可以提高“被检索到”的信号，也可能只是同一个原始记忆的多个派生结果。只有在来源、产生过程、时间和内容独立性经过证明时，才可把它作为额外证据考虑；默认不把命中通道数直接当作证据数量。

#### 4. 融合不是选择冠军

融合输出应是一个有边界的认知视图，而不是“最高分候选胜出”。可先按规范来源、记忆版本、派生关系和事实主张分组，再对每组决定：

```text
同义/重复
  → 合并表达，但保留全部必要来源和血缘
互补事实
  → 并列组合，并保留各自适用条件
默认规则 + 明确例外
  → 表达规则、例外范围和失效条件
同一事实的不同版本
  → 按当前有效性和验证状态标记版本关系
互斥事实
  → dispute / request-confirmation / block
来源不足或语义不确定
  → 保留不确定性，不生成确定性断言
```

融合至少保留：

- 原始 `memory_id` 或受控来源引用及派生链路；
- owner、tenant/space/scope、允许用途和适用主体；
- 记忆、代码、关系或决策的版本、生效/失效时间；
- 默认规则、例外、条件、前置依赖和回滚条件；
- 验证状态、验证依据、来源权威性和不确定性；
- 冲突对象、冲突类型、裁决状态和下一步动作；
- 当前可使用状态，以及投影时可展示的最小解释。

保留信息不等于全部信息都能展示。面向无权主体的融合、解释和审计必须再次执行最小披露；不能通过只隐藏原文而保留受限来源名称、冲突数量、分数差、路径或摘要来泄露事实。

#### 5. 冲突裁决先分类型，再决定动作

冲突裁决不应只有“保留高分项”和“丢弃低分项”。至少区分：

```text
scope conflict       → 可能是不同主体、环境、Task 或用途下均有效
version conflict     → 需要判断当前版本、回滚版本或历史版本
temporal conflict    → 不同时间窗口的事实，不必然互斥
rule/exception       → 一般规则与有边界例外
verification conflict→ 验证结果或证据状态不一致
semantic conflict    → 对同一对象/属性作出互斥断言
provenance conflict  → 来源或派生链路无法对齐
```

建议的处理顺序是：

1. 重新检查冲突双方的授权、用途、敏感性、版本和时间有效性；
2. 判断冲突是否可由 scope、环境、时间或明确例外解释；
3. 若能解释，融合为“默认规则 + 例外/适用条件”，不把例外升级为全局规则；
4. 若不能解释，保留冲突双方的必要来源和不确定性，标记 `dispute`；
5. 根据当前用途和风险选择有限展示、请求具备权限的主体确认，或阻断依赖该事实的自动执行；
6. 将确认结果写入受控的后续流程，不因一次对话回答自动修改 ACL、来源权威性或全局策略。

可以允许一个低风险、只需展示观点的任务看到“存在两个互斥且尚未确认的结论”，但不能让同一 `dispute` 在高风险变更、凭证处理、合规承诺或不可逆执行中充当确定性前提。冲突详情本身也受授权保护；没有权限的一方只能看到必要的有限状态，不能据此推断另一条受限记忆。

### 阶段 3：综合结论与建议

#### 1. 采用“先资格、后排序、再融合、按风险裁决”的统一边界

建议采用以下逻辑分层：

```text
Authorization / Purpose / Sensitivity / Validity Gate
  → 仅产生允许进入本次用途的候选

Candidate Ranking
  → 在允许候选内，按相关性、适用性、时效、权威性、验证、风险和冲突等维度形成优先级

Evidence-aware Fusion
  → 以来源/版本/派生关系分组，去重、组合、表达例外和保留不确定性

Conflict Decision
  → 无冲突可用；可解释冲突转为条件化结论；互斥冲突进入 dispute、确认或阻断

Projection / Execution Boundary
  → 按 Harness、用途、预算和风险提供最小视图；记忆不能变成工具授权或安全规则
```

该结构允许后续比较多种实现：排名融合、特征重排、规则与模型组合、分层排序或其他方法。无论采用何种实现，必须能够从结果回指门禁决定、各排序维度、证据分组、融合状态和策略版本。

#### 2. 采用多维候选记录，而不是固化单一总分

候选内可维护一个逻辑上的排序资料包：

```text
candidate
├── retrieval_signals
│   ├── channel / query intent / match reasons
│   └── channel-local rank or score
├── applicability
│   ├── task / code / harness / purpose scope
│   └── effective time and version fit
├── provenance
│   ├── source / owner / scope / lineage
│   └── authority and verification state
├── risk_and_conflict
│   ├── risk class / disclosure risk
│   └── conflict groups and unresolved uncertainty
└── policy_context
    ├── eligibility decision
    └── retrieval/ranking/fusion/projection policy versions
```

这里的结构是逻辑信息边界，不是最终字段 Schema。可以用排序列表、特征对象、事件记录或其他载体实现，但不能只保留一个总分而丢失决定依据。对于高风险候选，风险和冲突状态应作为门槛或状态机输入，而不是仅作为可被其他维度抵消的负向特征。

#### 3. 去重和证据计数以来源/血缘为准

去重至少考虑：

- 同一 `memory_id` 的多次命中；
- 同一来源内容的不同切片、摘要、embedding 和代码关联表示；
- 同一事实在不同索引或缓存中的派生结果；
- 同一决策在不同同步通道中的复制；
- 内容近似但 owner、scope、版本或适用条件不同的主张。

前四类通常是同一证据的不同表示，不能按命中次数提高独立证据强度；最后一类不能仅按文本相似去重，必须保留其边界并检查是否构成冲突。融合应能说明“有多少来源/主张”，而不以“命中了多少通道”替代来源独立性判断。

#### 4. 冲突结果的最小状态边界

不固化最终 Schema 的前提下，融合层至少需要表达以下逻辑状态：

```text
usable           → 已通过门禁且无阻断性冲突，可按用途投影
conditional      → 仅在明确 scope、时间、例外或验证条件下使用
dispute          → 互斥主张尚未解决，不能伪造确定结论
needs_confirm    → 需要具备权限的主体或受控流程确认
blocked          → 当前用途/风险不允许使用，或状态无法证明安全
stale/revoked    → 过期、撤回或版本不可用，不得作为当前事实
```

状态不是排名的别名。一个候选可以相关性很高但处于 `blocked`，也可以相关性普通但作为当前 Task 的明确约束处于 `conditional` 或高优先级。状态转换、确认权限、撤回传播和治理留待统一生命周期与权限议题，不在本轮固化具体协议。

#### 5. 解释、审计和策略版本的边界

对有权调用者，解释至少要能回答：

- 候选通过了哪些授权/用途/敏感性/有效性门禁；
- 哪些通道和局部依据找到它；
- 哪些排序维度使其在授权候选内优先；
- 它与哪些候选属于同一来源、派生或冲突组；
- 最终融合为什么是普通可用、条件可用、争议、确认或阻断；
- 使用了哪些权威版本、索引代次和策略版本。

解释不应把内部分数包装成“事实可信度”，也不应暗示分数差异就是权限差异。对无权主体只返回最小必要的拒绝、降级或需确认状态，避免暴露受限内容、来源、候选数、冲突对象和策略细节。

审计应至少关联请求主体、Harness、Task/Purpose、检索计划、候选决定、融合状态、最终投影/阻断、策略版本和必要的运行关联；默认记录引用、状态和原因类别，而不是完整原文。审计留存、脱敏、访问和删除传播属于治理范围；排序本身不能扩大审计可见性。

策略版本必须能区分至少：授权/过滤策略、召回策略、排序策略、融合/冲突策略和投影策略。策略回滚只影响后续决定，不重写已经产生的 Run Snapshot、Manifest、确认记录或审计记录；历史重放应使用当时版本，并明确当前权威状态是否已变化。

#### 6. 离线评测、灰度与回滚只验证质量，不替代治理

离线评测应同时覆盖：

- 无需记忆、应召回、不应召回和关键记忆漏召；
- 多通道重复、同源派生、不同来源独立证据和版本变化；
- 默认规则与明确例外、可解释冲突和真实互斥事实；
- 时效变化、撤回、未知有效性、权限拒绝和敏感性不确定；
- 不同 Harness、Task、Purpose、风险级别和上下文预算；
- 解释可复现、审计完整、策略版本正确和降级/阻断行为。

应分别观察相关性、适用性、新鲜度、来源/验证质量、冲突处理、上下文成本、延迟和安全硬指标，不能用单一平均分掩盖敏感误召回、跨边界泄露或高风险错误。评测集和标注本身也应遵循授权、脱敏和版本管理。

灰度时应先比较离线固定集，再在可控范围观察在线 Trace、纠正、任务结果和安全事件；具体流量、阈值、候选数、延迟目标和 SLA 不在本轮规定。出现安全门禁失效、泄露、撤回内容继续使用或高风险冲突被错误自动裁决，应停止扩大范围并回滚相关策略或关闭通道。回滚不等于删除证据，也不等于恢复已撤回的记忆。

### 阶段 4：专家团挑战

- **产品/UX**：用户希望“最相关的一条答案”，但单一冠军会掩盖例外和争议。建议在低风险场景给出简洁结论，同时让来源、适用范围和不确定性可展开；当需要确认或阻断时说明下一步，而不是展示难以行动的内部分数。
- **架构**：各通道分数不可直接比较，RRF 或学习排序都只能处理授权候选内的优先级。建议保留通道局部信号和来源分组，让排序与融合可以独立替换；不要把索引字段、内部特征或模型输出直接定为外部契约。
- **可靠性**：撤回、权限降级、索引落后和策略回滚可能在一次请求内交错发生。必须在候选生成和最终使用之间重新校验权威状态，并区分“没有命中”“通道失败”“候选被拒绝”和“结果被阻断”；无法证明时收窄或拒绝。
- **安全/隐私**：风险不能只是总分里的负权重，因为高相关、高权威内容仍可能不该被当前用途使用。要求门禁独立于排序，解释和审计按主体最小披露，且冲突双方不能通过差异分数、来源名称或数量被越权推断。
- **数据/质量**：多通道命中很容易被误报为多证据。必须用 owner、来源、派生链、版本和产生时间识别独立性；冲突标注、验证状态和适用范围比更复杂的模型更先需要稳定的数据基础。
- **治理/运营**：在线反馈可以帮助发现排序或融合错误，但不能自动扩大 ACL、公开 scope、恢复撤回内容或改变安全规则。策略必须可版本化、可离线比较、可小流量灰度和可回滚，历史决定不可被新策略改写。

专家团综合建议：采用“独立资格门禁 + 授权候选内多维排序 + 来源/血缘感知融合 + 显式冲突状态 + 风险分层投影”的方向。先建立可解释的候选和冲突评测，再比较排名融合、特征重排或学习方法；不以更高命中率、单一总分或更短延迟交换权限和安全边界。

## 子议题深化 5：不同 Harness 的完整上下文投影模板

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题承接议题 4 的下一个权威暂缓项：**“不同 Harness 的完整上下文投影模板”**。本轮只确认如何根据 Harness 能力、任务/用途、风险和预算生成最小投影，以及各类 Harness 应保留的语义层次、降级路径和授权复核边界；不固化最终 Connector Contract、字段 Schema、模板文案、token 预算、SLA 或具体 Harness API。

成功标准：

1. 投影由“当前 Harness 能力 × Task/Purpose × 风险 × 可用预算”共同决定，而不是把一段完整记忆文本复制给所有 Harness；
2. 开发、运维、研究/分析、PM/规划、人员接手和通用对话可以有不同投影重点，但共享不可删除的来源、scope、版本、适用条件、有效性、不确定性和阻断理由；
3. 投影前确认当前主体是否有权使用候选，投影后再次确认实际即将交付的内容、引用和派生摘要仍符合授权、用途、敏感性和有效性边界；
4. 记忆文本永远只是数据或证据，不能被投影成工具权限、系统指令、审批结果、安全策略或其他控制平面事实；
5. 能力不匹配、预算不足、敏感性未知、内容撤回/过期、版本冲突或授权无法证明时，默认收窄、引用化、请求具备权限的主体确认或阻断；
6. 方案能够指导后续 Connector 和 Harness 适配设计，但不预先决定最终接口、字段、模板措辞、预算数值、SLA 或某个厂商的 API。

### 阶段 1：头脑风暴

#### 1. 投影的输入不是一段 Prompt，而是一组受约束的上下文条件

最小投影应从以下逻辑输入计算：

```text
Request Context
  → User / Agent / Harness / Team / Project / Task / Code Context / Purpose

Harness Capability Profile
  → 能读取什么、能展示什么、能否展开引用、能否请求确认、能否执行工具

Memory Decision View
  → 已授权候选、融合结论、来源/血缘、版本、适用条件、有效性和不确定性

Risk & Budget Context
  → 任务风险、敏感性、错误后果、可用上下文容量、延迟和成本约束

Projection Decision
  → 直接内容 / 结构化约束 / 引用 / 脱敏摘要 / 待确认 / 阻断
```

`Harness Capability Profile` 只描述当前适配器能够安全处理哪些上下文形态，不等于授权。一个 Harness 声称支持工具、结构化输出或长上下文，不代表当前主体可以访问任何工具、字段或 scope；反过来，授权通过也不代表该 Harness 具备安全展示或执行该内容的能力。

#### 2. 最小投影的共同不变量

无论最终面向哪一种 Harness，每个可使用的投影项都必须能够回指：

```text
source / 来源或受控引用
scope / owner、tenant、space 和适用主体边界
version / 记忆、决策、代码或关系的版本
applicability / Task、文件、服务、环境、时间等适用条件
validity / 生效、失效、撤回和当前可使用状态
uncertainty / 未验证、冲突、推断和未知部分
blocking_reason / 未投影、降级、待确认或阻断的原因
```

这些是语义保真要求，不是最终字段 Schema。实现可以将它们放在每项旁边、统一引用目录、审计关联或其他受控载体中，但不能把摘要、重写、embedding、引用或工具返回值变成无来源的确定性事实。若某项的来源、scope、版本、适用条件或有效性无法保留，默认不作普通直接注入；必要时只返回最小的已授权状态或引用化结果。

投影应区分以下层次，而不是将它们混成一段指令：

```text
Safety / hard boundary
  → 当前 Harness 和任务必须遵守的已授权安全约束

Task facts / current state
  → 当前任务所需的、具有明确适用条件的事实

Decisions / exceptions
  → 决策、例外、前置条件、回滚或失效条件

Evidence / citations
  → 来源、证据强度、版本和可展开引用

Uncertainty / blocked state
  → 冲突、未知、撤回、过期、能力不匹配或阻断理由
```

“Safety”在这里仅指已经由受控策略层确定、且当前 Harness 有权接收的约束；记忆中的自然语言不得升级为系统安全规则。任何工具可用性、审批要求、运行环境限制和系统指令都必须来自 Harness/平台控制面，而不是来自投影内容。

#### 3. 能力、用途、风险和预算的最小投影决策

建议按以下顺序计算投影，而不是先生成长文本再截断：

```text
1. 解析当前 Task、Purpose、Harness 和风险等级
2. 发现当前 Harness 能力及其安全限制
3. 在投影前执行主体、scope、用途、敏感性、版本和有效性授权检查
4. 从已通过检查的融合视图中选择任务必需信息
5. 根据能力选择直接内容、结构化信息、引用或待确认状态
6. 根据风险和预算收窄、去重、压缩或转为可展开引用
7. 对即将交付的内容、摘要、引用和派生结果再次执行授权复核
8. 输出投影，或返回最小阻断/降级结果并记录原因
```

预算只决定在已获准内容中如何取舍，不决定“能否访问”。预算不足时，应优先保留安全边界、当前 Task/Code 局部约束和关键事实，再将证据和低优先内容引用化；不能以增加预算绕过敏感性未知、撤回、冲突或授权失败。引用化也不是过滤绕过：引用目标、标题、数量、来源名称和展开权限仍需单独检查。

风险越高，直接注入越少，证据和确认要求越高。低风险的研究讨论可以保留相互矛盾观点及其来源；高风险运维变更、凭证处理、合规承诺或不可逆操作，不能把未经确认的 `dispute`、未知敏感性或过期事实作为执行前提。无法判断风险时按较保守级别处理。

#### 4. 按 Harness 和用途的投影重点

以下是能力和内容重点的逻辑矩阵，不是最终模板、文案或接口契约：

| Harness / 用途 | 可优先投影的内容层 | 应特别保留的边界 | 默认降级方向 |
|---|---|---|---|
| 开发 | 当前文件/符号范围、接口与约束、任务决策、验证方式、禁止动作和必要证据引用 | 代码版本、仓库/Project scope、环境适用条件、命令结果来源；记忆不能授权执行命令或修改文件 | 超预算时保留局部约束和验证引用；关系不确定或版本不明时缩小到已确认文件/符号 |
| 运维 | 当前事件/指标状态、Runbook 适用条件、审批状态、执行前提、回滚条件和证据 | 环境、服务、时间窗口、变更授权、撤回/过期状态和高风险动作边界 | 缺少审批、状态或回滚条件时只提供诊断证据/引用，阻断自动执行 |
| 研究/分析 | 问题范围、来源、证据强度、方法/版本、相互矛盾观点和不确定性 | 事实与推断分离、来源 scope、时间有效性和样本局限；不能把相似度当作结论可信度 | 证据不足或敏感性未知时改为限定性引用、待核验问题或不输出内容 |
| PM/规划 | 目标、已确认决策、适用范围、业务影响、依赖、风险、未决事项和决策来源 | 决策版本、责任边界、时间条件、未决冲突和不可承诺事项；记忆不能形成组织授权 | 冲突或来源不足时并列呈现待决事项，不生成确定承诺或扩大范围 |
| 人员接手 | 当前状态、风险、争议、证据链接、已完成事项、待办和下一步 | 来源可追溯、有效性、责任/权限边界、未验证假设和阻断理由 | 上下文不足时优先输出状态和可核验引用，不填补未知事实 |
| 通用对话 | 与当前问题直接相关的简短结论、必要限定和可展开来源 | 不把简洁变成无来源断言；保留适用条件、不确定性和当前可使用状态 | 无法安全压缩时缩短结论、提供引用或明确说明无法确认 |

同一个事实在不同 Harness 中可以有不同的表达密度和展开方式，但不能因为面向不同受众就改变其授权范围、有效性、版本或冲突状态。表格中的“禁止动作”“执行前提”等是投影应报告的受控事实，不是由记忆文本授予动作能力。

#### 5. 能力不匹配和失败安全

投影器必须识别“有内容但当前 Harness 不能安全处理”和“没有获得授权”这两类不同问题：

```text
能力不支持结构化/引用/脱敏
  → 选择更窄的已支持表示，或阻断

能力可以处理，但当前主体或用途无权
  → 拒绝使用，不以改写、摘要或工具结果绕过

能力和授权均满足，但预算不足
  → 按优先级收窄，次要内容引用化

敏感性未知、撤回/过期或版本无法确认
  → 不作普通直接投影，必要时只保留最小阻断状态

存在未解决冲突
  → 低风险场景可有限呈现争议和来源；高风险场景确认或阻断

投影前后复核不一致
  → 丢弃受影响内容，收窄或阻断，不使用旧投影
```

阻断理由应足以帮助有权调用者采取下一步，但不能暴露无权对象的名称、内容、数量、冲突细节、敏感标签或其他存在性信号。审计可记录受控引用、决定、策略版本和原因类别；面向 Harness 的上下文只携带完成任务所需的最小信息。

### 阶段 2：权威/官方机制调研（访问日期：2026-09-20）

- Model Context Protocol（MCP）官方规范 2025-06-18：<https://modelcontextprotocol.io/specification/2025-06-18>（访问：2026-09-20）。规范将 MCP 定义为连接 LLM 应用与外部数据源和工具的开放协议，并分别规定 Resources、Tools、Roots、Authorization 等协议能力。它可作为“资源/上下文能力”和“工具/控制能力”分开的机制参考，但不规定企业记忆的 ACL、敏感性、投影预算或最终 Harness 模板；因此不能把 MCP 能力声明当作记忆授权。
- OpenAI Responses API 的 MCP/Connectors 官方文档：<https://platform.openai.com/docs/guides/tools-connectors-mcp>（访问：2026-09-20）。文档说明 Responses API 可通过 `mcp` 工具类型连接远程 MCP server，私有/本地服务可通过 Secure MCP Tunnel；文档还说明相关工具调用可以自动允许，也可以要求开发者明确批准。该机制支持将连接能力、授权参数和审批边界分开考虑，但不替本平台决定哪些记忆可投影，也不把记忆文本变成工具授权或系统策略。
- JSON Schema 官方规范总览：<https://json-schema.org/specification>（访问：2026-09-20）。官方文档将规范拆分为 Core 和 Validation，并提供不同词汇、方言和推荐输出结构。它可作为描述和验证结构化投影载体的稳定机制参考，但 JSON Schema 本身不决定主体授权、用途、来源权威性、有效性、撤回传播、token 预算或工具审批；使用 Schema 也不能替代投影前后复核。

共同规律：官方机制能够提供协议能力、工具/资源连接、审批或结构化验证的基础，但不会自动推导当前请求应接收的最小记忆视图。投影模板仍应由本平台的授权、用途、风险、预算、血缘和 Harness 能力边界共同决定；Connector 负责适配，不负责把记忆内容升级为控制平面权限。

### 阶段 3：综合结论与建议

#### 1. 采用“能力配置 + 用途策略 + 风险预算 + 最小投影”的逻辑模板

建议把不同 Harness 的完整投影抽象为四部分，而不是写成一个跨 Harness 的长 Prompt：

```text
Capability Envelope
  → 当前 Harness 能安全接收、展示、展开和请求确认的能力范围

Purpose Projection Policy
  → 当前 Task/Purpose 需要哪些约束、事实、决策、证据和不确定性

Risk/Budget Guard
  → 风险门槛、敏感性处理、已授权内容内的取舍和降级顺序

Evidence-bearing Projection
  → 最小内容 + 来源/scope/版本/适用条件/有效性/不确定性/阻断理由
```

这是逻辑分层，不是最终 Connector Contract 或字段 Schema。它允许不同 Harness 使用不同适配方式，同时保持同一组语义不变量。投影策略可以按用途和风险变化，但不得由普通记忆动态修改 Harness 的系统规则、工具清单、审批政策或访问控制。

#### 2. 采用两次授权复核和一次能力复核

投影边界建议固定为：

```text
Authority Check 1
  → 候选是否允许被当前主体用于当前 Purpose

Capability Check
  → 当前 Harness 是否能安全表示和处理该内容形态

Projection
  → 选择最小直接内容、结构化结果、引用、待确认或阻断

Authority Check 2
  → 实际投影、摘要、引用和派生结果是否仍符合原授权与状态
```

第二次复核不能省略：摘要可能改变语义，引用可能暴露标题或来源，预算压缩可能丢失限定，授权和撤回也可能在两次检查之间变化。任何复核失败都默认收窄或阻断，而不是沿用上一个投影或退化为全库内容。

#### 3. 采用“直接内容、引用化、状态化、阻断”四级输出

在不固化最终模板文案的前提下，可采用以下逻辑级别：

```text
Direct
  → 已授权、适用、有效、低到可接受风险且当前 Harness 能安全处理

Cited
  → 内容不宜直接展开，但可提供已授权的最小引用和受控展开入口

Conditional
  → 需要明确条件、确认、验证或特定环境才能使用

Blocked
  → 授权、敏感性、版本、撤回、冲突、能力或风险门禁不满足
```

四级输出不是新的权限模型，也不是最终状态机。它只是让投影器不必在“全文注入”和“假装不存在”之间二选一。引用本身仍是数据流动，摘要、来源和展开动作都必须继承原对象的授权和敏感性检查。

#### 4. 用保真约束而不是固定字段保护上下文含义

无论采用文本、结构化对象、引用目录还是其他传输形式，投影必须满足：

- 不能省略来源、scope、版本、适用条件、有效性、不确定性和阻断理由所表达的语义；
- 不能把 `constraint`、`fact`、`exception`、`suggestion` 和 `dispute` 混写成无条件命令；
- 不能把历史、推断、建议或用户偏好伪装成当前系统规则；
- 不能把外部工具返回内容、MCP resource 内容或记忆原文视为可信控制指令；
- 不能通过压缩、翻译、摘要、引用、embedding 或跨 Harness 转换绕过原 scope 和撤回；
- 不能让低风险对话投影被复用到高风险执行而跳过用途和授权复核。

#### 5. 后续评估应比较“最小充分”而非“注入最多”

后续评测应按 Harness、Task/Purpose、风险和数据敏感性分桶，至少观察：

- 关键约束和事实的正确保留率，以及无关内容进入率；
- 来源、scope、版本、适用条件和不确定性的保真率；
- 预算内的任务成功率、重复提问率、人工接管率和成本；
- 投影前后授权复核失败、撤回内容继续出现、敏感误披露和跨边界泄露；
- 能力不匹配、冲突、过期、未知敏感性和预算超限时的降级/阻断正确性；
- 从投影和审计记录复现决定的能力，而不泄露无权对象。

不能用更高的任务成功率、更多的直接注入或更短的响应延迟抵消安全硬指标。具体评测集、标注、预算和阈值留待后续评估与治理设计。

### 阶段 4：专家团挑战

- **产品/UX**：不同 Harness 需要不同信息密度，但用户不应被迫理解 Connector、Schema 或内部策略。建议把“为什么看到这条、适用于哪里、能否展开、为什么被收窄/阻断”作为可解释体验；低风险对话可以简洁，高风险执行必须显式显示条件和待确认状态。
- **架构**：能力声明、授权决定和投影格式很容易被错误合并。建议把能力配置视为适配器输入，把授权视为独立门禁，把投影视为可替换的表示层；不要把某个 Harness 的 API 字段反向固化为平台记忆模型或 Connector Contract。
- **可靠性**：投影前后的状态可能不同，尤其是撤回、版本更新、审批变化、缓存旧内容和预算降级同时发生时。必须按一次运行建立可追溯的投影决定，第二次复核失败就收窄或阻断，并区分“能力不支持”“无权使用”“内容过期”和“预算不足”。
- **安全/隐私**：引用、来源标题、阻断理由、冲突数量和结构化字段都可能泄露受限事实。要求最小披露、来源继承授权、未知默认保守；任何 Harness 的工具能力都不能由记忆文本开启，任何 MCP resource 或工具结果也不能自动成为系统指令。
- **研究/数据质量**：摘要越短不一定越安全，可能丢掉例外、有效期和不确定性。应评估压缩后的语义保真和条件保留，区分同一来源的多种投影与独立证据，不把 Harness 间的一致文本当作事实正确的证明。
- **治理/运营**：预算、模板和投影策略会随模型、Harness、成本和风险变化，但历史 Run Snapshot、Manifest 和审计记录不能被新模板重写。建议策略版本化、按用途分桶灰度、异常自动收窄，并把撤回和权限降级传播到直接内容、引用和派生摘要。

专家团综合建议：采用“独立能力描述 + 用途/风险驱动的最小选择 + 两次授权复核 + 带证据保真的多级输出”的方向。先验证不同 Harness 下的语义保真、失败安全和审计可复现，再决定 Connector 适配、结构化载体和用户展示方式；不以统一长 Prompt、单一模板或更多 token 换取表面一致性。

## 子议题深化 6：每层、每类记忆的具体 token/条数预算

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题承接议题 4 的下一个权威暂缓项：**“每层、每类记忆的具体 token/条数预算”**。本轮只确定预算的维度、分配原则、预算核算边界、内容形态区分、超预算的确定性降级、模型/上下文窗口适配和审计要求；不固化任何具体数字、最终算法、字段 Schema、模型、SLA 或永久不变的预算表。

阶段性边界：预算是已获准内容的容量与取舍约束，不是权限、用途授权、敏感性治理或工具授权。固定 Harness 安全规则、当前 Task 与当前代码约束优先于历史经验；预算不足不能绕过授权、扩大 scope、恢复撤回内容或通过压缩敏感内容规避保护。

成功标准：

1. 预算至少能够按 Harness、Task/Purpose、风险、记忆层级、记忆类型和可展开引用共同决定，而不是使用一份对所有请求相同的静态配额；
2. 明确区分直接内容、摘要、引用、元数据和证据的占用与语义职责，压缩不得丢掉来源、适用条件、有效性、例外、冲突和不确定性；
3. 固定安全规则、当前 Task/Code 必要约束和高风险阻断条件不能被历史经验、低优先级记忆或条数上限挤出；
4. 超预算时采用可重复、可解释的合并去重、压缩、引用化、继续检索、请求确认或阻断路径，禁止随机截断；
5. 预算能够适配不同模型、上下文窗口、输入/输出占用、工具定义、成本和延迟约束，但不把任一模型或窗口固化为平台契约；
6. 预算预估、实际 token/条数占用、降级动作、未纳入内容及最终投影均可审计，且审计本身遵守最小披露和权限边界；
7. 方案可指导后续实验和运行时策略，但不预先决定具体数值、最终预算算法、字段 Schema、模型选择或 SLA。

### 阶段 1：头脑风暴

#### 1. 预算先定义“可用容量”，不定义“可访问范围”

预算决策应位于授权之后：

```text
解析 User / Agent / Harness / Team / Project / Task / Code Context / Purpose
  → 执行 discover / read / use、scope、用途、敏感性、版本和有效性检查
  → 仅对当前允许使用的候选估算内容和元数据占用
  → 按 Harness、Task/Purpose、风险、层级、类型和引用能力分配可用容量
  → 形成直接内容、摘要、引用、元数据和证据的投影
  → 进行确定性降级或继续检索
  → 对实际交付内容再次授权复核并记录预估/实际占用
```

“预算不够”只能表示当前投影放不下全部已授权内容，不能表示可以读取更多内容，也不能把被拒绝内容塞进摘要、embedding、引用标题、计数或错误信息中。授权失败、用途不明、敏感性未知、撤回/过期或版本不可确认时，应拒绝、隔离或返回最小阻断状态，而不是提高预算。

固定 Harness 安全规则和当前任务/代码的必要约束属于不可被普通记忆淘汰的安全与任务边界；这不意味着为它们预先写入固定 token 数，而是意味着任何容量不足的策略都必须保留其可执行语义，无法保留时应收窄任务、继续检索、请求确认或阻断。Project、Team、User 和历史经验只能在当前用途、风险和剩余容量允许时参与竞争。

#### 2. 预算应是多维包络，而不是单一总数

逻辑上至少要同时考虑：

```text
Harness capability
  → 能接收文本、结构化内容、引用、展开请求或确认状态到什么程度
Task / Purpose
  → 当前任务需要哪些约束、事实、决策、证据和不确定性
Risk
  → 错误执行、错误承诺、泄露和不可逆影响的后果
Memory layer
  → 原始记录、事实/决策、聚合摘要或其他经治理的层级
Memory type
  → 安全约束、当前 Task/Code、Project/Team/User、经验、证据或敏感事实
Context occupancy
  → 系统/开发者消息、当前输入、工具定义、工具结果、记忆投影和预期输出
Model/runtime
  → 当前模型的上下文上限、tokenizer、可用输出空间、成本和延迟约束
```

预算应区分“本次请求可用的剩余容量”和“某层/某类的局部容量”，同时避免局部配额把必要的安全规则或当前 Task 约束挤出总容量。局部配额既可以作为保护上限，也可以作为在授权候选内的公平性和可解释性约束；本轮不决定其具体数学关系、借用规则或优先级算法。

条数不是 token 的替代物：短条目可能带有大量元数据、来源和证据，长条目也可能在去重后只贡献一项事实。条数上限、单项长度、总 token、引用展开深度和跨 scope 数量应分别核算；一条记忆的多个切片、摘要、embedding 或索引命中不能因重复表示而重复占用或伪造证据强度。

#### 3. 五类内容形态必须分别计量

| 内容形态 | 作用 | 预算与保真边界 |
|---|---|---|
| 直接内容 | 向 Harness 提供当前任务所需的原文或高保真事实 | 只纳入已授权、适用且有效的最小片段；不能因“直接”而丢失限定、例外或冲突状态 |
| 摘要 | 在保留必要语义的前提下降低表达长度 | 摘要必须能回指来源和版本，并保留适用条件、有效期、风险、不确定性与冲突；摘要不改变 ACL，也不能把推断写成事实 |
| 引用 | 以较小投影指向可受控展开的内容或证据 | 引用目标、标题、计数、来源名称、展开动作和展开权限均需独立授权；引用不是绕过过滤的隐形通道 |
| 元数据 | 表达 scope、版本、状态、适用范围、策略和降级原因 | 元数据不是“免费空间”，其暴露也可能泄露存在性或敏感事实；应按用途最小披露并计入实际占用 |
| 证据 | 支撑结论的来源、验证、时间、血缘、命令/工具结果或争议材料 | 证据应与直接结论分开计量和展示；高风险任务不能只保留结论而丢掉必要证据或阻断条件 |

压缩只允许改变表示密度，不允许删除使结论成立所必需的来源、scope、版本、时间、例外、冲突、验证状态和敏感性边界。对无法安全摘要的敏感或高风险内容，预算不足时应引用化、请求有权主体确认或阻断，不得通过更短文本掩盖其性质。

#### 4. 分层、分类和可展开引用的分配原则

预算分配可以遵循以下不可逆优先顺序：

```text
Harness 安全规则与当前系统边界
  → 当前 Task / Code 的必要约束和明确决策
  → 当前 Project 的必要事实与适用例外
  → Task/Purpose 直接需要的 Team / User 内容
  → 经过验证且与当前任务相关的历史经验
  → 可延迟展开的背景、冗余证据和低优先级内容
```

这不是权限优先级，也不是让高层级记忆自动覆盖低层级记忆；每一项仍须先通过授权、用途、敏感性、有效性和冲突检查。层级和类型预算应能够表达：

- 哪些内容必须直接可见，哪些内容可安全摘要，哪些内容只能作为引用；
- 哪些类型需要保留证据或确认，哪些类型可在低风险用途下延后展开；
- 同一记忆面向不同 Harness、Task/Purpose 或风险时为何获得不同投影；
- 跨 scope 内容是否需要更窄的上限、强制引用化或直接阻断；
- 当前可用容量不足时，是继续检索更适合的短证据，还是结束为待确认/阻断。

可展开引用必须是受控的、按对象和用途重新授权的后续动作，而不是把全文放入隐藏字段或让 Harness 自行扩大检索。若引用的展开结果仍超预算，应继续使用同一确定性降级规则，不能随机选择展开内容。

#### 5. 超预算的确定性处理

推荐的逻辑流程是：

```text
1. 计算当前模型/运行时的可用容量，扣除已占用上下文和必要输出空间
2. 过滤无权、过期、撤回、敏感性未知和状态不明的候选
3. 规范化并合并同源重复，保留来源/血缘和必要证据
4. 固定 Harness 安全规则与当前 Task/Code 必要约束
5. 保留高风险所需的条件、证据、确认和阻断信息
6. 对已授权的次要直接内容做保真摘要或改为受控引用
7. 仍不足时继续检索更适配的内容，或返回上下文不足/待确认/阻断
8. 记录每个纳入、合并、降级、引用化、未纳入和阻断决定
```

合并去重、摘要、引用化和继续检索的顺序可以由后续实验调整，但每次运行必须使用确定性、可解释且可复现的策略版本；禁止按字节位置、到达顺序、随机数或未记录的模型自由截断。若强制保留项本身无法安全容纳，应停止依赖该记忆的自动执行，而不是删掉安全条件、当前代码约束或风险警告。

预算超限不应把“结果很长”当作唯一错误：需要区分已有授权内容过多、必要证据缺失、当前模型无法承载、引用不能安全展开、检索没有找到更小的充分证据以及安全门禁阻断。不同原因的后续动作可以不同，但都不能退化为无边界召回或静默丢弃。

- Anthropic 官方 Token counting 文档：<https://platform.claude.com/docs/en/build-with-claude/token-counting>（访问：2026-09-20）。文档说明可在发送前计算消息 token，用于管理速率、成本、模型路由和目标长度；它可支撑预估层，但实际投影仍需记录运行时占用和授权决定。
- Anthropic 官方 Compaction 文档：<https://platform.claude.com/docs/en/build-with-claude/compaction>（访问：2026-09-20）。文档将 server-side context compaction 用于接近上下文窗口上限的长对话管理；这可作为“保留必要状态、生成受控压缩表示并继续运行”的机制参考，但平台仍需自行验证来源、例外、敏感性和撤回传播是否保真。
- Google Gemini API 官方“Understand and count tokens”文档：<https://ai.google.dev/gemini-api/docs/tokens>（访问：2026-09-20）。文档提供 Gemini API 的 token 理解与计数说明，可作为按模型/请求进行预估和实测的参考；它不规定企业记忆的分层预算、授权和超限动作。
- Google Gemini API 官方 Context caching 文档：<https://ai.google.dev/gemini-api/docs/caching>（访问：2026-09-20）。文档说明上下文缓存及缓存命中使用量的机制，可用于研究重复上下文的成本和容量影响；缓存不是权限系统，也不是把敏感内容压缩后绕过授权的方式，具体计费和运行行为仍需以实际模型与 API 文档为准。

共同规律：官方机制都表明 token 消耗取决于请求的完整表示、工具/多模态输入、模型和运行时；预估与响应 usage/运行记录应区分。压缩、缓存或重新计数只能帮助管理容量、成本和长上下文，不能替代授权、敏感性治理、来源保真、冲突处理和撤回传播。官方文档没有为本平台的 Harness、Task/Purpose、风险、记忆层级/类型提供一套可直接移植的固定 token/条数预算，因此本轮不编造具体数字。

### 阶段 3：综合结论与建议

#### 1. 采用“授权候选内的多维预算包络”

建议把预算抽象成运行时的逻辑包络：

```text
Eligibility Gate
  → 只有当前主体、Purpose、scope、敏感性和状态均允许的候选进入预算

Capacity Envelope
  → 当前模型/上下文窗口中扣除系统、任务、代码、工具和输出所需空间后的可用容量

Allocation View
  → Harness × Task/Purpose × Risk × Memory Layer × Memory Type × Expandability

Representation Choice
  → Direct / Summary / Citation / Metadata / Evidence

Deterministic Degradation
  → 去重合并 → 保真摘要 → 引用化 → 继续检索 → 确认或阻断

Audit View
  → 预估、实际、策略版本、纳入/排除/降级原因和最终投影
```

该包络不是单一总预算的替代字段，也不是最终 Schema。它的价值是让每次投影能够解释“容量受什么影响、为什么某类内容采用这种表示、为什么另一类内容被延后或阻断”，并允许后续按真实 Trace 比较不同策略。

#### 2. 预算分配的保护层与可变层

逻辑上可把内容分为两类：

- **保护层**：Harness 安全规则、当前 Task/Code 必要约束、当前执行必须知道的条件、风险警告、确认/阻断状态和使结论成立的最小来源。它们不能被低优先级内容挤出，也不能被摘要压成失去控制含义的文本。
- **可变层**：Project/Team/User 的相关事实、历史经验、补充背景、非关键证据和可展开内容。它们可根据 Task/Purpose、风险、Harness、层级/类型、相关性和剩余容量在直接内容、摘要或引用之间变化。

“保护层”是上下文完整性要求，不是授予这些内容越权的权限；其中任何一项仍须有当前有效授权。对敏感内容，保护层/可变层分类也不能替代字段或内容级治理；预算不足时只能收窄、脱敏（若另有授权规则）、引用、确认或阻断。

#### 3. 预估与实际占用必须可审计

预算核算至少应区分：

```text
estimated input tokens
  → 发送前按当前模型、tokenizer、表示形式和候选投影预估
reserved capacity
  → 为系统规则、Task/Code、工具定义、输出和运行时变化保留的空间
actual input tokens
  → 请求实际序列化后由运行时/API 报告或可验证计算的占用
memory direct/summary/citation/metadata/evidence usage
  → 记忆各内容形态实际贡献的占用
actual output/tool usage
  → 输出、工具定义和工具结果对窗口、成本和延迟的实际影响
degradation trace
  → 合并、摘要、引用化、继续检索、未纳入、确认或阻断的原因
```

估算必须带模型/表示/策略版本和时间语义；实际值优先于估算用于事后分析。若 tokenizer、模型、工具定义或上下文封装改变，不能直接比较未经归一化的数字。审计可记录 token/条数区间、计量来源、决策和引用，但不应为了计量保存不必要的原文、敏感字段或无权对象信息。

#### 4. 不同模型、上下文窗口、成本和延迟的适配

运行时应从当前模型和 Harness 能力读取可用上下文边界，并把输入、输出、工具/多模态内容、系统约束和记忆投影一起纳入容量判断。可以为同一 Harness/Task/Purpose 生成不同的预算视图：

- 上下文较窄时优先保留保护层、最小事实和可展开引用，必要时分步继续检索；
- 上下文较宽时也不自动注入更多历史或敏感内容，仍按用途、风险和最小充分原则取舍；
- 成本或延迟受限时优先去重、选择更适配的证据表示或分阶段检索，不能删除授权、来源和阻断条件；
- 模型切换时重新估算和记录，不能把一个模型的 token 计量、窗口上限或压缩行为当成另一个模型的事实；
- 预算策略更新时保留历史策略版本和 Run Snapshot，不用新预算重写过去已经作出的投影决定。

本轮只确认适配方向，不规定路由算法、压缩模型、模型清单、具体窗口、成本函数、延迟目标或服务级别。

#### 5. 后续评估边界

后续实验应按 Harness、Task/Purpose、风险、记忆层级/类型、模型和上下文窗口分桶，至少评估：

- 保护层内容的保留率、语义保真和当前任务约束漏失率；
- 直接内容、摘要、引用、元数据和证据各自的 token/条数占用及有效任务贡献；
- 去重、摘要、引用化、继续检索、确认和阻断的确定性与可复现性；
- 预估与实际 token、条数、成本、延迟和上下文超限的偏差；
- 不同模型/窗口下的任务成功率、重复提问率、人工接管率和引用展开率；
- 敏感误披露、跨边界泄露、撤回内容继续出现、授权失败绕过和高风险错误；
- 从 Trace、Manifest 和审计记录重现预算决定的能力。

质量、成本或延迟改善不能抵消安全硬指标。评测中若出现预算降级删除安全规则、当前代码约束、必要证据或阻断条件，应停止扩大策略，而不是简单增大预算。

### 阶段 4：专家团挑战

- **产品/UX**：用户通常只看到“回答不完整”，看不到预算层级。建议以“已提供的最小充分内容、可展开引用、需要确认或无法安全提供”解释降级，不展示复杂配额和内部 token 细节；预算不足不能伪装成“没有这条记忆”。
- **架构**：上下文窗口、工具定义、输出空间和记忆投影共同占用容量，单独给记忆设总数会产生错误安全感。建议预算包络与模型/Connector 能力解耦，保留逻辑内容类别和计量来源，不把某个 provider 的 usage 字段直接变成平台 Schema。
- **可靠性**：真实 token 化、工具结果膨胀、模型切换、重试和压缩可能使发送前估算失准。建议预估采用保守边界，发送后记录实际 usage；不一致时采用确定性收窄、继续检索或阻断，不能随机截断或沿用过期投影。
- **安全/隐私**：摘要、引用、元数据、条数、失败原因和缓存命中本身可能泄露受限信息。要求预算运算只在授权候选内进行，敏感内容不因变短而降低保护，审计和错误面向不同主体最小披露。
- **数据/质量**：按条数计量会奖励碎片化，按 token 计量会忽视证据和条件丢失。建议同时评估语义保真、来源/血缘保留、独立证据与同源派生，不能只用 token 节省率衡量压缩质量。
- **治理/运营**：预算策略会随模型、成本和任务变化，但权限、撤回和合规边界不能随预算变化。建议策略版本化、按风险分桶灰度，并把预算决定和实际消耗纳入可追溯 Run Snapshot；预算不足时宁可阻断高风险执行，也不能扩大授权。

专家团综合建议：采用“先授权、后计量；保护安全与当前任务；按 Harness/Task/Purpose/风险/层级/类型/引用能力分配；区分直接内容、摘要、引用、元数据和证据；确定性降级并审计预估与实际”的方向。先用真实 Trace 校准相对分配和降级效果，再决定具体数值与实现；不以固定配额、更多 token 或更激进压缩替代权限和安全治理。

### 自动审核与推进

## 子议题深化 7：ACL、用途授权、敏感字段和跨空间派生的完整策略

**状态：第 1 轮（自动执行中）**

### 主题与成功标准

本主题承接议题 4 的下一个权威暂缓项：**“ACL、用途授权、敏感字段和跨空间派生的完整策略”**。本轮把记忆发现、读取、使用、审计及其派生传播的治理不变量明确到可以约束后续架构和实验；不把任何具体 RBAC/ABAC 矩阵、策略语言、字段 Schema、脱敏算法、PDP/PEP API、审批角色、SLA 或固定实现写入产品契约。

本轮的核心边界是：**授权先于检索、融合和投影；相关性与预算只能在已授权候选内工作；派生表示不改变原始治理边界。**

成功标准：

1. 将 `discover`、`read`、`use`、`audit` 等动作分离，明确“可知道存在”“可读取内容”“可用于当前目的”“可查看审计证据”不是同一权限；
2. 将主体（principal）、scope、purpose、敏感性、来源权限、owner、related 和 derived 分开建模和判断，禁止用其中一个维度替代其他维度；
3. 在召回候选、读取原文、排序/融合、摘要/引用/embedding/Manifest 生成和最终 Harness 投影前执行与当前动作相匹配的授权检查；
4. 实行字段级最小披露：字段、片段、元数据、引用标题/计数、摘要、embedding 和审计信息都可能受保护，不能因换一种表示就自动降低治理要求；
5. 跨空间引用、复制、摘要、融合、embedding、缓存、提升或其他派生不继承来源权限，必须重新检查主体、目标 scope、目的、敏感性、来源权限、用途限制、血缘和撤回状态，并在需要时先完成受控脱敏或确认；
6. 索引、缓存、摘要、embedding、Manifest、排序分数、错误和拒绝结果不能扩大权限，也不能让无权主体推断受限对象的存在性、数量、关系、来源或敏感字段；
7. 撤回、降权、用途撤销、敏感性升级、owner 变更或策略更新能够传播到已生成的投影、缓存和派生链，并阻止后续使用；历史审计要保留当时决定，但不能成为继续使用的授权凭证；
8. 预算、相关性、来源权威性、跨通道重复命中或任务成功率都不能覆盖治理门禁；无法证明授权、用途、敏感性或撤回状态时，默认收窄、隔离、请求有权确认或阻断；
9. 方案可以指导后续策略评估和实现拆分，但不固化最终权限矩阵、策略语法、字段模型、脱敏算法、服务接口、审批角色或服务目标。

### 头脑风暴

#### 1. 先区分动作，再谈“有权限”

“这个主体能不能访问记忆”过于粗糙。至少应把一次请求拆成多个可独立拒绝、独立审计的动作：

```text
请求主体 / Harness / Task / Code Context / Purpose
  → discover：是否可以在当前 scope 和目的下知道某类对象或候选是否存在
  → read：是否可以读取目标对象或字段的内容
  → use：是否可以把已读内容用于当前目的、融合、决策、工具调用或输出
  → derive：是否可以生成指定目标 scope、目的和表示的派生物
  → project：是否可以向指定 Harness/受众投影指定字段或表示
  → audit：是否可以查看与本次请求或对象有关的审计信息
```

这里的 `derive` 和 `project` 不是把 `read` 的结果自动带出去的后处理；它们是对新动作、新受众、新表示和可能新 scope 的单独判断。`audit` 也不能因为“只是元数据”而默认公开：审计记录可能包含对象名称、来源、主体、拒绝原因、字段类别、时间差异和关系信息。

动作之间至少有以下不可逆约束：

- `discover = false` 时，不返回对象是否存在、候选数量、排名、分数差、错误差异、关系路径或“无权”所对应的可识别细节；
- `discover = true` 不推出 `read = true`；可以只返回统一的“可发现但需授权读取”状态，或只返回可公开的最小状态；
- `read = true` 不推出 `use = true`；读取用于审计、人工核验或某个目的，不等于可用于当前回答、训练、自动执行、跨空间复制或工具调用；
- `use = true` 不推出 `derive/project = true`；向另一个主体、scope、Harness 或用途传播必须重新判断；
- 对象可用于业务动作不推出其完整审计可见性，`audit` 需要按审计主体、目的和敏感性另行授权。

拒绝路径也必须动作隔离：一个动作被拒绝时，不应用另一动作的成功、相关性分数或历史授权来补偿。策略引擎或执行器可以内部保留更详细的拒绝原因，但面向当前主体的结果只能披露其获得授权的最小信息。

#### 2. 授权输入是多维上下文，不是单一 ACL 列表

一次判断至少需要同时考虑以下维度：

| 维度 | 判断对象 | 必须避免的替代关系 |
|---|---|---|
| 主体（principal） | 人、Agent、Harness、服务身份、代表谁执行及其会话/认证上下文 | Agent 身份不自动等于其背后用户或 owner 的全部权限；服务身份也不自动拥有调用者权限 |
| scope | tenant、space、Team、Project、仓库、环境、会话和目标空间的边界 | 同一组织、同一用户或可见关系不自动意味着跨空间可用 |
| purpose | 当前问答、检索、代码修改、诊断、审计、导出、训练、自动执行等用途及必要约束 | “已授权读取”不等于所有用途均可用；目的不明或目的漂移时应收窄或阻断 |
| 敏感性 | 对象、字段、片段、关系、推断风险和组合后的敏感程度 | 字段短、已摘要、已 embedding 或只剩计数不等于不敏感 |
| 来源权限 | 来源系统/空间对该对象和动作授予的当前权限、限制、有效期和撤回状态 | 本平台的内部关系、缓存命中或历史授权不能替代来源权限 |
| owner | 对内容、空间或治理责任负有控制/授权责任的主体或组织 | owner 不是每一次访问的自动批准者，也不等于内容中的相关人 |
| related | 与对象、项目、主体、代码或事件有关联的主体/空间/关系 | 相关不等于授权，不应通过关系边推断可读或可用 |
| derived | 由一个或多个来源生成的摘要、引用、embedding、融合视图、缓存、Manifest 或结论 | 派生物不是新的无主数据；其权限、用途、血缘和撤回应回到来源并重新判断 |

这些维度可以由 ACL、属性策略、关系授权、来源系统决定或组合提供，但本轮只规定逻辑职责，不规定最终模型。即使未来采用关系型授权，purpose、敏感性、来源限制和撤回传播仍不能被隐藏在一个“有关系即可”的判断里。

#### 3. 治理门禁必须早于召回、融合和投影

建议把任何记忆使用流程约束为：

```text
解析主体、调用方、代表主体、Harness、Task、Purpose、源 scope、目标 scope
  → 确认来源权限、owner/related/derived 关系、敏感性与当前版本/撤回状态
  → 针对 discover/read/use/derive/project/audit 分别作出最小授权决定
  → 仅在 discover 允许的边界内生成候选；仅在 read 允许的字段/片段内读取
  → 仅在 use 允许的当前目的内检索、排序、融合和工具使用
  → 目标 scope 或表示变化时重新执行 derive/project 授权和敏感性检查
  → 生成最小字段投影，并在交付前复核当前状态、撤回和策略版本
  → 记录不越权的决定摘要、血缘、策略版本和传播结果
```

不能先对全库做向量/关键词召回再隐藏无权结果；不能先读取原文再决定当前 purpose 是否允许；不能先让模型摘要再对摘要做 ACL；不能先写入公共缓存或 Manifest 再补做授权。对于无法在底层检索入口表达完整治理条件的索引，应先得到已授权的窄候选，或停用该入口，而不是用后置显示过滤补救存在性泄露。

融合也属于 `use`，不是纯算法动作。来自多个空间的候选即使都可读取，也只有在当前 purpose、目标 scope、字段敏感性、来源限制和独立血缘均允许时，才能放进同一融合视图。最终投影不是授权的最后一次“格式化”，而是一个可能缩小字段范围、改变受众和产生新派生物的治理动作。

#### 4. 字段级最小披露与组合风险

对象级允许不能替代字段级判断。一个记忆可读，不代表其所有字段、嵌套片段、关系、时间、来源名称、owner、访问状态和审计属性都可用于当前目的。逻辑上至少应逐层判断：

```text
对象是否可 discover
  → 哪些字段/片段可 read
  → 哪些字段/片段可用于当前 purpose
  → 是否需要遮蔽、泛化、引用化、确认或阻断
  → 哪些字段可以投影给当前 Harness/受众
  → 派生表示是否仍可由字段组合推断受限事实
```

最小披露不能只理解为“删除明显秘密字段”。以下内容也可能构成敏感披露：

- 字段是否存在、字段缺失原因、对象数量、命中次数、排序分数和候选差异；
- owner、related 空间、来源系统、版本、创建/更新时间、撤回状态和关系路径；
- 摘要中的唯一细节、引用标题、路径、错误类别、统计值、低基数计数和时间模式；
- embedding、索引词、缓存键、Manifest、Trace 关联、模型输入输出或多个低敏字段的组合推断；
- 把不同来源的局部事实融合后形成的更高敏感性结论，即使每个单字段单独都可见。

脱敏、泛化、摘要或引用化只能在策略明确允许并且能保留必要用途语义时使用；表示变短不代表权限放宽。无法证明某种处理阻断重识别、推断或用途漂移时，应减少字段、只返回状态、请求有权主体确认或阻断。具体脱敏算法、敏感分类表、字段 Schema 和阈值留待后续治理设计。

#### 5. owner、related、derived 和来源权限必须分开追踪

跨空间的授权判断至少要回答四个不同问题：

```text
谁负责/控制该来源或空间？                         → owner
谁与该内容或关系有关？                             → related
该表示由哪些来源、活动和版本生成？                 → derived / lineage
来源系统当前允许谁以什么 purpose 做什么动作？        → source permission
```

例如，某 Agent 可能是一个 Project 的成员（scope 关系），某用户可能是记忆内容中的相关人（related），某服务可能负责生成 embedding（derived activity），但这三者都不自动推出该服务可读取原文、该用户可将内容用于训练或该 Agent 可把结果写入另一个空间。来源权限必须作为输入而不是由平台关系猜测；owner 责任也不意味着 owner 以外的所有使用都可转授。

对任何派生物应保留可验证的来源与活动链路：来源对象、来源版本、参与的目的、目标 scope、产生主体/服务、表示类型、授权决定、敏感性判断、投影字段和撤回依赖。这里是逻辑要求，不是最终字段 Schema。血缘用于重新做治理判断和传播撤回，不是把所有来源内容自动暴露给查看派生物的人。

#### 6. 跨空间引用、融合和派生一律重新授权

“跨空间”不仅是把原文复制到另一个 tenant。以下动作都应视为新的传播或派生边界：引用链接、标题/计数、摘要、融合结论、embedding、索引条目、缓存、Manifest、评估样本、工具结果、导出、训练材料和任何提升可见范围的关系。

统一安全规则：

```text
source scope + source purpose + source permission
  → 不能直接继承为 target scope + target purpose + target permission

跨空间动作
  → 识别新主体/受众、目标 scope、目标 purpose、表示和敏感性
  → 重新授权 discover/read/use/derive/project/audit
  → 检查来源限制、owner/related/derived 血缘、当前版本和撤回
  → 仅生成字段级最小披露；必要时先执行已批准的脱敏或确认
  → 写入受控派生物，并把撤回/降权依赖传播到所有后续表示
```

引用是最容易被误当作“没有复制内容”的例外：引用目标、标题、路径、来源名称、存在性、展开动作及其展开结果均可能泄露信息，每一步都要按当前主体和 purpose 判断。融合结论也不因“模型新生成”而脱离来源限制；如果无法给当前目标主体提供来源允许的最小结论，就不能用模型推理替代授权。

禁止的默认规则包括：同一 user/Agent 可跨所有 Project 复用；同一 tenant 内可自由横向传播；owner 相关人可自动读取；读权限自动转成导出或训练权限；embedding/摘要/缓存可公开；一次审批永久覆盖未来 purpose；来自更高信任空间的记忆自动提升到低信任空间。是否存在例外只能由后续明确策略和有权流程决定，本轮不把例外固化为矩阵。

#### 7. 撤回、降权和策略变化要沿派生图传播

治理状态变化不是只删除原文：

```text
来源撤回 / 权限降级 / purpose 撤销 / 敏感性升级 / owner 变化 / 策略更新
  → 标记依赖该来源的索引、缓存、摘要、embedding、Manifest、融合视图和投影
  → 阻止新增 discover/read/use/derive/project
  → 重新评估可否保留、重算、脱敏、隔离或删除派生物
  → 传播到尚未消费的队列、工具结果和下游空间
  → 对已交付历史结果保留受控审计，并按后续治理规则处理其继续使用
```

派生链不完整、传播延迟未知、版本无法确认或策略判断失败时，不能把旧缓存当作安全结果；默认隔离、失效、收窄或阻断。重建必须从当前受信来源、当前授权、当前 purpose 和当前敏感性重新生成，不能从旧 embedding、摘要或 Manifest 反向恢复权限。历史 Run Snapshot 和审计记录用于说明当时发生了什么，不自动授予现在的使用权，也不应因新策略回写而伪造历史决定。

#### 8. 拒绝、错误和无权结果必须防止存在性泄露

对无 `discover` 权限的对象，查询结果应与“没有匹配”在对该主体可观察的维度上保持等价或足够不可区分。需要控制的观察面包括：

- 是否返回对象、计数、分页总数、命中通道、排序名次、相似度和候选总量；
- 错误码、错误文本、字段缺失、路径、来源名称、owner/related 名称和版本时间；
- 缓存命中/未命中、索引延迟、重试次数、过滤耗时、摘要长度和模型输出差异；
- “无权”“已撤回”“存在但不可读”“未找到”之间的区分是否会暴露受限事实。

有权审计主体可能需要更详细的内部原因，但这不改变面向普通调用者的最小披露。对 `read` 被拒绝而 `discover` 允许的情形，也只能返回必要的通用状态或受控引用，不能通过“请申请访问对象 X”把对象名称和敏感性暴露给无权主体。失败安全优先于友好的诊断信息。

### 权威/官方机制调研（访问日期：2026-09-20）

- **NIST SP 800-162，Guide to Attribute Based Access Control (ABAC) Definition and Considerations**：<https://csrc.nist.gov/pubs/sp/800/162/upd2/final>（访问：2026-09-20）。该指南把 ABAC 的核心放在主体、对象、操作和环境属性及策略评估上，可支撑本轮将主体、scope、purpose、敏感性、时间和环境作为独立输入；它不是本平台的最终 ABAC 矩阵、属性命名、策略语言或 PDP/PEP API，也不自动解决派生权限和存在性泄露。
- **NIST SP 800-53 Rev. 5，AC-6 Least Privilege 等控制族**：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问：2026-09-20）。官方控制目录可作为最小权限、特权操作限制、职责分离和审计边界的治理参考；它不直接规定记忆的字段 Schema、跨空间传播协议、具体审批角色或 SLA。
- **OAuth 2.0 Authorization Framework（RFC 6749）**：<https://www.rfc-editor.org/rfc/rfc6749>（访问：2026-09-20）。RFC 6749 定义了受限访问令牌、resource owner、client、authorization server 和 protected resource 等协议角色，说明令牌/授权是面向受保护资源的受限委托机制；它不等于本平台的对象级/字段级 ACL，不规定 purpose 限制、敏感字段治理或跨空间派生权限。scope 等协议概念不能直接当作本平台完整策略矩阵。
- **OAuth 2.0 Token Exchange（RFC 8693）**：<https://www.rfc-editor.org/rfc/rfc8693>（访问：2026-09-20）。RFC 8693 定义 token exchange、subject token、actor token 和受众/范围等协议语义，可参考服务代表调用者、受众变化和受限委托的显式表达；它不意味着新 token 自动继承原 token 的全部权限，也不替代对新 purpose、目标 scope、字段敏感性、来源限制和撤回的重新判断。
- **OpenFGA 官方 Concepts / Authorization Model 文档**：<https://openfga.dev/docs/concepts>（访问：2026-09-20）。OpenFGA 以用户、对象、关系和关系推导表达细粒度授权关系，可作为 owner、related、viewer 等关系授权的机制参考；关系存在不自动等于 discover/read/use/derive/project/audit 全部允许，且 purpose、敏感性、来源权限、派生血缘和撤回传播仍需由整体治理流程补足。本文不选定 OpenFGA 或其 DSL/API。
- **Open Policy Agent 官方文档**：<https://www.openpolicyagent.org/docs>（访问：2026-09-20）。OPA 将策略决策从执行代码中分离，并支持以输入数据评估策略，可作为把资格判断、用途判断和投影门禁与检索/执行器解耦的机制参考；OPA 本身不提供组织事实、来源权限、敏感分类、血缘传播、字段脱敏或审计留存，因此不应把 OPA 直接当成本平台完整治理方案或固定 PDP/PEP 接口。
- **NIST SP 800-57 Part 1 Rev. 5，Recommendation for Key Management**：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问：2026-09-20）。该指南涉及密钥生命周期、保护和撤销等密码治理背景；它可提醒实现不能仅依赖加密来解决授权和撤回，但不规定记忆的 ACL、用途策略、字段脱敏或派生传播协议。

共同规律和谨慎结论：NIST ABAC 强调以多类属性进行策略判断，OAuth 强调受限委托与受保护资源，OpenFGA 强调关系授权，OPA 强调策略决策与执行解耦。这些官方机制可以提供稳定的概念边界，但没有任何一个单独定义本平台所需的动作分离、字段级最小披露、跨空间派生重授权、撤回传播和存在性防护。因此本轮只吸收机制语义，不宣称存在可直接移植的最终方案。

### 综合结论与建议

#### 1. 采用“动作分离 + 多维资格门禁 + 最小投影”的治理骨架

建议将授权和记忆融合的逻辑边界固定为：

```text
Request Context
  → principal / represented principal / Harness / Task / Purpose
  → source scope / target scope / owner / related / derived lineage
  → sensitivity / source permission / validity / revocation state

Action-specific Authorization
  → discover
  → read (object/field/fragment)
  → use (purpose-bound retrieval/fusion/tool/output)
  → derive / project (new representation, audience or scope)
  → audit (audit subject and purpose)

Authorized Candidate Boundary
  → only now retrieve, rank, fuse, summarize, cite, cache or embed

Field-minimal Projection
  → permitted fields/representation for this Harness and audience

Fresh Recheck and Propagation
  → current policy/version/revocation/lineage check
  → record decision without expanding visibility
```

该骨架允许后续替换 ACL、ABAC、关系授权或组合策略实现，但不允许把动作合并成一个笼统的 `access=true`。`use` 是当前目的绑定的治理决定，`derive/project` 是新的传播边界，`audit` 是不同受众和不同敏感性下的独立可见性。

#### 2. 采用“资格与效用完全分离”

资格门禁至少独立判断：

```text
Eligibility
  = action + principal + source/target scope + purpose
  + sensitivity + source permission + validity/revocation
  + owner/related/derived lineage constraints

Utility
  = relevance + task fit + freshness + evidence quality + budget
```

只有 `Eligibility` 通过的候选才可以进入相关性排序、上下文预算、融合或模型选择。相关性高、来源权威、跨通道多次命中、成本更低或任务收益更大，均不能把资格失败变成资格通过；预算也只能在授权候选内做删减和表示选择。

#### 3. 采用“原始来源约束 + 派生物重授权”的传播规则

对直接内容和每类派生表示，都建议保存可回指的逻辑治理信息：来源和版本、派生活动/主体、源/目标 scope、目的、表示类型、敏感性判断、字段范围、权限决定、策略版本和撤回依赖。它们是重做判断和传播状态的依据，不是要求每次向用户展示的字段。

任何跨空间或受众变化都触发重新授权：

```text
source authorization
  ≠ target authorization
  ≠ derived authorization
  ≠ projection authorization
```

即便新表示不可逆、只含摘要、只含 embedding 或只含 Manifest，也不应自动获得更宽权限。若不能证明目标 purpose 和字段披露安全，派生动作必须缩小范围、先脱敏/确认或阻断。

#### 4. 采用“字段级最小披露 + 组合风险复核”

投影策略应先确定当前 Harness 和受众真正需要的字段/语义单元，再决定直接内容、摘要、引用、状态或阻断。引用目标、标题、计数、元数据、来源名称、向量和错误都纳入同一治理边界；字段允许性不能只按原始对象静态继承，而要考虑组合后是否形成更敏感的推断。

本轮确认以下原则但不固化实现：

- 默认不给全对象，只给当前 purpose 所需的最小字段/片段；
- 不能安全保留语义或阻断推断的内容，不用摘要/压缩伪装为低风险；
- 受限字段不能藏进摘要、引用、embedding、Manifest、计数、排序或错误；
- 投影越过空间、Harness、受众或用途边界时必须重新授权；
- 脱敏只是一种可能的受控表示，不是通用授权，也不预先决定算法。

#### 5. 采用“撤回/降权沿血缘传播 + 失败安全”

撤回、降权、敏感性变更、purpose 撤销和策略更新应使依赖图上的派生物进入重新评估，而不是只更新源记录。未能及时确认状态、血缘或来源权限时，默认停止新增使用、隔离旧表示、收窄投影或阻断。任何恢复都应从当前权威来源重新做授权和派生，不能以旧缓存或历史 token 恢复。

面向无权主体的错误和拒绝使用统一、最小且不泄露存在性；面向有权审计者才按其 purpose 披露必要的决定原因。可观察性、审计和调试不应成为侧信道，也不应扩大原始内容可见性。

#### 6. 用可替换机制而非最终实现承载治理职责

后续架构可以把职责分到来源系统、关系授权层、策略决策层、检索编排器、投影执行器和审计/血缘服务，但每个职责应能回答：

- 谁基于哪些输入作出了哪个动作的决定；
- 决定发生在召回、读取、融合、派生还是投影之前；
- 使用了哪个来源权限、purpose、敏感性和策略版本；
- 派生结果如何回指来源、目标 scope 和撤回依赖；
- 失败时如何防止存在性、字段和关系泄露。

本轮不规定服务边界、调用协议、决策缓存、同步模式、策略 DSL、最终字段 Schema 或审批工作流；后续实现必须证明这些逻辑不变量没有被适配层削弱。

### 专家团挑战

- **产品/UX**：用户希望“找到相关记忆”，但 `discover/read/use/audit` 分离会产生“能看到状态但不能打开”的情况。建议只解释对当前主体和目的有用的最小状态，提供申请、确认或缩小范围的下一步；不能用“更透明”名义展示受限对象名称、来源和拒绝原因。
- **架构**：ACL、关系授权、ABAC 和来源系统可能给出不同粒度和时效。建议以动作级资格门禁作为统一编排边界，保留 owner/related/derived 和源权限的语义区分；若底层索引不能在召回前安全过滤，就只接收授权窄候选或停用，不依赖后置隐藏。
- **可靠性**：撤回与缓存、异步 embedding、队列、重试和 Manifest 更新存在竞态。建议每个派生物绑定来源版本和撤回依赖，使用当前状态做最终复核；传播不完整时 fail closed 或收窄，禁止以“缓存短暂过期”作为全局放行理由。
- **安全/隐私**：最危险的泄露可能不是原文，而是对象存在性、owner、关系、计数、错误差异、摘要唯一细节和 embedding 推断。要求拒绝路径做侧信道审查，字段级决策覆盖所有表示，组合敏感性高于单字段时升级治理。
- **数据/质量**：跨空间融合容易把同源派生当作独立证据，也容易因字段脱敏损失适用条件。建议保留来源/血缘和派生活动，评估语义保真与泄露风险，不因更高召回率或更少 token 放宽 purpose 和授权。
- **治理/运营**：完整矩阵、审批角色、策略变更和 SLA 不能靠本轮文档臆定。建议先建立动作/场景/风险的评测集，验证撤回传播、无权等价响应、字段最小披露和跨空间重授权，再分阶段选择实现；策略回滚不能恢复已撤回权限。

专家团综合建议：采用“动作分离、授权先行、字段最小披露、跨空间不继承、派生重授权、血缘可追踪、撤回可传播、拒绝不泄露、质量和预算服从治理门禁”的方向。先验证安全不变量和失败路径，再讨论矩阵、策略语言、脱敏与服务接口；不以便利、相关性、成本、延迟或历史授权替代当前治理判断。

## 子议题深化 8：Manifest、索引、缓存和派生结果的一致性与撤回传播协议

### 主题与成功标准

本主题承接议题 4 的下一个权威暂缓项：**“Manifest、索引、缓存和派生结果的一致性与撤回传播协议”**。本轮只确定权威来源、版本、权限、血缘与各种派生投影之间的逻辑不变量，以及写入、更新、读取、投影、撤回和异步传播的安全边界；不固化最终事件 Schema、消息总线、服务 API、缓存键、索引字段、TTL、SLA、分布式事务或具体部署实现。

阶段性边界：**权威记忆、版本、权限和血缘是真相；Manifest、索引、缓存、摘要、embedding、融合视图和其他派生结果都是可失效投影。** 派生结果可以加速发现和读取，但不能成为授权、当前有效性或撤回状态的唯一来源。

每个派生投影至少需要在逻辑上绑定以下信息，不代表本轮规定最终字段 Schema：

```text
source revision(s)
  → 产生该结果所依据的一个或多个权威来源版本
policy / purpose
  → 生成、读取、投影和继续使用时适用的策略版本与用途
 generation / createdAt
  → 该派生结果的生成代次及创建时间
 dependencies
  → 直接和必要的传递依赖、来源/派生活动关系
 revocation state
  → 当前已知的撤回、权限降级、敏感性变化、失效或待复核状态
```

成功标准：

1. 明确权威记忆、版本、权限和血缘与 Manifest、索引、缓存、摘要、embedding、融合视图及其他派生结果的真相/投影边界；任何派生结果都不能反向授予权限或恢复当前有效性；
2. 每个派生结果能够逻辑回指来源 revision、policy/purpose、generation/createdAt、依赖和撤回状态，并能识别结果已过期、版本不匹配、依赖缺失、传播未完成或状态未知；
3. 写入、更新、读取和最终投影都执行与当前动作相匹配的权威版本、权限、用途、敏感性和血缘复核；不能因为缓存命中、Manifest 存在或 embedding 相似而跳过复核；
4. 撤回、权限降级、敏感性变化、冲突和迟到来源能够沿血缘传播到相关派生结果，至少阻止新增使用、收窄投影、标记待复核或进入隔离/重算路径；传播失败或状态无法证明安全时默认 fail closed 或收窄；
5. 异步传播能够安全应对重试、重复、乱序、分区、依赖暂不可见和部分重建，并支持可重放、幂等、对账/修复、dead-letter 和人工介入，不因最后到达或重复处理覆盖较新的权威状态；
6. 历史 Run Snapshot、当时的 Manifest 和审计记录保留当时决定及其依据，但不恢复当前权限、不替代当前授权，也不允许从旧缓存、旧 embedding 或旧 Manifest 反向恢复授权；
7. 方案可以指导后续一致性实验、血缘服务、投影器和运行治理，但不预先决定最终 Schema、API、索引、消息系统、TTL、SLA、事务模型或某个供应商的实现。

### 头脑风暴

#### 1. 先定义“谁是真相，谁是投影”

一致性讨论不能把所有数据副本视为同等权威。建议先区分：

```text
Authority
  → 记忆内容、当前版本、权限/用途决定、敏感性、有效状态和血缘事实

Projection
  → Manifest、倒排/向量/代码/关系索引、缓存、摘要、embedding、融合视图和投影结果

Run History
  → 历史 Run Snapshot、当时的输入、决定、策略版本和审计证据
```

三类对象的职责不同：

- **Authority** 决定当前能否发现、读取、使用、派生、投影和审计；
- **Projection** 只提供可重建的候选、加速结果或受控表示，不能自行改变 Authority；
- **Run History** 说明过去发生了什么，不能被当作当前授权缓存，也不能因当前策略变化而重写成另一种历史。

因此，“索引中还有记录”“缓存尚未过期”“Manifest 标记为 ready”“embedding 仍能相似命中”都不等于当前可用。派生层出现不一致时，应回到权威版本、权限和血缘重新判断，而不是让派生层反推真相。

#### 2. 派生结果的最小可验证绑定

每个派生结果都应具备可验证的逻辑绑定：

```text
derived result
├── source revision(s)
├── policy / purpose used for derivation
├── generation / createdAt
├── direct and transitive dependencies
├── current / known revocation state
├── representation kind and producer context
└── recomputation / quarantine eligibility
```

这不是要求固定字段或公开全部信息。其含义是：任何读取者或维护者都能判断“它基于哪一版来源、为哪个目的生成、何时/哪一代生成、依赖哪些对象、当前是否受撤回或权限变化影响，以及无法确认时该如何处理”。

逻辑绑定至少应覆盖：

- 摘要不能只绑定摘要文本而不绑定被摘要的来源版本和适用范围；
- embedding 不能只绑定向量和模型代次而不绑定输入来源、purpose 和当前撤回状态；
- Manifest 不能只声明“可用”而不携带或关联其来源 revision、策略上下文和依赖；
- 融合视图不能只保留最高分结论而丢失组成来源、版本、冲突和传播依赖；
- 缓存不能只按查询文本或对象标识命中，而忽略主体、purpose、策略、来源版本和撤回状态；
- 索引不能把物理删除、逻辑失效、权限降级和待复核混成同一种不可解释的状态。

#### 3. 写入和更新：先确认权威，再产生投影

建议把写入/更新约束为以下逻辑顺序：

```text
接收新记忆或权威变更
  → 认证主体、Purpose、目标 scope 和写入权限
  → 在权威层确认来源版本、敏感性、有效状态和血缘
  → 形成新的权威 revision 或受控状态变化
  → 产生可追踪的派生更新意图
  → 更新或重建 Manifest、索引、缓存、摘要、embedding、融合视图等投影
  → 对准备被读取/投影的结果执行当前权威复核
```

权威变更和派生更新可能不是同一时刻完成。重要的不是要求所有实现采用同步更新，而是不能在派生更新未完成时假装投影已经代表最新真相。更新过程应能区分：

```text
权威已更新、投影尚未完成
  → 标记过期/待传播/待复核，必要时收窄或阻断
投影完成但无法证明来源版本或策略上下文
  → 不作为当前可用结果，进入重建或隔离
收到较旧版本的更新请求
  → 不覆盖当前较新权威状态，转为忽略、补偿或重算
派生更新部分完成
  → 只使用能够证明安全和完整的部分，不扩大为全局可用
```

“写入成功”不能被简单理解为“所有索引和缓存已立即可读”。对外报告的写入状态、可发现状态、可读取状态和可用于当前 purpose 的状态可以不同，但面向调用者的表达仍需最小披露，不能借状态差异泄露受限对象。

#### 4. 读取和投影：命中之后仍要最终复核

任何派生命中都应经历两类检查：

```text
Projection eligibility check
  → 该结果是否来自可接受的 source revision、policy/purpose、generation 和依赖

Fresh authority check
  → 当前主体、当前 purpose、当前版本、当前权限、敏感性和撤回状态是否仍允许使用
```

读取流程至少应覆盖：

1. 解析当前主体、Harness、Task、Purpose、目标 scope 和风险；
2. 从 Manifest、索引或缓存得到候选/结果，但把它视为不可信投影；
3. 核对来源 revision、派生代次、依赖完整性和状态是否可解释；
4. 回到权威层复核当前权限、用途、敏感性、有效性、冲突和撤回；
5. 对最终将交付的原文、摘要、引用、embedding、融合结论或工具结果再次复核；
6. 复核失败时删除受影响内容、收窄结果、转换为引用/状态、请求具备权限的主体确认或阻断；
7. 记录必要的决定、版本、策略和传播状态，不把无权对象的细节写入面向调用者的错误或解释。

缓存命中不能跳过上述步骤。缓存未命中也不能推出对象不存在；索引缺失、传播迟到或投影暂不可用应与“没有匹配”区分于内部运维和审计，但不能通过对普通调用者可见的计数、时延、错误差异或候选数量泄露受限信息。

#### 5. 撤回和治理变化沿血缘传播

以下变化都应视为可能影响派生结果当前可用性的权威变化：

```text
来源撤回 / 删除 / 权限降级
purpose 撤销 / 目标 scope 改变
敏感性升级 / 字段限制改变
owner 或来源权限变化
版本替换 / 冲突确认 / 迟到来源到达
策略或治理规则变化
```

它们不应只更新来源对象，而应沿直接和传递血缘触发相关派生结果的重新评估：

```text
权威变化
  → 找到直接和传递依赖
  → 标记受影响的 Manifest、索引、缓存、摘要、embedding、融合视图和投影
  → 立即阻止新增的 discover/read/use/derive/project
  → 按当前授权决定收窄、重算、脱敏、隔离或删除
  → 传播到未消费队列、下游空间、工具结果和后续派生
  → 对无法确认的部分保持 fail closed 或更窄可用范围
  → 允许受控重试、对账和人工处理
```

传播“到达”不等于传播“生效”：处理者还要检查该变化相对于当前权威 revision 是否仍适用。旧撤回通知、重复通知或乱序通知不能把已经撤回的对象重新标记为可用；同样，迟到的旧版本内容不能覆盖较新的权限降级或敏感性变化。

撤回传播可以有短暂延迟，但在延迟期间不能以旧投影默认放行高风险使用。若系统无法证明某个派生结果尚未受影响，应按风险收窄或阻断，而不是把传播不确定性当成授权。具体传播时限、可用性目标和补偿窗口留待后续治理，不在本轮固化。

#### 6. 乱序、重复、分区和部分失败的安全语义

异步传播不应依赖“每条更新恰好处理一次”或“消息严格按顺序到达”的假设。实现至少应具备以下逻辑能力：

```text
重复处理
  → 同一权威变化重复到达时，结果不重复放大、不反向恢复授权
乱序到达
  → 依据来源 revision、生成代次或可验证的因果关系判断新旧，不以到达顺序覆盖
传播重试
  → 失败后可重试，重试副作用幂等，已成功部分不会造成额外授权
网络/分区
  → 分区恢复后可重新发现遗漏、对账并补偿，不把暂时不可见当成不存在
依赖缺失
  → 暂缓使用或进入待验证路径，不以不完整血缘生成普通投影
部分重建
  → 标记边界和影响范围，只开放可证明安全的部分
无法自动修复
  → 进入 dead-letter/隔离和人工介入，保留受控原因与后续动作
```

幂等不是只比较消息文本相同；处理结果还要受来源 revision、依赖、目的和撤回状态约束。一个旧消息即使此前从未处理过，也不能覆盖当前较新的权威状态。一个新消息重复处理，也不能因为重复写入而产生多份可见证据、扩大传播范围或绕过当前授权。

对账/修复应以权威层和血缘事实为输入，检查投影是否缺失、过期、重复、越界或无法证明安全；不能用索引、缓存、Manifest 或 dead-letter 内容互相“拼接”来创造新的权威真相。人工介入也只能通过受控授权和当前状态重新作出决定，不能直接把旧派生物标记为永久有效。

#### 7. Manifest、索引、缓存和不同派生表示的专项边界

| 投影 | 可以承担的职责 | 必须绑定/复核的逻辑事实 | 禁止推断 |
|---|---|---|---|
| Manifest | 描述一次运行或投影计划可见的内容、引用和代次 | 来源 revision、policy/purpose、generation/createdAt、依赖、当前撤回/失效状态、最终复核 | Manifest 存在或标记 ready 就是当前授权；旧 Manifest 可恢复新权限 |
| 关键词/向量/代码/关系索引 | 加速候选发现、相似度、结构或血缘查询 | 来源版本、索引代次、过滤边界、依赖完整性和可重建性 | 命中、排名、相似度、图可达性或索引存在授予 discover/read/use |
| 缓存 | 减少重复读取或重复投影成本 | 主体/用途/策略上下文、来源 revision、派生代次、撤回状态和有效性复核 | 命中就是新鲜；旧缓存可作为授权凭证或传播源 |
| 摘要/embedding | 提供压缩或语义候选表示 | 输入来源 revision、生成策略/用途、代次、依赖、敏感性和撤回状态 | 不可逆、无原文或只有向量就不受权限约束 |
| 融合视图 | 组织多个授权来源、例外和冲突 | 全部必要来源/版本、血缘、purpose、依赖、冲突和当前可使用状态 | 模型生成的新文本脱离来源限制；最高分结论替代权威事实 |
| 下游投影/工具结果 | 面向指定 Harness、Task 或受众提供最小结果 | 实际交付字段、受众、目的、最终复核和撤回依赖 | 已交付一次就永久可继续使用；工具输出可改变当前权限 |

该表是逻辑责任划分，不是最终索引设计、缓存键设计、字段 Schema 或接口契约。任何表示转换都应继承或重新验证来源约束，不能用“只是元数据”“只是候选”“只是摘要”“只是工具结果”规避撤回传播。

#### 8. 历史 Run Snapshot 与当前授权严格分离

历史 Run Snapshot 应保留当时运行所需的最小可复现信息，例如当时采用的 Manifest/投影引用、来源 revision、策略/purpose 版本、generation/createdAt、依赖和当时的授权/阻断决定。它的目的在于解释和审计：

```text
历史回放
  → 说明当时基于什么做出了什么决定

当前读取/投影
  → 重新检查当前主体、purpose、版本、权限、敏感性、血缘和撤回
```

两者不能混同：

- 历史 Snapshot 不因当前撤回而被改写成“当时没有发生”，但也不因此保留当前可读权限；
- 当前请求不能以“历史 Run 曾经使用过”作为授权凭证；
- 策略回滚可以帮助解释或重现某个历史决定，但不能恢复已撤回、已降权或敏感性已升级的对象；
- 从旧 Manifest、缓存、embedding、摘要、投影或审计记录重新生成时，必须回到当前权威来源重新授权，不能反向恢复授权；
- 历史内容的留存、删除、脱敏、审计可见性和取证范围仍受生命周期与治理策略约束。

### 权威/官方机制调研（访问日期：2026-09-20）

- **Transactional Outbox pattern**：<https://microservices.io/patterns/data/transactional-outbox.html>（访问：2026-09-20）。该机制将待发布的变化记录与业务更新放在同一受控写入边界，再由独立发布过程传递给消费者；文档特别提醒消息可能重复，因此消费者必须幂等。它可作为“权威变化与异步派生更新之间建立可恢复连接”的模式参考，但不规定本平台的事件 Schema、消息总线、分布式事务、重试次数、TTL 或 SLA，也不能解决所有跨系统一致性问题。
- **CloudEvents 1.0 Specification**：<https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md>（访问：2026-09-20）。规范提供跨平台事件上下文的通用表达，例如事件类型、来源、标识和时间等，可作为传播关联、去重和观测语义的参考；CloudEvents 不定义本平台的来源 revision、授权、purpose、血缘闭包、撤回状态或处理顺序，采用它不等于确定最终事件 Schema。
- **HTTP Semantics（RFC 9110）条件请求**：<https://www.rfc-editor.org/rfc/rfc9110.html>（访问：2026-09-20）。RFC 9110 定义了实体标签、`If-Match`、`If-None-Match` 等条件请求和缓存验证语义，可参考“基于版本/验证器避免无条件覆盖和复用旧表示”；HTTP 条件请求不替代当前权限、purpose、敏感性、血缘和撤回判断，也不直接规定内部 Manifest 或缓存协议。
- **Kubernetes API Concepts：Efficient detection of changes / watch**：<https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes>（访问：2026-09-20）。官方文档说明 watch、`resourceVersion`、断线后的重新列举/恢复以及资源版本过期等变化检测语义，可作为“异步观察、乱序/断线恢复和重新对账”的机制参考；Kubernetes watch 不是本平台的通用事件总线、授权系统、血缘协议或撤回保证，不能直接移植其字段或 API。
- **OpenTelemetry Context propagation 与 Traces**：<https://opentelemetry.io/docs/concepts/context-propagation/>、<https://opentelemetry.io/docs/specs/otel/trace/>（访问：2026-09-20）。官方机制支持在跨服务调用中传播 Trace/Span 关联并把一次运行的写入、传播、读取和投影串联起来，可作为诊断和运行观测的参考；Trace 关联不等于业务血缘、授权证明、删除/撤回完成证明，也不允许为了观测保存或暴露不必要的原文和敏感字段。
- **W3C PROV-O**：<https://www.w3.org/TR/prov-o/>（访问：2026-09-20）。该规范提供 Entity、Activity、Agent 以及生成、使用、派生关系的通用语义，可作为来源 revision、派生活动和依赖追踪的概念参考；它不规定记忆权限、撤回传播、缓存失效或本平台的最终血缘 Schema。

共同规律和谨慎结论：Transactional Outbox 关注可靠发布连接，CloudEvents 关注事件上下文互操作，HTTP 条件请求关注表示验证，Kubernetes watch 关注变化观察与断线恢复，OpenTelemetry 关注运行关联，PROV-O 关注来源和派生语义。它们都不能单独提供“权威状态 + 当前授权 + 撤回沿血缘传播 + 派生投影最终复核”的完整协议，因此本轮只吸收可复用的机制边界，不宣称存在可直接移植的最终方案。

### 综合结论与建议

#### 1. 采用“权威真相 + 可失效投影 + 最终复核”的一致性骨架

建议将逻辑边界固定为：

```text
Authority
  → current memory / revision / permission / purpose / sensitivity / lineage

Derivation Binding
  → source revision(s) + policy/purpose + generation/createdAt
  → dependencies + revocation state

Projection Update
  → Manifest / index / cache / summary / embedding / fusion view

Read & Projection Gate
  → validate projection binding
  → re-check current authority and intended audience/purpose
  → deliver minimum projection or narrow/block

Propagation & Repair
  → apply revocation/downgrade/sensitivity/conflict/late changes
  → retry, deduplicate, reconcile, quarantine or manual intervention
```

任何实现都可以选择不同的存储、传播和重算方式，但不能让派生层承担权威层职责。投影状态未知、绑定缺失、依赖不完整或最终复核失败时，默认减少可见范围或阻断，而不是将“不确定”解释成“仍然允许”。

#### 2. 将来源 revision、policy/purpose、generation/createdAt、依赖和撤回状态作为不可丢失的逻辑不变量

建议把以下不变量作为所有派生物的最低要求：

- **来源版本不丢失**：能够判断该表示是否仍基于当前可接受的 revision；
- **目的和策略不丢失**：能够判断它为哪个 purpose、受哪个策略上下文生成，不能把一次用途的结果无条件复用到另一用途；
- **生成代次和时间不丢失**：能够区分不同生成过程、重建和旧结果，避免最后到达覆盖当前状态；
- **依赖不丢失**：能够沿直接/传递血缘定位受影响的 Manifest、索引、缓存、摘要、embedding、融合视图和下游投影；
- **撤回状态不丢失**：能够区分当前有效、待传播、待复核、已撤回、权限收窄、隔离或未知，而不是只保留“存在/不存在”；
- **绑定不可伪造**：投影不能只在派生层自报来源版本或授权结果，读取时仍需以受信的权威信息复核。

这些是不变量，不是强制的外部字段名或数据格式。后续实现可以采用引用、版本资料包、血缘服务或其他载体，只要能证明上述语义未被压缩、摘要、缓存、索引或跨服务适配丢失。

#### 3. 写入、更新、读取、投影统一采用“先权威、后派生、再复核”

建议形成以下通用流程：

```text
Write / Update
  → authorize current action and validate source revision
  → commit or accept authoritative change
  → publish a recoverable derivation intent
  → update/rebuild projections with binding and dependencies

Read
  → obtain candidate from projection
  → validate binding and dependency status
  → re-check current authority, purpose, sensitivity and revocation

Projection
  → decide audience, fields, representation and risk
  → re-check actual output, summary, citation and tool result
  → deliver, narrow, quarantine, request confirmation or block

Repair
  → reconcile against authority and lineage
  → idempotently replay or rebuild
  → keep unresolved results isolated and available for controlled intervention
```

该流程不要求所有动作采用分布式事务，也不承诺实时强一致；它要求任何“暂时一致”都有可识别的影响范围和安全默认值。对高风险用途，无法确认撤回、权限或版本状态时应优先阻断；对低风险用途，也只能使用能证明当前允许的最小投影。

#### 4. 采用“变化沿血缘传播，状态不确定则收窄”的撤回规则

撤回、权限降级、敏感性变化、冲突和迟到来源都应触发依赖遍历和重新评估。传播动作至少包括：

```text
identify affected dependencies
  → stop new use and prevent stale projection
  → invalidate, narrow, quarantine or recompute
  → propagate to pending/downstream derivations
  → reconcile after retry or partition recovery
  → require current authorization before release
```

撤回传播的目标不是修改历史事实，而是阻止派生层继续把旧状态当作当前授权。历史 Run Snapshot 可以保留当时决定和证据；它与当前可用性分离。恢复投影时必须从当前权威来源重建并重新授权，旧缓存、embedding、Manifest、摘要和审计记录都不能成为授权源。

#### 5. 异步协议采用“可重试、幂等、可对账、可人工介入”的能力边界

后续实现应证明：

- 重复传播不会重复授权、重复扩大证据或改变当前状态；
- 乱序传播不会用旧 revision 覆盖新 revision；
- 分区恢复后能够发现遗漏并对账，不把暂时未读到的依赖当成不存在；
- 失败重试不会导致投影在不知情状态下继续被使用；
- 无法自动处理的结果进入 dead-letter/隔离并支持人工介入；
- 重放、回填和重建均以当前权威版本、权限、purpose、敏感性和血缘为准；
- 操作和传播状态对有权运维/审计主体可追踪，但不向无权主体暴露对象存在性、来源或敏感细节。

本轮只确认这些能力，不把“至少一次/至多一次”等具体投递保证、重试次数、退避方式、dead-letter 保留时间或人工响应时限写入产品契约。

#### 6. 读取安全优先于命中率和新鲜度表象

Manifest、索引和缓存的命中率、新鲜度、延迟和重建效率都是质量指标，不是授权指标。任何优化都不能：

- 用缓存命中跳过当前权限、purpose、敏感性和撤回复核；
- 用索引中的旧 revision 覆盖权威层的新 revision；
- 用摘要或 embedding 隐藏来源限制、敏感变化或撤回状态；
- 用 Manifest 的 `ready` 或类似状态证明当前允许投影；
- 用任务成功率、成本或延迟抵消撤回内容继续出现和跨边界泄露；
- 从旧派生结果反向恢复授权、owner、scope 或当前可用状态。

应把“没有命中”“投影暂不可用”“候选过期”“被当前授权拒绝”“传播未完成”和“结果被阻断”在内部治理上分别记录，同时对普通主体采用最小且不泄露存在性的外部表达。

#### 7. 后续评估围绕不变量和故障注入，不提前固化运行目标

后续实验至少应覆盖：

- 权威更新与 Manifest/索引/缓存/摘要/embedding/融合视图异步落后的窗口；
- 撤回、权限降级、purpose 撤销、敏感性升级和 owner/来源权限变化；
- 同一变化的重复、乱序、延迟、丢失、分区恢复和部分重建；
- 旧缓存命中、旧 embedding 命中、Manifest 误标 ready 和依赖缺失；
- 冲突来源、迟到版本和新旧策略交错；
- 高风险/低风险、不同 Harness、不同目标 scope 和不同派生深度；
- 历史 Run Snapshot 回放与当前授权重新检查；
- dead-letter、对账、人工介入和恢复后的幂等性；
- 是否泄露对象存在性、计数、来源、敏感字段、撤回状态或传播进度。

评估应同时看安全正确性、语义保真、恢复正确性、重算成本、可观测性和任务收益；具体指标、阈值、传播窗口、容量、SLA、告警门槛和灰度流程留待后续架构与运营设计。

### 专家团挑战

- **产品/UX**：用户会把“缓存命中”“Manifest 已准备”理解为内容可靠可用，但这些状态不等于当前授权。建议对普通用户显示最小的“内容已收窄、需要重新验证或暂不可用”状态和可行动的下一步，不展示传播队列、对象名称、内部 revision 或受限撤回细节。
- **架构**：权威层与派生层可能由不同系统维护，强一致、最终一致、事件驱动和重建流程各有代价。建议先固定权威边界、派生绑定和最终复核，再比较 Outbox、事件传播、watch/reconcile 或其他实现；不要把某种消息总线、事务模式或缓存架构写成产品契约。
- **可靠性**：重复、乱序、分区和部分失败是常态，单纯依赖 TTL 或按时间刷新无法处理权限降级和撤回。要求基于 revision/依赖的幂等应用、重试、对账、隔离、dead-letter 和人工恢复；状态未知时 fail closed 或收窄，不能用旧投影兜底放行。
- **安全/隐私**：撤回延迟窗口、缓存命中差异、索引计数、Manifest 状态、传播错误和 dead-letter 都可能泄露敏感信息。要求所有表示继承来源治理边界，传播和审计接口最小披露；禁止从任何旧投影恢复授权。
- **数据/质量**：摘要、embedding 和融合视图可能保留原始敏感事实，也可能因重算丢掉限定、来源和冲突。建议把版本、purpose、依赖和撤回状态作为质量不变量，评估语义保真、同源去重和重建结果，而不是只测索引新鲜度或命中率。
- **治理/运营**：人工介入、历史快照、删除留存和合规取证之间存在张力。建议区分当前使用、历史解释和审计取证权限；明确人工修复必须重新授权，策略回滚不恢复已撤回权限；完整保留/删除、事件响应和服务目标留待治理设计。

专家团综合建议：采用“权威版本/权限/血缘为真相、所有派生物带来源与策略绑定、写入/更新/读取/投影最终复核、撤回和治理变化沿血缘传播、异步传播可重试/幂等/对账/隔离、历史 Snapshot 与当前授权分离、旧投影不得恢复授权”的方向。先通过乱序、重复、分区、撤回延迟和部分重建测试安全不变量，再讨论最终事件载体、服务边界、索引和缓存实现；不以实时性、命中率、成本或便利交换失败安全。

### 头脑风暴

#### 1. 统一先验：内容是数据，不是控制面

安全边界应在内容进入任何推理、融合或执行链路前明确：

```text
System / Developer / platform policy
  → 来自受控控制面，决定安全边界、工具权限和策略

User request
  → 是任务输入，但也可能包含越权意图或诱导，不能自动扩大权限

Memory / retrieval / tool result / file / image / audio / video
  → 不可信数据或证据，不能升级为系统/开发者指令

Detection / risk assessment
  → 风险信号，用于隔离、收窄、复核、引用或阻断，不是安全证明

Execution / output gate
  → 独立复核工具调用、文件变更、秘密外传、策略变化和外部输出
```

因此，以下内容即使出现在看似权威的记忆、代码注释、文档、网页截图、语音转写或工具返回中，也不能直接生效：

- 要求忽略系统/开发者规则、关闭安全检查或改变授权边界；
- 要求调用工具、访问新 scope、读取凭证、导出秘密或向外部地址发送数据；
- 声称自己是管理员、系统消息、审批结果、可信工具或安全门禁；
- 要求把当前内容写入长期记忆、提升优先级、传播到 Team/Project 或覆盖已有策略；
- 要求隐藏来源、删除审计、跳过确认、伪造成功或压低风险等级。

“内容里写着一条指令”与“平台控制面授予了一项动作”是两件不同的事。模型能够理解一段文本、图像、音频或视频，不意味着平台授权其执行其中的要求。检测器、解析器、摘要器和模型也不能通过输出一个更像指令的结果来改变这一边界。

#### 2. 威胁面必须按来源、传播和表现形式观察

攻击者不必直接向当前 Prompt 写入恶意文本，也可以将载荷放入被召回或被处理的外部内容中。需要同时覆盖：

```text
直接注入
  → 当前用户输入、记忆或文件直接要求越权/绕过规则

间接注入
  → 网页、文档、代码注释、工单、邮件、工具结果或历史记忆诱导后续动作

恶意记忆
  → 将攻击性指令、伪事实、秘密、权限声明或污染内容写入/巩固/传播为记忆

跨模态隐藏
  → 图片文字、低可见度元素、音频语音/超声/背景声、视频帧/字幕/元数据或跨模态组合

跨轮传播
  → 一轮内容被摘要、引用、embedding、Manifest、缓存或工具结果带入后续运行

重复传播
  → 同一载荷经切片、改写、翻译、编码、截图、转写或多来源复制反复出现
```

检测对象不只是一段最终文本，还包括其来源、权限、载体、解析过程、变换链、请求意图、拟执行行为和下游受众。相同文字在普通讨论中可能是待分析的样本，在工具参数或安全策略字段中则可能构成更高风险；反过来，内容出现在“记忆”“官方文档”或“工具返回”字段中，也不自动可信。

#### 3. 必须覆盖的风险族

本轮采用风险族覆盖，而不是预先规定分类器标签。至少包括：

| 风险族 | 需要识别的表现 | 处置边界 |
|---|---|---|
| Prompt Injection | 覆盖规则、改变角色、伪造高优先级消息、要求隐藏/绕过门禁 | 内容保持数据；相关上下文隔离，不能改变控制面 |
| 越权请求 | 请求访问不属于当前主体、scope、Purpose 或 Harness 的内容/工具 | 重新执行动作级授权；不因内容声称获批而放行 |
| 秘密外传 | 索取凭证、系统 Prompt、内部路径、个人数据、密钥、隐藏上下文或受限记忆 | 输出和工具门禁独立阻断；解释不泄露被保护秘密 |
| 数据投毒 | 伪造事实、恶意偏好、错误安全规则、污染摘要/embedding/长期记忆或诱导巩固 | 进入待验证/隔离；不能凭重复、相似度或权威口吻升级 |
| 恶意链接/附件 | 可疑 URL、重定向、下载、宏、脚本、外部上传或附件中的诱导/载荷 | 链接和附件是数据；访问、下载、执行和外传分别授权 |
| 跨模态隐藏指令 | 图片中的文字/像素、音频中的语音/背景信号、视频帧/字幕/元数据或组合信号 | 各模态和转换结果均不可信；不可见不等于不存在或安全 |
| 对抗样本 | 让检测、OCR、ASR、分类或模型理解失效的扰动、边界样本和格式异常 | 解析/检测不确定即收窄、隔离或人工复核，不以未命中放行 |
| 编码/混淆 | Base64、转义、分隔、拼写变体、翻译、零宽字符、图像文字、音频编码等规避 | 可在受控解析层识别风险；解码结果不自动获得执行语义 |
| 间接注入 | 外部资源或工具返回内容要求模型修改任务、调用工具、泄露数据 | 来源内容与任务/控制面隔离；工具参数必须独立复核 |
| 重复/跨轮传播 | 同一载荷变形后进入记忆、摘要、缓存、Manifest、工具结果或后续 Prompt | 继承来源/风险/撤回状态；重复不增加可信度，支持追踪和撤回 |

表中风险族可以重叠。一个“请把这段内容存入 Project 记忆并发送到 URL”的图像文字同时涉及跨模态隐藏、记忆投毒、越权请求、链接和秘密外传；不应只保留一个低风险标签而丢失其他处置依据。

#### 4. 分层防御链

建议所有内容进入检索、融合、投影或执行链路时遵循以下逻辑顺序：

```text
1. Source / 来源
   → 谁提供、从哪里来、经过哪些中间系统和变换

2. Permission / 权限与用途
   → 当前主体能否 discover/read/use/derive/project，Purpose 是否匹配

3. Type / 类型与载体
   → 文本、结构化数据、代码、链接、附件、图片、音频、视频及混合内容

4. Parsing / 解析
   → MIME/格式、编码、OCR/ASR、字幕、元数据、压缩包、嵌套和解析不确定性

5. Content & Behavior Risk / 内容与行为风险
   → 注入、越权、秘密外传、投毒、恶意链接、对抗/混淆和拟执行行为

6. Projection Isolation / 投影隔离
   → 与系统/开发者指令、工具描述、策略字段和安全门禁分离，保留不可信标记

7. Tool & Output Gate / 工具与输出门禁
   → 工具参数、文件变更、网络访问、记忆写入、秘密输出和外部发送独立复核
```

这些层不是一次检测调用，也不是必须采用某种服务拆分。任何一层都不能假设前层已经“证明安全”；每一层只应提供自己的证据和风险信号。来源可信不能替代内容检测，内容未命中不能替代权限检查，解析成功不能替代行为门禁，模型拒绝也不能替代平台对工具和输出的强制控制。

#### 5. 来源与权限层：先限制能看什么、能传播什么

对记忆、检索候选、工具结果和多模态内容，至少重新判断：

```text
来源主体 / 来源系统 / 代表主体
  → source scope / target scope / owner / related
  → discover / read / use / derive / project / audit
  → 当前 Purpose、Harness、敏感性、版本和撤回状态
  → 是否允许解析、转写、OCR、embedding、摘要、记忆写入或外部发送
```

检测系统本身不应读取无权原文来“帮忙判断”。当内容没有足够授权、来源不明、用途漂移、撤回状态未知或跨空间传播未重新授权时，应在内容深入解析前隔离、收窄或阻断。允许看到一条内容，不代表允许把它用于安全分类、训练、记忆巩固、工具调用或导出；允许审计也不代表允许把原文投影给普通 Harness。

对解析产生的新表示也要做动作级判断：OCR 文本、ASR 转写、视频字幕、附件解压内容、链接标题、缩略图、embedding、摘要和风险报告都是派生数据，不继承更宽的权限，也不能以“检测需要”为理由绕过字段级、空间级和用途级限制。

#### 6. 类型与解析层：不可信的不只是正文

类型处理应覆盖内容本体及其可见、不可见和附带部分：

- 文本中的控制字符、零宽字符、方向控制、隐藏注释、模板变量、引用层和嵌套格式；
- 结构化数据中的字段名、字符串值、注释、超链接、公式、模板、脚本和未知扩展字段；
- 代码、配置、Markdown、HTML、PDF、Office 文档、压缩包、日志和数据库导出中的注释、宏、嵌入对象、外链及非正文内容；
- 图片中的可见文字、低对比度文字、边缘区域、二维码、截图叠加层、图像元数据和 OCR 结果；
- 音频中的语音、背景语音、音调/信号、静音区、字幕/歌词、元数据和转写结果；
- 视频中的每一帧或采样帧、字幕、音轨、画面文字、元数据、嵌入链接和跨帧出现的内容；
- 文件名、路径、Content-Type、扩展名、URL、重定向目标、归档内层级和工具声明的描述字段。

解析器只能产生“按某种方法得到的表示”，不能证明原始内容已被完整理解。无法解析、类型不匹配、嵌套过深、加密/压缩不可检查、OCR/ASR 置信不足、采样可能漏掉内容或转换链断裂时，应标记不确定并默认隔离、引用或阻断高风险使用。不能因“没有识别到文字”就宣称图片、音频或视频安全。

#### 7. 内容风险与行为风险必须分开

内容风险关注“它表达或隐藏了什么”，行为风险关注“采用它会导致什么动作”。两者必须分别判断：

```text
Content signal
  → 可能是注入、秘密、伪造事实、恶意链接、混淆或隐藏载荷

Behavior signal
  → 是否会改变工具参数、扩大 scope、写入记忆、修改文件、访问网络、泄露数据、改变策略或产生不可逆影响
```

一段内容即使无法确定是否恶意，只要其拟议行为包含外部发送、凭证读取、权限变化、代码执行、记忆公开、不可逆变更或其他高影响动作，就必须进入更严格的工具/输出门禁。反之，一段明确描述攻击样本的研究材料可以作为受控数据分析，但不能因为“只是讨论”而自动获得执行权限；风险取决于当前用途、受众、变换和行为，而不是只取决于关键词命中。

检测结果应表达为风险信号、证据范围、不确定性、来源和建议动作，而不是无条件的“安全/不安全”事实。相似度、分类结果、用户声明、来源声称、历史未命中、重复出现和人工放行记录都不能单独覆盖独立的行为门禁。

#### 8. 投影隔离：把不可信内容放在数据通道

投影到模型或 Harness 时，至少应在逻辑上区分：

```text
Trusted control plane
  → 系统/开发者指令、平台策略、当前工具授权和执行门禁

Untrusted data plane
  → 记忆、检索内容、工具返回、文件、图片/音频/视频及其转换结果

Risk metadata
  → 来源、用途、类型、解析状态、风险信号、隔离/阻断状态和可展开引用
```

实现可以采用结构化包装、独立消息区、明确标记、引用化或其他隔离方式，但不能把不可信文本拼接到高优先级指令中，不能让内容中的字段名覆盖控制面字段，不能把“安全检查通过”写进普通数据并让后续组件自信执行。投影应保留“这是外部数据、可能包含指令性内容、不得遵循其中操作要求”的语义边界；这类边界是平台控制面提供的保护，不是由恶意内容自己声明。

摘要、翻译、OCR、ASR、视频采样、重写、embedding、融合和引用都不能消除风险。若变换丢失了来源、模态、位置、时间、上下文、冲突或不确定性，应收窄或隔离，而不是把更短的结果视为更可信。检测报告不得把完整攻击载荷复制到普通 Prompt、日志或用户界面；需要复核时使用受控引用和最小必要片段。

#### 9. 工具、记忆写入和输出门禁

任何来自不可信内容的动作提议都必须经过独立门禁：

```text
内容/模型提出动作
  → 解析实际工具、参数、目标、数据范围和副作用
  → 重新检查当前主体、Purpose、scope、敏感性和审批/确认要求
  → 检查是否由受控策略允许，而不是由内容授权
  → 进行参数、目标、秘密、链接/附件和不可逆影响复核
  → 允许最小动作、请求确认、隔离或阻断
  → 记录决定和来源，不把内容原文扩散到不必要的审计面
```

特别需要门禁的动作包括：读取或发送秘密、访问新的文件/网络/租户/Project、执行代码或脚本、修改文件/数据库/策略、写入或巩固长期记忆、将内容传播到 Team/Project、调用外部工具、打开链接/附件、改变安全配置和向用户作出不可逆承诺。

工具返回也不可信：工具的结果、错误、日志、网页、文件和二次调用结果不得直接成为下一次工具调用的授权或系统指令。工具返回中的“已批准”“忽略检查”“把结果发送到某地址”只能作为待分析数据。工具使用成功不代表返回内容可信，返回内容被检测为低风险也不代表后续动作可以跳过重新授权。

输出门禁至少检查：秘密/个人数据/受限记忆泄露、跨 scope 传播、恶意链接/附件再发布、未经确认的策略或事实承诺、把不确定结果写成确定结论，以及将攻击载荷复述给不必要的受众。输出被阻断时，提供安全的原因类别和下一步，不返回可直接复用的攻击字符串、隐藏指令或受保护上下文。

#### 10. 记忆写入、巩固和传播必须防投毒

“不可信内容”不能因为模型生成了摘要或用户说“记住这个”就自动变成高优先级记忆。记忆写入和巩固至少要区分：

```text
candidate memory
  → 来源、主体、scope、Purpose、载体和原始风险状态

validation / review
  → 事实与建议、指令与数据、来源与适用范围、冲突与不确定性

write / consolidate decision
  → 是否允许写入、允许写入哪一层/哪一 scope、是否需要确认

derived propagation
  → 摘要、embedding、索引、Manifest、缓存和跨空间投影继承血缘与风险
```

以下内容默认不能直接升级为约束、长期偏好、组织规则或工具授权：自称系统/管理员的文本、未经核验的安全指令、要求秘密外传的请求、针对第三方的隐私/权限主张、只出现一次且来源不明的关键事实、检测/解析不确定的多模态内容，以及从其他不可信内容自动总结出的“规则”。重复出现、多个索引命中、相似 embedding、用户未反驳或模型高置信度都不能独立证明其正确或可巩固。

如果内容进入候选记忆，也必须保留来源、原始载体、解析/变换链、风险和验证状态；撤回、申诉、重新分类或新证据出现时，应沿血缘收窄、隔离、重算或撤回所有派生物。历史 Run Snapshot 可以说明当时为何使用，但不能让已撤回或已污染内容恢复当前可用性。

#### 11. 编码、混淆、对抗和跨模态处理的保守语义

受控解码或转换可以帮助识别风险，但有三个不可逆边界：

1. 解码结果仍是不可信数据，不能因“已经还原”而成为指令；
2. 解码失败、部分还原或多个解释并存时，不能选择最有利于放行的解释；
3. 解码、OCR、ASR、采样和跨模态对齐本身会产生新的派生结果，必须继承来源、权限、模态、位置/时间和不确定性。

应关注但不固化为穷尽清单的规避方式包括：多层编码、Unicode/零宽字符、同形异体、分词边界、拼写与语言变体、隐写/低对比文本、二维码/条形码、音频背景或非自然语音、视频单帧/闪现字幕、文件元数据、压缩包嵌套、链接重定向和跨文件拼接。检测覆盖不足不是放行理由；高风险动作在解析覆盖不完整时默认隔离、引用或阻断。

对抗样本测试应同时检查误报和漏报，以及检测失败后工具/输出门禁是否仍然有效。目标不是承诺“识别所有攻击”，而是确保任何未识别攻击也不能凭内容本身改变权限、策略或安全门禁，并尽量限制其传播和影响。

- **Google Cloud 官方：Defending against indirect prompt injection attacks**：<https://cloud.google.com/blog/products/identity-security/defending-against-indirect-prompt-injection-attacks>（访问：2026-09-20）。该官方文章讨论间接注入如何通过外部内容影响代理，以及需要将不可信内容与高影响动作隔离、采用纵深防御；它是机制和威胁说明，不是本平台的检测规则、分类器或跨模态完整覆盖证明。
- **OpenAI 官方安全最佳实践文档**：<https://platform.openai.com/docs/guides/safety-best-practices>（访问：2026-09-20）。官方开发者文档提供输入/输出处理、限制高风险行为、监测和人工复核等安全实践方向；这些实践可支撑“模型安全能力不能替代应用层工具与输出门禁”的边界，但不规定本平台的记忆写入策略、阈值、模型或 API。

共同规律和谨慎结论：官方资料分别提供风险分类、风险治理、对抗知识库、间接注入防御和内容安全控制的参考，但没有任何单一资料声称能检测所有 Prompt Injection、证明所有多模态内容安全或替代授权与工具门禁。因此本轮只吸收“纵深防御、持续测量、限制高影响动作、保留来源和事件处置”的稳定机制语义，不把官方分类名、模型安全设置或研究原型直接固化为平台契约。

### 综合结论与建议

#### 1. 采用“数据/控制面分离 + 分层防御 + 独立执行门禁”

建议将不可信内容的安全处理逻辑固定为：

```text
Trusted Control Plane
  → system/developer policy, current authorization, tool allowlist and safety gates

Untrusted Data Intake
  → memory / retrieval / tool result / file / image / audio / video

Source & Permission Gate
  → provenance, scope, purpose, action-specific authorization, revocation

Type & Parsing Gate
  → media/type, encoding, nested content, OCR/ASR/subtitle/metadata and uncertainty

Risk Assessment
  → prompt injection, exfiltration, poisoning, links/attachments, adversarial/obfuscated/cross-modal signals

Isolated Projection
  → data-only representation with source/risk/uncertainty, never control-plane semantics

Tool / Memory-write / Output Gate
  → independently validate actual action, target, fields, side effects and audience

Propagation & Incident Handling
  → quarantine, narrow, cite, review, version, rerun, revoke and audit
```

该骨架不要求每层由独立服务实现，但要求每层职责可验证、失败不会扩大权限，并且下游不能把上游“未命中”解释成安全证明。内容检测只能帮助决定内容如何被看见和处理；授权、工具和输出门禁必须由受控平台逻辑强制执行。

#### 2. 采用“风险信号 + 处置状态”，不采用“安全证明”

逻辑上至少要区分：

```text
untrusted
  → 已知来自数据通道，默认不能控制系统或工具

risk-signaled
  → 检测/解析/行为分析发现一个或多个风险信号

uncertain
  → 来源、权限、类型、解析、模态覆盖或风险判断不足

quarantined
  → 暂不进入普通检索、融合、投影、记忆巩固或执行链路

cited/narrowed
  → 仅提供最小、受控引用/状态/已授权片段，不给动作语义

needs_review/confirmation
  → 交由具备权限的主体或受控流程复核

blocked/revoked
  → 当前用途、风险或状态不允许使用，且阻断传播/撤回派生结果
```

这些是逻辑状态，不是最终状态机或 Schema。`not_detected`、`low risk`、`source trusted`、`user confirmed` 和 `model high confidence` 都不能单独转换为 `safe` 或 `authorized`。低风险内容仍须遵守数据/控制面分离；高风险内容可以在低风险、受控的分析目的下作为样本被引用，但不能进入工具或策略链路。

#### 3. 统一的最小检测与处置流程

建议每次记忆融合、工具调用、文件处理、多模态解析、记忆写入和输出都经过：

```text
1. 记录来源、主体、scope、Purpose、载体和变换链
2. 先执行 discover/read/use/derive/project 等动作级授权
3. 识别类型、嵌套、编码、链接/附件和模态范围
4. 在受控边界内进行解析和风险评估
5. 将内容与控制面隔离，附带来源、风险、不确定性和撤回依赖
6. 对拟议的工具、记忆写入、策略变化和外部输出独立复核
7. 允许最小安全用途，或收窄、引用、隔离、确认、阻断
8. 将决定、来源、规则/策略版本和变换链纳入审计
9. 发现污染、撤回或规则变更时沿血缘重跑、收窄或撤回派生物
```

步骤 2 必须在不必要的深度解析前发生，但授权通过也不表示内容可信。步骤 4 不能直接产出“可执行指令”。步骤 6 必须检查真实的工具目标和参数，而不是只检查模型声称的意图。步骤 9 不能只修改原始记忆，必须覆盖摘要、embedding、索引、缓存、Manifest、融合结果、已排队工具参数和下游投影。

#### 4. 对风险族采用共同安全规则，避免单点分类器

对于 Prompt Injection、恶意记忆、多模态隐藏、编码混淆、对抗样本、间接注入和数据投毒，建议共享以下不可逆规则：

- 规则命中是增加风险或触发复核的信号，不是完整安全证明；
- 规则未命中、解析成功或模型未拒绝不解除权限和工具门禁；
- 来源/权限、解析覆盖、行为后果和下游传播必须独立考虑；
- 同源重复、多个模态命中、多个索引命中和多轮复述不增加可信度；
- 载荷被翻译、编码、摘要、截图、转写、embedding 或改写后仍继承原风险和血缘；
- 高影响、不可逆、秘密相关或跨空间动作采用更严格的确认/阻断，不以业务成功率抵消；
- 无法确定时默认隔离、收窄、引用或阻断，不能选择最宽解释；
- 误报可以申诉和复核，但申诉不自动改变权限、不恢复撤回内容、不删除审计、不直接放行工具动作。

#### 5. 记忆和派生物采用“污染不升级、撤回可传播”规则

建议将风险状态和来源血缘作为所有派生物的不可丢失逻辑语义：

```text
untrusted source
  → untrusted/uncertain derived representation
  → restricted or quarantined memory candidate
  → no automatic promotion to constraint/system/tool authorization
```

只有在独立、适合当前事实类型的验证和当前用途授权均通过后，才可以讨论有限巩固；即使巩固，也不能删除原来源、风险、适用条件和撤回依赖。任何风险升级、投毒确认、误分类纠正、来源撤回、权限降级或规则变化都应：

```text
标记受影响来源和派生链
  → 停止新增使用和传播
  → 隔离/收窄/重算/撤回摘要、embedding、索引、缓存、Manifest、融合和投影
  → 处理已排队工具参数、待写入记忆和下游空间
  → 使用当前权威状态和新规则受控重跑
  → 保留历史决定与安全审计，但不恢复当前授权
```

重跑必须使用版本化规则、当前授权和明确的输入/变换范围；不能用“以前已通过”“用户曾确认”“缓存未过期”代替当前复核。撤回传播不应把攻击内容复制到更多日志、错误消息或 UI；审计只保留必要的受控引用和风险类别。

#### 6. 安全解释、审计、申诉与版本化

面向不同主体的解释应最小披露：

| 受众 | 可说明的内容 | 不应暴露的内容 |
|---|---|---|
| 普通用户/Harness | 内容被收窄、引用、隔离、需确认或阻断；下一步如何提供安全替代 | 完整攻击载荷、隐藏指令、系统 Prompt、秘密、无权来源和可复用绕过细节 |
| 有权操作者 | 风险族、来源/载体、解析范围、行为后果、处置决定和规则/策略版本 | 超出其 Purpose 的原文、秘密和其他受限空间内容 |
| 安全/审计主体 | 受控来源引用、变换链、规则版本、决定、传播影响、重跑/撤回状态和证据位置 | 不必要的原始敏感内容；不能因审计而扩大普通读取权限 |

审计至少应能回答：内容从哪里来、由谁在什么 Purpose 下处理、经历了哪些解析/变换、哪些风险信号触发、哪一层门禁作出什么决定、哪些工具/记忆写入/输出被允许或阻断、哪些派生物受影响，以及使用了哪个规则/策略版本。审计日志不应默认保存完整攻击文本、秘密或多模态原件；需要取证时使用受控访问、最小片段和生命周期规则。

误报申诉应进入独立复核流程，至少保留申诉主体、理由、相关版本、复核决定和传播影响。复核结果可以修正分类、允许一个明确且受控的分析用途或标记规则问题，但不能直接扩大 scope、工具权限、记忆公开范围或恢复已撤回派生物。规则/策略版本应支持离线重跑、结果对比、灰度和回滚；回滚不能重写历史 Run Snapshot，也不能撤销已经生效的阻断、撤回或权限降级。

#### 7. 后续评估应验证“漏检后的影响是否仍被限制”

后续评测不应只测检测准确率或单一命中率，至少要覆盖：

- 直接/间接注入、越权、秘密外传、数据投毒、恶意链接/附件；
- 文本、结构化数据、代码、HTML/PDF/Office、压缩包、图片、音频、视频及其 OCR/ASR/字幕/元数据；
- 编码/混淆、零宽/同形字符、多语言、截断、低质量媒体、对抗样本和解析失败；
- 单轮、重复、摘要、翻译、截图、转写、embedding、缓存、Manifest、跨轮和跨空间传播；
- 工具调用、网络/文件访问、秘密读取、外部发送、策略变更、记忆写入和不可逆动作；
- 误报申诉、人工复核、规则版本变化、重跑、撤回和部分传播失败；
- 检测漏报时，权限、投影隔离、工具门禁和输出门禁是否仍阻止高影响后果；
- 解释和审计是否足够复现决定，同时没有复制攻击内容或泄露受限事实。

质量指标、检测覆盖、误报/漏报目标、风险阈值、重跑窗口、阻断时限、人工响应、灰度门槛和 SLA 需要真实数据、威胁模型、内容类型、业务风险和 Connector 能力共同校准，本轮不固化具体数值。

### 专家团挑战

- **产品/UX**：用户希望看到清晰的“为什么不能用”，但过度解释可能复述攻击指令、泄露系统 Prompt 或暴露受限来源。建议用风险类别、处置状态、最小来源引用和可行动的安全替代解释；不要把“检测未命中”展示成“已证明安全”。
- **架构**：把检测器放在模型前并不能阻止模型误解工具返回或把摘要当指令。建议坚持控制面/数据面分离，权限和类型解析前置，风险检测多层化，工具/记忆写入/输出门禁独立存在；不把某个模型、分类器、MIME 规则或 Connector 字段固化为契约。
- **可靠性**：OCR/ASR、视频采样、编码转换、重试、缓存和异步撤回会产生漏检与旧状态竞态。建议记录变换链和覆盖不确定性，解析失败默认收窄/隔离，高风险场景最终复核，污染和撤回沿血缘重跑；不能用 TTL、缓存或历史放行兜底。
- **安全/隐私**：攻击者可通过低对比图像、背景音、单帧字幕、元数据、混淆文本或工具返回间接注入；防御也可能因扫描而读取更多敏感内容。要求检测遵守最小权限和用途，限制解析范围，所有载体不可信，未识别攻击仍不能获得工具/策略能力。
- **数据/质量**：重复命中、多个模态和多个派生物很容易被误当成独立证据；摘要可能去掉恶意上下文，也可能把攻击升级成看似可信规则。建议保留来源/血缘、原始载体类别、变换链、时间/位置和不确定性，分别评估内容风险与行为风险。
- **治理/运营**：误报申诉与安全阻断存在效率和责任张力。建议申诉只进入版本化、可审计的复核流程，不直接放行；规则变更先离线重跑和灰度，撤回/污染事件可追踪到所有派生物，历史审计与当前授权严格分离。

专家团综合建议：采用“所有外部内容不可信、控制面/数据面分离、来源/权限/类型/解析/内容与行为风险/投影/工具/输出纵深防御、检测不等于安全证明、失败默认隔离或收窄、污染和撤回沿血缘传播、解释最小披露、申诉与规则版本化”的方向。先用跨载体、跨模态、跨轮和漏检后果测试验证安全不变量，再选择可替换的规则、模型和 Connector 实现；不以更高召回、较低误报、更多自动执行或更少人工确认交换控制面边界。

### 自动审核与推进

**自动审核：当前方案无明显歧义，已确认通过，继续进入议题 4 的后续评估与治理细化。** 本轮已明确记忆、检索结果、工具返回、文件、图片、音频和视频均为不可信数据，不能成为系统/开发者指令、工具授权、策略变更或安全门禁；已明确检测不等于安全证明，采用来源/权限/类型/解析/内容与行为风险/投影隔离/工具与输出门禁的分层防御；覆盖 Prompt Injection、越权请求、秘密外传、数据投毒、恶意链接/附件、跨模态隐藏指令、对抗样本、编码/混淆、间接注入、重复/跨轮传播；失败或不确定时默认隔离、收窄、引用或阻断；安全解释和审计遵守最小披露；误报申诉、规则版本化、受控重跑、撤回和派生传播边界已明确。未固化具体分类器、阈值、模型、Schema、API、部署实现或 SLA，符合阶段性边界。

| 记忆候选、摘要、embedding、索引、缓存、Manifest、工具结果和跨空间投影的污染判定、血缘闭包、重跑与撤回事件协议 | 依赖议题 4 深化8的一致性/撤回协议、记忆生命周期和治理事件模型；本轮只确认风险和撤回必须沿血缘传播，留待以后讨论 |

| 安全解释、审计、攻击样本取证、敏感原件访问和最小披露的最终字段、留存和访问规则 | 依赖企业审计、隐私、取证和数据生命周期要求；本轮只确认不泄露攻击内容和受限事实，留待以后讨论 |

## 子议题深化 10：召回质量、泄露率、上下文过载率和任务成功率的完整评估体系

### 主题与成功标准

本轮要解决的不是选一个总分，而是建立一套能够回答“召回是否有用、是否适用、是否安全、是否足够、是否造成副作用，以及这些判断在什么主体和策略下成立”的分层评估体系。

阶段性成功标准：

1. **质量、容量、风险、任务结果分层**：至少分别评估召回相关性、适用性、时效性和证据充分性；排序、融合和冲突处理；上下文投影保真与预算；权限泄露、敏感误召回和撤回延迟；Prompt Injection 漏检后的实际后果；上下文过载；任务成功、安全副作用、成本和延迟。
2. **安全硬门禁独立于质量收益**：泄露、越权、秘密外传、危险工具动作和其他高影响安全副作用是独立的阻断条件；任务成功率、用户满意度、召回提升或成本下降不能抵消泄露或越权。
3. **结果可归因、可分桶、可复现**：每项指标都应能够按 Harness、Task/Purpose、风险等级、scope、记忆层/类型、模型和策略版本分桶，记录失败原因、样本量和不确定性；同一输入、授权快照、记忆版本、检索/融合/投影策略和模型版本应可重跑、比较、回滚。
4. **离线到在线形成证据链**：区分离线基准、回放/反事实、在线观测、灰度和人工复核的用途与局限，不能把一种评测结果冒充生产安全或任务收益证明。
5. **评测数据本身可治理**：评测样本、标注、攻击载荷、用户 Trace、受限记忆和派生数据仍受权限、用途、脱敏、删除、保留、血缘和撤回治理；无权看到原文不应通过指标、计数、排序或错误信息间接泄露事实。

本轮只确认评估维度、证据层级和决策边界，不固化最终指标公式、阈值、评测集、Schema、采样率、SLA 或平台 API。

### 头脑风暴

#### 1. 不能把“召回到了”当成“召回正确且可用”

同一条记忆可能语义相关，却不适用于当前 Task/Purpose；可能已经过期、被撤回、缺少证据或与更局部的事实冲突。因此质量评估至少要拆开：

```text
候选是否相关
  → 是否适用于当前主体、Task、Purpose、scope 和时间
  → 是否新鲜、有效、未撤回
  → 是否有足够且可追溯的证据
  → 是否在排序和融合后被正确表达
  → 是否被投影为当前 Harness 真正需要的最小上下文
```

应分别观察“应召回而未召回”“召回但不应使用”“召回正确但排序/融合错误”“融合正确但投影丢失条件或来源”“投影正确但导致任务或安全副作用”的失败链路。单一端到端成功标签无法替代这些中间证据。

#### 2. 质量评估应有正例、负例和反事实

评测不能只收集被系统召回的内容。需要同时包含：

- 当前 Task 明确需要的记忆，以及相关但不适用、过期、冲突、已撤回和无证据的记忆；
- 授权范围内的可用内容、相邻 scope 的受限内容、敏感内容和不存在/未知内容；
- 同一任务在不同策略、排序、融合、投影和预算下的可比较运行；
- “不召回更安全”“召回后收窄”“只给来源/引用”“召回完整证据”等可比较的反事实路径；
- 任务成功但引入安全副作用、任务失败但没有安全问题、质量下降但正确拒绝的样本。

反事实结果是评估决策影响的证据，不是把未真实发生的运行当成事实；必须标注假设、不可观测部分和适用范围。

#### 3. 四类边界要分别看待

```text
质量：是否找对、排对、融对、投影对
容量：是否超载、丢失重点、增加不必要的上下文
安全：是否越权、泄露、误用、撤回后仍可见，漏检后是否造成后果
任务：在安全边界内是否完成目的，并付出多少成本和延迟
```

任务成功率是末端结果，不可替代召回和安全证据；上下文长度不是上下文质量，压缩不是保真；低泄露计数也不能在受限样本缺失、低覆盖或错误采样时被解释为安全。

#### 4. “过载”要观测行为而非只看 token

上下文过载可能表现为关键约束被忽略、冲突被混淆、响应延迟/成本上升、模型引用错误、工具参数偏离、需要重复澄清或任务失败。应结合预算使用、有效信息密度、关键约束保留、模型/任务行为和人类复核判断；不能只用上下文长度或窗口占用作为过载结论。

#### 5. “漏检”必须追踪到后果

对于 Prompt Injection 或恶意记忆，评估不应止于检测器是否命中。至少要串联：

```text
内容是否被检测
  → 是否进入了不可信数据投影
  → 是否影响了模型计划或记忆写入
  → 是否越过工具/输出/权限门禁
  → 是否造成秘密暴露、跨 scope 传播、危险动作或不可逆影响
  → 是否及时隔离、撤回、告警和恢复
```

漏检但被独立门禁拦截，与漏检并造成实际泄露，属于不同严重度和不同处置证据；不能用一个“攻击检测率”掩盖后果差异。

#### 6. 人工标注不是无条件真值

召回适用性、证据充分性、冲突解释、任务是否真正完成和安全副作用有时需要领域人员或有权操作者复核。应保留标注依据、角色/Purpose、分歧和复核结果，区分观测事实、标注判断和推断；对无权评测者进行脱敏或最小化展示，避免通过评测流程扩大记忆访问范围。

### 综合结论与建议

#### 1. 采用分层评估树，而不是单一总分

建议把一次评估组织为可追溯的分层证据树：

```text
Run / Harness / Task / Purpose / risk / scope / versions
  ├── Retrieval quality
  │   ├── relevance
  │   ├── applicability
  │   ├── freshness / validity
  │   └── evidence / provenance sufficiency
  ├── Ranking & fusion
  │   ├── ordering utility
  │   ├── duplicate / conflict handling
  │   ├── exception and condition preservation
  │   └── source and uncertainty preservation
  ├── Projection & budget
  │   ├── constraint / fact / evidence fidelity
  │   ├── authorization and scope fidelity
  │   ├── budget behavior and overload signals
  │   └── omitted-content / expandability behavior
  ├── Security & governance
  │   ├── unauthorized recall / use / projection
  │   ├── sensitive false recall / cross-scope leakage
  │   ├── revocation and deletion propagation delay
  │   ├── missed-injection consequence
  │   └── audit / reproduction / containment
  └── Task outcome
      ├── task success and correctness
      ├── safety side effects
      ├── cost and latency
      └── human correction / escalation burden
```

各层可以有多个指标和证据，不要求压缩成同一量纲。若需要向不同受众汇总，只能展示保留分层、风险硬门禁和样本/不确定性说明的摘要，不能让总分掩盖严重失败。

#### 2. 明确每一层的评估问题

| 层次 | 要回答的问题 | 失败原因至少要能区分 |
|---|---|---|
| 召回 | 找到的内容是否与当前目的相关、适用、有效且有证据 | 未召回、误召回、过期/撤回、scope/Purpose 不适配、证据不足、解析/索引缺陷 |
| 排序/融合 | 重要内容是否优先，重复/冲突/例外是否正确表达 | 排序倒置、重复膨胀、冲突丢失、条件丢失、来源/不确定性丢失 |
| 投影/预算 | Harness 看到的内容是否保留必要含义、权限和来源，并控制负担 | 截断、压缩失真、条件/来源丢失、预算策略错误、不可展开、过载 |
| 安全 | 不允许的内容是否被召回/使用/传播，撤回是否生效，漏检是否造成后果 | 未授权召回、敏感误召回、跨 scope 泄露、撤回滞后、注入影响、门禁失败 |
| 任务 | 在安全边界内是否完成目的，代价和副作用如何 | 事实错误、工具/输出副作用、人工纠正、重试、成本、延迟、拒绝不当 |

“未知”“未观测”“无法标注”不应静默算作通过；应作为不确定性或评测覆盖限制记录。

#### 3. 采用五类互补评测面

1. **离线基准**：在版本化、脱敏、权限可控的样本上比较召回、排序、融合、投影和安全规则。适合回归和候选策略筛选，但不代表真实在线行为、授权变化或任务价值。
2. **回放/反事实**：基于受控 Run Snapshot、真实 Trace 的最小化副本或合成对照，重放不同模型、策略、预算、授权和记忆版本，比较“如果不召回/收窄/换排序/换投影”的结果。必须显式记录反事实假设，不能把模型评审或离线推断当成实际用户结果。
3. **在线观测**：在正常流量中观测实际召回、拒绝、投影、用户修正、工具动作、泄露信号、延迟和成本，并保留授权与策略版本。在线观测应尽量最小化原文，异常样本进入受控复核而非默认扩大读取。
4. **灰度**：对新模型、检索/融合/投影策略或安全规则进行受控对照，先验证回归、分桶差异、硬门禁和撤回行为，再逐步扩大范围。灰度不是降低安全要求的试验区；发现硬门禁失败应暂停或回滚，而不是以平均任务收益掩盖。
5. **人工复核**：由具备相应 scope 和 Purpose 的人员复核适用性、证据、冲突、敏感性、任务正确性和安全副作用，并记录依据、分歧、置信度/不确定性和复核版本。人工复核本身要受最小权限、脱敏、访问审计和删除/撤回规则约束。

五类评测面应互相校验：离线结果发现回归，回放解释策略变化，在线观测发现分布漂移，灰度验证真实影响，人工复核校准标签和失败原因；任何一类都不能独立宣称全局安全或全局质量。

#### 4. 评估数据与证据必须沿治理链管理

评测数据至少应保留其来源、授权主体、Purpose、scope、敏感性、脱敏状态、记忆/Trace 版本、变换链、标注角色、删除/撤回状态和允许的评测用途。应支持：

- 只让评测者看到完成判断所需的最小字段、引用或脱敏版本；
- 原始敏感样本、攻击载荷、用户 Trace 和人工批注分离保存、按权限访问；
- 评测集、标签和派生 embedding/摘要/索引具有可追溯血缘，源数据撤回或删除时能定位并处置派生物；
- 受限样本不因召回计数、排序位置、错误消息、统计切片或对照结果被间接披露；
- 评测集版本、标注变更、数据许可、去重、污染、覆盖缺口和已知偏差可复核；
- 历史结果可以保留用于审计和回归，但不使已撤回数据继续进入新的生产评估或授权链路。

#### 5. 安全硬门禁与质量收益分离

建议把决策分成至少两条通道：

```text
Safety gate
  → 发现泄露、越权、危险副作用、撤回失效或漏检造成高影响后果
  → 隔离、阻断、暂停灰度、回滚或进入事件处置

Quality / efficiency evidence
  → 比较相关性、适用性、时效、证据、投影、任务收益、成本和延迟
  → 仅在安全门禁通过的候选中选择或继续校准
```

安全门禁可以进一步按风险、scope、Purpose 和动作影响分层，但不应将“任务完成”“用户未投诉”“模型置信度高”“平均泄露很低”用来抵消一个已确认的越权或泄露。安全样本不足、漏报未观测或无法证明撤回生效时，应标记为评估不足或保守处置，而不是通过平均值放行。

#### 6. 统一记录上下文与失败原因

每个运行或评测事件至少应能关联以下维度，而不预设字段 Schema：

```text
Harness
Task / Purpose
risk category / severity context
subject and scope decision
memory layer / memory type
model / retrieval-fusion-projection strategy version
memory, manifest, authorization and policy versions
input / candidate / projected-context / action lineage
outcome, failure reason, sample count and uncertainty
```

失败原因应从链路中定位，例如：授权拒绝、scope 不匹配、召回遗漏、过期、证据不足、排序错误、冲突融合错误、条件/来源丢失、预算压缩失真、上下文过载、敏感误召回、撤回传播滞后、注入漏检、工具门禁阻断、工具副作用、任务事实错误、人工纠正、成本/延迟超出运行约束或观测缺失。清单是分类方向，不是最终枚举；未知原因和多重原因应可记录。

置信区间、误差范围或其他不确定性表达应随指标和样本量报告，不能只公布点估计；样本量只作为当前结论的证据背景，不在本轮固化统计方法、最小样本数或阈值。分桶后仍要防止小样本、重复样本、权限不均衡和选择偏差造成虚假比较。

#### 7. 回归、版本化、灰度和回滚形成闭环

任何模型、embedding、解析器、索引、排序/融合、投影预算、权限策略、Prompt/工具门禁、记忆版本或评测标签变化，都应能够：

```text
冻结输入与授权/策略快照
  → 用版本化评测资产重跑
  → 比较分层质量、安全、过载、任务、成本和延迟证据
  → 按 Harness / Task / Purpose / risk / scope 分桶检查回归
  → 受控灰度并继续在线观测与人工复核
  → 发现硬门禁失败时暂停/回滚，保存历史决定
  → 记录影响范围、修复、重跑和最终处置
```

回滚恢复的是受控运行版本，不应删除历史 Run Snapshot、覆盖审计、恢复已撤回记忆或绕过当前授权。新规则的“平均质量提升”不能掩盖某个高风险 scope、某类敏感记忆或某个 Harness 的严重回归。

#### 8. 暂定报告形态而非最终 Schema

建议面向工程、治理和产品分别提供：

- **质量视图**：召回、排序/融合、投影保真、适用性、时效、证据和过载信号，带分桶与不确定性；
- **安全视图**：未授权召回/使用/传播、敏感误召回、撤回延迟、注入漏检后果、工具/输出门禁和处置状态；
- **任务视图**：安全门禁通过后的任务正确性、人工纠正、成本、延迟和升级；
- **回归视图**：版本差异、灰度分布、失败原因变化、受影响 scope、回滚/重跑状态和数据覆盖限制。

这些是报告语义和阅读边界，不是最终数据库表、事件 Schema、指标 API 或控制台设计。

### 专家团挑战

- **产品/UX**：单一总分最容易被理解，但会把“任务完成”误读为“记忆安全且正确”。建议对外展示分层证据和安全状态，优先解释阻断原因、适用范围、来源和下一步；不要用排行榜掩盖高风险小分桶。
- **检索/数据质量**：相关性、适用性、时效和证据经常被一个相关性标签混合，公开 benchmark 也未必表示企业记忆语义。建议采用任务和 Purpose 绑定的判断，显式标注过期、冲突、撤回、条件和证据缺失，保留标注分歧。
- **安全/隐私**：为评估泄露而集中收集原始秘密，可能制造新的泄露面；用平均泄露率也可能隐藏稀有但严重的越权。要求评测数据最小权限、脱敏和血缘治理，安全硬门禁按风险/主体/scope 单独观察，不能用任务成功抵消泄露。
- **架构/平台**：离线结果容易因模型、索引、缓存、授权和策略版本不一致而无法复现。要求冻结 Run Snapshot 和版本链，回放涵盖授权变化、撤回、缓存/派生物和投影，而不是只重跑向量检索。
- **可靠性/运营**：在线指标会受分布漂移、重试、异常流量和人工介入影响；反事实可能把未发生的任务结果当作事实。建议区分观测、推断和人工判断，记录覆盖、样本量、不确定性、失败原因和灰度边界，故障时保守收窄并支持回滚。
- **安全评估/红队**：Prompt Injection 检测命中不等于系统安全，漏检后若工具/输出门禁仍有效，后果应与真实外传分开报告。要求评测完整的影响链，关注未识别攻击是否仍能改变权限、工具、记忆写入或跨空间传播。
- **治理/审计**：历史评测资产可能包含已撤回、删除或不再授权的数据。要求评估集和派生标签继承删除/撤回/用途约束；保留审计证据不等于继续保留可读取的原文，也不等于恢复当前生产使用权。

专家团综合建议：采用“分层指标与证据树、质量与安全双通道、离线/回放/在线/灰度/人工互证、按主体与风险分桶、失败原因和不确定性可见、评估数据同样受治理、版本化可重跑并支持回滚”的方向。先建立安全不变量和可复现证据链，再用真实任务和受控样本校准指标；不以单一总分、公开 benchmark 分数、平均任务成功率或低观测泄露率作最终放行理由。
