# 议题 9：企业级权限与治理

**状态：已确认（第 1、2、3 轮阶段性方案；当前独立讨论点已完成）**

## 问题定义

> 如何定义 User、Team、Project、Agent、Harness、MemorySpace、记忆、知识、工具、Run 和企业资源之间的读取、使用、写入、审核、发布、撤回与执行边界，并在高风险操作、权限变化和跨边界使用时保持最小权限、职责分离和可审计？

## 第 1 轮确认：主体—资源—动作授权与高风险治理门禁

本轮确认：

> **企业级权限治理采用“主体—资源—动作—用途—作用域—条件—风险—当前状态”的授权模型，授权决策与实际执行分离。读取、检索、引用、投影、写入、审核、发布、撤回、影响分析、审批和执行必须分别授权；能读不等于能使用，能使用不等于能写入，能发布不等于能执行。实际允许范围取当前主体权限、资源 ACL、MemorySpace 策略、来源血缘 ACL、用途策略、敏感性/脱敏策略、Harness Capability、Tool Policy、RunGate 和资产当前状态的交集，任一硬门禁失败时默认拒绝、隔离或进入审核。Agent、Harness 和 Governance Agent 不能自我授权、批准自己的高风险操作或代替人类承担高风险审批；高风险动作必须经过影响预览、风险分类、独立审批、RunGate、执行、验证和审计，并区分 proposer、approver、executor、verifier。权限必须具备生命周期、过期、撤回、暂停和传播机制；权限变化应阻断新检索和执行、重新解析 Manifest、重新评估派生数据和 pending Run，但不静默改写历史 Run。break-glass 只能限时、限范围并要求事后复核。**


归属、创建者、生产者、参与者、审核者、发布者、消费者、执行者、受益者和事故责任人分开建模，不能因为 Agent 产生了记忆就自动成为唯一 Owner。

### 5. 主体职责边界

| 主体 | 默认可做 | 默认不可做 |
|---|---|---|
| User | 读取被授权内容、提交反馈、发起请求 | 绕过 Project/Team/安全策略 |
| Team Owner | 管理 Team 范围资产、审核团队知识 | 修改其他 Team 或全局策略 |
| Project Owner | 管理 Project 范围资产、批准 Project 变化 | 自动扩大跨 Project 权限 |
| Agent | 按授权读取、生成候选、执行被允许动作 | 自我授权、自审自批、修改 ACL |
| Harness | 使用被投影上下文、调用允许工具 | 代替用户授予权限 |
| Governance Agent | 检测、分类、生成候选、传播状态 | 代替人类批准高风险变化 |
| Security/Privacy | 审核敏感、跨边界和高风险事项 | 无业务范围地任意修改内容 |
| Auditor | 查看授权范围内审计记录 | 修改业务资产或批准执行 |
| Platform Admin | 管理平台配置和基础设施 | 默认读取所有业务内容或代替业务 Owner |

### 6. Harness 与 Agent 边界

Harness Capability 仅代表外部执行能力，不代表当前授权：

```text
当前主体权限
∩ Harness Capability
∩ Project / Resource Policy
∩ Purpose Policy
∩ Tool Policy
∩ RunGate
```

Agent 只能使用当前授权上下文，不能把记忆文本当作权限，不能通过自然语言改变 ACL，不能批准自己的高风险 Action Proposal，也不能将候选直接变为 Published 或 Actionable。Governance Agent 可以检测、分类和生成治理候选，但不能代替人类批准高风险权限、敏感性、跨空间和生产操作。

### 7. 高风险操作门禁与职责分离

高风险操作包括生产部署、数据库写入、不可逆变更、权限修改、凭据使用、客户数据访问、跨租户访问、发布可执行 Skill、恢复敏感资产和扩大跨 Project 共享。

流程为：

```text
Action Proposal
  → 明确目的
  → 影响预览
  → 风险分类
  → 当前授权检查
  → Tool Policy
  → 独立审批
  → RunGate
  → 执行
  → 验证
  → 审计
```

高风险场景至少区分：

```text
proposer
approver
executor
verifier
```

默认禁止同一主体同时提议并审批、审批并执行或执行并完成最终验证。`break_glass` 只能限时、限范围、记录理由并要求事后复核，不能变成永久授权。


状态包括：

```text

```

```text
→ 失效相关 Projection / Index / Embedding
→ 重新评估派生资产
→ 保留历史 Run 审计
```

历史 Run 不被静默改写；正在运行的高风险 Run 可以暂停或要求重新授权。

第一版优先实现：

1. 统一授权请求和决策结构；
2. Subject、Resource、Action、Purpose、Scope 建模；
3. 读取、检索、引用、投影、写入、审核、发布、撤回、执行分离；

7. proposer / approver / executor / verifier 职责分离；
8. 权限过期、撤回、暂停和传播；
9. Agent 不自我授权；
10. Governance Agent 不代替高风险人类审批；
11. break-glass 限时、限范围、事后复核；
12. 全量授权与执行审计。

## 第 2 轮确认：权限继承、委托、冲突与策略组合

本轮确认：

> **权限继承、委托和策略组合必须分开建模。组织关系、资源关系、权限关系和 Harness/Agent 能力不是同一种语义；`member_of`、`owns`、`participates_in`、`acts_for`、`delegates_to` 不应自动等价为全部资源权限。权限继承按动作白名单控制，默认只继承明确允许的低风险动作；发布、撤回、导出、审批、执行、生产操作、敏感数据访问和跨空间动作不因组织或 Owner 关系自动继承。策略组合采用“硬拒绝优先、下级只能进一步收紧、未知或冲突默认拒绝/隔离/待审核”的原则。委托必须绑定主体、资源范围、动作、用途、条件、有效期、最大风险、是否允许再委托和撤回记录，并满足委托者有效权限的子集约束；Agent 和 Harness 不能透传用户全部权限，也不能无限再委托。所有代理操作必须同时记录原始用户、委托 Agent、执行 Harness、审批者和验证者。权限变化需要重新评估 Agent 委托、Harness Projection、Context Manifest、派生资产、Action Proposal、Run Plan 和 pending Run；历史 Run 保留原授权上下文，不静默改写。**

### 1. 关系、权限和能力分离

组织关系、资源关系、权限关系和执行能力分别建模：

```text
关系：member_of / owns / participates_in / acts_for / delegates_to / references / affects
权限：can_read / can_retrieve / can_reference / can_project / can_write / can_review / can_publish / can_revoke / can_execute
能力：harness_can_read / harness_can_write_workspace / harness_can_modify_repository / harness_can_run_tests / harness_can_access_database / harness_can_deploy
```

例如：

```text
member_of Team ≠ can_read_all_team_memory
acts_for User ≠ can_execute_all_user_actions
harness_can_deploy ≠ current_run_can_deploy
```

### 2. 继承按动作白名单控制

每个权限关系至少区分：

```text
inheritable_actions
non_inheritable_actions
approval_required_actions
delegable_actions
```

Team 成员或 Project Owner 可以按范围继承低风险读取、引用或管理动作，但 `publish`、`revoke`、`export`、`execute`、`approve_action`、生产变更、敏感数据访问和跨空间动作不因成员或 Owner 关系自动继承。

### 3. 收紧优先的策略组合

建议决策顺序：

```text
租户隔离 / 安全禁令
  → 法规与敏感性限制
  → 来源 ACL 与血缘限制
  → Organization Policy
  → Team Policy
  → Project Policy
  → Resource ACL
  → Purpose Policy
  → Harness Capability
  → Tool Policy
  → RunGate
  → 时间和条件检查
```

上游硬拒绝不能被下游允许解除；下游可以进一步收紧；`unknown` 不转换成允许；过期、撤回和冲突优先阻断；只有所有必要条件满足才返回 `allow`。

### 4. 受限委托与委托链

```text
Delegation
├── delegator
├── delegate
├── resource_scope
├── allowed_actions
├── purpose
├── conditions
├── start_at
├── expires_at
├── max_risk
├── allow_subdelegation
├── revocable
├── approval_refs
└── audit_refs
```

约束为：

```text
delegate_effective_permission
⊆
delegator_effective_permission
```

并且：

```text
委托动作
⊆
委托者已拥有动作
∩ Agent / Harness Capability
∩ Tool Policy
∩ RunGate
```

默认禁止无限委托和自动再委托；跨 Project、高风险和生产权限不得自动再委托。委托链需要记录谁授予了什么、授予给谁、目的、时间、过期、撤回和审批。

### 5. 代理责任链

代理操作必须记录：

```text
initiated_by_user
delegated_to_agent
executed_by_harness
approved_by
verified_by
```

不能只记录 `actor = Agent`。权限变化时重新评估 Agent 委托、Harness Projection、Context Manifest、派生资产、Action Proposal、Run Plan 和 pending Run。

### 6. 冲突与未知状态

| 状态 | 处理 |
|---|---|
| 明确硬拒绝与允许冲突 | 拒绝 |
| 上级禁止、下级允许 | 拒绝 |
| 资源 ACL 禁止、Project 允许 | 拒绝 |
| 来源 ACL 缺失 | 隔离 |
| 目的不明 | 拒绝 |
| 授权过期 | 拒绝 |
| 撤回状态不明 | 阻断 |
| 允许范围和委托范围冲突 | 取交集 |
| 高风险审批主体不明 | 待审核或拒绝 |
| 策略版本不一致 | 使用当前权威策略重新判断 |

不能由最后写入策略、Owner 级别、模型置信度、历史成功率或关系数量自动解决硬冲突。

### 7. 第一版优先能力

第一版优先实现：

1. 组织关系、资源关系、权限关系和能力关系分离；
2. Team、Project、User、Agent、Harness、MemorySpace 的关系类型；
3. 动作级继承白名单；
4. 受限委托对象；
5. 委托深度和禁止再委托；
6. 硬拒绝优先、下级只能收紧的策略组合；
7. 冲突、未知、过期和撤回的默认处理；
8. 授权链和委托链审计；
9. 权限变化对 Manifest、Projection、Index 和 pending Run 的传播；
10. 可解释授权决策；
11. 高风险动作独立审批；
12. 权限子集约束和当前上下文重新授权。


## 第 3 轮确认：高风险审批、Break-Glass、审计与紧急撤回

本轮确认：

> **高风险操作采用“Action Proposal → 版本化 Run Plan → 风险分类与影响预览 → 当前授权和策略检查 → 独立审批 → RunGate → 执行 → 执行差异记录 → 验证 → 决策/执行/影响审计 → 事后复核”的闭环。审批必须绑定具体资源、作用域、用途、revision、环境、Tool Call 集合、前置条件、验证、回滚、风险等级和有效期；目标资源、参数、revision、环境、权限、影响范围、风险或回滚方案发生关键变化时，原审批自动失效，必须重新生成计划和审批。高风险职责至少区分 proposer、approver、executor、verifier。Break-Glass 只用于绑定 Incident 的限时、限范围紧急止损或最小恢复，不得修改长期 ACL、扩大普通权限、发布新 Skill、扩大跨空间范围或删除审计，且必须强制事后复核。紧急撤回采用“同步阻断新 retrieval/projection/action 和 pending Run，再异步完成影响闭包、派生资产失效、通知、恢复/收窄/替代/撤回和复盘”的两阶段流程。审批、执行和影响状态分离，审计不可静默修改；高风险策略或审计系统不可用时默认阻断。**

### 1. 高风险操作分类

任一以下条件触发高风险流程：不可逆、生产环境、客户数据、权限或身份变更、凭据使用、跨租户或跨 Project、数据库写入、部署或发布、安全策略修改、敏感资产恢复、可执行 Skill 发布、大范围知识撤回或高影响 RCA 关闭。

第一版可使用 R0–R3 作为原则性分级：

```text
R0 只读、可逆、低影响
R1 受限工作区变更
R2 受控资源变更
R3 高影响或不可逆操作
```

R0 可按策略自动允许并审计；R1 需要明确授权、Tool Policy 和必要 RunGate；R2 需要独立审批、影响预览、验证和回滚；R3 必须人工或专门治理审批，不能仅凭策略自动放行。

### 2. 审批绑定不可变计划版本

审批必须绑定：

```text
proposal_id / version
run_plan_id / version
resource_scope
target_revision
environment
tool_call_set
purpose
risk_level
preconditions
verification_plan
rollback_plan
expires_at
```

以下变化会使审批失效：

```text
目标资源变化
revision 变化
工具参数变化
影响范围扩大
环境变化
风险升级
权限变化
来源撤回
回滚方案变化
```

审批失效后：

```text
RunGate = blocked
→ 重新生成 Plan
→ 重新审批
```

### 3. RunGate 独立复核

RunGate 执行前重新验证：

```text
当前主体和委托链
当前资源和作用域
当前用途
当前环境与 revision
当前资产和血缘状态
当前权限和敏感性
当前策略版本
审批状态和有效期
风险等级
前置条件
```

RunGate 不由 Knowledge Asset、Agent 或普通业务代码直接绕过。高风险策略或审计系统不可用时默认阻断。

### 4. Break-Glass 边界

`break_glass` 只允许绑定 Incident 的临时止损或最小恢复动作，例如：

```text
立即阻断新 retrieval
立即阻断新 action
暂停 pending Run
撤回明显泄露的派生投影
执行最小必要止损动作
```

不得直接：

```text
修改长期 ACL
扩大普通权限
发布新 Skill
扩大跨空间范围
删除审计记录
绕过所有验证
```

每次 Break-Glass 至少记录：

```text
incident_id
requester
reason
resource_scope
allowed_actions
max_risk
start_at
expires_at
approver_or_emergency_authority
post_review_required
```

必须限制资源、动作和有效期，禁止自动再委托，强制事后复核，不得转化为永久授权。

### 5. 紧急撤回两阶段流程

同步阻断：

```text
Source / Policy / Permission revoked
  → 权威状态立即变更
  → 阻断新 retrieval
  → 阻断新 projection
  → 阻断新 action
  → 暂停 pending Run
```

异步治理：

```text
影响闭包分析
  → 失效 Index / Embedding / Manifest
  → 评估 Knowledge Asset
  → 处理已发布投影
  → 通知 Owner / Security / Operations
  → 决定恢复、收窄、替代或撤回
  → 完成审计和复盘
```

失效优先，恢复谨慎。已完成历史 Run 保留原授权上下文和审计。

### 6. 三类审计与状态分离

决策审计记录请求主体、用途、资源、策略版本、授权结果、理由、审批和义务；执行审计记录计划、实际 Tool Call、计划外差异、结果、验证、回滚和残余风险；影响审计记录受影响资产、Run、Manifest、Project、阻断、撤回和传播状态。

审批状态与执行状态分离：

```text
审批：requested / under_review / approved / rejected / expired / revoked / superseded
执行：queued / gated / running / partially_executed / succeeded / failed / rolled_back / cancelled / blocked
```

审计记录不可由业务主体静默修改；敏感内容按最小必要原则记录和脱敏。

## 子议题深化1第1轮：R0–R3 的完整操作分类目录和阈值

### 主题与成功标准

本轮处理议题9第一个明确暂缓项。目标是把原则性 R0–R3 风险等级映射到可审计的动作属性、升级条件和最低门禁；不把示例分类当作跨企业永久阈值，也不以一个总分抵消硬风险。

成功标准：

1. 覆盖读取、检索、引用、投影、写入、审核、发布、撤回、导出、影响分析、审批和执行等动作；
2. 区分资产/数据影响、权限影响、执行副作用、范围和可逆性；
3. 明确“任一高风险属性触发升级”与硬拒绝优先；
4. 为 R0–R3 指定最低授权、审批、RunGate、验证、回滚和审计要求；
5. 处理组合动作、计划变更、环境变化、敏感/跨租户和不确定信息；
6. 未知或无法证明时不降级为低风险。

### 阶段1：头脑风暴

#### 1. 风险不是操作名称，而是动作实例属性

同一个 `read` 可能是 R0（当前 Project 的低敏摘要）或 R3（跨租户生产客户数据）；同一个 `publish` 可能是 R1（非敏感内部参考）或 R3（可执行 Skill/生产策略）。因此每次决策至少评估：

```text
action / object / data sensitivity / source ACL
purpose / subject / delegation / scope
cross-tenant or cross-space
production / customer / credential impact
reversibility / blast radius / duration
revision / environment / tool capability
approval / rollback / verification / current state
```

#### 2. 建议风险触发器

任一条件都可使动作至少升级到 R2，多个条件或不可逆/高影响可升级到 R3：

```text
production or customer data
credential use or identity/permission change
cross-tenant / cross-project / external export
irreversible deletion or migration
write to database/config/code/deployment
security/privacy/compliance policy change
execution or executable Skill/Run Plan
wide blast radius or unknown impact
source/lineage/sensitivity/rollback unknown
```

影响低不代表动作低风险；只读高敏数据和使用凭据仍可能是 R3。

#### 3. R0–R3 原则目录

```text
R0 低风险观察
  已授权低敏读取、关系摘要、只读健康检查、离线候选计算；
  无副作用、范围已知、可审计、当前 ACL/用途通过。

R1 受限可逆动作
  受限工作区草稿、非生产可逆配置/文档更新、低风险投影或灰度；
  明确用户授权、ToolPolicy、范围/版本绑定、结果记录和基本验证。

R2 受控资源变更
  受控环境写入、有限生产配置、低范围数据库/服务变更、脱敏导出、撤回/恢复候选；
  影响预览、独立审批、版本化计划、RunGate、回滚和执行后验证。

R3 高影响/不可逆动作
  生产大范围部署/迁移、客户/凭据/跨租户原文访问、权限/身份变更、不可逆删除、
  安全策略变更、可执行 Skill 发布、高影响撤回/恢复/风险接受；
  专门人工/治理审批、职责分离、强审计、实时差异、止损/回滚和事后复核。
```

#### 4. 读/写/治理动作最低矩阵

| 动作实例 | 默认级别 | 可降级条件 | 必须升级条件 |
|---|---|---|---|
| 低敏当前范围读取/检索 | R0 | 范围、用途、ACL 和敏感已知 | 跨边界、客户/生产/凭据或存在性敏感 |
| 受限摘要/投影/低风险灰度 | R0–R1 | 非敏感、可逆、无权限扩大 | 默认消费者变化、跨空间或高影响任务 |
| 草稿写入/候选生成 | R1 | 非生产、可回滚、无外部副作用 | 修改代码/配置/数据或影响共享消费者 |
| 审核/发布参考资产 | R1–R2 | 非敏感、范围不扩大、独立审核 | 可执行、生产 RCA/Skill、跨空间或敏感 |
| 受控生产/数据库/配置变更 | R2 | 范围小、可回滚、影响明确 | 不可逆、客户/权限/凭据、广泛影响 |
| 脱敏跨空间导出/影响分析 | R2 | 双边授权、脱敏验证、限时接收 | 原文、高敏、跨租户、可执行或外部副作用 |
| 权限/身份/安全策略变更 | R3 | 仅在经专门治理定义的低风险局部操作 | 任何扩大权限、跨边界或身份信任变更 |
| 不可逆删除/迁移/高影响恢复 | R3 | 不应自动降级 | 任一不可逆、保全/撤回冲突或影响未知 |

#### 5. 组合和未知规则

组合动作取最高风险并可进一步升级：例如“读取敏感源 → 生成跨空间摘要 → 发布 Skill → 运行工具”不能拆成四个 R0 规避 R3。任何源 ACL、用途、敏感性、范围、revision、环境、回滚或影响闭包未知时，最低为 `review/blocked`，不得默认 R0。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-53 Rev.5**：提供访问控制、审计、配置、事件响应、风险评估和系统完整性控制族，可借鉴按控制目标和动作上下文分层，而非仅按角色放行。它不规定本平台 R0–R3 命名或阈值。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-20）。
2. **Google SRE**：错误预算、渐进发布、回滚和过载保护可借鉴“风险与影响绑定操作强度”；SRE 不替代权限、隐私、跨租户和凭据治理。来源：<https://sre.google/sre-book/service-level-objectives/>（访问日期：2026-09-20）。
3. **议题9既有第3轮结论**：已规定 R0–R3 原则等级和高风险闭环，本轮补充动作目录、升级属性和组合规则，不改变职责分离与 RunGate 边界。
4. **议题7/8结论**：撤回、导出、灰度、影响分析和自进化都必须按当前权限、敏感、血缘、可逆性和消费者状态重新判定；本轮将其纳入共同风险分类。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **R0–R3 是按动作实例计算的原则风险层，不是角色固有等级或单一总分。R0 覆盖已授权低敏、只读、无副作用且范围明确的观察；R1 覆盖受限环境内可逆、低影响、无权限扩大动作；R2 覆盖受控资源/有限生产变更、脱敏跨空间导出、影响分析和需要独立审批、版本化计划、RunGate、回滚与验证的动作；R3 覆盖生产大范围、客户/凭据/跨租户原文、权限/身份/安全策略、不可逆删除/迁移、可执行 Skill、以及高影响撤回/恢复/风险接受，必须专门人工/治理审批和职责分离。任一不可逆、生产、客户/凭据、权限、跨租户、敏感、可执行或影响未知属性触发升级；组合动作取最高风险，未知不降级。R0 可按策略自动审计，R1 需明确授权与 ToolPolicy，R2 需独立审批/RunGate/回滚/验证，R3 禁止仅凭策略自动放行。**

#### 风险判定链路

```text
action instance
  → resolve subject/delegation/purpose/resource/scope
  → classify sensitivity, environment, customer/credential and tenant boundary
  → evaluate blast radius, reversibility, current state and lineage
  → apply hard triggers and highest-risk composition
  → assign R0–R3 or review/blocked
  → impact preview + plan/approval requirements
  → current RunGate and ToolPolicy check
  → execute, verify, audit and post-review
```

#### 失效与升级条件

审批/RunGate 自动失效并重新分类的条件包括：资源、参数、revision、环境、主体/委托、用途、敏感性、范围、风险、回滚方案、来源/血缘状态或实际影响发生关键变化。执行过程中发现计划外差异、影响扩大、权限撤回、审计不可用或安全异常时立即暂停/阻断并进入事后治理。

## 子议题深化2第1轮：多级审批、审批替代和组织假期代理

### 主题与成功标准

本轮处理议题9第二个明确暂缓项。目标是定义多级审批、同级替代、值班/假期代理和跨组织责任如何在不降低风险门槛、不形成无限委托和不允许自批的前提下运作；不冻结企业组织结构、法定签署规则或具体身份系统。

成功标准：

1. 区分审批级别、审批条件、审批人资格、替代关系和执行者；
2. 审批替代只能在原授权子集、有效期、范围和风险上限内运行；
3. 高风险审批保持职责分离，禁止 proposer/approver/executor/verifier 无条件重合；
4. 假期/值班代理可审查但不能扩大权限或改变风险等级；
5. 委托、替代、拒绝、超时、撤回和冲突都留下不可变审计；
6. 身份/组织系统不可用、审批链不完整或责任归属不明时默认阻断。

### 阶段1：头脑风暴

#### 1. 多级审批不是简单“多人点同意”

审批链应由动作风险、资源敏感性、范围、环境、变更可逆性、组织责任和合规义务决定。示例：

```text
R0 低风险：策略允许的自动记录或单级确认
R1 受限：资源 Owner 或职责 Owner 确认
R2 受控：资源/业务 Owner + 独立风险/安全或变更审批
R3 高影响：专门治理/安全/合规责任 + 业务责任，必要时双人或多方批准
```

“增加审批人数”不能替代审批者资格、独立性、计划绑定、RunGate 和执行后验证。

#### 2. 审批资格与替代资格分开

审批者资格至少检查：

```text
subject identity and assurance
role/authority for action and resource
purpose and scope
risk ceiling
independence from proposer/executor
current validity / delegation chain
conflict-of-interest status
training or certification where required
```

替代者不是天然拥有被替代者全部权限，只能在明确的 action/resource/purpose/risk/time 子集内作决定。替代关系不能再无限转委托。

#### 3. 替代、代理与应急权限

- **Named substitute**：明确指定、限时、限范围的同职责替代；
- **On-call delegate**：值班轮值中的预先授权成员，按班次和风险上限生效；
- **Break-Glass approver**：只绑定 Incident 的临时最小止损审批，需事后复核；
- **Quorum fallback**：多方中有人不可达时，按预设最低法定人数和不得降低的角色约束处理。

任何 fallback 都不能把 R3 降成 R1、把双人要求变成自批，也不能批准比委托者更广的范围。

#### 4. 超时不是批准

审批超时应按风险和策略进入 `expired/escalated/blocked`；只能在预授权、低风险、可逆范围内自动升级到下一合资格代理，不能用沉默、默认同意或最后一个审批者自动放行高风险动作。

#### 5. 冲突与多组织责任

跨 Project/租户、供应商或客户边界的审批需要明确源/目标责任。一个人同时是资源 Owner、Incident Commander、Security Reviewer 或执行者时，需要检查利益冲突和职责分离；组织关系和参与过任务不能自动产生审批权。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-53 Rev.5**：包含职责分离、最小权限、访问控制、审计和应急访问等控制思想，可借鉴审批资格、代理边界和不可抵赖记录；不定义本平台多级审批状态机。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-20）。
2. **NIST SP 800-63C**：讨论联邦身份和断言传递，可借鉴代理/联邦身份不能隐式扩大被传递的权限，身份上下文和受众必须明确；不替代企业审批责任矩阵。来源：<https://pages.nist.gov/800-63-4/sp800-63c.html>（访问日期：2026-09-20）。
3. **议题9既有结论**：已确认 proposer、approver、executor、verifier 分离，委托是原权限子集，Break-Glass 限时限域并强制事后复核；本轮将其细化到多级与假期代理。
4. **议题7/8结论**：血缘、撤回、跨租户和高风险自进化动作必须重新检查当前授权；审批替代不能绕过这些门禁。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **多级审批采用“风险/动作驱动的角色链 + 资格与独立性检查 + 受限替代 + 当前 RunGate 重检”的模型。R0 可按策略自动记录或单级确认，R1 需要职责 Owner，R2 需要资源/业务 Owner 与独立风险/安全或变更审批，R3 需要专门治理/安全/合规与业务责任的独立审批，必要时满足双人/法定人数；这些只是原则级最低门槛。Named substitute、on-call delegate 和 quorum fallback 只能在原授权的 action/resource/purpose/risk/time 子集内生效，不能降低风险、扩大范围、无限转委托或允许自批。审批超时不等于批准；低风险预授权可升级到合资格代理，高风险进入 expired/escalated/blocked。代理、审批、拒绝、冲突、撤回和事后复核均追加审计，身份/组织/审批系统不可用或责任不明时默认阻断。**

#### 审批生命周期

```text
requested
  → eligibility_resolved
  → approval_plan_versioned
  → pending_level_1 ... pending_level_n
  → approved | rejected | expired | escalated | blocked
  → RunGate_recheck
  → executed | cancelled
  → verification
  → post_review
```

每个审批节点绑定 `proposal/run_plan version、resource_scope、purpose、risk、required_role、approver、delegator、substitute_reason、valid_from/to、decision、evidence_refs`。计划或关键上下文变化使已经完成的节点失效，不得只补一个新签名继续执行。

#### 替代矩阵

| 情况 | 可自动处理 | 必须保留的门禁 |
|---|---|---|

## 子议题深化3第1轮：Break-Glass 的完整身份、密钥和技术实现

### 主题与成功标准

本轮处理议题9第三个明确暂缓项。目标是明确应急访问如何可信识别、限时授权、最小止损、密钥保护、全程审计和事后撤销；不选择具体 IAM/KMS/硬件厂商，也不把应急凭据设计成长期超级权限。

成功标准：

1. Break-Glass 绑定真实 Incident、主体、理由、范围、动作、最大风险和有效期；
2. 认证、授权、密钥/令牌发放和 ToolPolicy/RunGate 分离；
3. 紧急身份只能获得预定义最小动作子集，禁止无限委托、横向扩大和自批；
4. 凭据/令牌短期、一次性或可撤销，避免长期共享秘密；
5. 应急策略/身份/KMS/审计不可用时默认阻断高风险动作；
6. 使用、扩展、撤销、失败和事后复核均可追踪。

### 阶段1：头脑风暴

#### 1. Break-Glass 是受控异常，不是隐藏后门

一次应急授权至少绑定：

```text
incident_id
requester / verified principal / organization
reason / declared emergency
resource_scope / allowed_actions / max_risk
purpose / environment / target revision
start_at / expires_at / max_duration
approver_or_emergency_authority
credential/token reference and policy version
post_review_required / notification targets
```

没有 Incident、主体或范围不能通过“紧急”字样补齐。应急授权只允许预先定义的止损、阻断、最小恢复或取证动作。

#### 2. 身份与授权链

认证至少包含主体身份、认证强度、设备/工作负载证明、组织范围、委托链、Incident 绑定和时间条件。身份系统确认“谁”，授权策略确认“能在什么资源、用途、动作和风险上做什么”；两者不能由 Token 文本互相替代。

Break-Glass 审批者、执行者和验证者仍应分离；同一主体只能在明确预授权的最小止损模型中兼任部分角色，并强制事后独立复核。

#### 3. 密钥和令牌生命周期

应急密钥/令牌应具备：

```text
short-lived / bounded audience
least privilege / resource binding
non-exportable where possible
one-time or replay-resistant use
rotation / revocation
secure issuance and storage
use and failure audit
automatic expiry and emergency kill switch
```

恢复旧密钥、共享管理员密码、把凭据写入日志/Trace/Manifest 或通过聊天传递都不是合格方案。密钥服务不可用时不得回退硬编码、默认密钥或长期 Token。

#### 4. 允许动作和运行时边界

优先允许：阻断新 retrieval/action、暂停队列、撤回明显泄露投影、隔离缓存/索引、采集最小取证、恢复必要的只读健康能力。生产写入、数据库迁移、权限扩大、凭据导出、跨租户原文读取、不可逆删除和长期策略修改默认不在通用 Break-Glass 权限内，需要专门审批。

#### 5. 事后闭环

```text
authorize → issue → use → monitor → expire/revoke
  → reconcile actual actions vs allowed set
  → independent post-review
  → rotate/revoke emergency secrets
  → assess residual impact and violations
  → update policy/runbook
```

事后复核不是把未经授权的动作追认为已授权，而是确认事实、责任、影响、补救和制度改进。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-53 Rev.5**：包含应急访问、最小权限、职责分离、审计和账户管理等控制思想，可借鉴 Break-Glass 的预授权、限时、审计和撤销；不规定本平台的具体令牌或 KMS 实现。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-20）。
2. **NIST SP 800-57 Part 1**：强调密钥材料生命周期、保护、轮换、撤销和销毁，可借鉴应急密钥短期、限用途、可撤销和不可写入普通日志。来源：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问日期：2026-09-20）。
3. **NIST SP 800-63 系列**：身份认证、认证器和联邦断言可作为身份强度和受众绑定的参考；身份认证不自动授予资源动作权。来源：<https://pages.nist.gov/800-63-4/>（访问日期：2026-09-20；部分 CSRC 页面路径存在变化）。
4. **议题9既有结论**：已规定 Break-Glass 绑定 Incident、范围、动作、最大风险、时限、事后复核，不得长期改 ACL、扩大跨空间、发布 Skill 或删除审计；本轮补充身份/密钥技术边界。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **Break-Glass 采用“已验证主体 + 已绑定 Incident + 预定义最小动作 + 限时限域令牌/密钥 + RunGate/ToolPolicy 重检 + 全程审计 + 自动过期/撤销 + 独立事后复核”的模型。认证只证明主体，授权还需检查资源、用途、范围、风险、环境、revision、委托链和 Incident；应急 Token 不能通过自身文本获得权限。令牌/密钥应短期、限受众、资源绑定、尽可能不可导出、一次性/防重放、可轮换/撤销，并禁止写入日志、Trace、Manifest 或聊天。通用 Break-Glass 只允许预定义止损、阻断、隔离、最小恢复和取证；生产写入、权限扩大、跨租户原文、不可逆删除、凭据导出和长期策略变化默认需要专门审批。应急身份、策略、密钥、审计或 RunGate 不可用时高风险动作默认阻断；事后复核记录事实和补救，不追认未经授权的副作用。**

#### 技术边界链路

```text
incident intake
  → authenticate principal/device/workload
  → verify organization/delegation and incident authority
  → resolve allowed action/resource/max risk/time
  → independent approval or pre-authorized emergency policy
  → issue short-lived bound credential/token
  → RunGate + ToolPolicy execution check
  → monitor and append immutable audit
  → auto-expire/revoke/rotate
  → independent post-review and residual-risk decision
```

#### 失败状态

```text
identity_unverified
incident_unverified
scope_ambiguous
credential_service_unavailable
policy_or_audit_unavailable
expired
revoked
actual_action_mismatch
post_review_pending
```

这些状态都不能自动降级为允许；`policy_or_audit_unavailable` 对高风险路径是 fail-closed。

## 子议题深化4第1轮：审计记录的保留期限、加密和不可抵赖格式

3. 加密、密钥轮换、访问和密钥撤销不破坏必要验证能力；
4. 法律保全、合规删除、最小化和审计闭环有冲突处理路径；
5. 过期清理覆盖日志正文、附件、索引、备份、缓存和派生副本；
6. 审计系统不可用时高风险动作默认阻断，低风险本地缓冲也必须可校验和补传。

### 阶段1：头脑风暴

#### 1. 审计记录不是所有观测的永久副本

应分别记录：

```text
Decision Audit      请求、用途、资源、策略、审批、理由和义务
Execution Audit     计划、实际 Tool Call、差异、结果、验证、回滚和残余风险
Impact Audit        受影响资产、Run、Manifest、Project、阻断、撤回和传播
Identity/Policy     主体、委托、认证、策略版本、授权决策和失效
Lineage/Retention   来源/派生、保留理由、保全、删除/清理和验证
```

原始客户数据、凭据、完整生产请求体和无关 Trace 不应因为“审计”名义全部复制；需要引用、摘要、哈希或受控关联时优先最小化。

#### 2. 保留期限由多轴决定

```text
event_type / sensitivity / purpose
legal or regulatory obligation
incident / dispute / investigation hold
asset/Run lifecycle and business need
source and derivative lineage
storage/copy coverage
access and deletion policy
```

“统一保留 N 天”不足以覆盖安全事件、客户合同、审计、隐私删除和历史 Run 的不同要求。期限、保全和删除决策必须可追溯，不能由业务使用量单独决定。

#### 3. 不可抵赖是证据属性，不是绝对保证

至少需要：可信来源与时间、追加顺序、完整性校验、访问/修改控制、密钥保护、审计链验证和异常报告。哈希可检测内容变化但不自动证明是谁产生；数字签名能绑定签名主体但依赖密钥管理和撤销；WORM/append-only 降低修改风险但不解决错误采集、越权读取或物理灾备。

#### 4. 加密的不同边界

- 传输加密：保护采集/查询链路；
- 静态加密：保护存储、备份和导出；
- 字段/分区加密：降低敏感字段暴露面；
- 密钥访问审计：保护密钥本身的使用边界；
- 密钥轮换/撤销：需保持历史验证和合规销毁策略。

加密不能取代 ACL、用途、脱敏、最小化和不可篡改证明；密钥丢失、撤销或过期时要明确审计验证能力如何保留或降级。

#### 5. 到期和删除

到期流程应先冻结/核对保全和影响，再阻断访问、删除逻辑索引、清理派生副本和备份，最后验证并记录结果。若法律保全或安全调查要求继续保存，只能保留必要范围和受限访问；保留的审计不能成为检索原文或恢复权限的旁路。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-92**：讨论安全日志管理、生成、传输、存储、分析和处置，可借鉴日志源、时间、集中管理、访问控制和生命周期治理；不规定本平台审计对象、血缘或行业保留期限。来源：<https://csrc.nist.gov/pubs/sp/800/92/final>（访问日期：2026-09-20）。
2. **NIST SP 800-57 Part 1**：密钥生命周期、保护、轮换和撤销可作为审计加密及历史验证密钥管理的参考；不定义不可抵赖证据格式。来源：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问日期：2026-09-20）。
3. **NIST SP 800-53 Rev.5**：审计与问责、系统与通信保护、介质保护和事件响应控制族可借鉴职责、访问、保护和审计验证边界；不替代企业法务保留表。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-20）。
4. **议题7/8既有结论**：审计保留不扩大当前权限；软退休、撤回、外部副本和派生清理需要记录 unknown/failed，不能声称完整清除；本轮将该状态用于审计生命周期。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **审计采用按事件类型、敏感性、用途、保全/合规义务和生命周期分层的追加式证据模型，至少区分 Decision、Execution、Impact、Identity/Policy、Lineage/Retention 审计。记录优先最小化，凭据、客户数据、完整生产请求体和无关 Trace 不因审计名义复制；可用引用、摘要、哈希和受控关联证明事实。不可抵赖依赖可信来源/时间、追加顺序、完整性校验、访问/修改控制、密钥保护和可验证审计链，哈希、签名或 WORM 各自不能单独证明事实、主体或安全。传输/静态/字段加密和密钥生命周期必须与 ACL、用途、脱敏和验证能力联动。保留期限按事件/敏感/用途/法务保全/事故/资产生命周期决定，过期清理覆盖正文、附件、索引、缓存、备份和派生副本；保全与删除冲突时保留最小隔离证据并升级责任人。审计/策略不可用时高风险动作默认阻断；低风险缓冲必须具备完整性、容量、补传和失败审计。**

#### 审计事件最小包络

```text
event_id / event_type / occurred_at / received_at
principal / delegation / authenticator_ref
purpose / resource_scope / tenant/project/space
policy_version / decision / reason
plan/proposal/run/trace/lineage refs
sensitivity / redaction / retention_class / legal_hold
previous_event_digest / event_digest / signature_or_integrity_ref
storage/copy status / access status / expiry / deletion status
```

内部包络可含更丰富字段，但消费者按当前权限获得最小投影。时间顺序应区分源发生与接收，不因补传重写历史；重复事件需幂等标记。

#### 生命周期和验证

```text
captured → integrity_checked → retained
  → accessed/audited → hold_or_due
  → deletion_pending → deleted | retain_minimal | failed | unknown
```

`deleted` 只表示声明范围和方法的删除验证通过；备份、第三方副本或加密擦除无法证明时保留 `unknown/external_unknown`。审计链验证失败触发隔离、告警、影响分析和复核，不静默修复历史。

## 子议题深化5第1轮：权限撤回对已运行 Run 的逐工具处置策略

### 主题与成功标准

本轮处理议题9第五个明确暂缓项。目标是明确权限、凭据、来源 ACL、用途、策略或血缘在 Run 已开始后变化时，如何逐个 Tool Call/Attempt 评估继续、暂停、取消、补偿、回滚或人工接管；不把“权限撤回”简化成无条件杀进程，也不把历史批准视为当前执行授权。

成功标准：

1. 区分尚未开始、排队、等待审批、运行中、已完成和部分执行的 Tool Call；
2. 每个工具动作绑定当前主体、资源、用途、风险、计划版本、授权和幂等/停止能力；
3. 撤回优先阻断新高风险调用，对正在执行调用按工具能力和副作用状态单独处置；
4. 明确安全停止、取消、完成、补偿、回滚和人工接管边界；
5. 不重复副作用，不把失败/未知误报为回滚成功；
6. 权限恢复不能自动重放旧调用，必须重新生成/门禁；
7. 全程记录计划与实际差异、阻断原因、残余风险和事后复核。

### 阶段1：头脑风暴

#### 1. Run 状态不足以决定工具处置

一个 Run 可能包含多个 Tool Call/Attempt：

```text
queued / approval_pending
started / streaming
side_effect_committed
completed / failed / timed_out
cancel_requested / cancel_acknowledged
unknown_outcome / compensation_pending
```

权限变化对“尚未开始的调用”和“已经提交副作用的调用”含义不同，必须逐工具、逐 attempt、逐资源判断。

#### 2. Tool Capability Profile

每个工具/Connector 应声明或由受控适配器提供：

```text
read_only or write
reversible / compensatable / irreversible
idempotency support
cancel/stop support and deadline
transaction boundary
partial side-effect visibility
credential lease behavior
result certainty / reconciliation method
```

缺少能力声明不能自动选择安全取消或回滚；高风险工具默认进入人工/受控接管。

#### 3. 撤回处理顺序

```text
permission/policy/source revoke detected
  → authoritative state update
  → block queued and new Tool Calls
  → prevent token renewal/new credential issuance
  → mark active attempts for recheck
  → choose continue-to-safe-boundary | cancel | pause | compensate | rollback | manual takeover
  → reconcile actual external state
  → record impact and residual risk
  → reauthorize only with new plan and RunGate
```

正在执行的只读动作可在安全边界完成；涉及权限已撤回资源或高风险副作用的调用默认暂停/取消或人工接管，不能因调用快结束就自动放行。

#### 4. 按工具能力和副作用状态处置

```text
not_started / queued       → block; no side effect
approval_pending           → invalidate approval; replan
read-only in flight        → stop if supported, else bounded safe completion
reversible write in flight → cancel/rollback/compensate per verified capability
irreversible committed     → stop further calls; reconcile; no blind rollback
unknown outcome            → freeze duplicate actions; external reconciliation/manual review
partially executed         → inventory actual effects; compensate only idempotently
```

回滚不是默认动作：数据库、消息发送、外部 API、部署和客户通知可能无法安全逆转。补偿操作本身是新 Action Proposal，需要当前授权和独立门禁。

#### 5. 凭据和权限租约

撤回时应停止续租、撤销未使用凭据、使 Manifest/Projection 失效并阻断新的 token exchange；不能假设已发出的令牌立即从所有外部系统消失。外部系统无法确认撤销时标记 `revocation_unknown`，限制后续动作并进入影响分析。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-61 Rev.2**：遏制、根除、恢复和事后活动可借鉴先阻断继续损害、再分析和恢复；不能直接给出每种工具的取消/回滚规则。来源：<https://csrc.nist.gov/pubs/sp/800/61/r2/final>（访问日期：2026-09-20）。
2. **Google SRE**：过载保护、渐进发布和事故响应强调避免重试放大、明确停止/回滚和观察实际状态；可借鉴撤回时阻止新调用和防止重复副作用。来源：<https://sre.google/sre-book/load-balancing-using-client-side-throttling/>、<https://sre.google/workbook/incident-response/>（访问日期：2026-09-20）。
3. **议题9既有结论**：已确认权限撤回阻断新 retrieval/action、重新解析 Manifest、暂停/重新授权 pending Run，历史 Run 不静默改写；本轮将其细化为 Tool Call/Attempt 粒度。
4. **议题1 Connector 暂缓项结论**：幂等、重试、断线和外部副作用需要 Connector 能力声明和当前 RunGate；本轮继承而不冻结具体工具协议。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **权限撤回对运行中 Run 采用“新调用立即阻断 + 当前 Tool Call 逐 Attempt 重检 + 按工具能力和副作用阶段选择安全边界/取消/暂停/补偿/回滚/人工接管 + 外部状态对账 + 新计划重新授权”的模型。排队、待审批和未开始调用直接失效；只读在途调用可在明确安全边界内完成或停止；可逆写入仅在能力、幂等和回滚已验证时取消/补偿；不可逆或副作用已提交的调用停止后续动作、对账并记录残余风险，不盲目回滚；结果未知或部分执行时冻结重复动作并人工/受控处理。撤回同时阻止新凭据发放/续租、使 Manifest/Projection/Cache 失效，但外部令牌/系统撤销未知时标记 `revocation_unknown`。权限恢复不自动重放旧调用，必须绑定当前上下文、生成新 Plan 并通过 RunGate/ToolPolicy。补偿、回滚和人工接管都是新的受授权动作，计划/实际差异和审计不可静默覆盖。**

#### Tool Call 处置矩阵

| 状态/能力 | 默认处置 | 后续门禁 |
|---|---|---|
| 未开始/排队 | 阻断并失效计划/审批 | 新计划、当前授权和 RunGate |
| 等待审批 | 撤销 pending，重新评估 | 不能以原审批继续 |
| 只读在途 | 可停止或安全边界完成 | 结果和访问范围核对 |
| 可逆写入 | 取消/回滚/补偿（能力已验证） | 新动作授权、幂等和验证 |
| 不可逆副作用已提交 | 停止后续调用、对账 | 专门处置和残余风险审核 |
| 结果未知 | 冻结重复动作、外部对账 | 人工/受控恢复与新门禁 |
| 部分执行 | 盘点实际影响、局部补偿 | 不得把部分当成功/回滚完成 |

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| 分布式系统 | 取消请求发出是否等于动作已停止？ | 不等于；记录 requested/acknowledged/unknown，需外部状态对账。 |


## 子议题深化6第1轮：紧急撤回的跨租户通知和法律合规流程

### 主题与成功标准

本轮处理议题9第六个明确暂缓项。目标是定义源租户、目标租户、平台运营方、受影响客户和监管责任之间的紧急撤回通知、证据、升级与复盘边界；不替企业或客户作具体法律结论，不固化单一法域的时限。

成功标准：

1. 紧急撤回先完成权威阻断，再按影响和责任分层通知；
2. 区分内部运营通知、跨租户业务通知、受影响主体通知和监管/执法通知；
3. 每条通知绑定事件、影响范围、事实置信度、责任角色、时间线和下一步；
4. 避免过度披露源租户、客户数据、调查细节和安全弱点；
5. 明确法律保全、客户合同、数据主体权利和监管时限的冲突升级；
6. 通知失败、责任不明、影响未知或跨境规则不明时不得静默视为完成。

### 阶段1：头脑风暴

#### 1. 通知对象不是一个“管理员”

一次跨租户撤回可能同时涉及：

```text
平台 Incident Commander / Security / Privacy / Operations
源租户 Owner / Security / Privacy / 合规责任人
目标租户 Owner / Consumer Owner / Security / 合规责任人
受影响客户或数据控制者/处理者代表
受影响用户或数据主体（按法律与合同要求）
监管机构、执法机构或外部取证方（按适用规则）
```

平台可以负责事实编排、阻断、影响分析和通知投递，但不能仅凭平台角色推断谁是法律上的控制者、处理者、通知责任人或法定签署人。

#### 2. 通知等级与最小披露

建议把通知分成四层：

```text
N0 运行内部事件：阻断、排班、取证、恢复和审计所需人员
N1 跨租户运营通知：源/目标 Owner、安全和平台责任人
N2 客户/业务通知：说明服务影响、数据类别、已采取措施和客户动作
N3 监管/执法/数据主体通知：按适用法域、合同和责任矩阵决定
```

N0/N1 可在确认事件后立即发出；N2/N3 需要同时记录事实置信度、适用责任和法务/隐私审核状态。紧急阻断不能等待一封完整通知，通知也不能替代阻断。

每条消息采用最小必要披露：事件标识、发生/发现时间、受影响租户或服务范围、已确认与未知事实、阻断和缓解状态、对方需要采取的动作、下一次更新承诺、联系人和安全传输方式。凭据、原始客户数据、未验证归因、完整攻击路径和不必要的其他租户信息不得放入普通通知。

#### 3. 事件事实和法律结论分离

通知编排应分别记录：

```text
technical_fact_state: confirmed | probable | unknown | disproved
impact_scope: tenant / asset / consumer / time window
data_category: none | internal | personal | customer | credential | production
containment_state: blocked | partially_blocked | failed | unknown
legal_assessment: pending | not_applicable | applicable | disputed
notification_decision: notify | defer_with_reason | not_required_with_reason | escalate
```

“已撤回派生资产”不等于“所有外部副本已清除”；“没有发现访问”不等于“没有泄露”。通知必须保留未知项和更新机制，不能用模型置信度填补法律责任或事实缺口。

#### 4. 跨租户协调与通知失败

撤回流程应建立单一事件编号和跨租户关联编号，但各租户只看到其授权范围内的最小投影。投递至少记录目标、渠道、发送时间、版本、送达/拒收/未知状态和重试；高风险通知应使用经过验证的联系人和防冒用的安全渠道。

目标租户无法确认、联系人失效、跨境传输渠道不合规或通知系统不可用时，继续阻断和保存证据，升级到备用责任人/法务/合规，不把“已尝试发送”标为“已通知”。通知重试必须幂等，不能因重试扩大披露。

### 阶段2：其他产品/标准如何做（带来源）

1. **GDPR 第33、34条**：控制者发现个人数据泄露后，原则上应在无不当延迟且可行时不迟于72小时向监管机构通知；高风险时还可能需要向数据主体沟通。条文允许分阶段补充信息，并要求记录泄露事实、影响和补救措施。本平台借鉴“先记录和遏制、事实不足时分阶段补充”的机制，不把72小时机械套用于所有法域或替代责任认定。来源：<https://eur-lex.europa.eu/eli/reg/2016/679/oj>（访问日期：2026-09-21）。
2. **英国 ICO Personal data breach guidance**：强调组织应评估风险、记录所有个人数据泄露，并在适用时按监管时限报告；对受影响个人的沟通取决于高风险和具体情况。可借鉴“事件记录、风险评估、责任路径和通知证据”分离。来源：<https://ico.org.uk/for-organisations/report-a-breach/personal-data-breach/>（访问日期：2026-09-21）。
3. **NIST SP 800-61 Rev.2**：事故响应包含检测/分析、遏制/根除/恢复和事后活动，可借鉴先遏制、维护时间线、协调内部与外部沟通并复盘；不决定租户合同和法域通知义务。来源：<https://csrc.nist.gov/pubs/sp/800/61/r2/final>（访问日期：2026-09-21）。
4. **Microsoft Purview Communication Compliance**：体现通信治理应按组织策略、角色和审计进行受控访问；可借鉴通知与调查材料需要权限分层、最小披露和审计。它不是跨租户撤回的法律责任标准。来源：<https://learn.microsoft.com/en-us/purview/communication-compliance>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **跨租户紧急撤回采用“先权威阻断、后影响分级、事实与法律责任分离、最小必要披露、责任人确认、可验证投递、分阶段更新和完整复盘”的通知模型。N0 内部事件、N1 源/目标租户运营通知、N2 客户/业务通知、N3 监管/执法/数据主体通知分别建模；通知对象、时限和内容由适用法域、客户合同、控制者/处理者责任和事件事实决定，不能由平台默认推断。每条通知绑定 Incident、租户与影响范围、事实/未知状态、数据类别、阻断状态、责任角色、法务/隐私决定、版本、渠道、送达证据和后续更新时间。紧急阻断不等待法律意见，通知不替代阻断；影响未知、通知失败、跨境规则冲突、责任不明或证据不足时继续隔离并升级，不伪造“已通知”“已清除”或“不需报告”结论。历史事件、通知、决定和证据追加审计，租户之间只共享最小授权投影。**

## 子议题深化7第1轮：自动影响闭包的性能和一致性协议

### 主题与成功标准

本轮处理议题9第七个明确暂缓项。目标是定义权限撤回、源资产失效或策略变化后，如何在大规模血缘图中及时发现受影响的 Manifest、Embedding、Index、Cache、派生资产、Run 和跨空间投影，并在性能、事件乱序、重复投递和查询期间保持可解释的一致性边界；不固化具体事件总线、数据库或全局数值阈值。

成功标准：

1. 区分权威状态、影响闭包计算状态和各消费者生效状态；
2. 同步完成最小安全阻断，异步完成可追踪的影响闭包；
3. 支持幂等、乱序、重复、丢失、分区和重放，并能发现缺口；
4. 明确强一致、最终一致和未知状态下的检索/执行门禁；
5. 大规模图分析具备分片、优先级、预算、背压和降级边界；
6. 不以队列清空、超时或局部成功冒充全局传播完成。

### 阶段1：头脑风暴

#### 1. 影响闭包不是一次图查询

撤回事件可能影响：

```text
source asset / revision / lineage edge
→ derived asset / published projection
→ Embedding / Index / Cache / Context Manifest
→ pending or active Run / Tool Call
→ downstream Project / Team / tenant consumer
→ audit / notification / legal hold record
```

同一对象可能同时拥有权威状态、缓存状态、索引可见性、正在运行的快照和外部副本状态。必须记录每个节点的版本、事件游标、处理状态和证据，而不是只写一个全局 `revoked=true`。

#### 2. 两条路径：安全快速路径与完整闭包路径

```text
revoke accepted
  → authoritative state committed
  → synchronous deny/restrict at read, projection and action gates
  → enqueue versioned impact event
  → partitioned closure traversal
  → consumer invalidation/rebuild/reconciliation
  → closure verification and residual unknowns
```

同步路径只承担最小止损：新检索、投影、Action Proposal、pending Run 和高风险执行先按当前权威状态阻断。完整清理、重算、通知和历史影响分析可异步完成，但在闭包未知时不能解除高风险门禁。

#### 3. 一致性等级必须显式

每个消费者至少报告：

```text
active_version / required_source_version
last_applied_event / high_watermark
state: current | stale | pending | blocked | failed | unknown
proof: digest / acknowledgement / reconciliation_ref
```

- `current`：已应用不低于所需权威版本并通过校验；
- `stale`：仍可能命中旧内容，只能按策略降级或阻断；
- `pending`：已进入传播但尚未确认；
- `blocked`：安全门禁主动拒绝；
- `failed/unknown`：没有足够证据证明完成，不能自动放行。

缓存命中、索引删除、Embedding 重算、Manifest 重解析和 Run 暂停分别确认；一个消费者成功不代表闭包成功。

#### 4. 性能和安全的取舍

闭包任务应按风险和影响优先级调度：活跃高风险 Run、可执行投影、跨租户派生、生产/客户数据优先；低风险历史索引和统计副本可后台处理。需要设置并发、队列长度、遍历深度、单租户预算、重试上限和死信/人工队列，避免一次全局撤回压垮事件系统。

任何性能降级只能扩大隔离或延迟恢复，不能把 `unknown` 转成 `current`；当血缘图过大、事件延迟过高或依赖不可用时，优先保守阻断受影响范围，并向操作者显示覆盖率、缺口和预计下一步。

### 阶段2：其他产品/标准如何做（带来源）

1. **Apache Kafka 文档**：区分 at-most-once、at-least-once 和 exactly-once 语义，并强调处理语义、事务边界和外部系统协调不能被简单等同。可借鉴本平台采用至少一次传播、幂等应用、版本/游标和对账，而不宣称跨外部系统天然 exactly-once。来源：<https://kafka.apache.org/documentation/#semantics>（访问日期：2026-09-21）。
2. **Temporal Event History**：以追加事件历史和可重放状态重建运行上下文，可借鉴把撤回、阻断、暂停、传播和验证作为追加事件，避免静默覆盖历史 Run；它不提供本平台跨租户权限闭包策略。来源：<https://docs.temporal.io/encyclopedia/event-history>（访问日期：2026-09-21）。
3. **W3C PROV-DM**：将实体、活动和代理以及它们的派生/使用关系显式建模，可借鉴闭包遍历应基于可解释的血缘关系和版本，而不是只依赖缓存键。来源：<https://www.w3.org/TR/prov-dm/>（访问日期：2026-09-21）。
4. **Google SRE《Handling Overload》**：强调限流、背压、优先级和降级以避免过载级联，可借鉴影响传播任务设置预算、队列保护和保守降级；它不替代权限撤回和数据一致性判断。来源：<https://sre.google/sre-book/handling-overload/>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **自动影响闭包采用“权威撤回版本 + 同步最小阻断 + 至少一次版本化传播 + 幂等应用/对账 + 分片优先级遍历 + 显式消费者状态 + 缺口与未知可见 + 闭包验证后分级恢复”的模型。权威状态提交后，检索、投影、Action Proposal、pending Run 和高风险执行立即按当前状态阻断；Embedding、Index、Cache、Manifest、派生资产、已运行 Run、通知和外部副本通过带版本与游标的异步任务传播。每个消费者必须证明已应用所需版本，`stale/pending/failed/unknown` 不得伪装为 `current`。传播采用可重放、幂等、乱序容忍和缺口检测，不假设跨外部系统 exactly-once；大规模任务按风险、租户和影响分片，设置并发/队列/重试预算和背压。性能降级只能延迟恢复或扩大隔离，不能降低安全门禁；闭包未证实前不得恢复高风险检索、投影或执行。**

#### 推荐传播状态机

```text
revoke_committed
  → deny_path_active
  → impact_event_enqueued
  → traversing
  → consumer_update_pending
  → applied_and_verified
  → closure_verified
  → restore_review
  → restored | restricted | remains_blocked
```

失败分支：

```text
missing_event | out_of_order | duplicate | lease_expired
consumer_unavailable | version_conflict | dead_letter
reconciliation_failed | external_unknown
```

所有失败分支保留原权威阻断，进入重试、补偿、人工复核或长期 `unknown`，不能靠超时自动清除。

#### 闭包证明最小包络

```text
closure_id / root_event / authority_version
partition / tenant_scope / traversal_policy
expected_consumers / discovered_consumers
last_applied_event / high_watermark / gap_refs
consumer_state / acknowledgement / digest
retry_count / dead_letter_ref / reconciliation_ref
coverage / unknown_scope / started_at / completed_at
restore_decision / approver / audit_refs
```

`coverage=100%` 只有在声明的遍历范围、消费者目录和外部依赖均有依据时才可使用；无法枚举的外部副本必须显式列为 `external_unknown`。

## 子议题深化8第1轮：事后复核的完整 SLA、升级和责任矩阵

### 主题与成功标准

本轮处理议题9第八个明确暂缓项。目标是定义高风险授权、Break-Glass、紧急撤回、部分执行、未知结果和跨租户影响之后，如何按事件严重性完成事实复核、责任分离、升级、补救、证据闭环和制度改进；不冻结企业统一小时数、法定期限或组织职位名称。

成功标准：

1. 区分技术恢复完成、影响闭包、审计完成、法律/合规评估和事后复核完成；
2. 按风险、影响、未知范围和外部副作用设定分层目标与升级路径；
3. 明确 proposer、approver、executor、verifier、Incident Commander、Security/Privacy、Owner、Auditor 的责任边界；
4. Break-Glass 和未授权/计划外副作用必须强制复核，不因结果成功而免除；
5. 超时、责任不明、证据不足和跨租户冲突必须升级而非静默关闭；
6. 复核结论记录事实、影响、补救、残余风险、接受者和跟踪项，并防止追认未经授权行为。

### 阶段1：头脑风暴

#### 1. “恢复”不是“事件结束”

一次事件至少有多个闭环：

```text
technical_containment / service_recovery
permission_and_lineage_closure
external_impact_and_notification
security_and_privacy_assessment
execution_and_decision_audit
independent_post_review
corrective_action_follow_up
```

可以恢复服务但仍有外部副本未知、审计缺口、残余凭据、未完成客户通知或责任争议。状态必须分开，不能用 `Run succeeded` 或队列清空代表治理完成。

#### 2. SLA 应按目标和风险分层，而不是一个总时限

建议定义四类目标：

```text
TTA — time to acknowledge / assign owner
TTC — time to contain or maintain safe block
TTI — time to assess impact and notification obligation
TTR — time to recover, restrict, replace or remediate
TTP — time to complete independent post-review
```

R0/R1 低风险事件可采用轻量自动记录和批量复核；R2 受控变更要求独立复核、证据和残余风险结论；R3、Break-Glass、跨租户、客户/生产/凭据、不可逆或未知影响必须立即指定责任人、持续升级并完成独立复核。具体目标时长由真实 SLO、合同、法定时限和风险成本校准，不能在产品层伪造统一数字。

#### 3. 责任不是按“最后一个操作者”归因

责任矩阵至少区分：

```text
A — accountable：对决策/风险接受/法定动作负责
R — responsible：执行、调查、验证或补救
C — consulted：提供安全、隐私、业务、法律和架构意见
I — informed：按最小必要范围接收状态和结果
```

建议责任链：

| 阶段 | A | R | C | I |
|---|---|---|---|---|
| 权威阻断 | Incident/权限责任人 | Operations/Security | Owner、Privacy | 受影响消费者 |
| 影响分析 | 事件责任人或目标 Owner | 血缘/平台/安全 | 源 Owner、目标 Owner、Privacy | 审计与支持 |
| 复原/收窄/替代 | 资源/业务 Owner | 执行团队 | Security、架构、合规 | 受影响租户 |
| 法律/通知决定 | 法务/隐私责任人 | 指定合规团队 | 源/目标 Owner、Security | 运营与审计 |
| 独立事后复核 | 独立 Review Owner | 调查/审计团队 | 相关角色但不得自审 | 管理与风险委员会 |
| 改进项关闭 | 改进责任 Owner | 指定工程/运营团队 | Auditor、Security | 原事件参与者 |

角色名称可以映射到企业实际组织，但 `A` 不能仅由 Agent 或执行者自动承担；具体法律责任仍由企业治理确定。

#### 4. 升级触发器和超时处理

任一条件触发升级：

```text
R3 / break_glass / unauthorized_or_plan_mismatch
customer, production, credential, cross-tenant or regulator impact
unknown external state / missing lineage / audit gap
containment failed or impact expanding
SLA target missed / owner unavailable / conflict of interest
repeated policy failure or residual risk above accepted ceiling
```

升级不是把事件重新标成更高风险后就结束；必须重新指定 A/R、增加独立审查、保留原始时间线并维持安全阻断。超时默认 `escalated | blocked | review_overdue`，不能默认批准、默认关闭或追认。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-61 Rev.2**：将事故处理分为准备、检测/分析、遏制/根除/恢复和事后活动，可借鉴用事件生命周期、职责、时间线和经验反馈组织复核；不规定本平台的企业 SLA 或法定责任矩阵。来源：<https://csrc.nist.gov/pubs/sp/800/61/r2/final>（访问日期：2026-09-21）。
2. **Google SRE Postmortem Culture**：强调无责复盘、事实时间线、影响、根因、行动项和跟踪，避免把复盘变成惩罚或掩盖问题；本平台保留职责和责任接受者，但不把“无责”误解为免除治理、合规或未授权副作用责任。来源：<https://sre.google/sre-book/postmortem-culture/>（访问日期：2026-09-21）。
3. **Google SRE Incident Response Workbook**：强调事件指挥、角色分工、沟通、升级和恢复后的复盘，可借鉴 Incident Commander 与技术/沟通/运营角色分离。来源：<https://sre.google/workbook/incident-response/>（访问日期：2026-09-21）。
4. **议题9、7、10既有结论**：高风险操作、撤回、跨租户派生和导出均要求独立审批、证据、影响状态和不可静默修改；本轮把这些要求汇总为复核 SLA 与责任矩阵，不把复盘变成事后授权。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **事后治理采用“多闭环状态 + 风险分层目标 + 明确 A/R/C/I 责任 + 独立复核 + 超时升级 + 改进项跟踪”的模型。技术遏制/恢复、权限与血缘传播、外部影响/通知、审计、法律/隐私评估和独立复核分别完成并分别取证；R3、Break-Glass、计划外差异、跨租户、客户/生产/凭据、不可逆或未知影响必须强制独立复核。SLA 以 TTA（确认/指派）、TTC（遏制/安全阻断）、TTI（影响和通知评估）、TTR（恢复/收窄/补救）、TTP（独立复核）分解，由企业 SLO、合同和法定要求校准，不固化全球数字。超时、责任不明、利益冲突、证据缺失、遏制失败或外部状态未知进入 `escalated/blocked/review_overdue`，不得默认批准、关闭或追认未授权副作用。复核记录事实时间线、实际与计划差异、影响范围、通知/保全决定、补救、残余风险、责任接受者和可验证改进项；复盘促进无责学习，但不消除安全、合规或未授权行为的治理责任。**

#### 推荐复核状态机

```text
review_triggered
  → owner_assigned
  → evidence_preserved
  → containment_and_scope_reviewed
  → responsibility_and_conflict_checked
  → impact_and_legal_assessment
  → independent_findings
  → remediation_and_residual_risk_decision
  → action_items_tracked
  → accepted_and_closed | escalated | overdue | reopened
```

`accepted_and_closed` 的前提是：各适用闭环状态明确、证据范围和缺口已记录、独立复核完成、残余风险有明确接受者或仍被阻断、改进项有 Owner/截止目标/验证方式；发现新证据时允许 `reopened`，不得静默改写原结论。

```text
risk_level / trigger / scope / tenants / data_categories
timeline / planned_vs_actual / authorization_refs
containment / closure / notification / legal_hold states
A_R_C_I roles / conflicts / escalations / deadlines
evidence_refs / gaps / unknown_scope / findings
remediation / residual_risk / risk_acceptor
action_items / owners / due_targets / verification
independent_reviewer / decision / version / audit_refs
```
