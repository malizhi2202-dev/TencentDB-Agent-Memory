# 议题 6：代码场景和根因分析

**状态：已确认（第 1、2、3 轮阶段性方案；后续专题待讨论）**

## 问题定义

> 如何将 repo、revision、文件/符号、工具调用、错误、失败路径、修复和验证组织为可恢复的代码场景与 RCA，同时区分 Code Context、RCA 和 Work Thread？

## 第 1 轮确认：代码事实、问题因果与工作过程分离

本轮确认：

> **代码场景采用“事件日志 + 当前场景快照 + 结构化证据 + 可选 RCA 摘要”的组合。Code Context 负责绑定 repo/revision 的代码事实，RCA 负责区分症状、证据、假设、已确认根因、促成因素、修复和验证，Work Thread 负责跨执行者的工作过程与恢复。三者通过代码锚点、证据和事件关联，但不合并为一个 Memory。自动化可以提取命令、日志、diff、测试、失败路径和候选根因，但不能把推断当确定结论；最终根因、关闭状态、高风险修复和长期知识发布需要人工或受控审核。Patch、工具调用和 RCA 建议默认不可执行；敏感、权限、血缘、revision 或验证信息缺失时默认拒绝或隔离。**

### 1. 三类对象边界

#### Code Context

回答“当前代码是什么、问题涉及哪里、修改边界是什么”，包括 repo、branch、commit、worktree、文件、目录、符号、模块、调用关系、配置、依赖、API、Schema、测试和运行时版本。Code Context 偏向代码事实，必须绑定明确 revision，不应混入未经确认的根因结论。

#### RCA

回答“为什么发生、哪些证据支持判断、修复是否有效”，包括症状、影响、触发条件、证据、候选假设、排除过程、根因、促成因素、修复、预防行动、验证结果和残余风险。RCA 不能把相关性、时间先后或模型判断直接当成根因。

#### Work Thread

回答“谁为了完成什么工作，经过了哪些尝试，目前进行到哪里”，包括用户任务、Agent/Harness 执行、工具调用、中间计划、失败路径、阻塞、交接、当前状态和下一步。Work Thread 是工作过程主体，可以关联多个 Code Context 和 RCA，但不等于最终知识资产。

### 2. 代码场景结构

```text
Engineering Scenario
├── Identity
│   ├── scenario_id / title
│   ├── intent / user_request
│   ├── status
│   └── owner / participants
├── Code Anchor
│   ├── repository / branch
│   ├── revision / commit
│   ├── dirty_state
│   ├── environment
│   └── dependency/runtime versions
├── Scope
│   ├── files / symbols / modules
│   ├── tests
│   └── related APIs / schemas
├── Evidence
│   ├── tool calls / command outputs
│   ├── logs / stack traces
│   ├── diffs
│   └── user statements
├── Paths
│   ├── attempted / successful / failed paths
│   └── abandoned hypotheses
├── RCA
│   ├── symptoms / hypotheses
│   ├── confirmed root cause
│   └── contributing factors / confidence
├── Change
│   ├── proposed fix / applied diff
│   └── reverted / superseded changes
├── Verification
│   ├── tests / commands / results
│   ├── residual risks
│   └── acceptance status
└── Resume
    ├── current state / blockers
    ├── next recommended action
    └── required human decisions
```

第一版采用事件日志、当前场景快照、结构化证据和可选 RCA 摘要，不追求一开始建设完整图数据库。

### 3. 证据与 revision 边界

每条证据至少记录：

```text
Evidence
- type: command | log | code | diff | test | user_statement
- content / reference
- source_tool
- timestamp
- repo / revision
- scope
- supports / contradicts hypothesis
- confidence
- sensitivity
```

事实和推断必须分开：工具输出是 `observed fact`，“可能是缓存问题”是 `hypothesis`，经复现或独立验证后才能形成确认依据。自动提取结果应标注 `source`、`observed_at`、`revision`、`confidence` 和 `inferred`。

`repo + revision` 是 Code Context、RCA、Patch 和测试结果的共同硬锚点。缺少 repo 或 revision 时可以保留为临时证据或低置信候选，但不得发布为稳定 Code Context、确定性 RCA、可执行 Patch 或 Skill。

### 4. 失败路径与恢复

失败路径是一等数据：

```text
Attempt
├── goal
├── action
├── input_context
├── result
├── status
├── evidence_refs
└── next_decision
```

需要保留命令失败、测试失败、假设被证伪、工具不可用、权限不足、环境不一致、修改引入回归以及用户拒绝/取消等类型。恢复视图应明确已排除路径，避免下一执行者重复排查。

### 5. RCA 状态与验证闭环

RCA 至少区分：

```text
confirmed
hypothesis
missing_evidence
```

完整闭环为：

```text
症状
  → 证据
  → 假设
  → 验证动作
  → 结果
  → 根因结论
  → 修复
  → 回归验证
  → 剩余风险
```

必须允许多个根因、促成因素、修复和验证结果，不强行压缩为单一根因。验证至少区分静态检查、单元测试、集成测试、回归测试、原问题复现、监控/线上观察和人工验收。“已修改代码”不等于“问题已解决”。

### 6. 场景生命周期

```text
new
→ exploring
→ diagnosing
→ fix_pending
→ verifying
→ resolved
```

旁路状态：

```text
blocked / paused / needs_human_confirmation / abandoned / reopened
```

每次状态转移记录 `from`、`to`、`reason`、`evidence_refs`、`actor` 和 `timestamp`。`resolved` 至少要求根因达到规定确认级别、修复完成、验证达到接受标准、剩余风险已记录且必要人工确认完成。

### 7. 自动识别与人工确认

可自动提取 repo、branch、commit、worktree、文件/符号、工具调用、命令、退出码、日志、堆栈、diff、测试/构建结果、依赖版本、候选受影响文件、失败尝试和候选根因。

必须人工确认或受控审核：

- 最终根因；
- 业务影响和严重等级；
- 修复是否符合预期；
- 是否允许修改代码、配置、数据库或生产环境；
- 是否可以关闭场景；
- 是否为同一问题或新场景；
- 敏感数据是否可持久化；
- 是否提炼为长期 RCA、Code Context 或 Skill；
- 未验证风险是否可接受。

高风险操作不能由 Agent 代表用户批准，自动提炼器也不得重新执行工具来证明自己的结论。

### 8. Patch 与工具执行边界

以下内容默认是不可执行的声明性产物：

```text
patch candidate
写操作建议
tool call suggestion
runbook step
RCA recommendation
```

它们不自动产生 Git、配置、数据库、生产部署、工具调用或审批权限。真正执行必须经过：

```text
风险分类
  → 影响预览
  → 明确授权
  → RunGate / Tool Policy
  → 幂等控制
  → 执行结果记录
```

### 9. 安全与隐私门禁

代码、日志、工具参数和生产信息进入场景前应分类、脱敏和最小化。默认禁止持久化或发送密码、API Key、Token、Cookie、私钥、连接串、未授权生产客户数据、完整高敏感请求体和未授权跨 Project/租户内容。

源码、日志、用户输入、工具参数、生产数据、RCA 摘要、Embedding 和审计记录可能具有不同 ACL 与敏感级别，不能因为属于同一场景就统一放宽权限。身份、租户、Project、来源 ACL、血缘、revision 或验证信息缺失时，默认拒绝或隔离。

## 第 2 轮确认：代码场景血缘与跨版本、跨 Project 复用

本轮确认：

> **代码场景与企业记忆血缘采用结构化引用集合和不可变 revision 锚点，第一版不建设完整图数据库。Work Thread、Code Context、Evidence、RCA、Patch Candidate、Verification 和 Knowledge Asset 通过 `references`、`derived_from`、`applies_to`、`verified_by`、`invalidated_by` 等关系关联。同 revision 可精确复用；祖先/后代 revision 只能作为需复核候选；分支、rebase 或关系不明时不得默认复用。跨 Project 不复制原始代码、日志、生产数据或未脱敏 Patch，只能在当前主体权限、来源 ACL、目标策略、用途、敏感性和发布状态交集内生成抽象化、脱敏派生经验。缺少 revision、血缘、权限或撤回传播确认时默认隔离或阻断。**

### 1. 代码场景的血缘节点与关系

建议至少关联以下节点：

```text
Code Repository / Revision
File / Symbol / Module
Work Thread
Tool Call / Run
Observation / Evidence
RCA
Change / Patch Candidate
Verification Result
Knowledge Asset
Consumer Projection
```

最小关系集合：

```text
Work Thread
  ├── references → Code Context
  ├── contains → Evidence
  ├── produces → RCA Candidate
  └── records → Verification

Evidence
  ├── observed_in → Tool Run
  ├── anchored_to → Repo Revision
  ├── supports → Hypothesis / Root Cause
  └── contradicts → Hypothesis / Root Cause

RCA
  ├── applies_to → Repo Revision / Environment
  ├── explains → Symptom
  ├── proposes → Change
  └── verified_by → Verification Result

Knowledge Asset
  ├── derived_from → Scenario / RCA / Evidence
  ├── applies_to → Project / Code Scope / Version
  └── projected_to → Harness / Consumer
```

关系本身应记录来源、创建时间、策略版本和当前状态。第一版可以用结构化引用集合实现，但必须保留未来扩展为血缘图的语义。

### 2. 跨 revision 复用规则

- **同 revision**：repo、commit、路径、符号和环境一致时，可作为高相关候选；仍需检查资产状态和当前权限；
- **祖先/后代 revision**：可作为候选，但必须检查相关文件、符号、diff、API、依赖和测试，并标记需要当前版本复核；不得自动视为当前事实或已验证 Patch；
- **分支、rebase 或关系未知**：只能作为低置信历史参考，不进入默认 Code Context，不形成确定性 RCA，不允许 Patch 自动应用；
- **不同 repo 或 Project**：错误签名相似不等于适用，必须重新检查代码结构、依赖、环境、业务边界、ACL 和 RCA 条件。

RCA 应表达：

```text
repository
revision_range
file/symbol scope
runtime/environment
dependency range
trigger conditions
exclusions
```

代码未触及相关范围时可以继续作为候选；相关文件、依赖、接口或运行条件发生变化时，必须复核或暂停默认使用；来源撤回、权限变化或证据失效时立即阻断。

### 3. 跨 Project 复用

默认禁止复制源代码全文、内部路径、原始日志、客户数据、生产拓扑、私有工具参数、未脱敏 Patch 以及 Project 内部人员/权限信息。

允许的路径是：

```text
Project A RCA
  → 去除项目专属细节
  → 保留可泛化症状、条件、模式和验证方法
  → 脱敏与权限检查
  → Project B / Team 复用候选
```

目标候选应明确来源 Project、适用/不适用条件、抽象化程度、脱敏策略、验证状态和目标消费者。抽象化不等于扩大权限，跨 Project 仍需目标授权和适用性审核。

### 4. 权限、撤回与安全边界

有效复用权限至少取：

```text
当前主体权限
  ∩ 来源 Project ACL
  ∩ 目标 Project / Team 策略
  ∩ Purpose / Use Policy
  ∩ 敏感数据策略
  ∩ 资产发布状态
```

能读 Project A 不等于能发布到 Project B；能看 RCA 不等于能看原始日志和代码；能使用抽象经验不等于能回溯源项目细节。

源代码、日志、生产数据、工具参数、Patch、RCA 摘要和 Embedding 可能具有不同 ACL 与敏感级别，不能因属于同一场景而统一放宽权限。

```text
Source Code / Log / Evidence revoked
  → RCA / Patch Candidate 重新评估
  → Knowledge Asset 暂停或撤回
  → Code Context / Index / Embedding 失效
  → Context Manifest 重新解析
  → 受影响 Run 阻断或重新授权
```

无法证明来源和影响范围时，不得继续跨 Project 复用，应隔离相关资产并等待人工处理。

### 5. 第一版边界

第一版优先实现：

1. repo、revision、file、symbol 结构化锚点；
2. Work Thread、RCA、Evidence 和 Verification 的引用关系；
3. 稳定工具、Run 和 Trace ID；
4. 同 revision 精确复用；
5. 跨 revision 候选复用与复核标记；
6. 跨 Project 只生成抽象化、脱敏候选；
7. 当前 ACL 与目标策略交集检查；
8. 来源变化触发资产暂停和 Manifest 重解析；
9. 缺血缘、权限或 revision 时 fail-closed。

第一版不建设全量代码因果图、自动修复 Patch、跨 Project 原文复制或无人工确认的高风险知识发布。

## 第 3 轮确认：RCA 的证据演进与复发治理

本轮确认：

> **RCA 采用“证据追加、结论版本化、可重新打开”的持续治理模式。新验证、复发事件和使用反馈先形成结构化复核事件，不直接覆盖 RCA；根因、适用范围、修复状态和预防行动分别演进。相似错误只能生成关联候选，不能自动证明同一根因；修复有效不等于根因完整，测试通过不等于生产风险消失。RCA 的 `reference/retrieval/action` 状态分离，代码、环境、依赖、权限或源证据变化触发适用性复核；生产、安全、合规和高影响 RCA 必须人工或受控审核，敏感、权限、血缘或验证失败时默认暂停、隔离或阻断。**

### 1. RCA 采用证据追加、结论版本化

```text
已发布 RCA v1
  → 新证据 / 新验证 / 复发事件
  → 自动生成 RCA v2 候选
  → 差异与证据审查
  → 人工或受控审核
  → 发布 RCA v2
```

旧版本保持不可变，不直接覆盖。事实层、假设/根因层、修复/预防行动层和适用性层可以分别演进，但每次变化都必须保留来源、版本和变化原因。

### 2. 根因、验证与适用范围

RCA 根因候选至少区分：

```text
hypothesis
confirmed_root_cause
contributing_factor
disproved_hypothesis
missing_evidence
```

每个候选关联支持证据、反证、验证动作、验证结果、适用环境和当前置信状态。RCA 可以包含多个根因、促成因素、修复和验证结果，不强行压缩为单一根因。

验证结果应说明对 RCA 的影响：

| 验证结果 | RCA 处理 |
|---|---|
| 成功复现原问题 | 增强对应假设，但不单独证明根因 |
| 未能复现 | 降低假设可信度，并记录环境和输入条件 |
| 排除某假设 | 标记 `disproved`，避免重复排查 |
| 修复后问题消失 | 支持修复有效，但不单独证明根因完整 |
| 修复后仍复现 | 暂停“已解决”，重新评估根因和范围 |
| 只在特定环境有效 | 收窄适用范围 |
| 产生新回归 | 建立新的证据和关联场景 |
| 验证环境与生产不一致 | 只能标记部分验证 |

必须保持：

```text
修复有效 ≠ 根因完整
未复现 ≠ 问题不存在
测试通过 ≠ 生产风险消失
```

适用性至少记录：

```text
repository
revision_range
file/symbol scope
runtime/environment
dependency range
trigger conditions
exclusions
```

### 3. 复发事件处理

同类问题再次发生时，不自动合并为原 RCA，也不自动创建完全孤立的新 RCA：

```text
复发事件
  → 比较错误签名、代码范围、环境、触发条件和时间
  → 生成关联候选
  → 判断同一根因、同一模式新根因、修复不完整、新版本回归或表面相似
  → 人工或受控审核
```

关系语义区分：

```text
reproduces      / 复现同一问题
recurs          / 同一根因再次发生
regresses       / 修复后回归
related_to      / 相关但未确认同一根因
contradicts     / 与原结论冲突
supersedes      / 新 RCA 替代旧 RCA
```

错误签名相似只能产生候选关联，不能自动证明相同根因。

### 4. 修复、预防行动与观察期

```text
修复
  → 测试与回归
  → 原问题复现验证
  → 发布或上线
  → 指标观察
  → 检查是否复发
  → 预防行动完成
  → 标记持续有效
```

RCA 生命周期建议为：

```text
draft
→ evidence_gathering
→ hypothesis
→ root_cause_confirmed
→ fix_in_progress
→ verification_pending
→ resolved
→ monitored
→ reopened
→ superseded / revoked / archived
```

`root_cause_confirmed` 不等于修复完成；`resolved` 需要修复和验证达到接受标准；`monitored` 表示进入观察期；复发或新证据可使 RCA `reopened`。生产和高影响问题应在修复后继续观察，具体期限留待以后讨论。

### 5. 使用反馈与消费者状态

反馈先形成结构化复核事件：

```text
使用反馈
  → 关联 RCA 版本和消费者
  → 判断影响
  → 追加证据或生成新版本
  → 人工/受控审核
  → 保留、收窄、暂停、替代或撤回
```

反馈至少区分根因错误、适用范围过宽/过窄、修复无效、预防措施无效、步骤不可执行、证据不足、表达不清和权限/敏感问题。

同一 RCA 对不同消费者可以有不同状态：

```text
reference_status
retrieval_status
action_status
```

例如：根因存在争议时，事件时间线仍可作为事实参考，但不能驱动修复；新环境验证失败时，RCA 可保留历史说明，但不得进入自动执行链路。

### 6. 自动化与人工边界

可以自动追加日志、指标、Trace、测试和 revision，关联复发候选，比较版本，统计复发，标记环境变化、生成修订候选和提醒行动项。

必须人工或受控审核：最终根因、关闭 RCA、复发是否同根因、适用范围变化、长期知识提炼、生产/安全/合规/高影响修复结论、撤回/恢复 RCA 和残余风险接受。

代码、日志、生产数据和工具参数进入 RCA 前必须经过当前 ACL、敏感性、脱敏和最小化检查；撤回源证据、权限变化、血缘断裂或验证失败时，默认暂停、隔离或阻断。

## 子议题深化1第1轮：场景与 Work Thread、Task、Run 的完整 Schema 和关系

### 主题与成功标准

本轮针对前述第一项明确暂缓事项，讨论代码工作连续性中的对象边界和关系语义。目标不是提前冻结最终 Schema、API、数据库表、事件协议或状态阈值，而是建立后续架构可以共同遵守的语义骨架。

本轮成功标准：

1. 明确区分 Code Scenario、Work Thread、Task、Work Phase、Execution、Run、Harness Session、Checkpoint、Revision、Context Manifest、Environment Snapshot、Artifact、Decision 和 RCA 的职责，不以“任务”“运行”或“记忆”互相替代；
2. 能表达多 repo、多 branch、多 revision、多环境，以及它们在同一场景中的并行、切换、派生和复核关系；
3. 能保留工具调用、日志、测试、失败、修复、验证等证据的来源、顺序、版本和血缘，并支持暂停、恢复、重开、交接和派生；
4. 明确 source 与 derived 的区别，且任何派生结论都能回溯到源证据和当时上下文；
5. 将知识权限、执行权限和工具权限分离，明确 RunGate 与 ToolPolicy 是两个独立门禁；
6. 保留不可变事件、对象版本和历史快照，使用追加而非覆盖的方式修正历史；历史快照只说明过去发生过什么，不自动授予当前读取、发布、执行或工具调用权；
7. 为后续实现提供足够约束，同时明确仍需实证、治理和架构决策的内容，避免把本轮讨论误读为最终实现契约。

### 阶段1头脑风暴

#### 1. 先按“问题、工作、尝试、证据、知识”分层

代码场景（Code Scenario）是面向一个工程问题或目标的长期问题边界和证据容器；它回答“要解决什么、影响什么、目前是否被解决、哪些结论仍然成立”。它不是一个待执行动作，因此 **Scenario 不是 Task，也不是 Run**。Scenario 可以长期处于调查、等待、暂停、关闭后重开或派生状态，且可以关联多条工作线、多个版本、多个环境和多个 RCA。

Work Thread 是围绕一个场景或相关目标持续推进的工作连续性。它记录参与者、交接、当前工作上下文、阻塞、下一步和恢复点，允许不同 Harness、Agent 或人工执行者接续。它不是单次会话，也不等同于某个执行结果。

Task 是一个可分派、可检查和可交付的工作承诺，具有明确的目标、输入约束、完成条件和责任归属。Task 可以被拆成多个 Work Phase，并由一次或多次 Execution 尝试完成。**Task 完成只表示该任务的完成条件已满足，不表示场景已解决，更不表示知识已经发布。**

Work Phase 是 Task 或 Work Thread 中具有相近目的和准入条件的一段工作阶段，例如复现、定位、修复、验证或复盘。它用于组织过程和切换条件，不应取代 Task 的业务目标，也不应把每个阶段机械地当成一个独立知识对象。

Execution 是对某个 Task 或 Work Phase 的一次逻辑尝试，包含所选上下文、计划动作、实际过程、结果、失败原因和后续决策。一次 Execution 可以因为暂停、工具不可用、权限拒绝或环境失配而产生多个具体 Run；是否采用一对一或一对多的落地方式留待架构验证，但语义上必须能区分“逻辑尝试”和“具体执行”。

Run 是一次在明确主体、上下文、环境、权限和 ToolPolicy 约束下发生的具体执行实例。它可以产生工具调用、日志、指标、测试结果、变更和验证证据。**Run 成功只表示这次被授权执行返回了成功结果，不表示 Code Scenario 已解决；**场景是否解决还需要 RCA、修复范围、验证、残余风险和必要人工确认共同判断。

Harness Session 是一次 Agent/Harness 交互或会话容器，负责承载消息、上下文装配、模型或执行器连续性以及会话级恢复。它可以承载多个 Work Thread、Task、Execution 或 Run，也可能只进行讨论而没有 Run；因此不能用 Session 替代工程工作对象。

Checkpoint 是可恢复的时间点快照，记录当时的工作位置、已知事实、未决决策、输入引用、待办和恢复约束。Checkpoint 应不可变；继续工作时创建新的 Checkpoint，而不是覆盖旧 Checkpoint。Checkpoint 只提供恢复依据，不自动重新授予已过期的权限，也不保证其引用的 branch、环境或工具仍然可用。

#### 2. 代码、上下文、环境、产物和结论层

Revision 是代码或其他可版本化对象的具体身份锚点，可以来自 commit、变更集、标签、补丁基线或外部版本标识。Branch 是可移动的命名引用，不能替代稳定 Revision；rebase、force-push 或分支切换可能改变其指向。一个 Scenario 可以同时关联多个 repo、branch 和 revision，并需标注它们之间是基线、比较对象、依赖、目标修改、复现版本还是历史参考。

Context Manifest 是一次对工作所需上下文的声明和装配结果：包括要带入的 Revision、文件/符号范围、任务与场景引用、证据引用、策略限制、脱敏结果和必需的环境条件。它是“本次工作使用或拟使用哪些上下文”的可审计视图，不是原始代码、完整日志或权限本身；Manifest 变化应生成新版本或新快照。

Environment Snapshot 是某一时点对运行条件的可追溯描述，例如操作系统、运行时、依赖、容器/镜像、配置摘要、服务端点类别、特性开关、硬件和时间窗口。它应尽量通过实际观察或可验证声明建立，不能把一个历史环境快照当作当前环境保证。缺少关键环境来源时，应降低验证结论的适用范围，而非补猜值。

Artifact 是工作过程中产生、引用或交付的可识别产物，例如 diff、补丁候选、构建包、测试报告、日志摘录、截图、RCA 草案或脱敏知识候选。Artifact 可以是源产物，也可以是由 Run、Evidence、其他 Artifact 或人工编辑派生的产物；“Artifact”本身不等于“Knowledge Asset”，发布为知识需要另行经过知识治理、权限和撤回控制。

Decision 是对方向、范围、授权、假设、风险接受、关闭、重开或发布的明确判断。Decision 必须带有提出者、决策依据、适用范围和版本/时间；自动生成的建议只能是 proposed，不应伪装成人工批准。后续决策可以 supersede 旧决策，但不得擦除旧决策及其当时依据。

RCA 是对症状、影响、触发条件、证据、假设、根因、促成因素、修复、验证和残余风险的版本化解释。RCA 可以引用 Scenario、Revision、Run、Artifact 和 Decision，但不拥有修改代码、执行工具或发布知识的权限；RCA 结论与场景状态也必须分开演进。

#### 3. 对象职责与生命周期草案

下表是语义和审计边界，不是最终状态机或字段 Schema。状态名称、转移条件和阈值应由真实工作流、风险级别和治理矩阵继续校准。

| 对象 | 主要职责 | 生命周期关注点 | 不应承担的职责 |
|---|---|---|---|
| Code Scenario | 维护工程问题/目标的范围、关联证据、解决判断和长期连续性 | 创建、调查、暂停、关闭、重开、派生、撤回/失效 | 不充当 Task、Run 或执行授权 |
| Work Thread | 维护跨执行者的工作连续性、交接、阻塞和下一步 | 开启、推进、暂停、恢复、交接、结束、重开 | 不等于 Harness Session 或最终知识 |
| Task | 表达可分派的工作承诺和完成条件 | 提议、就绪、进行、阻塞、完成、取消、重开 | 不直接证明场景解决或知识发布 |
| Work Phase | 组织复现、诊断、修复、验证等阶段 | 进入、暂停、完成、回退、跳过、重开 | 不替代 Task 目标或 RCA 结论 |
| Execution | 记录一次逻辑工作尝试及其结果 | 计划、开始、暂停、失败、结束、重试、放弃 | 不等同于一次具体工具进程 |
| Run | 记录一次受约束的具体执行实例和执行证据 | 请求、门禁、运行、成功、失败、中断、重试/恢复 | 不单独决定场景已解决 |
| Harness Session | 承载 Agent/Harness 的交互和上下文连续性 | 创建、活跃、挂起、恢复、结束、过期 | 不拥有工程对象的业务关闭权 |
| Checkpoint | 固化可恢复的历史位置和恢复输入 | 创建、验证、消费、supersede、失效 | 不恢复旧权限或覆盖历史 |
| Revision | 锚定代码/配置/依赖的版本身份 | 创建、引用、比较、标记失效或不适用 | 不表达工作进度或根因结论 |
| Context Manifest | 声明并审计一次上下文装配 | 草拟、装配、审核、使用、重算、失效 | 不替代 ACL、ToolPolicy 或 RunGate |
| Environment Snapshot | 锚定一次观察到的运行条件 | 采集、校验、引用、过期、撤回 | 不保证未来环境一致 |
| Artifact | 保存可识别的中间或交付产物 | 产生、校验、版本化、引用、发布候选、撤回 | 不自动成为知识或可执行动作 |
| Decision | 保存带依据的判断和授权/方向选择 | 提议、接受、拒绝、supersede、撤回 | 不隐藏依据，不凭历史自动授权 |
| RCA | 版本化解释问题原因与修复验证 | 取证、假设、确认、验证、监控、重开、替代、撤回 | 不替代事实证据或执行门禁 |

可以有示例性的生命周期，但本轮不固化全量状态集合：Scenario 可从新建到调查、诊断、待修复、验证、解决，并旁路暂停或重开；Task/Phase/Execution/Run 分别维护自己的进度；Session/Checkpoint 维护会话和恢复；RCA/Artifact/Manifest 维护版本与有效性。任何状态转移都应追加事件并引用证据，不能只更新一个当前状态字段。

#### 4. 建议关系骨架

关系描述应区分“包含/组织”“引用/使用”“产生/派生”“验证/解释”“授权/约束”和“替代/撤回”，不要只用一类通用 `related_to`。下列关系表达方向性和语义，具体名称可在后续协议设计时调整：

```text
Code Scenario
  ├── organizes → Work Thread
  ├── scopes → Revision / Environment Snapshot
  ├── assembles_from → Context Manifest
  ├── records → Decision / RCA / Artifact
  └── reopened_by / derived_into → later Scenario

Work Thread
  ├── decomposes_into → Task / Work Phase
  ├── coordinates → Execution / Run
  ├── resumes_from → Checkpoint
  ├── uses → Context Manifest / Environment Snapshot
  └── records → handoff / blocker / decision events

Task
  ├── grouped_by → Work Phase
  ├── attempted_by → Execution
  ├── hosted_in → Harness Session
  ├── constrained_by → current policy and authorization
  └── completed_by → Decision / Verification evidence

Execution
  ├── materialized_as → Run(s)
  ├── uses → Revision / Context Manifest / Environment Snapshot
  ├── observes → Tool Call / Log / Test Result
  ├── fails_with / succeeds_with → Evidence
  └── produces → Artifact / Verification / Checkpoint

Run
  ├── admitted_by → RunGate decision
  ├── bounded_by → ToolPolicy
  ├── emits → immutable execution events
  ├── produces → Tool Call / Log / Test / Artifact
  └── contributes_to → Task / RCA / Verification / Scenario evidence

Artifact / Evidence / Decision / RCA
  ├── has_source → user statement / repository / tool / human review
  ├── was_derived_from → source evidence and prior versions
  ├── applies_to → Revision / Environment / scope
  ├── verified_by → Verification result or review
  └── invalidated_by / superseded_by → later event or decision
```

关系本身也应具备来源、时间、创建者/执行者、适用范围、版本、敏感级别、ACL、用途、完整性和撤回传播信息。关系不应隐式扩大被关联对象的权限：引用一个私有 Log 不会让引用者获得 Log 内容；引用一个已发布知识候选不等于获得执行权限。

#### 5. source 与 derived 的分层

建议把对象和证据分成以下几类，而不是简单以“原始/非原始”二分：

- **observed source**：实际读取的 commit、工具返回、命令退出结果、测试结果、日志、环境探针、用户明确陈述；
- **declared source**：用户或授权系统声明的目标、约束、授权、业务影响和完成条件，仍需标注声明者和是否已验证；
- **curated source**：人工审核后确认的 Decision、根因结论或范围判断，必须保留审核依据和版本；
- **derived**：由解析、聚合、摘要、相似性关联、候选 RCA、Context Manifest、统计视图或知识投影生成的内容，必须能回溯到输入和生成规则；
- **mixed**：含有源事实和派生解释的对象，例如带证据引用的 RCA 或含人工裁决的场景摘要，应分别标注事实段和推断/裁决段。

Derived 不应覆盖 source。抽取器可以生成新的 Evidence 或候选关系，但不能把模型推断写回成 observed fact；修订、纠错、脱敏和撤回都通过新版本/新事件表达。Artifact 既可能是 Run 的源输出，也可能是由多个源证据整理出的派生产物，因此血缘要落在实例和版本上，而不是仅落在类型上。

#### 6. 失败、恢复、重开和派生

工具调用、日志、测试和失败不能只作为 Run 的字符串输出；至少要能按发生顺序关联到调用主体、输入上下文、目标 Revision/Environment、退出或结果、敏感处理、证据引用和后续判断。失败类型应覆盖命令/构建/测试失败、假设被证伪、权限拒绝、工具不可用、环境不一致、超时、取消、修改引入回归和用户拒绝/取消。

暂停与恢复的语义应是：

```text
active work
  → pause event + Checkpoint + blocker/required decision
  → later resume request
  → re-check current identity, ACL, Revision, Environment, Context Manifest,
    ToolPolicy and RunGate
  → continue as new Execution/Run or explicitly resume the logical attempt
```

恢复不能盲目重放历史工具调用，尤其不能重放有副作用的写操作。重开表示新证据、复发、权限/环境变化或验证不足使既有结论不再足够；应关联旧 Scenario/RCA/Decision 并产生新的版本或工作分支。派生 Scenario 表示从共同历史中拆出不同问题、版本、Project 或处理目标，继承的是经授权的引用和血缘，不是原场景的全部权限或关闭结论。

#### 7. 多 repo、revision、branch 和 environment

一个 Scenario 可以包含：

```text
repo A @ revision a1, branch feature-x, environment test
repo A @ revision a2, branch main,    environment staging
repo B @ revision b7, branch release, environment production-like
```

但每个 Evidence、Artifact、RCA 判断和 Verification 都要能说明其实际适用的 repo/revision/environment 范围。branch 只作为当时的命名线索和观察值；稳定引用应落到可验证的 revision 身份。rebase 或 force-push 后，旧 revision 仍是历史事实，新 revision 需要重新建立比较和验证关系。

跨 repo 或跨环境关联需要明确关系类型：依赖、镜像、服务调用、共同变更、复现目标、对照版本或仅为相似参考。相似错误签名、同名 branch 或相同路径不构成同一代码事实。缺少版本、环境或跨仓库血缘时，结果只能作为候选参考，不能自动进入当前 Context Manifest、确定性 RCA 或可执行 Patch。

#### 8. 共同 envelope 与对象专属 payload

建议所有对象、事件、快照和关系共享一个概念上的 envelope，用于承载跨对象一致的审计维度：对象/事件身份、类型与版本、发生/观察/生效时间、主体和租户边界、父子或关联引用、来源与派生链、完整性/幂等线索、敏感级别、ACL、用途、撤回/有效性信息以及当前视图所需的状态提示。

各对象再拥有专属 payload：

- Scenario：问题目标、影响范围、解决判断和场景级摘要；
- Work Thread/Task/Phase：工作目标、责任、分解、完成条件、阻塞和交接；
- Execution/Run/Session：执行计划、具体输入、运行器、会话关系、结果和执行证据；
- Revision/Manifest/Environment：代码身份、上下文装配和运行条件；
- Checkpoint/Artifact：恢复点和产物引用、内容摘要、校验及派生关系；
- Decision/RCA：判断、依据、适用性、验证、风险和审查记录。

这里的 envelope 和 payload 是设计分层，不是最终字段清单。不要在本轮决定字段名称、必填性、嵌套形式、序列化格式、API 路径、数据库表、事件主题、状态枚举或状态阈值；这些应由后续 Schema/接口/存储/事件专题基于真实样本和兼容性要求分别定案。

#### 9. 权限分离：知识、执行、工具和两个独立门禁

至少分成三种权限面：

1. **知识权限**：读取、检索、引用、导出、发布、共享、撤回 Knowledge Asset 或 RCA/Artifact 投影；
2. **执行权限**：提出、批准、启动、暂停、恢复、重试、取消某个 Action/Execution/Run，以及接受风险或变更结果；
3. **工具权限**：调用某类工具、访问某个资源、使用某种参数/网络/文件/生产能力的具体能力边界。

`ToolPolicy` 是能力和约束声明，例如工具类型、资源范围、参数限制、网络/文件/环境约束、禁止事项和审计要求；它不是某一次执行的批准。`RunGate` 是针对当前主体、当前 Run、当前 Context Manifest、当前风险和当前授权的准入/持续控制；它不是 ToolPolicy 的替代，也不得放宽 ToolPolicy。两者独立检查：没有 RunGate 不能运行；有 RunGate 但超出 ToolPolicy 仍不能运行；知识可读/可引用也不会自动获得执行或工具权限。

RunGate 的判断还应重新核验当前身份、Project/租户、资源 ACL、敏感策略、Revision/Environment 适用性、幂等/副作用风险、人工确认和撤回状态。历史 Run、历史 Decision 或历史 Checkpoint 只能证明当时曾经允许或发生过什么，不能直接作为当前授权。

#### 10. 不可变事件、版本、快照与幂等

建议采用“不可变事件 + 版本化对象 + 可重建当前视图”的原则：

- 事件只追加，不修改已记录的事实；发现错误时追加更正、撤回、supersede 或 invalidation 事件；
- 对象内容的变化产生新版本，旧版本保持可审计并明确有效性；
- 当前 Scenario/Thread/Task/Run 视图是事件和对象版本的派生投影，可以重建，不能把投影当作唯一事实；
- 每次事件、关系和派生结果都应有生产者/来源、时间、输入引用、规则或人工依据及幂等线索；重复投递不得产生重复副作用；
- “观察到”“声明”“推断”“人工确认”“执行结果”必须可区分，不能因为进入同一时间线就获得同等可信度；
- append-only 不等于永不撤回。敏感数据、权限变化或来源撤回可以使当前投影不可见、不可用或不可执行，同时保留最小必要审计指针；
- 历史快照可用于审计、复盘和解释过去的 Context Manifest，但不授予当前访问权、发布权、执行权或工具权；当前请求必须重新做权限、适用性和门禁判断。

### 阶段2权威/官方机制调研（访问日期2026-09-20）

本阶段只提取可借鉴的机制，不把外部标准的对象命名或字段直接当成平台最终模型。

#### 1. OpenTelemetry：观测关联，不是业务工作流模型

OpenTelemetry 官方 Signals 文档将 Traces、Metrics、Logs 等作为可观测信号，并通过上下文传播和 Trace/Span 关联帮助串起一次操作及其子操作。对本议题的启发是：Run、Tool Call、日志、测试和验证应保留可互相关联的 trace/span 或等价关联线索，便于从具体执行回到 Work Thread 和 Scenario。

边界是：OpenTelemetry 主要解决观测数据的采集、关联和导出，不定义 Scenario、Task 完成、RCA 根因、知识发布、ACL、RunGate 或撤回语义。因此 trace/span 只能作为证据关联和时间线线索，不能直接推导“场景已解决”或“允许执行”。

#### 2. W3C PROV-O：Entity、Activity、Agent 与派生/生成关系

W3C PROV-O 用 `Entity`、`Activity`、`Agent` 及其关系表达实体、活动、代理、使用、生成、关联和 `wasDerivedFrom` 等 provenance 语义。这与本议题的 source/derived、Run 产生 Artifact、Evidence 支持 RCA、Decision 由 Agent/人工作出等关系高度契合。

建议借鉴其方向性：源证据、Artifact、Revision 和 Decision 可作为实体；Run/Execution 可作为活动；用户、Agent、Harness、工具或审核者可作为代理；用使用、生成、派生和关联表达血缘。边界是 PROV-O 是通用 provenance ontology，不替代平台的对象职责、状态、权限、敏感等级、撤回传播或执行审批；映射应保持可解释，而不是为了“符合 ontology”强行合并对象。

#### 3. SLSA：产物 provenance 与构建环境证据

SLSA 官方规范关注软件供应链 provenance，包括产物 subject、构建定义、外部参数、构建器和已解析依赖等信息，并强调验证 provenance 以支持产物可信性判断。对本议题的启发是：构建/测试 Artifact 应能说明其对应 Revision、构建定义、依赖、执行环境和产生它的运行器，且验证时应检查 subject 与实际产物是否匹配。

边界是 SLSA 主要针对软件供应链和构建 provenance，不涵盖用户任务分解、跨会话恢复、RCA、人工决策、知识权限或一般工具执行授权。可以把 SLSA provenance 作为某类 Artifact/Environment/Run 的强证据来源，但不能将 SLSA 合规或构建成功等同于 Scenario 已解决。

#### 4. CDEvents/CloudEvents：事件互操作的参考 envelope

CDEvents 官方资料面向软件交付生命周期事件，并以 CloudEvents 生态的事件上下文和 subject/type 等概念支持不同 SDLC 工具之间的互操作。对本议题的启发是：如果未来跨 Connector、CI/CD、测试或部署系统交换事件，应把事件来源、类型、主体、时间、关联上下文和幂等线索与领域对象引用分开，避免把某个系统的内部表结构直接暴露为平台契约。

边界是 CDEvents 描述的是交付领域的互操作事件，不是本平台完整的 Scenario/Thread/Task/Run 模型，也不定义 RCA、敏感数据、知识发布、RunGate 或 ToolPolicy。可借鉴事件 envelope 和互操作思路，但领域 payload、权限判断和状态阈值仍需独立设计。

#### 5. Git 官方机制：Revision 稳定锚点与 branch 移动性

Git 官方文档区分 revision、commit、branch、ref 和 worktree 等概念。对本议题的直接启发是：代码事实和验证结果应优先绑定可解析的具体 revision/object identity；branch 是引用名和工作流线索，可能移动；worktree 是某个工作目录视图，不能单独作为代码版本身份。rebase、重写历史、分支切换和多 worktree 都要求重新记录关系，而不是假设路径或 branch 名足以说明代码相同。

边界是 Git 只表达版本控制事实，不知道业务问题是否解决、环境是否等价、工具是否安全、RCA 是否成立或知识是否可以发布。Git revision 作为证据锚点仍需与 repo 身份、环境快照、作用范围、权限和验证结果共同使用。

#### 6. JSON Schema/OpenAPI：契约校验参考，不提前冻结领域模型

JSON Schema 的核心机制支持对实例进行结构、类型、约束和注解校验；OpenAPI 可用于描述 HTTP API 的请求/响应契约。对本议题的启发是：未来可以分别为 envelope、对象 payload、事件和接口建立可演进的契约，并用版本、兼容性和校验结果防止字段漂移。

边界是：Schema/API 描述不能自行解决对象语义、来源可信度、派生血缘、撤回传播、当前授权或事件幂等。尤其不能因为一个历史 JSON 能通过 Schema，就认为它拥有当前权利或代表真实观测。最终字段、兼容策略、存储模型和 API 形态留待后续专题。

### 阶段3综合结论与建议

#### 1. 结论

本轮形成以下阶段性结论：

> **Code Scenario 是面向工程问题/目标的长期边界和解决判断；Work Thread 是跨执行者的连续工作；Task 是可分派的承诺；Work Phase 是工作组织单元；Execution 是逻辑尝试；Run 是受当前门禁约束的一次具体执行；Harness Session 是会话容器；Checkpoint 是不可变恢复点；Revision、Context Manifest 和 Environment Snapshot 分别锚定代码身份、使用上下文和运行条件；Artifact 保存产物；Decision 保存判断；RCA 保存版本化解释。它们通过有方向、有来源和有适用范围的关系连接，但不合并为单一 Memory。Scenario 不是 Task/Run，Run 成功不是场景解决，Task 完成不是知识发布。所有派生结论、知识投影和执行结果都必须保留 source/derived 血缘、敏感与权限边界；知识权限、执行权限和工具权限分离，RunGate 与 ToolPolicy 独立；事件和对象版本追加且不可变，历史快照只证明过去，不授予当前权利。**

#### 2. 建议的最小实现分层

1. **事实采集层**：接收用户声明、repo/revision、工具调用、日志、测试、环境探针和人工事件，先保存来源、时间、敏感和完整性线索；
2. **对象与关系层**：以 Scenario/Thread/Task/Phase/Execution/Run 等对象组织工作，建立引用、使用、生成、派生、验证、替代和撤回关系；
3. **恢复与视图层**：由不可变事件和对象版本派生当前工作视图、Checkpoint、Context Manifest 和待办，不把视图更新当作事实覆盖；
4. **证据与 RCA 层**：把失败、假设、修复、验证和残余风险独立建模，允许多个证据和多个结论版本；
5. **知识治理层**：对 Artifact/RCA/Scenario 摘要生成 Knowledge Candidate，单独处理发布、检索、引用、撤回和消费者状态；
6. **执行治理层**：从当前上下文生成 Action/Execution/Run 请求，分别通过当前授权、RunGate 和 ToolPolicy，写回不可变执行证据；
7. **跨系统适配层**：用 OpenTelemetry/CDEvents 等机制接入观测或交付系统，用 Git/SLSA/PROV-O 语义补充 revision、产物和血缘，而不让外部协议决定领域边界。

#### 3. 应优先验证的工作样例

建议先用少量真实样例校准关系和生命周期，而不是先写全量 Schema：

- 单 repo、单 revision、单环境的“复现—修复—回归验证”；
- 同一 Scenario 在两个 branch 和两个 revision 上并行排查，最终一条线被证明不适用；
- 工具权限不足导致 Run 被拒绝，之后由人工补充授权再启动新 Run；
- Run 成功但测试/线上验证不足，Scenario 仍保持未解决或待确认；
- Task 完成后生成 RCA/Artifact 候选，但知识发布被权限或敏感策略阻断；
- Session 结束后使用 Checkpoint 恢复，但当前 branch、环境或 ToolPolicy 已变化，需要重新确认；
- 源日志撤回后，相关 RCA、Manifest、Embedding/知识投影和后续 Run 被暂停或重新评估；
- 同一问题在新 revision 复发，派生新 RCA/Scenario 关系而不是覆盖旧历史。

### 阶段4专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| 系统架构 | 如果一个 Run 关联多个 Task，或一个 Task 跨多个 Run，如何避免关系歧义？ | 用 Execution 表达逻辑尝试、Run 表达具体执行、Task 表达承诺；允许关系带角色和适用范围。具体基数和一致性规则留待真实样例验证。 |
| SRE/可观测性 | Trace/Span、日志和测试结果可能乱序、重复或采样，能否作为完整事实？ | 只能作为带来源和完整性标记的证据；采用关联线索而非假设全量事件，缺失/采样必须影响证据强度和验证结论。 |
| 安全/合规 | Checkpoint、历史 Manifest 和事件中可能残留凭据或过期授权，如何防止恢复越权？ | 快照与权利分离；恢复前重新检查身份、ACL、敏感、撤回、Revision、Environment、ToolPolicy 和 RunGate；敏感源撤回时按血缘暂停或隔离。 |
| 数据治理 | source 与 derived 可能混在同一摘要，如何支持撤回和解释？ | 保留事实/声明/推断/裁决分段及输入引用；派生对象版本化、可重算、可失效，不能只保留不可解释的最终摘要。 |
| DevOps/供应链 | 构建成功或 SLSA provenance 完整是否足以关闭代码场景？ | 不足。它只证明某类产物和构建过程；场景关闭还需 RCA、业务影响、修复范围、验证和残余风险判断。 |
| 产品/运营 | 用户只想“修好问题”，对象过多会不会增加负担？ | UI 可提供 Scenario/Thread/Task 的简化视图，但底层仍需保留 Run、Evidence、Revision、权限和血缘；不以简化界面牺牲可审计边界。 |
| 知识工程 | Task 或 RCA 完成后能否自动发布经验？ | 不能默认发布。知识发布是单独的知识权限与治理动作，必须检查敏感、ACL、血缘、适用范围、验证和撤回能力。 |
| Agent/Harness 运行时 | 恢复是否应该重放原 Run，还是新建 Run？ | 无副作用的读取可在策略允许时重建上下文；有副作用或环境变化时默认新建/重新门禁的 Run，并关联旧 Execution/Checkpoint，禁止无条件重放。 |

挑战后仍需坚持的反例约束：

```text
Run succeeded            ≠ Scenario resolved
Task completed            ≠ Knowledge published
Branch name matches       ≠ Revision is identical
Historical authorization  ≠ Current authorization
RCA confidence            ≠ Tool execution permission
Trace correlation         ≠ Complete causal proof
Artifact exists           ≠ Artifact is trusted or publishable
Checkpoint exists         ≠ Checkpoint can restore old rights
```

### 自动审核与推进

本轮可由自动审核器执行的检查：

1. 检查对象是否属于已声明边界，是否错误地把 Scenario、Task、Run、Session 或 RCA 当作同一类型；
2. 检查每个事实、关系、Artifact、RCA 候选和摘要是否有来源、时间、适用 Revision/Environment 和派生引用；
3. 检查 Run 是否同时具备当前 Context Manifest、Environment Snapshot、主体、幂等线索、RunGate 结果和 ToolPolicy 约束引用；
4. 检查 Task/Run/Scenario 的状态是否被错误地自动联动，例如 Run 成功直接关闭 Scenario、Task 完成直接发布知识；
5. 检查 branch 是否被错误当成稳定 revision，跨 repo/环境关系是否缺少明确类型和血缘；
6. 检查工具调用、日志、测试、失败、修复、验证是否可定位到具体 Execution/Run 和证据版本；
7. 检查暂停、恢复、重开、派生是否追加新事件/版本，恢复前是否重新执行当前权限和门禁检查；
8. 检查敏感、撤回、ACL 或血缘缺失时是否进入隔离/暂停/阻断，而不是继续检索、发布或执行；
9. 检查重复事件、重复投影和重试是否具备幂等行为，不产生重复副作用；
10. 检查历史快照或历史 Decision 是否被错误地当作当前权利；
11. 检查知识权限、执行权限、工具权限是否分开记录，且 RunGate 没有替代或放宽 ToolPolicy；
12. 检查派生对象能否回溯 source，撤回源证据后是否能枚举受影响的 RCA、Manifest、Artifact、知识投影和 Run。

自动审核器可以标记缺失、冲突、候选关系和风险，也可以生成新的派生报告或待确认 Decision；不能自动确认最终 RCA、接受高影响风险、关闭 Scenario、发布敏感知识、扩大权限或批准高风险 Run。状态推进应至少分为“自动可推进的机械性记录”“需要人工/受控审核的语义判断”“必须阻断的安全/血缘缺失”三类，具体门槛和角色矩阵留待治理专题。

## 子议题深化2第1轮：跨 repo、跨 revision 的场景合并、分支和 rebase 处理

### 主题与成功标准

本轮针对前述第二项明确暂缓事项，讨论跨 repo、跨 revision、分支演进和代码变更复制场景下，如何建立可审计的场景关系、映射和合并候选。这里的“合并”首先是关系判断或生成派生场景，不是静默把两个 Scenario、RCA、Task、Run 或 Knowledge 合成一个对象，也不是修改 Git 历史。

本轮成功标准：

1. 明确区分“同一工程问题”“相似文本”“同一代码变更”和“同一运行”，并避免用错误签名、标题、路径、branch 名或单一 hash 直接证明它们相同；
2. 明确建模 repository identity、commit/tree/blob/revision、branch/ref/tag、fork/mirror、worktree、submodule、monorepo、多 repo dependency 和 environment 的不同身份及边界；
3. 能描述 merge、rebase、cherry-pick、squash、split、duplicate、related、derived 等关系的证据、方向、适用范围和不确定性，而不把它们静默归一为 merge；
4. 能保留 common base、patch provenance、revision mapping、semantic equivalence、validation 及冲突类别；映射不完整、关系冲突或含义不明时，结果进入 candidate/review/isolate，绝不自动高置信关闭；
5. 源 Scenario、RCA、Task、Run、Knowledge 和其历史保持可追溯；生成的合并场景必须是带血缘的 derived 对象，不能覆盖或删除来源，也不能继承来源的全部权限；
6. 明确 Scenario/RCA/Task/Run/Knowledge 仍然分离，权限判断独立，RunGate 与 ToolPolicy 的既有边界不因跨 repo 或跨 revision 关系而改变；
7. 只形成语义和验证边界，不冻结最终图算法、Schema、Git provider API、阈值、模型或 SLA。

### 阶段1头脑风暴

#### 1. 先区分四类“相同”

以下四类关系应分别记录，不能用一个 `same` 或 `merge` 字段代替：

| 判断对象 | 能说明什么 | 不能直接说明什么 |
|---|---|---|
| 同一工程问题 | 症状、影响、触发条件、代码/服务范围和业务目标可能属于同一问题边界 | 不证明使用了同一 repo/revision、同一根因、同一修复或同一场景生命周期 |
| 相似文本 | 标题、错误消息、堆栈或自然语言描述有相似表达，可用于检索候选 | 不证明问题、根因、代码、变更或运行相同 |
| 同一代码变更 | 两个 revision 之间存在可追溯的同一变更、补丁系列或等价效果候选 | 不证明它们解决同一工程问题、在同一环境有效或应合并 Scenario |
| 同一运行 | 两条证据来自同一个可验证的 Run/Execution 身份或同一执行事件 | 不证明同一 Run 只服务一个 Scenario，也不证明该 Run 成功解决场景 |

因此，`similar_text` 可以支持检索；`same_change` 需要补丁或 revision 映射证据；`same_run` 需要运行身份和事件关联；`same_problem` 还需要 RCA、范围和验证证据。任何一类关系都不能绕过当前权限、敏感性和适用性检查。

#### 2. 代码身份必须分层

**Repository identity** 是仓库主体的身份，不等于显示名称、目录路径或默认远端 URL。平台至少应保留来源系统、组织/命名空间、provider 资源标识、可验证的 canonical 来源、fork/mirror 关系和采集时间；Git 本身不提供跨服务的全局 repository identity，因此外部声明只能先作为 assertion，不能无证据覆盖既有身份。相同名称、相同路径或相同 URL 文本不自动证明是同一仓库。

**Revision 与 Git object** 应区分：

- commit 是带 tree、父提交和元数据的提交对象；commit hash 是对象身份线索，但必须结合 hash 算法、对象类型、仓库命名空间、可解析性和来源证据；
- tree 描述某一目录快照，blob 描述文件内容；相同 tree 或 blob 可能被不同提交、分支或仓库复用，不能单独证明同一 Scenario；
- `revision` 是平台引用的稳定版本锚点，可包含 commit、tag 指向对象、外部变更集或经验证的版本标识，必须注明来源和解析状态；
- **同一 hash 不等于同一场景**：即使对象内容或 commit hash 相同，也不能跳过问题范围、运行环境、来源权限、证据和生命周期判断。

**Branch/ref/tag** 是命名引用或观察值，不是稳定的场景身份。branch 可以移动，force-push 或 rebase 会改变其指向；tag 也必须记录其对象类型和解析时刻，不能只保存 tag 名。应同时记录“当时 ref 指向的 revision”和当前重新解析结果，二者变化时追加事件而不覆盖历史。

**Worktree** 是某个仓库的工作目录视图，可能有独立 HEAD、index、未提交改动和环境状态；同一 repo 可以有多个 worktree。路径、worktree 名或本地目录不等于 repo identity 或 revision identity，dirty state 必须单独作为证据和适用性限制。

**Fork/mirror、submodule、monorepo 和多 repo dependency** 也不能混为一谈：

- fork 是独立仓库主体，需保留 `forked_from`、同步时点和分叉关系；
- mirror 是复制/同步关系，需保留源、目标、方向、同步状态和是否允许回写，不能因内容暂时相同而合并身份；
- submodule 是主仓库中的特定子仓库 revision 指针，子仓库有自己的 repo identity 和历史；
- monorepo 仍是一个 repo identity，但文件/目录、组件、构建边界和子问题范围可以不同；路径相同或模块同名不构成跨仓库等价；
- 多 repo dependency 是构建、服务调用或版本约束关系，不是 Git merge，也不表示依赖仓库与主仓库属于同一场景；
- environment 是运行和验证条件的独立身份。相同 revision 在测试、预发布、生产或生产仿真环境中不能默认视为同一运行或同一验证结论。

#### 3. 关系词必须表达不同的历史事实

| 关系 | 语义边界 | 场景处理原则 |
|---|---|---|
| `merge` | 两条历史通过共同基线和合并操作形成新的历史结果 | 只证明历史组合，不证明问题相同或自动关闭来源 Scenario |
| `rebase` | 将一组提交相对于新的基线重新播放，通常产生新的提交身份 | 保留旧/新提交映射、基线和未映射项；不能把新旧 commit 当同一对象 |
| `cherry_pick` | 将一个或多个已有提交引入另一条历史并生成新的提交 | 记录源 commit、目标 commit、应用结果和冲突；这是变更来源关系，不是场景合并 |
| `squash` | 多个提交压缩为较少提交或一个提交 | 记录源范围、压缩结果和可能丢失的逐提交映射；不能伪造精确一一对应 |
| `split` | 一个变更、提交序列或场景被拆出多个目标范围 | 目标是 derived 场景/变更候选，来源保持不变，不能静默关闭原场景 |
| `duplicate` | 发现重复或高度重叠的候选对象 | 只生成去重候选，等待范围、权限和生命周期审核 |
| `related` | 存在主题、依赖、共同证据或时间关系，但未确认相同 | 不进入默认高置信合并或自动关闭 |
| `derived` | 从一个或多个来源经过明确规则、人工判断或分析生成新对象 | 必须保留 source、规则/依据、版本和适用范围，生成对象不继承全部来源权限 |

`merge`、`rebase`、`cherry_pick`、`squash`、`split`、`duplicate`、`related` 和 `derived` 都不是“静默 merge”的别名。关系还应说明方向、证据来源、映射完整性、创建者、时间、适用 revision/environment 和当前审核状态。

#### 4. 合并候选需要多层证据

建议按以下顺序形成候选，而不是直接按文本或相似度合并：

```text
repo identity / object identity
  → common base 与历史拓扑
  → patch provenance / revision mapping
  → 文件、符号、依赖和 API 范围
  → semantic equivalence 候选
  → environment 与验证结果
  → Scenario / RCA / 生命周期判断
  → candidate / review / isolate / accepted relation
```

- **Common base**：记录共同祖先、比较两端、是否存在多个可用 base、base 的解析来源和时间。共同祖先只说明历史关系，不说明问题或变更语义相同；
- **Patch provenance**：记录源 commit、目标 commit、diff/patch、patch-id 或 patch series 比较、应用方式、作者/工具声明和结果。patch-id、文本重叠或相同文件范围只能生成候选；
- **Revision mapping**：记录 old revision → new revision 的方向、方法、映射粒度、映射完整性和未映射/多对一/一对多项。rebase、squash 和 split 不能强行填成一一映射；
- **Semantic equivalence**：结合代码结构、行为、依赖、配置、API、测试、运行观察和人工/受控审查判断。代码文本相同、补丁相似或编译通过都不足以单独证明语义等价；
- **Validation**：在当前目标 revision 和 environment 中重新检查原问题、修复效果、回归、剩余风险和权限。历史验证只说明当时版本和环境，不自动升级为当前结论。

#### 5. 冲突、缺失和不确定性必须显式降级

至少区分以下冲突类别：

```text
identity_conflict       repo、provider、对象类型或 hash 算法不一致
history_conflict        common base、parent、merge/rebase 拓扑不一致
mapping_conflict        old/new revision 映射多解、缺失或完整性不足
content_conflict        patch、文件、符号或上下文无法无冲突应用
semantic_conflict       代码结果看似相近但行为、API、依赖或业务含义不同
environment_conflict    OS、runtime、依赖、配置、服务或数据条件不一致
evidence_conflict       运行、测试、日志、人工声明或来源证据互相矛盾
permission_conflict     当前主体、源/目标 ACL、用途或敏感策略不满足
status_conflict         来源已关闭、重开、撤回或其结论与新证据不一致
```

缺失 common base、部分 patch mapping、无法验证语义、环境不匹配、来源撤回、权限不明或关系有多种解释时，最多形成低置信候选或进入审核/隔离；不得用默认值、最后写入者、单一模型分数或“没有冲突输出”把它提升为高置信关系，更不能自动关闭 Scenario 或 RCA。

#### 6. 保留来源和历史，派生合并场景

建议采用以下不可变方向：

```text
Source Scenario A / Source Scenario B
  → relation assertions + common base / patch / mapping evidence
  → candidate merged view or review package
  → accepted decision（如有）
  → Derived Scenario M
```

`Scenario M` 是派生对象，必须引用来源 Scenario 的版本、关系断言、证据、适用 revision/environment、审核决定和生成规则。A、B 的原始事件、RCA、Task、Run、Knowledge、权限和历史状态继续保留；M 的状态变化不能覆盖 A/B，也不能自动继承其关闭结论、ACL、执行权或工具权。若后续证据推翻关系，M 可以被标记失效、拆分或撤回，但来源历史不被静默改写。

Scenario 合并关系与 RCA 合并、Task 去重、Run 归并、Knowledge 发布是不同决策面。它们可以互相引用，但不能因为 Scenario 关系成立就自动合并 RCA、完成 Task、合并 Run、发布 Knowledge 或扩大权限。`RunGate` 仍只针对当前 Run/Execution、主体、上下文、风险和授权进行准入；`ToolPolicy` 仍只定义工具能力和约束，跨 repo/revision 关系不能放宽任一门禁。

### 阶段2权威/官方机制调研（访问日期2026-09-20）

本阶段只提取官方机制能支持的事实和可借鉴边界；Git、GitHub、SLSA 或 PROV-O 的命名不直接变成本平台最终 Schema、图算法或审批规则。

#### 1. Git revision、merge-base 与历史重写

Git 官方 `gitrevisions` 文档把 revision 参数作为解析提交和其他对象的命名机制，`git merge-base` 用于寻找三方合并可用的最佳共同祖先，并明确一对提交可能存在多个 merge base。可借鉴的是：common base 必须是带解析来源的历史证据，且应允许多解和不完整；不能把“有共同祖先”当作同一问题或同一变更证明。

Git 官方 `git-merge` 文档描述了基于共同祖先的三方合并和冲突处理；`git-rebase` 文档描述把提交重新应用到新的 upstream，并会判断已有等价提交等情况；rebase 后应保留旧提交、新提交、基线和被跳过/无法映射的项。由此可知，rebase 是历史变换和提交重放，不是旧/new commit 的身份合并，也不是 Scenario 自动合并。

#### 2. Git cherry-pick、patch-id 与 range-diff

Git 官方 `git-cherry-pick` 文档定义为应用已有 commit 引入的变更，并为每个变更记录新的 commit；发生冲突时由操作者继续、跳过或终止。`git-patch-id` 提供对补丁内容的变更签名辅助，`git-range-diff` 可比较两版 patch series。它们适合生成 patch provenance 或 revision mapping 候选，但补丁签名、应用成功或 patch series 相似都不等于同一 commit、同一 Scenario、同一根因或当前环境验证通过。

#### 3. Git worktree 与 submodule

Git 官方 `git-worktree` 文档将 worktree 描述为附属于同一 repository 的多个工作树及其区分元数据；这支持把 repo identity、worktree identity、HEAD、index 和 dirty state 分开记录。Git 官方 `gitsubmodules` 文档说明 submodule 作为另一个 Git repository 被主项目引用，主项目记录其特定 revision；因此 submodule 应以跨 repo dependency/嵌套引用处理，而不是把子仓库历史静默纳入主仓库 Scenario。

#### 4. GitHub 仓库复制、Fork/Mirror 的谨慎借鉴

GitHub 官方文档把 fork 作为独立的仓库对象，并提供仓库复制/镜像相关做法。可借鉴的是：fork 或 mirror 应保留源仓库、目标仓库、同步/分叉关系和时间状态，不能只因代码内容相同就合并 repository identity。GitHub 的产品语义、provider ID、权限和同步能力不应直接当作跨 provider 的统一 API；其他 Git provider 需要单独验证和适配。

#### 5. W3C PROV-O：来源、活动与派生

W3C PROV-O 以 Entity、Activity、Agent 及使用、生成、关联和 `wasDerivedFrom` 等关系表达 provenance。可借鉴的是把源 Scenario/Revision/Evidence、分析或映射活动、审核主体和派生 Scenario 分开，并保留方向性和来源。PROV-O 不定义代码相等性、Scenario 关闭、权限、RunGate、ToolPolicy 或 Git provider 关系，因此不能用 ontology 映射替代语义验证和治理判断。

#### 6. SLSA provenance：构建材料和验证边界

SLSA provenance 关注软件产物的 subject、buildDefinition、builder、材料和构建运行信息。可借鉴的是把构建/测试 Artifact 与输入 revision、依赖、构建器和环境绑定，并验证 subject 与实际产物是否匹配。SLSA provenance 能增强代码变更和验证的来源证据，但不证明两个 Scenario 是同一问题，也不授予跨 repo 访问权、知识发布权或 Run 执行权。

### 阶段3综合结论与建议

#### 1. 阶段性结论

> **跨 repo、跨 revision 的场景合并应被建模为“身份与历史证据 → 变更/版本映射 → 语义与环境验证 → 受控关系决定”的过程。Repository identity、commit/tree/blob/revision、branch/ref/tag、fork/mirror、worktree、submodule、monorepo、多 repo dependency 和 environment 分层记录；branch 名不是身份，同一 hash 也不是同一 Scenario。merge、rebase、cherry-pick、squash、split、duplicate、related、derived 各自保留历史语义，不能静默 merge。任何合并候选都必须保留 common base、patch provenance、revision mapping、semantic equivalence、validation 和冲突/缺失信息；源 Scenario、RCA、Task、Run、Knowledge、权限及历史不可覆盖，生成结果是可撤回的 derived Scenario。部分映射、冲突或关系不明时只能 candidate/review/isolate，绝不高置信自动关闭；RunGate 与 ToolPolicy 不因关系判断而改变。**

#### 2. 建议的最小语义分层

1. **Identity 层**：记录 repo、provider/namespace、对象类型、hash 算法、revision、ref/tag 观察值、worktree、submodule 和 dirty state；
2. **Topology 层**：记录 parent、common base、merge/rebase/cherry-pick/squash/split 的历史关系及其完整性；
3. **Change Mapping 层**：记录源/目标 commit 或 revision range、patch provenance、映射方向、粒度、方法和未映射项；
4. **Scope/Semantics 层**：记录文件、符号、模块、API、依赖、构建边界、业务影响、触发条件和不适用条件；
5. **Validation 层**：记录目标 revision、environment、测试/构建/复现/线上观察和人工审查的结果与局限；
6. **Relation Decision 层**：生成 `candidate`、`review`、`isolate` 或经授权接受的关系/派生 Scenario，保留断言、证据、责任主体和版本；
7. **Governance 层**：独立检查 Scenario/RCA/Task/Run/Knowledge 的权限、撤回、发布和执行边界，重新执行当前 RunGate 与 ToolPolicy 检查。

这些是后续实现必须能表达的语义层，不是最终图结构、字段集合或接口协议。

#### 3. 第一版优先验证的样例集

建议先用事件回放和真实脱敏样例验证，而不是先实现自动合并算法：

- 同一 repo、同一 commit、不同工程问题：验证“同一 revision 不等于同一 Scenario”；
- 两个 repo 使用相同 branch 名和相同 hash：验证 repository identity、来源和场景边界；
- fork、mirror 暂时同步后发生分叉：验证独立身份、同步关系和权限；
- 同一变更经过 merge、rebase、cherry-pick 和 squash：验证 old/new mapping、patch provenance 和一对多/多对一缺口；
- 一个提交拆成多个提交/场景，或多个提交聚合后又拆分：验证 split、derived 和不可逆信息损失；
- common base 多解、缺失或历史被重写：验证 history conflict 和 candidate/review/isolate；
- monorepo 不同目录、submodule 不同 revision、多 repo dependency 联动：验证 scope 和 dependency 不是 merge；
- 同一 revision 在不同 runtime、依赖、配置或生产仿真环境运行：验证 environment separately；
- patch 看似等价但测试、API、行为或业务影响不等价：验证 semantic conflict；
- Scenario 关系被接受但 RCA、Task、Run、Knowledge 权限或发布状态不同：验证对象和权限不串联，RunGate/ToolPolicy 不被放宽。

### 阶段4专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| Git/版本控制 | 同一个 commit hash 是否足以证明两个仓库和两个 Scenario 相同？ | 不足。须同时检查对象类型、hash 算法、repo 来源/命名空间、可解析性、问题范围、环境和生命周期；同 hash 只提供有限对象证据。 |
| 分布式系统/数据治理 | rebase、squash 或 split 后如何避免伪造精确映射？ | 记录映射方向、粒度、方法、完整性和未映射项；允许一对多、多对一、部分和未知，不用空字段伪装一一对应。 |
| DevOps/供应链 | patch-id、构建 provenance 或测试通过能否自动合并场景？ | 只能增强 patch/Artifact 证据，不能单独证明同一问题、语义等价、环境等价、根因一致或场景已解决。 |
| Monorepo/依赖治理 | monorepo 路径、submodule 和多 repo dependency 是否应该展开成一个图节点？ | 需要保留各自 identity 和关系；可以建立 scope、depends_on、pinned_to 或共同变更候选，但不静默合并 repo 或 Scenario。具体图形留待后续。 |
| SRE/运行验证 | 同一 revision 在不同环境失败/成功，是否应合并为一个场景？ | 先区分 environment 和触发条件；可以 related 或 same_problem_candidate，但验证结论按环境记录，不能用一处成功关闭另一处风险。 |
| 安全/权限 | 来源 Scenario 合并后，能否继承来源 ACL、Knowledge 发布权或 Run 权限？ | 不能。派生 Scenario 重新计算当前主体、来源/目标 ACL、用途、敏感性和发布状态；引用关系也不扩大权限。 |
| RCA/知识工程 | 代码变更映射被接受，是否可以同时合并 RCA 和 Knowledge？ | 不可以。Scenario、RCA、Task、Run、Knowledge 各自保留版本、证据、状态和审核；关系成立只生成候选引用。 |
| 产品/运营 | 用户需要一个“重复问题”按钮，严格边界会不会过于复杂？ | UI 可以隐藏复杂度并展示候选、依据、冲突和下一步，但底层必须保留 source/derived、review/isolate 和不可变历史，不能用便捷操作绕过审核。 |
| 执行治理 | 合并候选确认后，能否复用旧 Run 或直接执行 Patch？ | 不能。新请求仍按当前 Context Manifest、Revision、Environment、主体、RunGate 和 ToolPolicy 重新准入；旧 Run 只能作为历史证据或受限复用候选。 |

必须保留的反例约束：

```text
same branch name       ≠ same repository or revision
same hash               ≠ same scenario
same tree/blob          ≠ same commit history or same problem
similar text            ≠ same issue or root cause
same patch              ≠ same validation or same environment
rebase/cherry-pick     ≠ same commit identity
merge history          ≠ merge Scenario
Scenario relation      ≠ merge RCA/Task/Run/Knowledge
historical permission  ≠ current permission
accepted mapping       ≠ RunGate approval or ToolPolicy expansion
```

### 自动审核与推进

本轮可由自动审核器执行的检查：

1. 检查 repo identity 是否包含来源、命名空间/provider、对象类型、hash 算法、解析状态和时间；名称、路径、branch、tag、worktree 是否被错误当作稳定身份；
2. 检查 commit/tree/blob/revision 是否区分，same hash、same tree 或 same blob 是否被错误提升为 same Scenario；
3. 检查 fork/mirror、submodule、monorepo、多 repo dependency 和 environment 是否以独立对象/关系记录，而非静默合并；
4. 检查关系是否区分 same_problem、similar_text、same_change、same_run、merge、rebase、cherry-pick、squash、split、duplicate、related 和 derived；
5. 检查 common base、parent/topology、patch provenance、revision mapping、映射方向、粒度、完整性和未映射项是否可追溯；
6. 检查 semantic equivalence 是否有代码范围、依赖/API、触发条件、环境、测试/复现/人工审查证据，且没有把文本相似或 patch-id 当作充分证明；
7. 检查 identity、history、mapping、content、semantic、environment、evidence、permission 和 status 冲突是否显式标注；
8. 检查缺失、部分映射、冲突或歧义是否只进入 candidate/review/isolate，是否错误地自动接受关系、关闭 Scenario/RCA 或删除来源；
9. 检查 source Scenario、RCA、Task、Run、Knowledge 的版本、事件、权限和历史是否保留，derived Scenario 是否引用来源、规则、证据和适用范围；
10. 检查合并关系是否错误联动 Task 完成、Run 成功、Knowledge 发布、ACL 继承或 RCA 确认；
11. 检查跨 repo/revision 产生的新 Run 是否重新核验当前 Revision、Environment、Context Manifest、权限、RunGate 和 ToolPolicy；
12. 检查自动化只生成 assertion、mapping、candidate、review package 或 isolate report，不直接改写 Git 历史、扩大权限、执行 Patch、发布敏感 Knowledge 或高置信关闭场景。

自动审核器可以做身份解析、拓扑比较、变更映射、证据收集、冲突分类和回放报告；不能独自裁决语义等价、同一工程问题、最终根因、合并关闭、权限继承或高风险执行。推进分为“可自动记录的观察/映射”“需要人工或受控审核的关系/语义判断”“必须隔离或阻断的身份、权限、血缘和验证缺失”三类。

下一步自动推进：建立最小跨 repo/revision 事件回放测试集，覆盖 merge、rebase、cherry-pick、squash、split、fork/mirror、worktree、submodule、monorepo、多 repo dependency、environment 差异、部分 mapping 和冲突；输出关系候选、证据闭包、影响范围和阻断结果，先校准语义和失败路径，再讨论实现契约。

## 子议题深化3第1轮：RCA 多根因的完整因果图和自动裁决算法

### 主题与成功标准

本轮针对“RCA 多根因的完整因果图和自动裁决算法”这一明确暂缓事项，讨论如何表达多个相互作用的解释、证据和验证闭环。这里的“因果图”首先是可审计的解释与证据组织方式，不是立即建设图数据库、冻结字段 Schema，或授权系统自动裁决根因。

本轮成功标准：

1. 明确区分 `observation`、`symptom`、`correlation`、`association`、`causal hypothesis`、`confirmed root cause`、`contributing factor`、`trigger`、`condition`，不因时间先后、相关性、模型分数、单次修复成功或多数票而越级；
2. 能表达并行根因、必要条件、充分条件、反馈环、共同原因、缺失变量、替代解释和争议，而不强行压缩成单链或唯一根因；
3. 每条因果边都能追溯方向、证据、代码/服务版本、环境、适用范围、置信与不确定性、反事实或可验证预测，以及可能推翻它的反证；
4. 区分 source 与 derived，RCA 解释可追加、版本化、审查、撤回和重新打开，任何结论都能回到源观察、实验、运行、代码和环境上下文；
5. 明确根因确认不等于修复完成、不等于 Scenario 已解决、不等于知识发布、不等于执行授权；修复、验证、复发和使用反馈必须形成闭环；
6. 规定自动化仅生成候选、证据图、冲突/缺失提示和实验建议，不能自动确认高影响根因、关闭事故、扩大权限或执行修复；
7. 分离知识读取/发布权限、敏感数据权限、血缘与撤回控制、RunGate 和 ToolPolicy；本轮只形成语义、证据和治理边界，不固化最终因果算法、图 Schema、阈值、模型、领域标注或 SLA。

### 阶段1头脑风暴

#### 1. 先把“看到什么”“推测什么”“确认什么”分层

RCA 中的节点不应都叫“原因”。建议保留以下阶段性语义；它们是解释状态和使用边界，不是最终枚举或数据库字段：

| 术语 | 阶段性含义 | 可以支持 | 不能直接支持 |
|---|---|---|---|
| `observation` / 观察 | 在特定时间、来源、版本和环境中直接观测到的日志、指标、Trace、代码状态、测试结果或人工事实陈述 | 记录发生过什么及其上下文 | 直接说明为什么发生或具有普遍性 |
| `symptom` / 症状 | 面向用户、系统或业务表现的异常现象，如错误、延迟、数据偏差或失败率升高 | 定义需要解释的结果节点和影响范围 | 直接等于根因 |
| `correlation` / 相关性 | 两个变量或事件在给定样本、窗口和条件下共同变化的统计关系 | 生成检验候选、限定观察范围 | 证明方向、机制或反事实 |
| `association` / 关联 | 事件、对象、代码范围或上下文之间存在可追溯联系，但因果含义未确定 | 组织证据、寻找共同上下文和候选解释 | 证明一方导致另一方 |
| `causal hypothesis` / 因果假设 | 对方向、机制、适用条件和可观察后果的可反驳解释 | 指导实验、复现、对照和反事实检查 | 仅凭模型分数或叙述成为确认根因 |
| `confirmed root cause` / 已确认根因 | 在明确范围内经过足够独立证据、反事实/干预或受控审查支持，且替代解释已处理的结论 | 形成当前 RCA 解释及后续行动依据 | 表示修复完成、风险归零或可自动执行 |
| `contributing factor` / 促成因素 | 增加发生概率、扩大影响或降低恢复能力，但可能不是单独产生症状的完整机制 | 表达多因素和防御缺口 | 被自动提升为唯一根因 |
| `trigger` / 触发因素 | 使既有脆弱性、条件或机制在特定时点显现的事件 | 解释为何现在发生 | 证明触发因素是深层根因 |
| `condition` / 条件 | 使关系成立、失效或改变强度的环境、配置、流量、依赖、数据或时间约束 | 限定适用范围和实验设计 | 把条件本身默认当作根因 |

同一实体在不同 RCA 版本、范围或证据级别中可以改变解释状态，但不能覆盖原观察。`observation` 是事实记录；`symptom` 是结果表现；`correlation` 和 `association` 是关系描述；`causal hypothesis`、`confirmed root cause`、`contributing factor`、`trigger` 和 `condition` 是不同的解释角色。任何自动分类都必须保留原始证据和不确定性。

#### 2. 多根因不是“找出一条最长链”

一个症状可能由多个并行路径共同产生：

```text
共同原因 ─┬─> 配置漂移 ──> 资源耗尽 ──> 症状
          └─> 依赖抖动 ──> 重试放大 ──> 症状
流量峰值 ────────────────────> 资源耗尽
部署变更 ──> 条件改变 ────────> 依赖抖动
重试放大 ─────────────────────> 流量峰值/队列增长（反馈）
```

上述只是表达例子，不是固定图 Schema。RCA 至少应允许：

- **并行根因**：多个相对独立的机制分别足以解释同一症状，或共同达到影响条件；
- **必要条件**：在当前范围内没有该条件时路径不成立，但必要不等于充分；
- **充分条件**：在已声明条件下足以产生结果，但可能不是唯一路径；“充分”必须绑定范围、版本、环境和实验，不得脱离上下文泛化；
- **联合条件**：单个因素不足，多个因素组合才触发结果；
- **共同原因**：一个上游变量同时影响多个观测，避免把共同结果误判成互相导致；
- **触发与脆弱性分离**：部署、流量、超时等可能是 trigger，缺陷、容量或错误默认值可能是长期 condition/contributing factor；
- **反馈环**：重试增加负载、负载增加超时、超时又触发更多重试等循环，必须标记时间窗口和可能的稳定/不稳定阶段；
- **缺失变量**：当前证据不足以区分的变量、未采集信号、不可观测机制或未验证环境，显式保留为未知；
- **争议和替代解释**：多个假设可同时存在，分别记录支持、反证、未决实验和不适用条件。

“根因”可按 RCA 范围存在多个层次：某个服务的局部机制、一次事故的触发链、组织/流程的促成因素或恢复失败的防御缺口，不应强制选择唯一层次。结论必须说明是在解释症状、事故扩大、修复失败还是复发。

#### 3. 因果边必须是可审计的断言

每条候选或确认边至少需要表达以下语义槽位；这是审计要求，不是最终图 Schema：

```text
source_node -> target_node
  direction: 方向及其依据
  relation_kind: association | correlation | causal_hypothesis | confirmed ...
  evidence_refs: 源观察、实验、代码、配置、日志、指标、Trace、测试和人工审查引用
  source_revision / target_revision: 代码、配置、依赖或 RCA 解释版本
  environment_scope: 环境、数据、流量、时间窗口和运行条件
  applicability: 适用范围与排除范围
  confidence / uncertainty: 当前判断及未知、偏差、测量误差和替代解释
  prediction_or_counterfactual: 若改变/移除 source，预期观察什么
  falsifiers: 哪些结果会削弱、推翻或收窄该边
  actor / created_at / review_state: 产生、审查和版本信息
```

方向不是由时间排序自动得出。时间顺序可作为 `before/after` 观察关系，但不能代替 `causes`；“A 先发生、B 后发生”至少还需要机制、干预/对照、自然实验、重复复现或其他适合范围的证据。边的置信表达当前证据状态，不是跨场景可比较的统一概率；缺少基线、选择偏差、测量缺口、混杂或版本信息时，应显式降低可用性或进入隔离。

#### 4. 反事实和预测是区分解释的工具，不是自动证明器

对每条 `causal hypothesis`，优先写出可观察预测：在相同或可比的版本、环境、输入和流量条件下，若改变候选因素，症状、指标、日志、Trace 或回归结果应如何变化；若候选因素不是原因，哪些结果应不出现。可能的验证动作包括：

```text
现象与范围确认
  → 复现/对照条件建立
  → 改变一个或一组明确因素
  → 观察预先声明的结果
  → 检查替代解释、回归和副作用
  → 追加证据并更新 RCA 版本
```

一次修复后症状消失只能支持“该变更在该条件下有效”，不能单独证明改动的完整根因：变更可能同时绕开多个路径、改变观测、移除 trigger、改变流量或掩盖问题。未复现也不等于问题不存在；测试通过也不等于生产风险消失；模型给出高分也不等于完成干预验证。

#### 5. 证据分层、冲突和不可观测性

证据应保留来源和产生方式，而不是先汇总为一个分数。可按用途分为：

- **事实观察**：原始或受控摘录的日志、指标、Trace、错误、时间、代码/配置版本、测试结果和人工陈述；
- **机制证据**：代码路径、配置解析、依赖行为、资源边界、数据流、调用关系和已知约束；
- **比较/干预证据**：复现、对照、回滚、开关、隔离、注入、变更前后观察和自然实验；
- **反证与排除**：与候选方向矛盾的结果、不同环境失败、无法复现、修复后仍复现、替代假设得到支持；
- **解释产物**：人工或工具派生的图、摘要、候选排序、实验建议和冲突报告。

解释产物属于 `derived`，不能冒充 `source`。同一日志摘录、测试结果或 Trace 可支持多个假设，也可被不同 RCA 版本重新解释，但不得修改源内容。证据之间矛盾时保留各自版本、时间、范围和来源，标记冲突，不以最后写入、单一来源、简单多数或单一模型输出消除争议。

需要显式记录：选择偏差、幸存者偏差、观测缺失、采样和聚合方式、时间窗口、环境不一致、代码变更、测量误差、未控制混杂、不可复现以及无法观测的变量。无法观测不等于不存在，也不允许用常识或领域默认值悄然填补。

### 阶段2权威/官方机制调研（访问日期2026-09-20）

本阶段只提取公开机制支持的边界和可借鉴做法，不把任何资料直接变成本平台最终因果算法、图 Schema、阈值、模型、领域标注或 SLA。未引用 RFC；RFC 不是本轮依据。

#### 1. NIST AI RMF：风险管理、有效性和不确定性治理

NIST AI Risk Management Framework 1.0 及其官方页面将风险管理组织为 Govern、Map、Measure、Manage，并强调记录上下文、限制、测量、风险和持续管理。可借鉴的是：RCA 自动化应先明确使用场景、影响对象、风险、证据局限和责任主体；测量和管理应持续更新，而不是把一次模型输出当最终判断。对于高影响事故，自动系统应提供可审计的依据、未知和升级路径，保留人工责任与复核。

NIST AI RMF 不定义软件事故的根因图、因果识别算法、事故关闭门槛或企业权限模型。因此它支持治理和不确定性边界，不授权平台用一个风险分数确认根因、关闭事故或执行修复。参考：<https://www.nist.gov/itl/ai-risk-management-framework>、<https://airc.nist.gov/airmf-resources/airmf/>

#### 2. W3C PROV-O：source/derived 和可追溯来源

W3C PROV-O 通过 Entity、Activity、Agent 以及使用、生成、关联和派生等关系表达 provenance。可借鉴的是：源观察、实验活动、分析结果、审查主体和派生 RCA 应保持方向性引用；新解释应能回到生成它的活动和源实体，撤回或失效可以沿血缘识别影响范围。

PROV-O 不规定“causes”如何被证明，也不规定 RCA 状态、置信阈值、权限、RunGate、ToolPolicy 或事故关闭。因果边不能仅因是 provenance 边就被视为因果边；平台还需分别保存观察先后、关联、假设、实验和审查语义。参考：<https://www.w3.org/TR/prov-o/>。

#### 3. OpenTelemetry：多信号关联不等于因果证明

OpenTelemetry 官方 Signals 文档描述 traces、metrics、logs 等遥测信号及其关联能力；Trace/Span 上下文、时间和属性有助于把一次请求路径中的观测组织起来。可借鉴的是：RCA 应保留信号来源、时间、资源/服务上下文、版本和关联 ID，并允许从不同信号形成证据集合；采集和导出边界、采样和缺失也应进入不确定性说明。

OpenTelemetry 记录可观测信号，不自动定义因果方向、混杂控制、干预实验或根因确认。Span 先后只能说明观测顺序；指标相关、Trace 共现或日志相似不能单独证明某服务导致症状。参考：<https://opentelemetry.io/docs/concepts/signals/>、<https://opentelemetry.io/docs/concepts/context-propagation/>。

#### 4. Google SRE：事后复盘、假设检验和修复验证

Google SRE 官方关于无责复盘和监控分布式系统的资料强调，复盘应关注系统和过程改进、记录影响与时间线，并用监控信号理解系统行为；时间线和共同出现的事件是调查基础，不是根因自动证明。可借鉴的是：RCA 应保留影响、观测、假设、验证、行动项、未决风险和复发反馈，鼓励报告促成因素与防御缺口，而不是只找一个可归责个人。

SRE 资料不定义通用多根因图、自动裁决模型、企业知识发布或执行授权。修复后的观测和行动项只能作为验证与反馈的一部分，不能因为告警消失就自动确认根因完整或关闭高影响事故。参考：<https://sre.google/sre-book/postmortem-culture/>、<https://sre.google/sre-book/monitoring-distributed-systems/>。

#### 5. DoWhy/因果推断资料：谨慎借鉴建模与反驳思路

DoWhy 官方项目资料将因果分析区分为建模、识别、估计和反驳等步骤，并支持用图表达假设、检查识别条件和执行 refutation。可借鉴的是：任何因果估计都依赖显式假设、变量定义、数据生成过程、可识别性和适用范围；“结果看起来合理”不应替代对假设和反驳测试的说明。实验建议可参考干预、对照和反驳思路，但必须由领域责任人判断安全性和可执行性。

DoWhy 不是本平台 RCA 的权威裁决器，其 API、方法或模型不能直接固化为企业算法；不同事故的观测性、混杂、干预成本、版本和安全约束不同。统计估计、因果图或 refutation 结果都不能绕过证据血缘、权限、人工审核和高影响变更门禁。参考：<https://www.pywhy.org/dowhy/>、<https://github.com/py-why/dowhy>（项目官方资料，访问日期：2026-09-20）。

### 阶段3综合结论与建议

#### 1. 阶段性结论

> **RCA 应采用“多节点、多边、可反驳、带范围和版本的解释图”，而不是强制单链或唯一根因。观察、症状、相关/关联、因果假设、确认根因、促成因素、触发因素和条件必须分层；时间顺序、相关性、模型分数、单次修复成功和多数票只能提供线索或支持，不能单独证明根因。每条边需表达方向、证据、版本/环境/范围、置信与不确定性、反事实或可验证预测及反证；并行根因、必要/充分/联合条件、反馈环、共同原因、缺失变量和争议必须可表示。自动化只生成候选、证据图、冲突/缺失报告和实验建议，最终高影响根因确认与事故关闭仍需人工或受控审核。RCA 解释采用 source/derived、追加、版本化和可撤回机制；根因确认、修复完成、Scenario 解决、Knowledge 发布和执行授权是独立决策。**

#### 2. 建议的语义层（不是最终图 Schema）

1. **Observation 层**：记录源信号、代码/配置状态、运行、测试、人工陈述和采集限制；保留时间、revision、环境、范围、敏感级别和来源 ACL；
2. **Outcome 层**：表达 symptom、影响、用户/服务范围、严重性事实和时间窗口；严重性评定与因果判断分离；
3. **Relation 层**：分别记录 before/after、correlation、association、depends_on、supports、contradicts 等非因果或证据关系；
4. **Causal Explanation 层**：记录候选方向、机制、条件、必要/充分/联合声明、预测、反事实、替代解释和反证；
5. **Graph/Path 层**：允许多个路径、并行根因、反馈环、共同原因和未观测变量，保留局部图、适用范围和争议，不要求全局闭合；
6. **Decision 层**：分别记录 hypothesis、confirmed_root_cause、contributing_factor、trigger、disproved 和 unresolved 等阶段性判断，以及审查依据和责任主体；
7. **Action/Validation 层**：分别记录修复候选、已执行变更、验证结果、残余风险、复发、回滚和预防行动；不得把行动结果倒写成因果事实；
8. **Governance/Lineage 层**：记录 source/derived、RCA 解释版本、撤回、ACL、敏感性、血缘、知识发布状态及 RunGate/ToolPolicy 检查结果。

这些层次是后续实现必须能表达的语义边界，不规定节点表、边表、嵌套 JSON、图数据库、存储索引或事件协议。

#### 3. 多根因的审查原则

- **先问解释目标**：是在解释症状、事故开始、影响扩大、恢复失败、修复失败还是复发；不同目标可有不同根因集合；
- **先确认范围再谈确认**：每个判断绑定 repository、revision、代码/服务范围、runtime、依赖、配置、数据、流量、时间窗口和环境；
- **优先保留竞争假设**：证据不足时并列呈现支持和反证，不强迫投票产生唯一结果；
- **分开“导致发生”和“使影响更大”**：触发、脆弱性、促成因素、恢复缺口和共同原因分别处理；
- **要求可反驳**：没有可验证预测、反事实比较或合理反证路径的叙述只能作为待调查假设；
- **避免泄漏未来信息**：不能用修复后结果、事故关闭决定或知识使用成功反向改写事故发生时的事实；
- **复核而非覆盖**：新证据产生新 RCA 版本或复核事件，旧版本保持可追溯；撤回的是结论/适用性/派生资产状态，不抹掉合法历史记录；
- **确认仍是有范围的确认**：`confirmed_root_cause` 表示在声明的版本、环境和证据范围内达到受控审核要求，不是永恒真理或跨 Project 通用结论。

#### 4. 修复、验证和复发反馈闭环

```text
症状/影响观察
  → 证据与版本/环境锚定
  → 多个候选解释与竞争预测
  → 复现、对照、干预或安全实验建议
  → 结果、反证、缺失和副作用追加
  → RCA 解释版本化/审核
  → 修复或缓解行动（独立授权）
  → 当前 revision/environment 验证
  → 发布/上线后观察与复发检测
  → 反馈、撤回、收窄、重新打开或新 RCA
```

修复验证至少区分：原问题是否复现、候选机制的预测是否命中、修复是否只改变了观察窗口、回归/副作用、不同环境结果、监控观察和人工验收。`root_cause_confirmed`、`fix_applied`、`verification_passed`、`scenario_resolved`、`knowledge_published` 和 `execution_authorized` 必须是分离状态，不能由一条自动边联动完成。

#### 5. 权限、敏感、血缘与执行边界

RCA 图可能同时引用源码、日志、Trace、指标、用户输入、生产数据、配置、凭据痕迹、实验结果、Embedding、知识摘要和审计记录。它们的 ACL、敏感级别、保留/撤回规则和可见范围可以不同：

```text
当前主体读取权 ∩ 来源 ACL ∩ 目标用途策略 ∩ 敏感数据策略
  → 可见的证据/派生解释范围

来源或血缘撤回
  → 受影响边/节点/RCA 版本重新评估
  → 派生 Knowledge/Index/Embedding 暂停或撤回
  → 相关 Run/Action 重新授权或阻断
```

引用关系不扩大读取权限；能看 RCA 摘要不代表能看原始 Trace 或生产数据；能读取知识不代表能发布知识或执行修复。`RunGate` 负责当前行动/运行的风险、主体、上下文和明确授权；`ToolPolicy` 负责工具能力、参数、资源和沙箱约束；二者都不能被因果图结论替代，也不能因“根因已确认”自动放行。

### 阶段4专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| 因果推断/统计 | 有时间先后、相关系数或因果模型分数，是否就能确认根因？ | 不能。它们最多支持观察或候选；方向、机制、混杂、范围、干预/对照、预测和反证仍需审查。 |
| SRE/事故响应 | 告警消失、回滚成功或一次修复后不再复现，是否足以关闭 RCA？ | 不足。只能说明当前条件下的修复/缓解结果；仍需验证根因完整性、回归、环境范围、观察和复发反馈。 |
| 分布式系统 | Trace 的父子顺序是否天然是因果图？ | 不是。它提供关联和观测顺序；采样、异步、重试、时钟和缺失信号可能改变解释，必须保留不确定性。 |
| 机器学习/自动化 | 多模型或多数票能否裁决多个根因？ | 不能自动升级为确认，尤其不能用于高影响事故关闭。模型输出是 derived evidence，需可追溯输入、适用性、反证和人工/受控审核。 |
| 数据治理/血缘 | 图上引用了原始日志，是否所有消费者都能回溯查看？ | 不能。引用不扩大权限；源撤回、敏感变化或血缘断裂时，派生 RCA、索引和行动候选应暂停/撤回/隔离。 |
| 代码/供应链 | 同一 revision、相同 patch 或构建成功能否证明根因？ | 不能。它们可绑定代码和构建证据，仍需问题范围、环境、触发条件、机制和验证；同一变更也可能掩盖多个路径。 |
| 安全/合规 | 自动实验建议能否直接在生产执行？ | 不能。建议是声明性 derived 产物；生产或高影响实验必须经过当前权限、风险审查、RunGate、ToolPolicy 和明确授权。 |
| 产品/运营 | 用户只想要一个“根因”和一个关闭按钮，是否应简化底层？ | 可以简化展示，但不能简化事实模型。界面可给出主假设、并行解释、未知和下一步，并明确“确认根因”与“问题已解决”的差异。 |
| 组织治理 | 多根因是否会稀释责任、导致无法行动？ | 不应。图可分出触发、促成因素、防御缺口和责任行动；行动项、Owner、风险和验证分别治理，不用虚构单一根因换取可操作性。 |
| 领域专家 | 不同领域的“必要/充分/根因”定义是否可统一？ | 不能在本轮固化。平台保留声明、范围和证据槽位，领域标注、判定规则和确认责任留待实际领域治理。 |

必须保留的反例约束：

```text
时间先后                  ≠ 因果
相关性/association         ≠ 因果方向
模型分数                  ≠ 根因确认
多数票                    ≠ 证据闭包
单次修复成功              ≠ 根因完整
告警消失                  ≠ Scenario 已解决
测试通过                  ≠ 生产风险消失
Trace 父子顺序            ≠ 完整因果图
相同错误签名              ≠ 同一根因
共同结果                  ≠ 互相导致
trigger                   ≠ 深层根因
contributing factor       ≠ 唯一根因
root cause confirmed      ≠ fix completed
root cause confirmed      ≠ Knowledge published
root cause confirmed      ≠ execution permission
引用/血缘                  ≠ ACL 继承
RunGate                   ≠ ToolPolicy
```

### 自动审核与推进

#### 1. 自动审核器可以检查和生成的内容

自动化可以：

1. 从日志、指标、Trace、代码、配置、测试、变更和人工输入中提取 `observation` 与 `symptom` 候选，并保留 source、时间、revision、environment、范围、采样和敏感性；
2. 生成非因果的时间、调用、版本、依赖、引用和证据关联，明确标记为 `association`/`correlation`/`before-after`，不自动标记为 causes；
3. 形成多根因候选证据图或局部解释视图，展示并行路径、共同上游、可能反馈环、缺失变量、替代解释、冲突和未观测部分；
4. 对每条候选边检查是否有方向依据、证据引用、版本/环境/范围、置信与不确定性、可验证预测/反事实和反证入口；缺项则降级或标记不可确认；
5. 比较 RCA 版本、修复前后观察、不同环境、复发事件和使用反馈，生成追加证据、复核事件、收窄/失效候选和待调查项；
6. 生成安全、声明性的实验/验证建议，说明目的、前置条件、预期观察、可能反证、回滚/停止条件和权限要求；建议不得直接调用工具或执行写操作；
7. 检查 source/derived、血缘、ACL、敏感性、撤回状态和当前 revision/environment 是否完整，输出隔离、暂停或阻断报告；
8. 检查 `confirmed_root_cause`、`fix_applied`、`verification_passed`、`scenario_resolved`、`knowledge_published` 和 `execution_authorized` 是否被错误联动；
9. 对高影响、安全、合规、生产或权限相关 RCA 强制生成人工/受控审核任务，并保留审查者、依据、异议和决定版本。

#### 2. 自动化不能做的事

自动化器不能仅凭时间顺序、相关性、模型分数、图连通性、单次修复成功、测试通过或多数票：

- 自动把 `causal hypothesis` 升级为高影响 `confirmed root cause`；
- 从多个候选中强行选择唯一根因，删除并行根因、缺失变量或争议；
- 自动关闭事故、把 Scenario 标记 resolved、接受残余风险或撤销人工责任；
- 自动执行修复、实验、生产变更、数据库操作、凭据使用或发布高敏感知识；
- 自动扩大读取、发布、执行或工具权限，继承历史 ACL，或绕过 RunGate/ToolPolicy；
- 覆盖 source observation、旧 RCA 版本、反证、撤回记录或审计事件；
- 将 RCA 解释直接变为 Patch、Run Plan、Skill 或跨 Project 可执行知识。

#### 3. 自动推进的阶段性门槛

本轮只建议使用语义状态，不规定数值阈值、统一评分、模型或 SLA：

```text
source observations collected
  → evidence-linked candidate explanations
  → conflict/missing/uncertainty review
  → safe validation proposal
  → evidence appended and RCA versioned
  → human/controlled confirmation where required
  → separate repair authorization
  → separate verification and recurrence monitoring
```

若出现身份、revision、环境、权限、敏感性、血缘、验证结果或高影响责任不明，自动结果进入 `review`、`isolated`、`paused` 或 `blocked`，不因等待超时、默认值或最后写入者自动推进。低风险、只读、脱敏和明确授权的证据整理可以自动执行，但仍需记录输入、输出和版本。

#### 4. 下一步验证样例

下一阶段先用真实脱敏事件和事件回放校准语义，不先实现自动裁决算法：

- 两个并行缺陷分别足以造成相同症状，验证不强行单链；
- 两个因素单独不足、组合才触发，验证必要/充分/联合条件声明；
- 共同上游同时影响多个服务，验证不把共同结果互判为因果；
- 重试—负载—超时形成反馈环，验证方向、时间窗口和稳定性局限；
- 部署是 trigger、容量是 condition、代码缺陷是候选根因，验证层次分离；
- 时间高度相关但通过对照/反事实排除因果，验证相关不越级；
- 修复后症状消失但替代路径仍存在，验证单次修复成功不等于根因完整；
- 不同 revision、runtime、配置和数据条件产生相反结果，验证适用范围和版本化；
- 观测缺失或敏感证据不能读取，验证 missing variable、权限隔离和 fail-closed；
- 源日志撤回或血缘断裂后，验证 RCA 版本、索引、Knowledge 和 Action 候选的暂停/撤回传播；
- RCA 根因确认、修复、验证、Scenario 关闭、知识发布和 Run 执行分别请求，验证状态和门禁不串联。

## 子议题深化4第1轮：工具调用、日志、指标和 Trace 的统一采集协议

### 主题与成功标准

本轮针对“工具调用、日志、指标和 Trace 的统一采集协议”暂缓项，目标是确定跨 Connector、Harness、运行器和可观测性系统接入时必须保持的语义边界，而不是冻结最终数据库 Schema、传输协议、采样比例或厂商 SDK。成功标准是：四类信号可在同一 Work Thread/Execution/Run/Scenario 下关联；观察事实、派生指标和 RCA 判断不混淆；乱序、重试、采样、断连和补发可被识别；敏感数据默认最小化；来源、revision、环境、权限、血缘和完整性可审计；缺失或不可信时 fail-closed，不伪造“完整 Trace”。

### 阶段1头脑风暴

#### 1. 统一的是关联语义，不是把四类信号压成一种对象

- **Tool Call**：某主体在某 Run 中请求、获准、执行或拒绝一个工具动作，必须能表达 policy decision、参数摘要、资源范围、结果状态和副作用边界。它不是普通日志，也不是 Trace Span 的别名。
- **Log/Observation**：带来源的离散观察或文本/结构化记录，保存发生时间、采集时间、资源、级别、完整性和敏感标记。日志内容可能缺失、重复或被脱敏。
- **Metric**：按时间窗口聚合的数值观测，必须说明指标名称、单位、聚合口径、窗口、来源、样本量/覆盖和是否估算。指标不能反向充当逐事件事实。
- **Trace/Span**：一次请求、任务或工具链路的关联上下文与区间观察；父子关系表示传播和调用关联，不自动证明因果，也不保证所有异步、重试和采样事件都存在。
- **Event ledger**：平台自身的不可变控制事件（例如 run_started、tool_denied、evidence_received、redaction_applied、gap_detected），用于顺序、状态和审计；它与外部日志/Trace 分离。

因此统一协议应提供一个**关联 Envelope**和各信号的专属 Payload：共用身份、时间、作用域、关联 ID、来源、版本、敏感、完整性和幂等线索；不同信号保留自己的语义、保留策略和查询模型。

#### 2. 最小共同关联上下文

建议每次采集至少尝试携带：`event_id`、`signal_type`、`source_connector`、`observed_at`、`received_at`、`tenant/project/space`（按授权可见）、`scenario_id`、`thread_id`、`execution_id`、`run_id`、`trace_id`、`span_id`、`parent_span_id`、`repository`、`revision`、`environment_ref`、`actor_ref`、`attempt`、`sequence_or_cursor`、`schema_version`、`sensitivity`、`redaction_status`、`integrity_status` 和 `idempotency_key`。

这些是语义槽位而非最终字段要求。缺少某个关联 ID 时应记录 `missing_context` 和降级范围，不用随机补值；不能把 session_id、request_id、trace_id、run_id 互相替代。跨 Connector 传播时，外部系统的原始 ID 作为 source reference 保留，同时生成平台内部不可碰撞的关联标识。

#### 3. 事件状态与时间必须分开

采集至少区分：源系统发生时间、事件中声明的逻辑时间、平台接收时间、持久化时间和处理时间。顺序优先依据源 sequence/cursor；没有可靠顺序时只能显示近似时间线并标记不确定。重试、批量、异步回调和网络延迟可能导致 Trace、Log、Metric、Tool Call 乱序，不能由接收顺序重写事实。

采集、传输、处理、持久化和导出分别记录结果。`accepted` 不代表 `durably_stored`，`sampled` 不代表 `absent`，`redacted` 不代表原文可恢复，`span_end` 不代表工具副作用成功。错误、缺口、延迟、重复和部分失败都应成为可查询的控制事件。

#### 4. Tool Call 是高价值且高风险证据

工具协议需要至少区分 `requested → policy_checked → approval_pending/approved/denied → started → completed/failed/cancelled/timed_out`，并允许重试和人工接管产生新 attempt。参数默认只保存类型、哈希、受控摘要或引用；密钥、Token、Cookie、私钥、完整生产请求体和未经授权客户数据不进入统一事件流。工具结果与工具授权、RunGate、ToolPolicy、Audit 的引用分开，不能因 Trace 有 span 就视为已批准或可重放。

#### 5. 日志、指标、Trace 的互相引用有边界

- Log 可以引用 `trace_id/span_id/run_id`，但不应内嵌完整敏感上下文；
- Span 可以关联事件和日志，但需标识 link、parent、follows-from 等语义，异步消息不能硬造父子关系；
- Metric 可以带 exemplar 或关联 trace 样本，但聚合值只能指向样本/窗口，不能代表全量请求；
- Tool Call 可以同时产生 Span、Log 和 Metric，但它们是不同观察，不应复制成四份“事实”；
- RCA 使用这些信号作为 evidence collection，并记录采样、缺失、冲突、推断和适用范围。

#### 6. 失败路径与降级

Connector 离线、授权过期、采样丢失、时钟漂移、超载、schema 不兼容、脱敏失败、队列重复、源撤回和跨租户边界不明都必须有显式状态。只读、低风险、脱敏的观测缺口可进入 `partial`；身份、权限、敏感性、revision、完整性或来源不明时进入 `isolated/blocked`，不得进入确定性 RCA、知识发布或高风险执行上下文。采集失败不能阻塞业务副作用时，至少写入本地不可变最小审计事实和缺口标记；具体缓冲和补发策略留待 Connector 专题。

### 阶段2：其他产品/标准如何做（带来源）

1. **OpenTelemetry Signals 与 Context Propagation**：官方将 traces、metrics、logs 作为相互关联但语义不同的信号，并通过 Context 传播 trace/span 关联。可借鉴统一资源/上下文、跨服务传播和 signal-specific 语义；不能据此推导完整事件账本、工具授权、RCA 因果证明、跨租户权限或可靠全量采集。来源：<https://opentelemetry.io/docs/concepts/signals/>、<https://opentelemetry.io/docs/concepts/context-propagation/>（访问日期：2026-09-20）。
2. **OpenTelemetry Logs Data Model 与 Tracing API**：日志模型强调时间、观察时间、severity、body、attributes、resource 和 trace/span 关联；Tracing API 定义 Span 生命周期与上下文操作。可借鉴发生/观察时间分离、资源属性、Span 边界和 link 语义；SDK/API 不负责凭据脱敏、平台审计或工具副作用授权。来源：<https://opentelemetry.io/docs/specs/otel/logs/data-model/>、<https://opentelemetry.io/docs/specs/otel/trace/api/>（访问日期：2026-09-20）。
3. **W3C Trace Context**：定义跨服务传播 `traceparent`/`tracestate` 的互操作上下文。可借鉴传播格式和供应方互操作；Trace Context 是关联标识，不是身份认证、权限证明或因果图。来源：<https://www.w3.org/TR/trace-context/>（访问日期：2026-09-20）。
4. **CloudEvents**：提供事件 envelope 的 type、source、subject、time、id、data content type 等互操作元数据。可借鉴事件元数据与领域 payload 分离、幂等线索和版本演进；CloudEvents 不规定本平台的 Run、ToolPolicy、敏感分类、事件账本或补发一致性。来源：<https://cloudevents.io/>、<https://github.com/cloudevents/spec>（访问日期：2026-09-20）。
5. **Prometheus 数据模型**：以 metric name 与 label set 标识时间序列，并通过时间序列聚合观察系统状态。可借鉴“指标口径、标签、时间窗口与样本”必须明确；指标 cardinality、抓取延迟和聚合会造成信息丢失，因此不能用一个数值替代事件级取证。来源：<https://prometheus.io/docs/concepts/data_model/>（访问日期：2026-09-20）。
6. **Google SRE Monitoring**：将监控信号用于发现和定位问题，强调延迟、吞吐、错误等指标及其局限。可借鉴信号选择和告警/排障分工；监控告警不等于 RCA 确认，也不等于场景解决。来源：<https://sre.google/sre-book/monitoring-distributed-systems/>（访问日期：2026-09-20）。

综合限制：这些标准共同支持“可关联、多信号、带资源和时间的观测”，但没有一个标准单独定义本平台的工具授权、事件账本、证据完整性、撤回传播、跨 Project ACL、RCA 状态或高风险执行门禁。

### 阶段3：总结、结论与建议

#### 1. 阶段性结论

> **统一采集协议采用“共同关联 Envelope + 信号专属 Payload + 平台事件账本”的三层结构。Tool Call、Log、Metric、Trace/Span 和 RCA Evidence 保持不同语义，通过 scenario/thread/execution/run/trace/span/revision/environment 等有来源的关联引用连接；不把 Trace 当完整事实，不把 Metric 当逐事件证据，不把日志文本当因果结论，不把 Tool Span 当授权或成功证明。每条观测保留 source、发生/接收时间、资源与范围、版本、采样/缺口、敏感与脱敏、完整性、幂等和撤回状态。乱序、重复、重试、异步、部分采样和补发必须可识别且追加，不以接收顺序覆盖源事实。缺少身份、权限、来源、revision、环境、敏感性或血缘时，观测只能降级、隔离或阻断，不能升级为确定性 RCA、知识发布或高风险执行。**

#### 2. 推荐的协议分层（语义契约，非最终 Schema）

```text
Connector / Harness / Runtime / Collector
  → Ingestion Envelope
      source + signal_type + event_id + timestamps
      subject/resource + scope + context IDs
      schema/version + integrity + sensitivity + redaction
      sequence/cursor + attempt + idempotency + sampling
  → Signal Payload
      Tool Call | Log | Metric | Trace/Span | Artifact/Observation
  → Normalization / Validation
      identity, ACL, revision, environment, schema, dedup, ordering, gap
  → Event Ledger + Signal Store
      append-only control event + signal-specific retention/query
  → Evidence View / Run Timeline / Metrics View
  → RCA candidate / Knowledge candidate (derived, gated)
```

Envelope 只负责共用元数据和证据边界，不能借 envelope 自动获得跨空间权限。规范化层应保留原始 source reference 和规范化版本；规范化失败不能覆盖原始失败事实。事件账本记录接收、校验、去重、缺口、脱敏、隔离、撤回和投影状态，信号存储按各自查询与保留需求实现。

#### 3. 关键规则

- **身份与范围**：actor、connector、tenant/project/space、resource、repository/revision 和 environment 必须有可信来源；缺失时标为 unknown，不猜测。
- **时间与顺序**：保留 source/observed/received/processed 时间和 sequence/cursor；时钟漂移与乱序显式记录；UI 可排序不等于事实重排。
- **关联与完整性**：关联 ID 只表示同一上下文或传播关系；parent/link/follows-from 分开；采样率、缺口和覆盖范围随证据传递。
- **幂等与重试**：使用 source event identity、connector identity、sequence/cursor 和 attempt 形成去重/补发线索；重复到达不重复副作用；重试是新 attempt，不覆盖旧结果。
- **脱敏与最小化**：采集前、入口处、存储前和导出前均可执行策略；保存摘要/哈希/引用优先；原始高敏内容不得通过“统一协议”绕过 ACL。
- **撤回与失效**：源证据撤回、ACL 变化、revision 失效或脱敏策略变化时，派生 Evidence/RCA/Manifest/Knowledge/Metric projection 必须可枚举并进入复核/暂停/撤回；历史审计事实不被静默覆盖。
- **信号完整性**：采集器应能报告 `complete/partial/sampled/gapped/late/duplicate/rejected/isolated` 等语义状态；具体枚举和阈值留待实测。
- **执行边界**：协议只采集和关联，不发放权限、不批准 Run、不重放 Tool Call、不执行修复；RunGate、ToolPolicy、Audit 和 Knowledge 发布保持独立。

#### 4. 最小可验证回放集

先用脱敏真实事件和可控事件回放验证，不先固定数值阈值：

1. 一个 Run 产生工具 Span、结构化 Log、延迟 Metric 和结果 Evidence，四类信号能关联但不重复计数；
2. 异步回调先到、父 Span 后到，系统保留 link/late 语义，不伪造父子顺序；
3. 同一事件重复投递、同一 Tool Call 重试，去重不产生重复副作用，attempt 可分辨；
4. Metric 只有聚合窗口，Trace 被采样，Run 时间线明确“部分覆盖”，不生成全量结论；
5. Connector 断连后补发带 gap/cursor，重复和迟到事件仍能追加并重建视图；
6. 脱敏失败、身份缺失、跨 Project ACL 不明、revision 缺失时进入隔离/阻断；
7. 源 Log 撤回后，关联 RCA/Knowledge/索引/指标投影可枚举并暂停或复核；
8. Trace 与 Metric 显示相关但不存在可确认因果，RCA 保留 hypothesis/uncertainty；
9. Tool denied、approval pending、tool failed、run succeeded 四种状态不被 UI 或聚合指标混成一个“成功”；
10. schema 版本不兼容时保留原始拒绝/隔离事实，不能按默认字段静默解析。

### 阶段4：专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| 可观测性架构 | 既然 OTel 已有 trace/log/metric，为什么还要平台协议？ | OTel 解决信号和上下文互操作；平台仍需 Tool Call 语义、事件账本、ACL、敏感、revision、撤回和 Run/Scenario 关系。采用适配层，不重复发明传播格式。 |
| 分布式系统/SRE | 乱序、重试、异步和采样会不会让“统一时间线”误导用户？ | 时间线必须是带完整性状态的派生视图，保留源时间、接收时间、cursor、gap、link 和采样；缺失时显示 partial/unknown，不补造顺序。 |
| 工具运行时 | Tool Span 是否已经足以记录调用？ | 不足。授权、参数最小化、资源范围、attempt、副作用、结果和拒绝原因是 Tool Call 专属语义；Span 只能作为关联观察。 |
| 数据/指标工程 | 统一 envelope 会不会把高基数、长日志和指标混在一个存储？ | 不应共用物理模型。统一元数据和事件账本，Payload/索引/保留按信号分离；协议统一不等于存储统一。 |
| 安全/隐私 | 采集越完整，泄露面越大，如何避免“可观测性优先”？ | 默认最小化、分级脱敏、按源 ACL 隔离；凭据和客户数据不进入流；身份、用途、血缘或脱敏失败即隔离/阻断。 |
| 产品/运营 | 用户只想看一条可读的 Run 时间线，是否可以隐藏复杂性？ | 可以提供简化视图，但必须显示 partial、sampled、gapped、redacted 和 unknown 状态，并能下钻到授权证据；不能用漂亮时间线冒充完整取证。 |
| 数据治理/血缘 | 指标和摘要派生后如何撤回？ | 每个派生结果保留 source refs、版本、窗口/覆盖和投影状态；源撤回触发影响枚举与暂停/复核，不覆盖历史审计。 |
| 可靠性/成本 | 全量采集成本高，是否直接提高采样率或永久保留？ | 不在本轮固化比例和保留期。按风险、信号类型和用途分层，保留完整性/覆盖证据；高风险工具控制事件与最小审计优先。 |

必须保留的反例约束：

```text
trace_id                 ≠ actor identity
parent span              ≠ causal proof
span exists              ≠ tool approved
run succeeded            ≠ tool succeeded / scenario resolved
metric aggregate         ≠ every underlying event
sampled                  ≠ absent
accepted                 ≠ durably stored
received order           ≠ source order
redacted                 ≠ publicly readable
historical context       ≠ current authorization
correlation              ≠ root cause
```

### 自动审核与推进

自动审核可检查：Envelope 是否有来源、版本、时间、关联和幂等线索；信号类型和专属语义是否混用；source/received 时间与 sequence 是否保留；重复、乱序、gap、采样、脱敏和拒绝状态是否可见；Tool Call 是否引用当前 RunGate/ToolPolicy 结果但未把它们合并；RCA/Knowledge 是否保存 source refs、revision、环境、ACL 和不确定性；撤回后派生投影是否进入影响评估；事件 ledger、signal store 和视图是否可区分。

自动审核不能仅凭 Trace 连通性、指标异常、日志相似度、接收顺序、采集成功或模型摘要确认根因、补齐缺失事件、批准工具、重放调用、发布敏感知识、扩大权限或关闭 Scenario。协议的机械性校验和低风险脱敏整理可自动推进；身份、权限、血缘、敏感、生产副作用或完整性争议必须进入受控审核/阻断。

## 子议题深化5第1轮：场景关闭、严重等级和生产变更的完整审批矩阵

### 主题与成功标准

本轮针对“场景关闭、严重等级和生产变更的完整审批矩阵”暂缓项。目标是把 Code Scenario 的解决判断、业务影响分级、生产/数据库/凭据等变更授权放入可审计且职责分离的治理闭环；不把 RCA 置信度、Run 成功、告警消失或测试通过直接等同于关闭，也不在本轮冻结企业组织、SLA 数值或全部操作目录。

成功标准：

1. 分离 Scenario 状态、RCA 状态、修复/变更状态、验证状态和知识发布状态；
2. 形成影响分级与动作风险分级的最小交叉矩阵；
3. 明确 proposer、approver、executor、verifier、incident owner 的职责不能由同一主体无条件兼任；
4. 关闭必须绑定范围、revision、环境、证据、验证、残余风险和有效决策；
5. 生产变更必须经过版本化计划、影响预览、当前权限检查、独立审批、RunGate、执行差异记录、回滚/止损和事后复核；
6. 计划、环境、revision、参数、风险或权限变化时原批准自动失效；
7. 紧急止损有受限 Break-Glass 路径，但不能借机扩大长期权限或删除审计；
8. 所有状态和审批都可追溯，策略/审计不可用时默认阻断高风险动作。

### 阶段1：头脑风暴

#### 1. 不同问题不能共用一个“关闭”按钮

- **Scenario closure**：声明当前问题边界内已达到接受标准，且范围、版本、环境、影响、残余风险和后续观察已记录；
- **RCA confirmation**：在声明范围内根因解释达到相应审核级别；
- **Fix applied**：某变更或缓解已执行；
- **Verification passed**：规定的验证证据达到要求；
- **Production change completed**：生产动作已按计划完成并记录实际差异；
- **Knowledge published**：经验通过知识治理后可被引用；
- **Incident resolved/monitored**：影响停止或进入观察期。

这些状态可以按顺序关联，但不能自动联动。一个场景可以“修复完成但验证不足”，也可以“验证通过但根因仍为 hypothesis”，更不能因为知识已发布就重新授权生产执行。

#### 2. 影响等级与操作风险是两个轴

建议保留两个独立轴：

```text
Impact: I0 无用户/业务影响或仅内部实验
        I1 受限范围、可快速恢复
        I2 多用户/重要服务受影响
        I3 广泛、关键业务、合规/安全或重大数据影响

Action risk: R0 只读/低风险/可逆
              R1 受限工作区或低影响可逆修改
              R2 受控资源、生产配置或有限数据库变更
              R3 不可逆、广泛生产、权限/凭据/客户数据/跨租户变更
```

等级名称和数值只是语义草案，不是统一企业阈值。影响等级回答“已经造成或可能造成多大影响”，操作风险回答“计划动作可能造成多大影响”；I3 的只读取证不必等同于 R3 生产写入，但 I0 的凭据使用仍可能是 R3。

#### 3. 关闭请求必须是有范围的决策

关闭请求至少要明确：Scenario/Incident 身份、问题和影响范围、repository/revision、环境和时间窗口、触发条件、关联 RCA 版本、修复/缓解引用、验证清单与结果、未验证路径、残余风险、观察/复发计划、回滚或重新打开条件、请求者和审核依据。关闭是一个新 Decision，不覆盖历史事实；后来复发应追加事件并将场景重新打开或建立有关系的新场景。

#### 4. 生产变更必须绑定不可变 Run Plan

生产部署、数据库写入、凭据使用、权限变更、客户数据访问、跨 Project/租户、不可逆迁移、可执行 Skill 发布和高影响知识撤回，至少走：

```text
Action Proposal
  → versioned Run Plan
  → scope / impact / risk preview
  → current identity, ACL, ToolPolicy and precondition check
  → independent approval
  → RunGate
  → execution with actual-diff capture
  → verification / rollback or stop
  → decision, execution and impact audit
  → post-change review
```

计划必须包括目标资源、作用域、revision、环境、工具调用集合、参数摘要、前置条件、验证、回滚/止损、风险等级、有效期和责任角色。方案或现实条件发生关键变化时，旧批准不能继续沿用。

#### 5. 紧急路径不是普通捷径

Break-Glass 仅可用于已绑定 Incident 的最小止损或恢复，例如阻断泄露投影、暂停新的高风险 Run 或恢复必要服务；必须限主体、动作、资源、时间和最大风险，记录理由、审批/应急权限、实际差异并强制事后复核。不得用它修改长期 ACL、扩大跨空间共享、发布新可执行知识、删除审计或跳过所有验证。

### 阶段2：其他产品/标准如何做（带来源）

1. **Google SRE Incident Response**：官方资料强调事故响应中的角色分工、协调、沟通和恢复过程；可借鉴 Incident Commander/运营协调与执行职责分离，以及先恢复影响、再完成复盘的流程边界。它不定义本平台 Scenario、RCA、Knowledge、RunGate 或企业审批矩阵。来源：<https://sre.google/workbook/incident-response/>（访问日期：2026-09-20）。
2. **Google SRE Postmortem Culture**：无责复盘强调记录影响、时间线、促成因素和行动项，避免把事故归结为单一个人；可借鉴“关闭/复盘仍需保留未决风险与行动项”的原则。它不授权自动关闭或自动接受生产风险。来源：<https://sre.google/sre-book/postmortem-culture/>（访问日期：2026-09-20）。
3. **Google SRE Monitoring Distributed Systems**：监控用于发现和理解系统行为；可借鉴用指标和观测支持验证，但告警消失或单一指标恢复不等于根因确认、场景解决或变更安全。来源：<https://sre.google/sre-book/monitoring-distributed-systems/>（访问日期：2026-09-20）。
4. **本项目议题9第3轮既有结论**：已确认 Action Proposal → 版本化 Run Plan → 风险/影响预览 → 独立审批 → RunGate → 执行 → 验证 → 审计/复核闭环，定义了 R0–R3 原则性动作风险、Break-Glass 边界和紧急撤回两阶段流程。本轮将其应用到代码场景关闭和生产变更，不重新发明权限治理，也不覆盖议题9的实现暂缓项。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **代码场景关闭采用独立、范围化、可重新打开的 Decision，不由 RCA 确认、Run 成功、测试通过、告警消失、修复完成或知识发布单独触发。影响等级与动作风险等级分离；建议以 I0–I3 表达影响，以 R0–R3 表达动作风险，具体阈值由企业治理校准。关闭至少绑定 Scenario/Incident、repository/revision、environment、影响窗口、RCA/修复/验证证据、残余风险、观察与重开条件、责任角色和决策版本。生产、数据库、凭据、权限、客户数据、跨 Project/租户、不可逆变更及高影响知识动作复用议题9的版本化 Run Plan、独立审批、RunGate、执行差异、验证、回滚/止损、审计和事后复核闭环；计划、资源、revision、环境、参数、权限、风险或回滚变化使审批失效。Break-Glass 只允许绑定 Incident 的限时最小止损/恢复，不能扩大长期权限或删除审计。**

#### 最小状态分离

```text
RCA: hypothesis / confirmed / reopened / superseded / revoked
Fix: proposed / authorized / applied / rolled_back
Verification: pending / partial / passed / failed / expired
Scenario: open / diagnosing / fix_pending / verifying / resolved / monitored / reopened / blocked
Change: proposed / approved / gated / running / partially_executed / succeeded / failed / rolled_back / cancelled
Knowledge: candidate / reviewed / published / suspended / revoked
```

这些状态是语义示例，不是最终枚举。状态变化必须追加事件并引用证据、决策和 actor；`resolved` 至少要求接受标准、必要验证、残余风险和复核义务已记录，`monitored` 表示仍需观察而非永久关闭。

#### 关闭与变更矩阵（原则级）

| 场景 | 影响/风险示例 | 最低路径 | 自动化边界 |
|---|---|---|---|
| 只读取证、低影响内部实验 | I0/R0 | 当前授权 + ToolPolicy + 审计 | 可按策略自动运行；不得自动关闭高影响场景 |
| 工作区可逆修复 | I0–I1/R1 | 明确授权、版本/范围记录、验证 | 可生成计划和证据；执行是否自动化由策略决定 |
| 受控生产配置或有限数据库变更 | I1–I2/R2 | 影响预览、独立审批、RunGate、回滚、验证 | 不得仅凭 RCA 或历史批准放行 |
| 广泛生产、权限/凭据/客户数据/跨租户/不可逆变更 | I2–I3/R3 | 专门人工/治理审批、双人职责分离、RunGate、实时差异、回滚/止损、事后复核 | 禁止自动批准、自动执行和自动接受残余风险 |
| 高影响场景关闭或安全/合规事件 | I2–I3，动作风险视关闭动作而定 | 证据闭包、责任人复核、观察/重开条件、影响审计 | 可自动汇总证据；不能自动确认关闭或掩盖缺口 |
| Break-Glass 止损 | I1–I3/R2–R3 | Incident 绑定、最小范围、限时授权、实际差异、事后复核 | 可自动阻断新动作；不可自动扩大权限或删除审计 |

该矩阵只规定最低门槛，不能替代企业按资源、行业、客户合同和法律要求制定更严格规则；硬拒绝、未知权限、审计/策略不可用、来源撤回或计划失配时优先阻断。

### 阶段4：专家团挑战

| 专家视角 | 关键挑战 | 本轮回应/保留项 |
|---|---|---|
| SRE/事故响应 | 事故期间是否应为了恢复速度跳过关闭和审批？ | 可用受限 Break-Glass 做最小止损，但关闭、长期修复和风险接受仍分离，并强制事后复核。 |
| 安全/合规 | I0 小影响是否会掩盖凭据或权限风险？ | 影响和动作风险双轴；小影响的凭据使用仍可为 R3，硬门禁优先于影响等级。 |
| 变更治理 | 审批后参数或 revision 变化能否继续执行？ | 不能。关键计划事实变化使批准失效，必须重新生成计划、预览和审批。 |
| 工程架构 | 测试通过后关闭是否过度保守？ | 不过度。测试只是验证的一类证据；环境、流量、回归、残余风险和观察期仍需按范围判断。 |
| 产品/运营 | 多个状态会不会让用户无法理解？ | UI 可给出“当前主状态 + 缺口 + 下一门槛”，底层保持状态分离，避免一键关闭制造错误确定性。 |
| 数据治理 | 关闭后原始证据撤回怎么办？ | 历史审计保留合法事实，派生 RCA/Knowledge/索引按血缘重新评估；必要时重新打开或收窄适用范围。 |
| 组织治理 | proposer、approver、executor、verifier 分离是否影响小团队效率？ | R0/R1 可按明确策略简化；R2/R3 和高影响关闭不得因组织规模自动取消职责分离。 |

必须保留的反例：

```text
RCA confirmed       ≠ Scenario resolved
fix applied         ≠ verification passed
verification passed ≠ production risk gone
alert recovered     ≠ root cause complete
run succeeded       ≠ change approved
approval exists     ≠ current plan still valid
low business impact ≠ low action risk
break-glass         ≠ permanent authorization
knowledge published  ≠ execution permission
```

### 自动审核与推进

自动化可以检查关闭证据是否绑定明确范围、revision、环境、验证、残余风险和重开条件；检查影响/风险分级是否存在冲突；核对 proposal、Run Plan、审批版本、当前资源、参数、权限、ToolPolicy、RunGate 和实际执行差异；生成缺口清单、关闭候选、复核任务、观察提醒和撤回影响报告；在明确授权的低风险范围内汇总证据和写入机械性审计事件。

自动化不能仅凭指标、Trace、模型摘要、测试通过、修复成功或审批历史自动关闭高影响 Scenario、接受残余风险、批准生产变更、使用凭据、扩大权限、执行不可逆动作或把 Break-Glass 变成长期授权。身份、计划、revision、环境、权限、敏感性、血缘、审计或回滚信息缺失时进入 `blocked`/`review`；策略或审计服务不可用时高风险动作默认阻断。

### 自动审核：当前方案无明显歧义，已确认通过，准备进入下一轮/下一个议题。

本轮阶段性批准记录：在用户已授权自动继续的范围内，采用“影响等级与动作风险双轴 + 状态分离 + 版本化 Run Plan/独立审批/RunGate + 受限 Break-Glass”的方案。该方案直接承接议题9已确认的治理闭环，避免把代码场景的关闭判断误变为执行授权；选择可逆、范围一致且不冻结具体企业阈值，暂无需要用户裁决的重大歧义。

## 子议题深化6第1轮：代码、日志、生产数据和凭据的完整分类脱敏规则

### 主题与成功标准

本轮讨论进入场景、证据、Trace、RCA、Artifact、Checkpoint、Knowledge 和审计的代码/日志/生产数据/凭据分类与脱敏边界。目标是形成可执行的语义框架，但不虚构通用检测算法、合规法律结论、行业阈值或永久安全保证。

成功标准：

1. 区分数据内容敏感性、来源权限、用途、环境、生命周期和派生风险；
2. 明确凭据、个人/客户数据、生产数据、源码/内部拓扑、日志和 RCA/Embedding 等不同对象不能用一个标签处理；
3. 定义识别—处理—验证—发布/使用门禁，且验证者不能由生成者单独兼任；
4. 说明原文、摘要、哈希、伪名、Embedding、Index、Cache 和 Trace 投影的差异风险；
5. 缺少分类、权限、血缘、脱敏结果或目标用途时默认隔离/阻断；
6. 源撤回或策略变化时，派生资产和正在等待的动作可被枚举、暂停和复核。

### 阶段1：头脑风暴

#### 1. 分类至少需要多轴，而不是单一 public/private

建议每条证据同时携带：

```text
content_class: credential | pii | customer_data | production_data
                source_code | internal_topology | operational_log
                trace_context | metric | rca_derived | embedding | audit
sensitivity:    public | internal | restricted | confidential | highly_restricted
source_acl:     来源主体、Project/租户和用途限制
purpose:        observe | diagnose | verify | audit | derive | retrieve | action
environment:    dev | test | staging | production | unknown
lifecycle:      transient | retained | published | suspended | revoked
reidentification_risk: unknown | low | reviewed | high
```

这些轴不可互相替代：开发环境的客户数据仍可能是高敏感；脱敏源码仍可能包含内部拓扑；哈希仍可能因字典攻击成为可关联标识；`internal` 不是“可供所有员工检索”；`sanitized` 不是永久安全或已获发布授权。

#### 2. 凭据必须按“不可持久化、不可回显、不可进入派生”处理

API Key、Token、Cookie、密码、私钥、连接串、签名材料、临时授权票据和包含秘密的环境变量默认属于 `credential`。统一场景流只允许保存是否存在、类型、来源引用、指纹/不可逆校验、时间和处置结果；不得保存可恢复原文、完整请求/响应、命令行参数或模型上下文中的秘密。

发现疑似凭据时，处理顺序是：停止传播 → 最小化隔离 → 通过安全通道轮换/撤销（若已获授权）→ 影响范围分析 → 清除未授权投影/缓存 → 审计和复核。扫描器误报不能自动把普通业务值公开，扫描失败也不能标记为安全。

#### 3. 代码与日志的风险来自组合和上下文

源码可能包含私有路径、客户标识、凭据、漏洞、内部域名、拓扑、注释中的个人数据和未发布业务逻辑；日志可能包含请求体、SQL、手机号、邮箱、IP、用户 ID、Authorization header、错误堆栈和跨租户数据。脱敏不能只做正则替换：必须保留语义所需最小片段，并重新检查组合重识别、跨事件关联、时间窗口、错误堆栈和嵌套字段。

#### 4. 生产数据和测试数据不能仅因“用于排障”放宽

生产客户数据、生产配置、拓扑、数据库快照和真实请求/响应默认受限；导入测试或 RCA 前需明确目的、字段最小化、授权范围、保留期限、隔离环境和删除/撤回路径。合成、采样、聚合、泛化或字段级掩码可能降低风险，但不自动证明不存在重识别或业务语义破坏。

#### 5. 派生对象继承风险但不盲目复制权限

RCA 摘要、错误签名、Embedding、Index、Cache、Context Manifest、Skill 候选和统计指标都可能泄漏源信息。派生对象需记录 source refs、变换、策略版本、适用范围、验证状态和目标用途；引用关系不扩大 ACL，低敏文本也不能绕过源撤回。Embedding/Index/Cache 不能当作“不可读所以无风险”。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST SP 800-122**：将 PII 保护与识别、影响评估、最小化和生命周期治理联系起来。可借鉴按风险和用途分类、不能只靠字段名称判断、应记录保护措施与处理范围；它不替代企业客户数据、代码和 Trace 的具体分类目录。来源：<https://csrc.nist.gov/pubs/sp/800/122/final>（访问日期：2026-09-20）。
2. **NIST SP 800-57 Part 1**：强调密钥材料的生命周期、保护、使用和销毁。可借鉴凭据/密钥与普通日志字段分开治理、最小暴露、轮换/撤销和审计；它不定义本平台的 Token 检测、事件协议或跨空间发布策略。来源：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问日期：2026-09-20）。
3. **OWASP Secrets Management Cheat Sheet**：建议避免秘密进入源码、日志和错误输出，采用集中管理、轮换、最小权限和泄露响应。可借鉴“秘密发现后应处置，不只是打码展示”；具体密钥系统和应急流程仍依赖企业架构。来源：<https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html>（访问日期：2026-09-20）。
4. **GitHub Secret Scanning**：官方 Secret scanning 用模式和合作伙伴规则发现提交等位置的疑似秘密，并支持告警/处置。可借鉴多来源检测和误报处理；扫描并不证明无秘密，检测结果也不应把原文放进通用事件流。来源：<https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning>（访问日期：2026-09-20）。
5. **议题10第1–3轮既有结论**：已确认识别—处理—验证三阶段、组合重识别检查、源/目标双边责任、派生血缘和失败隔离。本轮将其落到代码场景的证据类型，不改变议题10已经确认的跨空间权限与撤回边界。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **代码场景敏感治理采用多轴分类和用途绑定，而不是一个统一敏感标签。凭据/密钥默认禁止持久化原文、回显、Embedding、RCA 派生和跨空间传播；个人/客户/生产数据、源码/漏洞/内部拓扑、操作日志、Trace、指标、RCA、Embedding、Index、Cache 和审计分别记录来源 ACL、敏感性、用途、环境、保留/撤回状态和派生血缘。采集和派生遵循“识别 → 最小化/处理 → 脱敏后验证 → 受限发布/使用”，生成者不能独立完成最终验证或批准。脱敏不是单纯替换：必须检查显式秘密、字段级敏感、组合重识别、语义保真、跨事件关联和执行安全。缺少分类、权限、用途、血缘、验证或目标环境时默认隔离/阻断；源撤回、权限收窄或策略变化先阻断新的 retrieval/projection/action，再完成影响闭包和派生资产复核。**

#### 最小处理矩阵

| 类型 | 默认处理 | 可保留的最小证据 | 禁止/高风险内容 |
|---|---|---|---|
| 凭据/密钥 | 不落原文；隔离、告警、轮换/撤销走专门授权 | 类型、来源引用、不可逆指纹、处置状态 | 原文、可逆密文、完整 header、命令参数、模型上下文 |
| 个人/客户数据 | 字段最小化、掩码/泛化/合成，单独 ACL | 聚合统计、去标识样本、必要的验证结果 | 无授权跨租户复制、完整请求体、稳定可逆伪名 |
| 生产数据/配置 | 生产权限、用途和环境绑定；优先采样/聚合/合成 | 受控摘要、范围、时间窗口、查询结果引用 | 完整快照、拓扑细节、客户数据、未审查导出 |
| 源码/漏洞/内部拓扑 | revision 锚定、范围最小化、目标用途限制 | 文件/符号引用、必要片段、版本和验证 | 未授权全文、私有路径、可利用细节的跨空间发布 |
| 日志/Trace/Tool 参数 | 结构化字段白名单，入口和导出再检查 | 事件 ID、状态、脱敏摘要、授权引用 | Secret、完整生产 body、跨租户上下文、原始参数 |
| RCA/Embedding/Index/Cache | 保留血缘、适用范围和验证状态，按消费者重新授权 | 抽象模式、来源引用、窗口/覆盖说明 | 以派生对象绕过源 ACL、把摘要当公开或可执行知识 |

“可保留”不代表自动可发布；实际范围仍取主体、源 ACL、用途、目标策略、敏感性、血缘和资产状态的交集。

#### 验证闭环

```text
source intake
  → classification + purpose + scope
  → secret/PII/customer/production/code detection
  → minimize / redact / generalize / tokenize / aggregate / isolate
  → explicit-secret check
  → sensitive-field check
  → combination re-identification check
  → semantic-fidelity and applicability check
  → independent review where required
  → restricted projection / retrieval / action decision
  → lineage, retention, revoke and audit
```

任何检查为 `unknown`、`pending` 或 `failed` 时不能当作 `passed`。脱敏结果需记录删除/泛化/替换差异、策略版本、验证者、目标用途和适用范围；验证失败不覆盖原始事实，原始事实也不能自动继续传播。


### 自动审核与推进

自动化可以执行分类候选、Secret/PII 模式检测、字段白名单检查、凭据原文阻断、敏感字段统计、脱敏差异报告、重识别风险候选、血缘完整性检查、撤回影响枚举和受限审计记录。它可以在明确策略允许的低风险范围生成脱敏摘要，但不能声明永久安全、自动批准高敏内容、独自完成最终验证、扩大 ACL、发布跨空间可执行知识或恢复已撤回源。

必须人工或受控审核的情况包括：凭据疑似真实、生产/客户数据原文访问、跨租户/跨 Project、漏洞和内部拓扑发布、组合重识别不明、语义保真争议、脱敏失败、法律/合同限制和高影响执行。缺少主体、用途、源 ACL、目标策略、revision、环境、血缘、验证或撤回状态时默认 `isolated/blocked`。

## 子议题深化7第1轮：Code Context、RCA、Patch 候选知识化和下游撤回

### 主题与成功标准

本轮处理“Code Context、RCA、Patch 候选知识化和下游撤回”暂缓项。目标是明确代码场景产物如何从事实和候选进入受控 Knowledge Asset，以及源变化、权限收窄、revision 漂移或验证失败时如何阻断和撤回下游使用；不把候选变成自动执行 Patch，也不冻结最终 Schema、评分、审核角色或存储实现。

成功标准：

1. 分离 Source Observation、Scenario/RCA、Patch Candidate、Knowledge Asset、Action Proposal、Run Plan 和执行结果；
2. 任何知识候选能回溯来源、revision、环境、权限、敏感和验证；
3. Code Context、RCA 和 Patch Candidate 使用对象专属证据与发布门槛；
4. 发布、检索、注入、行动和执行是独立消费者状态；
5. 源变化、撤回、权限变化、revision 不适用或验证失效时，能沿血缘阻断/暂停/重算/撤回；
6. 不因“知识发布”获得代码修改、工具或生产权限；
7. 旧版本和历史 Run 可审计，但不能恢复当前权利。

### 阶段1：头脑风暴

#### 1. 产物分层

```text
Source Observation / Evidence
  → Code Scenario / RCA explanation
  → Patch Candidate (声明性建议)
  → Knowledge Candidate
  → reviewed Knowledge Asset
  → consumer projection (reference/retrieval)
  → Action Proposal / Run Plan (重新绑定当前上下文)
  → independently authorized execution
```

- **Code Context**：绑定 repo、revision、文件/符号/模块、依赖、架构关系、不变量和变更边界；回答“当前代码事实是什么”；不是源码全文，也不是补丁已应用。
- **RCA**：保留症状、影响、证据、竞争假设、根因状态、修复、验证、适用范围和残余风险；回答“在什么范围内如何解释”；不是运维批准。
- **Patch Candidate**：声明性修复建议、diff 引用或变更意图；必须关联代码锚点、原因、前置条件、风险、验证和回滚；不是 Git 写操作或可执行命令。
- **Knowledge Asset**：经对象专属审核后供指定消费者引用的版本化资产；发布不等于可行动。
- **Action Proposal/Run Plan**：针对当前主体、任务、revision、环境、权限和工具能力重新生成的行动请求；不能直接从历史 Patch 或知识文本继承执行权。

#### 2. 对象专属证据门槛

Code Context 至少需要稳定 repo/revision、定位范围、代码/依赖/测试或 Owner 依据、适用和不适用条件、过期触发器；RCA 需要事件与影响范围、证据链、假设/确认状态、反证、修复和验证；Patch Candidate 需要变更目标、目标 revision、预期差异、影响/风险、前置条件、测试/回滚计划和声明性状态。缺一项则保留为候选或隔离，不用统一质量分数补齐。

#### 3. 事实、推断、建议必须分段

知识化应保留至少三类内容：`observed_fact`、`derived_explanation`、`proposed_action`。例如“某测试在 revision X 失败”是事实；“可能由依赖初始化顺序导致”是候选解释；“将初始化移到某模块”是 Patch 建议。后续发布可以把三者放在同一资产的不同区段，但不能把建议写成事实或通过摘要抹掉不确定性。

#### 4. 发布与消费者状态分离

```text
asset: candidate → review → published → suspended/revoked/superseded
reference: blocked/allowed
retrieval: blocked/allowed
injection: blocked/allowed
action: blocked/eligible
execution: never implied; requires new RunGate
```

一个 Code Context 可以允许受限 reference，却因 revision 漂移禁止 retrieval；RCA 可以供复盘检索，却不能直接触发生产修复；Patch Candidate 默认 `action=blocked`。任何消费者状态必须带当前主体、用途、目标范围、策略版本和检查时间。

### 阶段2：其他产品/标准如何做（带来源）

1. **议题5既有知识化结论**：已建立候选—审核—发布—复核—撤回生命周期，区分资产内容状态与 reference/retrieval/action，并明确 Published 不等于 Actionable。本轮将该生命周期具体化到代码场景，不重复定义通用知识对象治理。
2. **W3C PROV-O**：Entity、Activity、Agent 及派生/使用关系支持把 Code Context、RCA 和 Patch Candidate 连回源证据和生成活动。PROV-O 不定义代码适用性、审批、撤回传播或执行授权。来源：<https://www.w3.org/TR/prov-o/>（访问日期：2026-09-20）。
3. **SLSA Provenance**：构建产物可以关联源 revision、构建定义、构建器、依赖和环境，为 Code Context/验证提供强证据。SLSA 不证明 RCA 正确、Patch 安全或生产变更获批。来源：<https://slsa.dev/spec/v1.1/>（访问日期：2026-09-20）。
4. **OpenTelemetry Signals**：Trace、Log、Metric 能提供运行观察和关联，但不构成完整因果证明；因此只能作为 RCA evidence collection 的输入。来源：<https://opentelemetry.io/docs/concepts/signals/>（访问日期：2026-09-20）。
5. **议题9/10既有结论**：发布、跨空间派生、撤回、权限、Tool Policy 和 RunGate 彼此独立；源撤回先同步阻断新使用，再异步完成影响闭包。本轮沿用这些边界。

### 阶段3：总结、结论与建议

#### 阶段性结论

> **Code Context、RCA 和 Patch Candidate 先作为带来源、revision、环境、适用范围、敏感性、权限和验证状态的知识候选，不直接成为执行对象。Code Context 证明代码定位和约束，RCA 解释问题及证据范围，Patch Candidate 描述声明性变更建议；三者都必须区分事实、推断和行动。通过对象专属审核后才可形成 Knowledge Asset，且资产发布、reference、retrieval、injection、action eligibility 和 execution 分离。任何 Action Proposal/Run Plan 都必须针对当前主体、Harness、Project、Task、revision、环境、Tool Policy 和 RunGate 重新生成；知识发布不授予代码写入或生产权限。源证据撤回、ACL 收窄、revision/依赖/环境漂移、脱敏失败、验证失效或血缘断裂时，先阻断受影响新使用和行动，再沿血缘暂停、重算、收窄或撤回派生资产。历史版本和 Run Snapshot 仅用于受控审计，不能恢复当前权利。**

#### 推荐治理链路

```text
collect facts
  → anchor repo/revision/environment and ACL
  → classify fact / inference / proposal
  → create Code Context / RCA / Patch Candidate
  → validate object-specific evidence and applicability
  → privacy/security/owner review (as risk requires)
  → publish versioned Knowledge Asset
  → project with consumer-specific permissions
  → current retrieval/injection check
  → independently generate Action Proposal/Run Plan
  → RunGate + ToolPolicy + execution audit
  → append result, verification, feedback and lineage
```

#### 撤回和失效传播

```text
source revoke / permission narrow / revision drift / validation failure
  → authoritative control event
  → block new retrieval, injection, action and pending high-risk Run
  → enumerate RCA, Code Context, Patch, Knowledge, Embedding, Index, Cache,
    Manifest, Harness projection and queued Action descendants
  → suspend / recompute / narrow / revoke by evidence
  → notify owners and consumers
  → re-review before restore
```

无法证明影响闭包、缓存失效或权限状态时，保持阻断，不以“暂时没检索到”作为清理完成证明。已发生的历史执行和审计事实不被静默覆盖，但其输出仍按当前策略限制访问。

反例约束：

```text
published             ≠ actionable
RCA confirmed         ≠ patch approved
```

## 子议题深化8第1轮：场景与 Work Thread、Task、Run 的完整 Schema 和关系

### 主题与成功标准

本轮处理“场景与 Work Thread、Task、Run 的完整 Schema 和关系”。目标是明确 Engineering Scenario、Work Thread、Task、Run、Attempt、Evidence 和 Code Context/RCA 的对象边界、关系方向、生命周期与恢复语义；不冻结具体数据库 Schema、事件总线或 API 字段实现。

### 阶段1：头脑风暴

四类对象回答不同问题：

```text
Engineering Scenario：问题/目标及其代码、证据、RCA 和验证范围
Work Thread：跨执行者和 Harness 的连续工作过程
Task：线程中可独立分配、验收和恢复的工作单元
Run：一次 Harness/Agent 执行实例及其授权和环境快照
Attempt：Run 中一次工具或策略路径尝试
```

建议关系为：

```text
Scenario 1 ──< WorkThread
WorkThread 1 ──< Task
Task 1 ──< Run
Run 1 ──< Attempt
Attempt ──< Evidence
Scenario ──< CodeContext / RCA / Change / Verification
Task/Run ──references──> Scenario / CodeContext / RCA
Task ──depends_on──> Task
Run ──resumes/replaces──> Run
```

关系不能互相替代：一个 Run 可以执行多个 Task，但不因此成为 Scenario Owner；一个 Task 可以有多个失败/重试 Run，但不应把失败 Run 覆盖成成功；Work Thread 是过程连续性，不是最终知识资产。

### 阶段2：其他产品/标准如何做（带来源）

1. **OpenTelemetry Trace Data Model**：通过 Trace/Span 关联跨服务操作、父子关系和上下文传播，可借鉴 Run/Attempt 的关联与时间边界；Trace 关联不等于授权或业务所有权。来源：<https://opentelemetry.io/docs/specs/otel/trace/>（访问日期：2026-09-21）。
2. **W3C PROV-DM**：将实体、活动、代理及使用、生成、派生和责任关系分开建模，可借鉴 Scenario/Task/Run/Evidence 的关系应显式表达，不能只依赖嵌套日志。来源：<https://www.w3.org/TR/prov-dm/>（访问日期：2026-09-21）。
3. **议题1既有 Connector/Run 结论**：Run 需绑定 Harness、能力、环境、revision、授权和幂等边界；失败、恢复、重放和交接不得静默覆盖历史。
4. **议题5/9既有结论**：Code Context、RCA 和 Skill 是不同知识资产；Run Snapshot、Tool Policy 和 RunGate 需要与业务任务关系分离。

### 阶段3：总结、结论与建议

> **代码场景采用“Scenario—WorkThread—Task—Run—Attempt”分层模型。Scenario 表示目标、范围、代码锚点、证据、RCA、变更和验证；WorkThread 表示跨 Harness/Agent 的连续过程；Task 表示可分配、依赖和验收的工作单元；Run 表示一次带 Harness、主体/委托、环境、revision、Manifest、策略版本和生命周期快照的执行；Attempt 表示具体工具/路径尝试及结果。Run、Attempt、Evidence、CodeContext、RCA 和 Verification 通过不可变引用和显式关系关联，失败、取消、恢复、替换和重试生成新状态/事件而不静默改写历史。Task 完成需满足自己的验收条件，Run 成功不等于 Task 或 Scenario 完成；Scenario Owner、Task Assignee、Run Executor、Evidence Producer 和 RCA Reviewer 分开记录。**

#### 对象最小包络

```text

  scenario_id / intent / scope / owner / participants
  code_anchors / status / evidence_refs / rca_refs
  acceptance / residual_risk / created_at / closed_at

WorkThread:
  thread_id / scenario_ref / participants / harnesses
  handoff_refs / continuity_state / current_task / audit_refs

Task:
  task_id / thread_ref / parent_or_dependency_refs
  objective / inputs / outputs / acceptance / assignee
  status / priority / risk / current_run / history_refs

Run:
  run_id / task_ref / harness / agent / delegation
  authorization_context / manifest_ref / environment
  repository_revision / plan_version / started_at / ended_at
  status / outcome / resume_or_replacement_ref

Attempt:
  attempt_id / run_ref / tool / input_digest / status
  side_effect_state / evidence_refs / retry_or_compensation_ref
```

#### 生命周期与一致性

```text

WorkThread: open → handed_off → active → paused | closed
Task: ready → assigned → running → blocked | succeeded | failed | cancelled
Run: queued → gated → running → paused | succeeded | failed | cancelled | unknown

```

## 子议题深化9第1轮：跨 repo、跨 revision 的场景合并、分支和 rebase 处理

### 主题与成功标准

本轮处理跨 repo、跨 revision 的场景合并、分支和 rebase 处理。目标是定义何时可以合并工作场景、如何保留 revision/branch/rebase 语义、如何处理冲突和复用候选，避免把相似任务或共同文件误判为同一事实；不固化具体代码图数据库或自动合并算法。

### 阶段1：头脑风暴

场景合并必须区分：

```text
same_scenario        同一目标、连续线程或明确交接
related_scenario     目标/代码/证据相关，但生命周期独立
derived_scenario     从既有场景派生新分支或新修复
duplicate_candidate  可能重复，等待验证
unrelated            仅有表面相似
```

合并证据至少包括：

```text
repository_identity / tenant / project
base_revision / head_revision / commit ancestry
branch / fork / merge-base / rebase mapping
file/symbol/API anchors
intent / task identity / participant handoff
evidence time / environment / dependency versions
```

共同 repo 或文件不是充分条件；共同错误文本也可能只是同一症状。缺失祖先关系、revision、时间线、权限或场景意图时，应保留关联候选而不是合并。

#### 分支与 rebase

```text
base scenario at revision R0
  ├── branch A → attempts / changes / evidence
  └── branch B → attempts / changes / evidence

rebase / merge
  → record old-to-new revision mapping
  → compare changed paths/symbols and semantic conflicts
  → preserve branch-specific evidence
  → create merged candidate or keep branches separate
  → revalidate Code Context/RCA/Knowledge consumers
```

Rebase 改写 commit identity，不应静默把旧证据的 revision 替换成新 revision；需要记录映射、重放/验证状态和不再适用的引用。

### 阶段2：其他产品/标准如何做（带来源）

1. **Git merge documentation**：说明合并有共同祖先、冲突和结果提交等语义，可借鉴场景关系记录 merge-base、分支和冲突，不把文本相似当历史关系。来源：<https://git-scm.com/docs/git-merge>（访问日期：2026-09-21）。
2. **Git rebase documentation**：说明 rebase 会将提交重新应用到新基线并产生新的提交身份，可借鉴保留旧 revision、映射和重新验证，不静默改写历史证据。来源：<https://git-scm.com/docs/git-rebase>（访问日期：2026-09-21）。
3. **W3C PROV-DM**：派生、使用和生成关系为分支场景与知识消费者提供可追溯血缘；可借鉴 branch/merge/rebase 是活动和关系，不是简单字段覆盖。来源：<https://www.w3.org/TR/prov-dm/>（访问日期：2026-09-21）。
4. **议题1/5既有结论**：跨 Harness 交接、Code Context、RCA 和知识资产必须保留 revision、适用范围、权限和撤回边界；祖先/后代 revision 默认是需复核候选。

### 阶段3：总结、结论与建议

> **跨 repo/revision 场景采用“关系候选先行、revision/祖先证据确认、分支独立保留、rebase 显式映射、合并后重新验证”的模型。同一目标的明确连续交接可合并 Work Thread；同 repo/同 revision 且代码锚点、意图和证据一致可复用；祖先/后代 revision、分支、fork、rebase 或跨 repo 只能形成 `related/derived/merge_candidate`，不能自动宣告同一场景。合并必须记录 repository/tenant/project、base/head/merge-base、branch、old→new revision mapping、文件/符号/API 差异、冲突、证据和责任；分支证据不丢失，rebase 不覆盖旧 revision。合并或 rebase 后 Code Context、RCA、Patch Candidate、Verification 和 Knowledge Asset 都重新检查适用性、权限、敏感性和撤回状态；无法证明时保持隔离或需审核。**

```text
  → rebase_revalidation
  → reusable | narrowed | invalidated
```

`merged_verified` 只表示关系和指定验证范围成立，不等于所有分支内容安全合并；旧场景和旧 Run 仍保留不可变审计。

## 子议题深化10第1轮：RCA 多根因的完整因果图和自动裁决算法

### 主题与成功标准

本轮处理 RCA 多根因的完整因果图和自动裁决算法。目标是明确症状、事件、条件、根因、促成因素、证据、修复和验证之间的因果关系与不确定性，支持多个并行或交互根因；不把候选图或模型评分当作最终事实，不固化特定因果推断算法。

### 阶段1：头脑风暴

单一“根因”字段不足以表达真实事故。至少区分：

```text
symptom          用户/系统观察到的现象
trigger          直接触发事件
root_cause       经验证的必要或主要原因
contributing     增加发生概率/影响的条件
latent_condition 长期缺陷、设计或治理条件
mitigation       遏制措施，不一定消除根因
fix              修复动作
verification     证明修复有效的结果
```

因果图节点应记录类型、时间、revision、环境和置信状态；边应表达：

```text
causes / enables / precedes / correlates_with
exacerbates / mitigates / verified_by / contradicts
```

相关性、时间先后和共同上游不能直接升级为因果。多个根因可能是并行必要条件、替代条件、链式条件或相互作用；图应允许分支、循环检测和未决边。

#### RCA 推理链

```text
observations
  → normalize events and timelines
  → build candidate causal graph
  → attach supporting/contradicting evidence
  → test counterfactual or reproduction where possible
  → separate confirmed / plausible / rejected / unknown
  → independent review
  → fix and verification
  → reopen on contradictory evidence
```

“自动裁决”应限于排序、去重、冲突检测和建议下一验证动作；高影响根因、生产修复和长期知识发布需要受控审核。

### 阶段2：其他产品/标准如何做（带来源）

1. **W3C PROV-DM**：提供实体、活动、代理及使用、生成、派生、影响和责任关系的通用表示，可借鉴 RCA 保留证据与责任链；PROV 不自动证明因果真值。来源：<https://www.w3.org/TR/prov-dm/>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

> **RCA 采用“类型化因果图 + 多源证据 + 不确定性状态 + 反例/反事实验证 + 受控裁决”的模型。图节点区分症状、触发、根因、促成因素、潜在条件、缓解、修复和验证；边区分 causes/enables/precedes/correlates/exacerbates/mitigates/verified_by/contradicts。每条边和节点绑定证据、时间、revision、环境、来源和状态。算法可自动归一化时间线、构建候选、检测矛盾/循环、按证据排序、计算下一验证动作和发现重复模式，但不能把相关性、最后发生事件、模型置信度或多数票直接裁决为确认根因。根因状态至少为 `confirmed/plausible/rejected/unknown`；高影响、生产、权限/安全和跨租户 RCA 需要独立审核。修复必须有验证和残余风险；新证据可使 RCA reopened，旧结论不可静默覆盖。**

## 子议题深化11第1轮：工具调用、日志、指标和 Trace 的统一采集协议

### 主题与成功标准

本轮处理工具调用、日志、指标和 Trace 的统一采集协议。目标是让一次代码场景中的执行、观测、错误、验证和 RCA 可通过统一关联标识追溯，同时保留不同信号的语义、采样、敏感性和可靠性边界；不替代各 Harness、Connector 或可观测性后端的具体实现。

### 阶段1：头脑风暴

四类信号不能压成同一种事件：

```text
Tool Call    计划、主体、工具、参数摘要、授权、结果和副作用状态
Log          离散文本/结构化事件、时间、级别、来源和上下文
Metric       数值时间序列、单位、聚合和采集窗口
Trace        跨服务操作、Span、父子关系和持续时间
```

统一采集应提供共同包络：

```text
signal_id / signal_type / occurred_at / received_at
trace_id / span_id / parent_ref / scenario_ref / thread_ref
run_id / task_id / attempt_id / tool_call_id
principal/delegation / tenant/project/space
repository/revision / environment / policy_version
purpose / sensitivity / redaction / source_connector
status / sampling / sequence / integrity_ref
```

关联上下文用于追踪，不自动授予权限。工具参数、客户数据、凭据、日志正文和 Trace 属性必须按当前 ACL、用途和敏感性最小化；缺失或不可信上下文不能靠猜测补齐。

#### 采集与传播链

```text
Harness/Connector
  → authenticated capture
  → normalize signal envelope
  → attach trusted context
  → redact/classify
  → buffer/ingest with sequence and idempotency
  → store/query under ACL
  → correlate to Scenario/Task/Run/Attempt
  → derive RCA/metrics/knowledge candidate
```

采集失败需区分未采集、采集失败、延迟、丢失、采样和权限拒绝；不应把缺失观测当作没有发生。

### 阶段2：其他产品/标准如何做（带来源）

1. **OpenTelemetry Logs Data Model**：定义日志记录、时间、严重性、属性和 Trace/Span 关联，可借鉴统一日志包络与关联字段，同时保留日志语义。来源：<https://opentelemetry.io/docs/specs/otel/logs/>（访问日期：2026-09-21）。
2. **OpenTelemetry Metrics Data Model**：区分指标点、时间、属性、单位和聚合语义，可借鉴指标不能伪装成逐事件证据。来源：<https://opentelemetry.io/docs/specs/otel/metrics/>（访问日期：2026-09-21）。
3. **OpenTelemetry Trace Data Model / W3C Trace Context**：提供 Span、上下文传播和父子关联，可借鉴跨 Harness/Connector 追踪；Trace ID 不等于主体授权或事实签名。来源：<https://opentelemetry.io/docs/specs/otel/trace/>、<https://www.w3.org/TR/trace-context/>（访问日期：2026-09-21）。
4. **NIST SP 800-92**：安全日志管理涵盖生成、传输、存储、分析和处置，可借鉴日志来源、时间、完整性、访问和生命周期治理。来源：<https://csrc.nist.gov/pubs/sp/800/92/final>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

> **统一采集采用“信号专属语义 + 共同关联包络 + 受信上下文 + 采集状态可见 + 当前权限/用途过滤”的协议。Tool Call、Log、Metric、Trace 分别保留计划/副作用、文本事件、数值聚合和跨服务时序语义，通过 `trace_id/span_id/scenario_id/thread_id/task_id/run_id/attempt_id/tool_call_id` 等引用关联，而不互相替代。采集端必须绑定受信主体、租户/Project、repo/revision、环境、策略版本、Purpose、敏感级别、采样和序列；上下文传播不授权，Trace 关联不证明因果，指标不证明逐次调用，日志缺失不证明未发生。敏感字段默认最小化/脱敏；采集失败、延迟、采样、权限拒绝和丢失分别记录，RCA 和高风险治理必须暴露证据缺口。事件传播采用幂等键、序列/水位和可验证完整性，历史信号不可静默覆盖。**

## 子议题深化12第1轮：场景关闭、严重等级和生产变更的完整审批矩阵

### 主题与成功标准

本轮处理场景关闭、严重等级和生产变更的完整审批矩阵。目标是把 Engineering Scenario、RCA、修复、生产变更和关闭决定的责任、风险、证据、验证与升级边界明确化；不固化企业最终职位、法定人数、SLA 数字或具体工单系统。

### 阶段1：头脑风暴

场景关闭至少拆分为不同决定：

```text
contained       风险/影响已遏制
resolved        修复已完成且原问题验证通过
monitored       进入观察期，仍有残余风险
closed          证据、责任、审计和行动项闭环
reopened        新证据或复发使结论失效
```

严重等级应按影响而不是日志级别决定：

```text
S0 informational / no material impact
S1 bounded development impact
S2 customer, shared service or material delivery impact
S3 production, security, privacy, credential, cross-tenant,
   irreversible or unknown high-impact event
```

生产变更必须独立于 RCA 结论：一个 RCA 可以支持多个变更；变更获批不自动证明根因正确；场景关闭不等于所有改进项完成。

#### 审批链

```text
scenario/RCA evidence
  → severity classification
  → impact and risk preview
  → proposed fix / production change
  → current authorization and Tool Policy
  → independent approval
  → RunGate
  → execute
  → verify / observe
  → residual risk acceptance
  → close or reopen
```

### 阶段3：总结、结论与建议

> **场景治理采用“严重等级 + 证据闭环 + 变更独立审批 + RunGate + 验证/观察 + 残余风险接受 + 可重开”的矩阵。S0/S1 可在预授权和审计下轻量关闭；S2 需要业务/服务 Owner、技术负责人和独立验证，涉及共享服务或客户影响时增加沟通/风险审查；S3 涉及生产、客户、权限、凭据、隐私、安全、跨租户、不可逆或未知影响，必须 Incident Commander、业务/资源 Owner、Security/Privacy/变更责任和独立 verifier 按组织规则审批，不能仅凭 Agent、RCA 模型或事后成功自动关闭。生产变更单独绑定 Action Proposal/Run Plan、目标 revision、环境、工具集合、前置条件、验证、回滚和有效期；计划、权限、环境、影响或风险变化使审批失效。`contained`、`resolved`、`monitored`、`closed` 和 `reopened` 独立记录，残余风险和未关闭行动项不可隐藏。**

#### 原则矩阵

| 等级 | 典型影响 | 最低门禁 | 关闭/升级 |
|---|---|---|---|
| S0 | 无物质影响、观察或低风险资料 | 当前授权、证据、自动审计 | Owner/策略允许时关闭 |
| S1 | 受限开发影响、可逆变更 | 任务 Owner、基本验证、回滚/停止 | 超时/复发升级 S2 |
| S2 | 客户、共享服务或交付影响 | 独立技术/业务审核、影响沟通、验证和观察 | 未闭环或扩散升级 S3 |
| S3 | 生产、安全、隐私、凭据、跨租户、不可逆/未知 | Incident/Owner/Security/Privacy/变更责任、独立 verifier、RunGate、强审计 | 不得自动关闭；残余风险和法务/治理决定显式记录 |

等级是原则边界，不替代具体法域、合同和组织政策；任一硬属性可使事件至少升级到 S3。

## 子议题深化13第1轮：代码、日志、生产数据和凭据的完整分类脱敏规则

### 主题与成功标准

本轮处理代码、日志、生产数据和凭据的完整分类脱敏规则。目标是定义进入 Scenario、Evidence、RCA、Trace、知识候选和审计的不同数据类别、识别/处理/验证/访问边界；不固化某一家 DLP、扫描器、密钥系统或单一行业分类表。

### 阶段1：头脑风暴

数据分类至少区分：

```text
public / internal / confidential
source_code / proprietary_logic
personal_data / customer_data
production_data / operational_topology
credential / secret / token / key
security_event / vulnerability / incident_evidence
regulated_or_legal_hold
```

分类不是只看字段名；路径、日志上下文、组合关联、环境、租户和可重识别性都可能改变敏感级别。凭据必须是最高优先级硬门：识别后立即阻断传播并撤销/轮换，不以“已脱敏”文字代替验证。

#### 三阶段治理

```text
identify/classify
  → minimize/select purpose
  → transform: remove/mask/pseudonymize/generalize/tokenize/hash
  → validate: secret scan + re-identification + semantic/scope check
  → authorize consumer projection
  → retain/delete under lifecycle
```

不同用途需要不同投影：RCA 可能需要错误类型、时间和影响，不需要客户姓名或完整请求体；Code Context 需要 revision/符号和最小代码片段，不需要生产凭据；审计需要授权和决定证据，不需要复制所有源正文。

### 阶段2：其他产品/标准如何做（带来源）

1. **NIST Privacy Framework**：提供数据处理识别、治理、控制和沟通的隐私风险框架，可借鉴目的限制、最小化、责任和持续评估。来源：<https://www.nist.gov/privacy-framework>（访问日期：2026-09-21）。
2. **NIST SP 800-88 Rev.1**：强调介质清理、净化和验证，可借鉴脱敏/删除后的副本状态和验证证据，不把逻辑标记当物理清除。来源：<https://csrc.nist.gov/pubs/sp/800/88/r1/final>（访问日期：2026-09-21）。
3. **NIST SP 800-57 Part 1**：密钥材料生命周期和保护可借鉴凭据/密钥不得进入普通日志、Trace、RCA 或知识资产，发现后需撤销、轮换和审计。来源：<https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final>（访问日期：2026-09-21）。
4. **GDPR**：数据最小化、目的限制、准确性、保留限制与安全原则可作为个人数据处理边界参考；不替代企业数据分类和客户合同。来源：<https://eur-lex.europa.eu/eli/reg/2016/679/oj>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

> **代码场景数据采用“分类硬门 + 用途最小化 + 识别/处理/验证三阶段 + 投影级权限 + 凭据零持久化”的模型。代码按公共/内部/专有逻辑和安全敏感度分类，Code Context 只保留当前授权所需 revision/路径/符号/最小片段；日志按结构化字段、错误上下文、个人/客户/生产字段、拓扑和凭据痕迹分类，RCA 默认使用摘要、引用和哈希；生产数据按租户、客户、个人、业务敏感和环境隔离，默认不进入普通知识；凭据、Token、Cookie、私钥、连接串和可恢复秘密识别即阻断，不写入普通存储/日志/Trace/Manifest，并触发撤销/轮换。处理可删除、遮盖、不可逆替换、伪名化、泛化、聚合或令牌化；验证必须检查显式秘密、组合重识别、语义/证据完整性、适用范围和下游副本。不同消费者只获得目的绑定的最小投影，脱敏不扩大源 ACL，unknown/验证失败进入隔离。**

#### 数据类别与默认处理矩阵

| 类别 | 默认处理 | 可保留的最小证据 | 硬门 |
|---|---|---|---|
| 普通代码/Code Context | 按 revision/范围授权，最小片段 | repo、revision、路径/符号、必要代码引用 | 跨 Project/外发需重新授权 |
| 专有逻辑/漏洞/安全事件 | 受限访问、抽象/伪名化、独立审核 | 影响、版本、漏洞类型、验证引用 | 不进入普通检索/跨空间 |
| 普通日志/Trace | 字段筛选、采样、脱敏 | 时间、类型、关联 ID、摘要/哈希 | 原文按用途授权 |
| 个人/客户数据 | 删除、遮盖、伪名化/聚合 | 必要类别、影响范围、不可逆引用 | 数据主体/合同/法域门禁 |
| 生产数据/拓扑 | 最小化、泛化、隔离 | 资源类别、环境、影响和版本 | 生产/跨租户专门审批 |
| 凭据/秘密 | 不持久化，立即阻断和撤销/轮换 | 类型、指纹/引用、处置状态 | 禁止原文进入任何普通资产 |

#### 验证状态

```text
classification: unknown | classified | disputed
secret_scan: unknown | passed | failed
sensitive_scan: pending | passed | failed | needs_review
reidentification: unknown | passed | failed | needs_review
semantic_fidelity: unknown | passed | degraded | failed
propagation: pending | verified | partial | external_unknown
```

任何硬失败或必要状态 unknown 时，消费状态至少为 `isolated/blocked/needs_review`；不能用总体评分抵消秘密泄露或权限失败。

## 子议题深化14第1轮：Code Context、RCA、Patch 候选知识化和下游撤回

### 主题与成功标准

本轮处理 Code Context、RCA、Patch 候选知识化和下游撤回。目标是定义代码事实、根因结论和修复候选如何从场景中派生为受治理知识资产，以及源 revision、权限、验证或安全状态变化时如何阻断、收窄、撤回和通知下游；不把 Patch Candidate 自动变成可执行变更。

### 阶段1：头脑风暴

三类资产语义不同：

```text
Code Context    当前/指定 revision 的代码事实和边界
RCA             证据支持的症状、根因、影响、修复和残余风险
Patch Candidate 候选修改、假设、差异、验证计划和失败/回滚条件
```

统一知识化流程：

```text
Scenario evidence
  → classify asset type
  → source/revision/permission/sensitivity check
  → extract or abstract
  → validation and transformation report
  → candidate review
  → publish scoped knowledge version
  → consumer projection
  → source/policy/revision change
  → block, suspend, narrow, supersede or revoke downstream
```

Patch Candidate 只能描述候选差异和验证计划，不能携带凭据、工具授予、生产批准或 RunGate 放行。RCA 结论必须保留证据、反例、状态和适用条件；Code Context 必须绑定 revision 和范围。

### 阶段2：其他产品/标准如何做（带来源）

1. **W3C PROV-DM**：派生、使用、生成和责任关系可借鉴知识资产保留 Scenario/Evidence/Revision/Patch 的血缘，而不是复制孤立文本。来源：<https://www.w3.org/TR/prov-dm/>（访问日期：2026-09-21）。
2. **NIST SP 800-53 Rev.5**：访问控制、配置管理、审计和系统完整性可借鉴代码/修复资产发布需版本、授权、验证和变更追踪。来源：<https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final>（访问日期：2026-09-21）。
3. **NIST SP 800-88 Rev.1**：清理和验证边界可借鉴源撤回/删除传播到索引、Cache、Manifest 和派生资产，并记录无法证明的副本状态。来源：<https://csrc.nist.gov/pubs/sp/800/88/r1/final>（访问日期：2026-09-21）。
4. **OpenTelemetry Trace Data Model**：Trace/Span 可作为运行证据关联，但不授予知识发布、修复执行或当前权限。来源：<https://opentelemetry.io/docs/specs/otel/trace/>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

> **Code Context、RCA、Patch Candidate 采用“资产专属语义 + Scenario/Evidence/Revision 血缘 + 候选—审核—发布 + 当前消费者授权 + 级联撤回”的模型。Code Context 只能表达指定 repo/revision/路径/符号/依赖的代码事实；RCA 只能表达带证据、反例、状态、影响和残余风险的分析；Patch Candidate 只能表达候选 diff、前置条件、验证、停止/回滚和失败处理。知识化发布不授予工具、凭据、写入、生产、跨租户或 RunGate 权限；Patch Candidate 默认 `action_status=blocked`。源 revision、权限/敏感性、血缘、验证、环境或策略发生硬变化时，权威状态先阻断下游 retrieval/projection/action，再沿血缘暂停、收窄、生成新版本、替代或撤回；历史版本保留受控审计但不注入新 Run。恢复必须重新检查当前主体、Purpose、ACL、适用 revision、环境、Tool Policy、RunGate、验证和回滚。**

## 子议题深化15第1轮：场景恢复成功率、RCA 误判率和重复失败率的完整指标体系

### 主题与成功标准

本轮处理场景恢复成功率、RCA 误判率和重复失败率的完整指标体系。目标是建立可区分对象、分母、时间窗口、证据质量和安全边界的评估指标，用于发现恢复质量和知识/根因错误，而不是用单一成功率自动放行或退休资产；不固化企业最终阈值、采样规模或 SLO 数字。

### 阶段1：头脑风暴

三个名称都容易被误用：

```text
scenario_recovery_success
  不仅是 Run succeeded，还要任务验收、环境适用、无未声明副作用和观察期通过

RCA_misclassification
  不仅是人工不同意，还要区分候选、确认、复现失败、误归因和证据不足

repeat_failure
  不仅是相同错误文本，还要考虑同一根因/场景/版本/时间窗口和修复后复发
```

指标必须按 `scenario/task/run/attempt`、Harness、repo/revision、环境、严重等级、资产版本、租户和权限范围分层，避免聚合掩盖高影响失败或数据缺失。

#### 指标族

```text
Recovery
  recovery_attempt_rate
  recovery_completion_rate
  acceptance_verified_rate
  time_to_resume / time_to_resolve
  rollback_or_compensation_success
  residual_unknown_rate

RCA quality
  candidate_to_confirm_rate
  confirmed_root_cause_precision
  false_confirmation_rate
  missed_root_cause_rate
  evidence_sufficiency_rate
  reopen_after_confirmation_rate

Repeat failure
  recurrence_rate_after_fix
  duplicate_attempt_rate
  same_root_cause_recurrence
  same_symptom_different_cause_rate
  retry_amplification_rate
  unresolved_repeat_rate

Safety and data quality
  unauthorized_action_rate
  sensitive_leakage_rate
  stale_context_use_rate
  missing_evidence_rate
  sampling/coverage rate
  unknown_external_state rate
```

### 阶段2：其他产品/标准如何做（带来源）

1. **Google SRE Monitoring Distributed Systems**：强调监控信号、告警、聚合和故障排查应与用户影响和可操作性结合，可借鉴按服务/场景/版本分层并避免单一平均值。来源：<https://sre.google/sre-book/monitoring-distributed-systems/>（访问日期：2026-09-21）。
2. **Google SRE SLO**：SLO、SLI 和错误预算可借鉴把恢复目标和观测覆盖分开，并保留时间窗口、分母和数据质量；不定义 RCA 误判指标。来源：<https://sre.google/sre-book/service-level-objectives/>（访问日期：2026-09-21）。
3. **NIST SP 800-55 Rev.2**：信息安全测量强调指标目的、定义、数据源、计算、分析和改进闭环，可借鉴每个指标明确 owner、分母、证据、限制和使用决策。来源：<https://csrc.nist.gov/pubs/sp/800/55/v2/final>（访问日期：2026-09-21）。
4. **NIST AI RMF**：风险管理强调治理、映射、测量和管理，可借鉴对模型/自动化 RCA 记录不确定性、误差、人工复核和残余风险；不把框架指标直接当产品阈值。来源：<https://www.nist.gov/itl/ai-risk-management-framework>（访问日期：2026-09-21）。

### 阶段3：总结、结论与建议

> **场景质量采用“结果验收而非 Run 成功 + RCA 结论质量分层 + 根因/症状复发区分 + 安全/证据覆盖旁路指标”的指标体系。恢复成功必须定义场景/Task 验收、目标环境和 revision 适用、必要验证、观察窗口、无计划外高风险副作用和残余风险状态；RCA 指标分别测量候选→确认、确认精确性、误确认、漏判、证据充分性和确认后重开，人工不同意不直接等同误判；重复失败按同根因、同症状异根因、重复 Attempt、重试放大和修复后复发区分。每个指标记录 numerator/denominator、窗口、采样/漏失、分层、数据来源、版本、置信区间或不确定性、owner 和决策用途。低覆盖、选择偏差、权限拒绝、未知外部状态和人工标注不足必须单独报告；任何指标都不能自动授予权限、降低风险、确认 RCA、关闭场景或退休知识资产。**

#### 指标契约

```text
metric_id / name / definition / purpose
numerator / denominator / exclusions / unit
window / cohort_dimensions / source_refs
asset_version / policy_version / label_version
sampling / missingness / confidence_or_uncertainty
owner / reviewer / collection_status
threshold_status / action_if_breached / audit_refs
```

#### 核心定义示例

```text
recovery_completion_rate =
  accepted_and_verified_tasks /
  eligible_recovery_tasks

RCA_false_confirmation_rate =
  confirmed_RCA_later_rejected_or_reopened_for_wrong_cause /
  confirmed_RCA_with_sufficient_follow_up

same_root_cause_recurrence_rate =
  incidents_recurred_after_verified_fix /
  incidents_with_verified_fix_and_observation_window
```

分母必须排除或单独标记取消、无权访问、证据不足、环境不可用和观察期未完成样本；不能把这些样本静默归为成功或失败。小样本、标签漂移和版本变化必须显示不确定性。

#### 指标状态和用途

```text
proposed → instrumented → quality_checked
  → reported → reviewed → action_tracked
```

指标本身也可能 `stale/disputed/invalidated`；采集逻辑、标签、分母或策略变化时生成新指标版本，不能静默改写历史报告。
