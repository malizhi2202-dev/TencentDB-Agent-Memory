# 议题 3：记忆自动归属

**状态：已确认（第 1 轮阶段性方案）**

## 问题定义

> 平台如何自动判断一条记忆属于 User、Team、Project 或 Agent 哪个 `MemorySpace`，并在归属不明、跨边界或发生冲突时安全处理？

本议题只讨论记忆的规范归属与归属关系，不把归属与记忆层级、ACL、执行者或发布状态混为一谈。

## 第 1 轮确认：单一规范 owner 与保守归属

本轮确认采用：

> **单一规范 owner + 多关系关联 + 证据驱动候选 + 硬约束优先 + 保守默认落点 + 跨边界提升需确认。**

### 1. 归属对象与语义

```text
MemorySpace
├── User
├── Team
├── Project
└── Agent
```

- **User**：个人长期偏好、个人工作方式或私有上下文；
- **Team**：团队共享的长期认知、协作方式和跨项目经验；
- **Project**：与特定代码库、业务对象、项目目标或 Work Thread 绑定的记忆；
- **Agent**：特定 Agent/Harness 的运行经验、工具使用方式或私有执行上下文。

每条可治理记忆只有一个 `canonical_owner_scope`，同时可以关联多个 scope：

```text
Memory
├── canonical_owner_scope：唯一规范归属
├── related_scopes
├── referenced_resources
└── affected_scopes
```

### 2. 归属不等于权限

```text
属于 Team ≠ 所有 Team 成员都可以读取
属于 Project ≠ Project 内所有主体都可以修改
由 Agent 产生 ≠ 记忆属于 Agent
被某 Project 引用 ≠ 记忆归属于该 Project
```

归属表达规范责任和语义边界。发现、读取、使用、修改、审核和发布仍由 ACL、策略和数据治理分别决定。

### 3. 归属判断信号

平台可以综合以下信号生成归属候选：

- 成员明确选择的 Project、Team 或 MemorySpace；
- Connector 验证的 Harness Session 与 Project/Team 绑定；
- 已确认的 Work Thread、Task 和 owner 关系；
- repo、服务、工单、文档、数据库或业务对象引用；
- 内容中的团队规则、个人偏好或 Agent 运行语义；
- 参与主体、历史记忆关联和实际使用范围；
- 经过权限校验的显式“仅个人”“团队共享”等声明；
- 敏感性、来源权限和跨边界影响。

以下信号不得单独决定 owner：

- 产生记忆的 Harness；
- 当前执行者；
- 消息发送者或发现者；
- 被引用次数；
- 模型置信度；
- 单个 Project 的一次性使用；
- Team 成员身份或参与人数。

### 4. 候选、裁决与审计

归属流程采用候选与规则裁决，而不是让模型直接写入最终 owner：

```text
事件 / 记忆进入
  → 提取归属信号
  → 生成 owner candidates
  → 应用硬约束和边界规则
  → 计算置信度与冲突
  → 自动落位 / 请求确认 / 治理队列 / 隔离
  → 记录归属决定及依据
```

归属决定至少应保留：

```text
Ownership Decision
├── candidate_scopes
├── selected_scope
├── signal_refs
├── decision_reason
├── policy_version
├── model_or_rule_version
├── confidence
├── decided_at
└── reviewer / confirmation
```

默认判断顺序是硬边界优先，而非简单分数排序：

```text
显式且经授权的归属声明
  → 已确认的 Work Thread / Project / Team 关系
  → 经 Connector 验证的资源绑定
  → 稳定历史关联
  → 内容语义推断
  → 保守默认落点
```

### 5. 默认落点与不明归属

| 情形 | 建议归属 |
|---|---|
| 与明确 Project、repo、服务或业务对象绑定 | Project |
| 跨多个 Project 且描述团队共同系统或规则 | Team 候选，需按策略确认 |
| 明确是个人偏好或私有工作方式 | User |
| 只描述 Agent/Harness 的运行方法或工具经验 | Agent |
| 一次性工作过程 | 先保留在 L0，不自动提升为长期 owner scope |
| 无法判断、跨边界或涉及敏感内容 | 保留较窄边界、L0 或 `ownership_pending` |
| 多个候选互相竞争 | 不静默选择，进入确认或治理队列 |

核心原则：

> **宁可暂时留在较窄的原始边界，也不自动扩大为 Team 或跨 Project 共享。**

归属判断失败不能导致 L0 原始证据丢失，但不得据此向上晋升。

### 6. 产生者、归属者、参与者与受益者

```text
Producer        = 产生证据的 User / Agent / Harness
Canonical Owner = 对记忆负责的 User / Team / Project / Agent
Participants    = 参与形成或使用记忆的主体
Beneficiaries   = 可能从记忆中受益的主体
```

例如：Agent 在 Project A 中发现长期故障模式时，Producer 可以是 Agent，Canonical Owner 默认是 Project A；只有经过证据积累、权限与治理确认后，才可能提升为 Team 归属。

### 7. 跨边界提升与归属迁移

归属变化采用版本化的提升或迁移流程，不直接覆盖 owner：

```text
Project Memory
  → Team Promotion Candidate
  → 影响范围与权限预检
  → 脱敏与冲突检查
  → 授权确认
  → 新 owner 生效
```

以下关系必须区分：

- `related_to`：相关；
- `referenced_by`：被引用；
- `participated_by`：参与形成；
- `affected_scope`：受到影响；
- `promoted_to`：经治理后提升；
- `transferred_to`：显式转移 owner。

历史 owner、旧版本、提升原因、权限检查和确认记录均应保留。

### 8. 硬约束与安全边界

以下情况不能仅依赖模型判断：

- 凭据、密钥、个人隐私或受保护个人信息；
- 归属主体无权发布到目标 scope；
- 跨租户、跨 Team 或跨 Project；
- 同一内容存在多个竞争 owner；
- 生产操作、合规规则或高影响决策；
- 资源边界与 Work Thread 边界不一致；
- 来源证据不足或无法验证。

处理方式：

```text
不自动扩大 scope
  → 保留原始证据
  → 生成归属候选
  → 请求有权主体确认
  → 或进入治理 / 隔离队列
```

## 第 2 轮确认：MemorySpace 边界、关系与归属转换

本轮确认：

> **User、Team、Project、Agent 采用四类并列 MemorySpace，通过显式关系表达组织、参与、引用、影响和派生；Team 与 Project 可以有关联，但不自动继承 owner 或权限；跨空间复用默认采用受控引用，长期共享采用经过证据、权限、敏感性和影响范围检查的派生条目；只有显式 Transfer 才改变规范 owner；空间归档或 Agent 退役不自动删除或转移记忆。**

### 1. 四类 MemorySpace 不是严格树形

```text
MemorySpace
├── User Space
├── Team Space
├── Project Space
└── Agent Space
```

四类空间具有不同语义：

| Space | 主要语义 | 不应自动推断 |
|---|---|---|
| User | 个人偏好、个人方法和私有上下文 | 用户参与 Project 不等于获得 Project 记忆 owner |
| Team | 团队共享的长期认知和协作规则 | Project 属于 Team 不等于 Team 自动拥有 Project 记忆 |
| Project | 项目、代码库、业务对象或 Work Thread 边界 | Team 成员参与不等于记忆自动扩大到 Team |
| Agent | Agent/Harness 私有运行经验和工具上下文 | Agent 产生证据不等于 Agent 拥有业务记忆 |

不采用严格的 `Team → Project → Memory` 单一树形作为规范模型。Team 与 Project 可以存在组织关系，例如 `belongs_to`、`participates_in` 或 `references`，但这些关系不自动意味着 owner、读取权或发布权继承。

### 2. 归属、关联、引用和派生分开建模

```text
Memory M
├── canonical_owner = Project A
├── related_to = Team X
├── referenced_by = Project B
├── participated_by = User C
├── affected_scope = Team Y
└── derived_to = Team X Memory Candidate
```

关系语义必须区分：

- `owns`：承担规范责任；
- `belongs_to`：组织或结构关系；
- `participates_in`：参与形成或协作；
- `references`：引用内容或资源；
- `affected_scope`：受到影响；
- `derived_from`：目标记忆由源记忆派生；
- `promoted_to`：经过治理后提升为更大范围的规范记忆。

关联关系不等于共享，引用关系不等于所有权，组织关系不等于权限继承。

### 3. 跨空间复用优先引用，长期共享采用派生

低风险、只读复用时，原记忆继续属于原 owner，只在授权后生成面向目标请求的引用投影：

```text
Project Memory
  → Team 请求上下文
  → 授权后的受控引用投影
```

需要长期共享时，不直接搬家，而是生成目标空间的派生候选：

```text
Project Memory
  → Team Promotion Candidate
  → 证据、敏感性、冲突、影响范围和权限检查
  → Team 审核
  → Team L3 派生条目
```

派生条目必须保留 `derived_from`、源版本、生成记录和独立生命周期。源记忆撤回、过期或权限变化时，目标派生条目需要重新评估，不得静默继续作为有效知识。

### 4. Owner 迁移采用显式 Transfer

跨空间复用、引用或派生都不改变原 owner。只有受控的 Transfer 流程才改变规范 owner：

```text
旧 owner
  → Transfer Candidate
  → 权限与资源影响预检
  → 新 owner 确认
  → owner 生效
```

关系变化和 owner 变化必须分开建模，历史 owner、旧版本、变更原因、权限检查和确认记录均需保留。

### 5. User 与 Agent Space 的限制

User Space 可保存个人表达偏好、个人工作习惯、与企业 Project 无关的个人上下文以及用户明确声明为私有的信息；不应默认独占 Project 事实、Team 约束、第三方隐私或个人无权独占的企业知识。

Agent Space 可保存特定 Agent/Harness 的工具经验、运行配置、失败模式和私有执行上下文；不应默认保存团队业务规则、Project 规范事实、生产操作约束或绕过来源资源权限的长期知识。

### 6. 空间生命周期

空间归档、解散或 Agent 退役不自动删除、转移或改变记忆真相：

```text
Project archived
  → Project Space archived / 只读
  → 保留历史 owner 和来源
  → 按策略继续只读、迁移、派生、过期或删除

Agent retired
  → Agent Space 停止新增或转为只读
  → Agent 产生的业务记忆不随 Agent 自动删除
  → 依据规范 owner 和来源关系继续治理
```

空间生命周期变化应触发影响评估，但不能静默改变 ACL、历史版本或规范归属。

### 本轮明确暂缓事项及原因

以下内容留待以后讨论，不在本轮固化：

| 暂缓内容 | 暂缓原因 |
|---|---|
| 四类 MemorySpace 的具体数据库 Schema、关系表和索引 | 属于后续数据架构设计，当前先确认语义和边界，留待以后讨论 |
| Team/Project 组织关系的完整继承矩阵 | 需要结合企业组织模型和权限策略，留待以后讨论 |
| 派生条目的同步、冲突、源撤回和版本传播算法 | 依赖血缘、生命周期和知识化模型，留待以后讨论 |
| Transfer 的审批级别、权限差异报告和回滚细节 | 属于企业级权限与治理，留待以后讨论 |

## 第 3 轮确认：归属候选的风险分级与处置

本轮确认：

> **记忆归属风险采用硬门禁与任一高风险即升级，不使用单一模型置信度或复杂总分自动放行。归属候选分为自动落位、自动暂存、人工确认/治理队列和隔离四种处置。自动落位必须满足主体、来源、权限、边界、敏感性、无冲突和可逆性等条件；跨边界、敏感、冲突、来源不明、高影响或难以撤回的内容不得自动正式落位；隔离内容不得进入普通检索、摘要和自动执行链路。治理队列必须有责任人、时限、证据、决策理由和升级路径；权限、归属、审计或撤回失败时默认拒绝写入或隔离。**

### 1. 风险判断维度

归属风险至少同时考虑：

1. **影响范围**：当前会话、单个 User、Project、Team、跨组织或跨租户；
2. **敏感性**：普通偏好、内部信息、个人隐私、凭证、合规数据；
3. **证据强度**：明确声明、直接观察、重复验证、系统推断或来源不明；
4. **可逆性**：是否容易撤回、纠正和清理派生结果；
5. **冲突程度**：是否与既有 owner、ACL、记忆或当前指令冲突；
6. **执行影响**：是否影响权限、生产操作、发布、删除或高影响决策。

不采用单一总分自动放行。任一高风险维度都可能触发升级。

### 2. 四种处置结果

| 处置 | 适用情形 | 平台动作 |
|---|---|---|
| **自动落位** | 低影响、非敏感、归属唯一、来源可信、无冲突、可撤回 | 写入对应 scope，保留来源和审计 |
| **自动暂存/候选** | 证据尚少、影响尚小，但不适合成为正式长期记忆 | 保留候选，不驱动高影响使用 |
| **人工确认/治理队列** | 跨边界、敏感、冲突、影响扩大或多个合理 owner | 展示候选、证据、影响和处置建议，等待授权主体处理 |
| **隔离** | 疑似越权、恶意注入、高敏感、来源不可信或无法安全归属 | 不进入普通检索和自动生成链路，仅限授权人员处置 |

自动暂存与治理队列必须区分：前者是低风险但尚未成熟，后者需要明确责任人、处理时限和决策记录。

### 3. 自动落位的最低条件

自动正式落位必须同时满足：

- 能识别记忆主体、来源和候选 owner；
- 来源允许平台保存和使用；
- 目标 scope 唯一且当前主体有权写入；
- 不涉及高敏感个人信息、凭证或高影响内容；
- 不存在 owner、权限或内容冲突；
- 影响范围限于当前 User、Project 或明确的小范围；
- 错误后可以撤回、纠正和清理传播结果；
- 归属决定可解释、可审计。

模型置信度只能作为辅助信号，不能替代身份认证、授权证明或用户同意。

### 4. 风险升档与硬门禁

出现以下任一情况，不能自动正式落位：

- 候选 owner 不唯一；
- 跨 User、Project、Team、租户或组织；
- 包含隐私、凭证、健康、财务、身份或安全信息；
- 来源是推断、转述、未经验证的第三方信息；
- 与已有记忆、ACL、用户指令或 Work Thread 关系冲突；
- 可能影响权限、生产、资金、删除、发布、合规或人事决策；
- 归属错误难以发现、撤回或清理；
- 批量导入、异常高频写入或疑似提示注入；
- 无法确定用途、保存期限、共享范围或删除责任人。

严重的越权、泄露、恶意注入或高危执行影响应直接隔离，而不是仅进入普通审核队列。

### 5. 治理队列的最小字段

```text
Ownership Review Item
├── memory_candidate
├── candidate_scopes
├── current_scope
├── evidence_refs
├── sensitivity
├── impact_scope
├── reversibility
├── conflicts
├── suggested_action
├── reviewer
├── due_at
├── decision
└── decision_reason
```

治理队列必须配置责任人、处理时限、升级路径、审核依据、最终决定和理由，不能成为无期限的暂存区。

### 6. 失败安全、撤回与降级

以下动作失败时，默认拒绝写入或隔离：

- 权限检查；
- 归属解析；
- 敏感性判断；
- 审计记录；
- 撤回传播；
- 目标 scope 访问验证。

发现错误归属时：

```text
发现错误
  → 冻结旧记忆使用
  → 停止新增传播
  → 纠正或迁移
  → 清理索引、缓存、派生摘要和同步副本
  → 保留必要审计记录
```

隔离内容不得进入普通检索、摘要、Context Manifest、自动执行或默认训练链路。撤回、删除和权限降级不能只修改 owner 字段。

## 补充专题确认：归属变化的下游传播

本专题确认：

> **记忆归属变化采用版本化、事件化和下游重新解析的传播模型。检索、Context Manifest 和知识化候选都按当前 owner、ACL、用途、敏感性和有效性重新判断；历史版本和 Run Context Snapshot 保持不可变，只保留当时的归属与授权快照，不因后续变化被静默改写。跨空间提升优先生成带血缘的派生条目，不直接迁移原记忆；源记忆收窄、撤回或失效时，相关派生内容进入重新评估、暂停或撤回流程。**

### 1. 归属变化的四类事件

```text
ownership_pending → confirmed
owner_scope → narrowed_scope
owner_scope → promoted_scope / derived_scope
owner_scope → rejected / isolated / withdrawn
```

归属确认、收窄、扩大/提升以及撤回/隔离分别处理，不统一修改一个 owner 字段：

- **确认**：记忆进入目标空间的正常治理流程，保留原始 L0 来源、归属依据和确认记录；
- **收窄**：新请求不再按原较大范围召回，历史版本保留但按当前权限控制；
- **扩大/提升**：不能直接扩大检索范围，先做来源 ACL、敏感性、冲突、脱敏和影响范围检查，优先生成目标空间派生条目；
- **拒绝/隔离/撤回**：停止正常检索和知识化传播，追踪索引、缓存、派生摘要和同步副本。

### 2. 对检索的影响

检索必须在召回前按照当前请求重新判断：

```text
检索请求
  → 识别当前 User / Agent / Harness / Project / Task
  → 计算当前可见和可使用的 MemorySpace
  → 过滤 owner、关联关系、敏感性和 publication_state
  → 执行语义、关键词和实体检索
  → 处理版本、冲突和有效时间
  → 返回带来源和归属解释的结果
```

不能先全库召回再在最后隐藏内容，因为相似度、计数、排序和摘要都可能泄露受限信息。被禁止使用的内容不应影响候选排序。

至少区分：

```text
discover = 是否能知道记忆存在
read     = 是否能读取内容
use      = 是否能用于召回、总结或生成 Prompt
manage   = 是否能确认、修改、撤回或迁移
audit    = 是否能查看来源和历史
```

### 3. 对 Context Manifest 的影响

Context Manifest 必须在具体请求边界重新解析：

```text
归属变化
  → 更新可用 MemorySpace 关系
  → 重新计算 ACL、用途和敏感性
  → 重新筛选可用记忆
  → 生成新的 Context Manifest
```

旧 Manifest 和正在运行的 Run Context Snapshot 不因新归属事件被静默改写。新请求、恢复、交接和新 Run 默认使用最新有效版本；权限撤销、敏感信息暴露、归属撤销和高风险 owner 变化可以暂停受影响 Run 并要求重新解析。

Manifest 至少记录：

```text
memory_id
source_revision
owner_scope
inclusion_reason
authorization_context
policy_version
sensitivity_decision
redaction_state
```

### 4. 对历史版本的影响

必须区分：

```text
historical_owner       / 当时的规范归属
current_owner          / 当前规范归属
historical_visibility  / 当时的可见性与授权
current_visibility     / 当前重新判断的可见性
```

历史版本和 Run Snapshot 保留过去发生过什么，但不是权限绕过通道：

```text
历史存在 ≠ 当前可读
曾经可读 ≠ 现在可读
曾经属于 Team ≠ 永久属于 Team
```

审计人员可以在受控权限下查看历史；普通用户仍须经过当前 ACL、用途、敏感性和数据治理判断。

### 5. 对知识化候选的影响

归属变化必须传播到 L3 以及 Wiki、Skill、RCA、Template、Code Context 等候选：

```text
源归属变化
  → 检查 derived_from 和源版本
  → 检查源证据与当前有效性
  → 检查敏感性、脱敏和目标权限
  → 重新评估适用范围
  → 保留、收窄、暂停或撤回候选
```

Project → Team 的提升不能直接把 Project 版本发布为 Team Wiki 或 Skill，应先生成带血缘的 Team 派生候选。源记忆收窄、失效或撤回时，相关候选应暂停发布；已发布内容标记复核或按策略撤回，不能继续无条件宣称原适用范围。

派生条目和知识化候选应独立记录：

- 依赖的源版本；
- 当前是否仍满足发布条件；
- 源 owner、有效性或权限发生了什么变化；
- 是否需要重新审核；
- 是否已经通知使用方。

### 6. 传播与阻断原则

- 高风险归属变化同步阻断后续受影响使用，并要求重新解析；
- 普通归属变化可以异步触发索引、缓存、派生内容和 Manifest 影响评估；
- 传播任务失败时暂停扩大传播，不能继续发布；
- 归属变化不反写历史事件中的 owner，也不修改已生成的 Snapshot；
- 撤回、删除和权限降级必须覆盖主存储、检索索引、缓存、派生摘要、Manifest 和知识化候选，具体清理协议另行治理。

冲突单位可为：单字段、关系、Memory Item、MemorySpace 集合、派生条目或权限上下文。解决流程应为：

```text
Detect → Classify → Common Baseline → Evidence/Time/Scope Check
→ Permission/Lifecycle Check → Candidate Resolution → Verify → New Revision
```

候选处理：保留多候选、追加纠正、收窄 Scope、建立冲突关系、指定 Owner、生成 Transfer Candidate、隔离或人工审核。不能用最新事件、最高置信度或多数参与者直接覆盖规范 Owner。

自动处理仅限重复事件、明确同义关系、同一主体的低风险元数据纠正和有共同基线的可逆变化；Owner Transfer、跨空间、敏感内容、权限冲突和事实不明必须升级。

### 阶段 2：官方/权威机制调研

- CRDT：<https://crdt.tech/>（访问：2026-09-19）。参考特定数据类型上的可收敛合并；不能替代 Owner、权限和业务语义裁决。
- Martin Fowler Event Sourcing：<https://martinfowler.com/eaaDev/EventSourcing.html>（访问：2026-09-19）。参考追加事件、状态重建和历史保留；重放不能静默覆盖历史或绕过当前政策。
- OpenFGA Relationship-Based Access Control：<https://openfga.dev/docs/modeling/what-is-a-relationship-based-access-control-model>（访问：2026-09-19）。参考关系授权与业务冲突分离；授权关系不自动成为唯一 Owner。

共同规律：结构可合并不等于语义可接受；冲突解决需要版本、时间、来源、Scope、权限和生命周期；高影响冲突保留历史并显式升级。

### 阶段 3：总结、结论与建议

建议采用语义单元优先、字段/对象辅助、跨单元约束验证的算法边界：

```text
Conflict Candidate
→ Common Baseline / Revision Comparison
→ Evidence and Temporal Validity
→ Scope / Permission / Lifecycle Constraints
→ Candidate Resolution
→ Cross-unit Validation
→ M0/M1 Auto or M2 Governance
→ New Revision / Correction Record
```

建议等级：

- M0：重复、格式或明确同义，不改变归属语义，可自动处理；
- M1：共同基线明确、低风险、可逆、无权限/Scope 冲突，可自动生成新 Revision 并验证；
- M2：Owner、跨空间、敏感性、权限、Transfer、生命周期或证据冲突，只生成候选并隔离/审核。

自动解决不等于自动发布，自动发布不等于自动执行；所有决定记录输入版本、证据、策略、动作、验证和未解决项。

## 子议题深化 7：Connector 元数据缺失、错误绑定和迟到事件的完整处理规则

**状态：已完成（第 1 轮，自动审核通过）**

### 主题与成功标准

本主题严格承接原暂缓项：**“Connector 元数据缺失、错误绑定和迟到事件的完整处理规则”**。本轮只确定 Connector 事件在元数据不足、绑定错误、迟到/乱序、重复/重放、来源修正或无法验证时的安全处理原则、状态转换和下游影响，不固化具体 API、事件 Schema、固定阈值、重排窗口、保留期限或 SLA。

成功标准：

1. 元数据缺失时可保留原始证据和有限处理上下文，但不得因猜测扩大 MemorySpace、Owner、权限或传播范围；
2. 错误绑定能够被识别、隔离、停止继续传播，并通过追加纠正和影响重算恢复，而不是静默覆盖历史；
3. 迟到、乱序、重复和重放事件不会覆盖更新的有效版本，也不会重复产生归属副作用；
4. 来源修正、撤回和重新验证有明确的版本、血缘、幂等和审计语义；
5. 不可验证来源不会成为规范 Owner、授权依据或自动执行输入，且处理失败默认收窄、暂存或隔离；
6. 规则能够与既有的风险门禁、归属迁移、历史引用和下游传播原则衔接。

### 阶段 1：头脑风暴

Connector 元数据不应被视为一组“有值即可使用”的字段，而应区分其存在性、真实性、时效性、范围和用途。事件进入后至少需要分别判断：

```text
Connector 身份是否已认证
来源资源是否可验证
事件身份是否可去重
事件针对哪个资源/关系/时间区间
绑定是否与当前 Work Thread / Project / Team 一致
事件版本是否仍可应用
来源是否允许保存、读取和传播
```

元数据异常类型包括：

```text
missing          # 未提供必要上下文
malformed        # 格式存在但不可解析或不符合约束
stale            # 可识别但已超过其可证明的有效时期
ambiguous        # 多个资源、主体或 Scope 都可能匹配
contradictory    # 不同元数据或来源相互冲突
misbound         # 已绑定到错误的 Project、Team、User 或 Agent
unverified       # 无法证明来源、授权或资源关系
late             # 到达时已越过当前处理进度
out_of_order     # 与已处理事件的逻辑顺序不一致
duplicate        # 同一事件或同一有效变化重复到达
replay           # 历史事件被再次投递或主动重放
correction       # 对既有事件、资源绑定或归属事实的修正
```

建议采用以下安全处理路径：

```text
接收
  → Connector 身份与来源验证
  → 元数据完整性/一致性/时效检查
  → 资源与 Scope 绑定检查
  → 事件身份去重与重放判断
  → 版本、时间顺序和当前水位判断
  → 权限、用途、敏感性和风险门禁
  → 自动暂存 / 生成候选 / 隔离 / 拒绝
  → 版本化应用与下游影响评估
```

元数据缺失的分级规则：

- **缺失但存在独立可验证的窄边界**：只能在该已验证的原始边界内保存为候选或低风险事件；不得根据内容语义、产生者身份、最近使用的 Project 或 Team 成员身份补出更大的 Scope；
- **缺失且没有可验证边界**：保留受限的原始证据和“待归属/未验证”状态，不进入普通长期记忆、跨空间派生、自动摘要或执行链路；
- **格式错误、歧义或相互矛盾**：不通过“容错解析”猜测 Owner 或资源，进入治理/隔离路径，并保留失败原因；
- **元数据过期**：只按能够证明的历史有效区间处理，不能把历史绑定当作当前绑定；当前归属不明时收窄或暂停，不自动继承旧 Scope。

错误绑定应以“影响面”为单位处理，而非只改一条当前记录：

```text
发现绑定错误
  → 标记事件、绑定和受影响派生结果
  → 冻结错误绑定驱动的新增使用与传播
  → 保留原始事件、旧版本和发现依据
  → 生成授权的 Correction / Rebinding Candidate
  → 重新检查来源、时间、Scope、权限和敏感性
  → 生成新 Revision 或隔离结果
  → 重算索引、缓存、Manifest、摘要和派生候选
  → 验证影响已收窄或纠正，并写入审计
```

纠正不能把错误绑定伪装成从未发生，也不能让纠正事件恢复已撤销的权限。历史 Run、Manifest 和审计快照保持当时的事实；新请求按当前有效版本和当前授权重新判断。

迟到/乱序事件需要同时保留至少三种时间语义：来源声明的事件时间、平台观察/接收时间和处理/决定时间。事件时间描述“何时发生”，接收时间描述“何时被看见”，处理时间描述“何时影响了当前投影”；三者不能互相替代。水位只表示处理进度或对某段输入的暂时完整性判断，不表示事件事实必然正确。

建议规则如下：

- 对同一可识别资源或关系维护版本和顺序上下文；旧版本不能以“最后到达”覆盖较新的有效版本；
- 水位之前到达的迟到事件不能静默回写当前 owner。若它可能改变历史有效区间，应生成纠正/重算候选，并重新执行权限和风险检查；
- 乱序事件若无法证明其与当前版本的关系，保持待处理或隔离，不强行拼接到当前状态；
- 迟到事件即使来源可信，也必须经过幂等、版本冲突、撤回和当前策略检查；“可信”不等于“可直接应用”；
- 需要重放历史事件时，应把重放当作受控重算，并与实时接收区分。重放不得绕过当前安全门禁、恢复旧权限或修改不可变历史决定；
- 水位推进、重排、重算或投影失败时，默认停止扩大传播，并显式记录“未知/待验证”，不得用成功状态掩盖不完整。

重复和重放规则：

- 在来源提供稳定事件身份时，以“来源 + 事件身份 + 适用上下文”判断同一事件；没有稳定身份时，只能使用受限的等价性判断，并将不确定性升级，不能假设内容相同就一定是同一事件；
- 同一事件的再次投递应产生幂等结果：不重复创建 Owner 决定、归属迁移、通知、派生或执行副作用；
- 同一事件身份对应不同内容、不同来源证明或不同绑定时，视为身份冲突，隔离而不是任选其一；
- 重放旧的绑定、撤回或纠正事件不能越过更新的版本、撤回状态或当前权限；
- 策略或模型版本变化可以触发受控重算，但重算应生成新的决定/投影，不覆盖原始接收和历史决定。

来源修正与不可验证来源规则：

```text
来源声明修正
  → 验证修正者和修正范围
  → 关联被修正的原事件/版本
  → 判断是补充、替代、撤回还是冲突
  → 生成 Correction Revision
  → 重新评估 Owner、权限、传播和派生结果
```

只有能够验证修正主体、来源关系和适用范围的修正，才可进入正常纠正流程；其余修正保留为未验证声明并隔离。无法验证来源时，可以在受限审计区域保留原始材料（前提是保存本身获准），但不得将其作为规范归属、跨空间提升、ACL 推断、自动执行或默认训练依据。之后若来源得到验证，应从新的验证时点重新进入完整归属判断，不能把此前的未验证状态静默追认成已确认事实。

### 阶段 2：权威调研

- CloudEvents 规范 v1.0.2：<https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md>（访问：2026-09-20）。参考事件上下文中的来源、类型、身份和版本语义，以及跨传输的一致事件识别；规范不替代业务 Owner、权限和来源真实性判断。
- W3C PROV-O：<https://www.w3.org/TR/prov-o/>（访问：2026-09-20）。参考 Entity、Activity、Agent 及其生成、使用、派生关系，支持把原始事件、纠正、派生记忆和决定分开追溯；不规定企业记忆的归属裁决。
- RFC 3339：<https://www.rfc-editor.org/rfc/rfc3339>（访问：2026-09-20）。参考明确区分并表达带时区的时间信息；时间格式正确不等于事件顺序或事实有效性成立。
- Kubernetes API Concepts：<https://kubernetes.io/docs/reference/using-api/api-concepts/>（访问：2026-09-20）。参考 Resource Version、Watch、资源版本比较和变更观察中的并发/过期处理；其资源版本不是通用业务事件时间，也不能直接替代归属版本。
- Apache Kafka 文档“Message Delivery Semantics”：<https://kafka.apache.org/documentation/#semantics>（访问：2026-09-20）。参考至少一次、至多一次和精确一次处理语义的边界，以及消费者仍需设计幂等；传输层语义不能自动保证跨系统归属副作用只发生一次。
- RFC 7232：<https://www.rfc-editor.org/rfc/rfc7232>（访问：2026-09-20）。参考 ETag/条件请求所体现的版本匹配和避免盲目覆盖原则；HTTP 条件机制不替代事件血缘、时间有效性和权限检查。

共同规律：事件身份、来源、时间、版本和派生关系必须可追溯；传输重复是常态，消费者应幂等；版本冲突和迟到输入要显式处理；来源与事件的可识别性不等于来源已获授权或内容已被验证。任何机制都不支持“缺 metadata 就猜 Scope”或“最后到达即为真”。

### 阶段 3：总结、结论与建议

建议把 Connector 处理划分为四个相互独立的判断面：

```text
Identity       = 这是不是可识别、可去重的事件
Provenance     = 它来自谁、通过什么连接、能否验证
Binding        = 它指向哪个资源、Work Thread 和 MemorySpace
Temporal State = 它对哪个有效时间/版本生效、是否迟到或冲突
```

四个判断面中任意一个不成立，都不能由其他面“补齐”成正式 Owner。特别是：

1. **缺失元数据默认收窄**：只能保留已验证的最窄边界；无法验证则 `ownership_pending` 或隔离。内容、模型分数、产生 Agent、最近活动和成员身份只能生成候选，不能扩大 Scope；
2. **错误绑定默认隔离**：冻结由错误绑定产生的新增检索、摘要、派生和执行，保留历史证据，使用追加纠正、版本化重算和影响核验完成修复；
3. **迟到/乱序默认版本保护**：事件时间、接收时间、处理时间分开，版本/水位用于判断处理进度，不能用到达顺序覆盖事实；不确定的迟到输入转为候选、待重算或隔离；
4. **重复/重放默认幂等**：重复投递不重复改变归属或传播；同身份冲突、旧撤回重放和跨版本重放进入冲突处理；
5. **修正默认追加而非覆盖**：修正必须绑定原事件/版本、修正主体、影响和新决定；历史快照不可被静默改写；
6. **不可验证来源默认不具权威性**：可保留受限证据，但不能驱动 Owner、授权扩大、普通检索或自动执行；重新验证后重新决策。

推荐的阶段性状态语义为：

```text
received
→ verified / unverified
→ binding_pending / bound / binding_conflict
→ current / late / out_of_order / duplicate / replay
→ candidate / applied / corrected / withdrawn / isolated
```

这些是治理语义而非最终枚举；一个事件可以同时具有“来源未验证”“绑定待定”和“迟到”等维度。状态变化应追加记录，不能把异常状态压扁成一个成功/失败标志。

最小安全不变量：

- 缺失或不可信元数据永不扩大 Scope；
- 错误绑定永不继续扩大传播；
- 迟到事件永不凭到达顺序覆盖较新的有效版本；
- 重复/重放永不重复产生不可逆副作用；
- 历史快照永不因当前纠正被静默改写；
- 任何无法验证、无法授权或无法审计的关键步骤失败时，默认暂存、收窄或隔离。

### 阶段 4：专家团讨论

- **产品/UX**：用户需要看到“来源未验证”“绑定待确认”“事件迟到/正在重算”“已隔离”等可理解状态，以及影响范围和下一步；不能用“同步成功”掩盖数据尚未具备归属资格。
- **架构**：Connector 接入、来源证明、绑定解析、事件去重、版本投影和归属决策应保持职责分离；规范事件/证据不可被投影状态替代，纠正应生成新版本和血缘关系。
- **可靠性**：假设至少一次投递、重复、断连、迟到、乱序、重放和部分失败；要求幂等、版本保护、水位推进、可重算、暂停和失败可见，但具体窗口、容量和恢复目标留待运行设计。
- **安全/隐私**：缺失元数据不是扩大可见性的理由；绑定错误要先阻断传播；隔离内容不进入普通检索、摘要、Manifest、自动执行和默认训练；错误详情和隐藏资源关系仍按最小权限展示。
- **治理/审计**：需要能回答“谁在何时以哪个来源证明、绑定和版本作出了什么决定”，并区分接收事实、推断候选、纠正事实和当前有效决定。

专家团综合建议：采用“验证—窄边界—版本保护—幂等—隔离—追加纠正—影响重算”的阶段性规则。Connector 只提供归属证据入口，不自动获得扩大 Scope、授予权限或改变历史事实的能力。
