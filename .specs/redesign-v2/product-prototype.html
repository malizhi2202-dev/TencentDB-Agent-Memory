PRODUCT DESIGN PROTOTYPE · v2

让团队的记忆，成为 Agent 的工作能力

一个以 Project 为工作现场、Agent 为执行主体、MemorySpace 为认知边界的团队记忆与协作控制面。这里把“能访问什么、固定带什么、本轮用了什么”明确分开，并用审批、Run 和审计保证每次执行可解释。

工作现场
Project 协作边界

任务、Agent、资产、记忆围绕项目聚合。

执行主体
Agent 唯一原子

Agent 定义、装配、运行和版本可追踪。

认知边界
MemorySpace 隔离与策略

按用户、团队、项目、Agent 管理记忆。

治理证据
Run 可回放

工具、审批、结果和异常串成一条链。

产品解决什么问题

记忆散落

对话、Wiki、代码、技能各自存放，Agent 不知道何时使用。

关系不可见

项目、任务、Agent、空间、资产之间靠人工拼接。

执行不可解释

无法回答本次运行使用了哪些知识，为什么允许工具调用。

三条产品原则

关系优先

先建立 Project、Agent、Task、Space 的真实关系，再做页面。

契约先行

每个 UI 都必须有真实读模型、命令、权限和验收证据。

安全默认

未知能力拒绝，副作用先审批，错误不静默，状态可回放。

USER GUIDE

使用指南：从第一次登录到一次可追踪执行

参考 intent-os-platform 的“模块 → 环境 → 启动 → 产品使用 → 常见问题”结构，改写为产品用户的操作路线。

推荐上手路径

选择 Team 和 Project

Team 决定组织公共池，Project 决定协作边界。首次使用先在顶部上下文选择器中确认。

创建或选择 Agent

配置 Agent 的角色、模型、提示词和默认能力。不要把 Agent 当作普通成员，它是执行原子。

装配知识、技能和记忆空间

先看“可访问”，再配置“固定装配”，最后在运行详情中确认“本轮生效”。

创建任务并运行

任务有明确状态和负责人；运行遇到高风险工具会进入审批中心。

复盘与沉淀

在 Run 记录查看工具、召回、审批和结果；将稳定经验沉淀为记忆、Playbook 或 Skill Candidate。

什么时候使用记忆？

跨会话事实、用户偏好、项目决策、已验证的故障处理经验。

什么时候使用知识库？

需要引用原文、版本、文件位置和权限继承的团队资料。

什么时候创建 Skill？

一个重复出现、步骤稳定、可供多个 Agent 复用的方法。

CORE CONCEPTS

核心概念：先理解对象，再理解页面

每个概念都回答“它是什么、何时使用、如何操作、为什么存在”。

六个核心对象

对象是什么用户动作
Team组织归属轴与公共资产池成员、角色、公共资产
Project协作工作现场目标、任务、成员、Agent、记忆
Agent唯一执行主体配置、装配、运行、版本
Task跨会话要完成的工作分配、推进、阻塞、验收
MemorySpace记忆与知识的权限边界挂载、策略、浏览、治理
Run一次执行的事实记录回放、审批、诊断、复盘

三层关系：最容易混淆的概念

Accessible · 可访问

回答：Agent 按 Team、Project、Owner、ACL 能看到什么？

为什么：权限是候选集，不能等同于实际使用。

Fixed · 固定装配

回答：哪些 Skill、Wiki、Code、Space 长期配置给 Agent？

为什么：固定配置是默认能力，不代表每次都注入。

Effective · 本轮生效

回答：这一轮 Run 实际使用了什么版本和策略？

为什么：只有快照才能复现和解释一次运行。

ARCHITECTURE

总体架构：从用户动作到可追踪结果

借鉴 intent-os 的分层与统一执行链，但保持 TencentDB 的轻量记忆平台定位。

Web / SDK / Agent Adapter
用户入口、插件、工作台↓Panel / BFF
读模型聚合、命令适配、鉴权上下文↓Domain
Project · Agent · Task · Space · Governance↓MemoryCore / Knowledge
检索、写入、技能、Wiki、CodeGraph↓Infrastructure
SQLite · 图/向量 · LLM · OTel

为什么分层？

防止 Web 绕过权限直接查内核；把页面需求转成稳定读模型；让记忆算法可以替换而不重做 UI。

统一执行链

Request → Scope → Bundle → ToolPlan → Approval → Run → Events

所有入口最终进入同一条链，避免每个模块自定义状态。

可插拔但不静默

模型、向量、知识 Provider 可以替换；解析失败必须显式失败或告警，不能偷偷切换存储。

检索为什么这样设计

先解析 Scope

先过滤权限，再做向量、关键词和图扩展，避免召回后才补权限。

融合与去重

多路结果使用 RRF，近重复折叠，保留来源和 lineage。

预算打包

按 token budget 选择最有价值的片段，不把所有记忆塞进 Prompt。

解释后注入

展示分数、原因、空间和来源，再进入 Agent 上下文。

SEQUENCES

调用时序：每一步为什么存在

产品原型用静态事件演示一次完整请求；真实系统应由事件、Run 和审批共同驱动，而不是由 UI 猜状态。

一次对话与记忆注入

用户消息→Scope Resolver
身份 / 项目 / 空间→Memory Search
向量 / 关键词 / 图→RRF + Rerank
去重 / 预算→Guard
脱敏 / 注入防护→Agent / LLM
设计理由：权限过滤必须早于召回；所有召回结果要带来源和解释；低相关内容不进入上下文，避免“看起来记住了但实际误导”。

一次高风险工具调用

Agent 计划→Tool Inventory→Policy Gate→Approval Pending→Human/API Decide→Run 执行→Audit / Trace
设计理由：副作用只能出现在批准之后；审批详情与事件流分离；列表只给决策所需信息，敏感参数在授权后按权限查看。

记忆写入与技能沉淀

Conversation / Task→Candidate→Domain + Space→Write Policy→Write / Review→Memory Version→Trace → Skill Candidate

GLOSSARY & FAQ

术语与常见问题

术语定义不要混淆
Agent能够接收请求、解析上下文、调用工具并产生结果的执行主体。不是 Team，也不是一次 Run。
Skill渐进披露的提示词和文件包，描述做事方法。不是 Tool；不会凭空新增函数。
Tool运行时可调用的能力，需分类、授权、审批。不是知识文档。
Memory可被检索、带来源和谱系的长期记忆条目。不是完整原文知识库。
Run一次执行的事实、状态、事件和结果。不是 Task；Task 是跨会话目标。
Playbook从成功工作方法沉淀出的可复用流程资产。不是隐式的聊天摘要。

FAQ

为什么不直接把所有资料塞进 Prompt？

上下文有限、相关性不可控且容易越权。产品将检索、过滤、预算和解释拆开。

为什么要有 Project 和 Team 两套边界？

Team 是组织归属，Project 是协作关系；项目成员可以跨团队。

为什么必须保存 Bundle 快照？

没有快照无法解释某次运行用了哪个版本，也无法复现问题。
