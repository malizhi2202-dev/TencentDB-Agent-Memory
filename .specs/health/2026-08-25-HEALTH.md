## 6 维生产代码风险（内置回退）

### 🔴 R2 · Change Propagation 变更传播：双路径数据获取

**Symptom**：`CodeGraphPage.tsx:120` 用 `authFetch('/engine/graph')` 取图谱数据，`knowledge-api.ts:541` 有 `knowledgeApi.code.graph()` 走 KS 权限路径但从未被前端调用。

**Source**：Fowler · Refactoring · Divergent Change — 同一数据有两种获取方式，改权限模型时需要同时改两个路径。

**Consequence**：当前前端绕过 KS 的 `requireKnowledgeRead` 资源权限校验，任意 Panel 认证用户可读取任意 repo 的图谱数据。修复权限时需同时改两条路径，或漏改一条导致安全漏洞。

**Remedy**：CodeGraphPage 改用 `knowledgeApi.code.graph()` 替代 `authFetch('/engine/graph')`；`engineProxy` 路径降级为内部调试端点。

---

### 🔴 R2 · Change Propagation 变更传播：Chat 双 bug 导致功能完全不可用

**Symptom**：`NexusChatPanel.tsx:36` 读 `localStorage.getItem('panel_session')`，正确 key 是 `tdai-panel.session`。`code-graph-routes.ts:261` 用 `res.text()` 缓冲 SSE 流。

**Source**：Pragmatic Programmer · Orthogonality — 两个独立 bug 叠加导致单一功能完全失效，且各自修复后还需验证组合。

**Consequence**：Chat 功能对任何用户都不可用。即使修复了 localStorage key，SSE 流式体验也不存在（缓冲代理）。

**Remedy**：① 改用 `getPanelSession()` 替代 `authHeaders()`；② Chat 代理改为 `new Response(res.body, { headers: { 'Content-Type': 'text/event-stream' } })` 透传。

---

### 🔴 R3 · Knowledge Duplication 知识重复：NODE_COLORS / guessLang 多处定义

**Symptom**：
- `NODE_COLORS` 在 `GraphCanvas.tsx:18` 和 `FileTreePanel.tsx:50` 各定义一份，内容不完全一致（FileTreePanel 多了 `Type` 键，缺少 `Process`/`Community`/`Section`/`Route` 键）
- `guessLang` 在 `CodeInspector.tsx:16` 和 `CodeReferencesPanel.tsx:19` 重复定义，逻辑完全相同

**Source**：Pragmatic Programmer · DRY — 同一知识（颜色映射、语言推断）被表达在多处，且已出现不一致。

**Consequence**：改一处颜色，另一处忘记改 → 视觉不一致。新增语言支持需改两处。

**Remedy**：提取到 `src/pages/codegraph/constants.ts`，统一导出 `NODE_COLORS`、`EDGE_COLORS`、`TYPE_TO_LAYER`、`guessLang`。

---

### 🔴 R4 · Accidental Complexity 偶然复杂：多标签代码查看器过设计

**Symptom**：`CodeReferencesPanel` 支持同时打开多个文件标签（`codeTabs: CodeTab[]`），但用户一次只看一个文件。`CodeGraphPage` 维护 `codeTabs` / `activeCodeTab` 两个状态 + 4 个回调。

**Source**：Brooks · No Silver Bullet — Accidental Complexity。多标签是"我们觉得用户可能需要"而非"用户实际需要"。

**Consequence**：113 行代码 + 2 个 state 管理了一个未被使用的功能（实际场景中用户不会同时打开 3+ 个文件对比）。

**Remedy**：简化为单文件查看，`selectedNode.filePath` + `content` 直接渲染，去掉 `codeTabs` 数组。

---

### 🟡 R1 · Cognitive Overload 认知过载：12 个组件 2120 行，~25% 死代码

**Symptom**：`CodeInspector`（55 行）、`NodeTypeLegend`（38 行）从未被引用；`codegraph.css` 中 ~180 行 CSS 类（`_cg-left`、`_cg-legend`、`_cg-inspector`、`_cg-bottom`、`_cg-processes`、`_cg-right-overlay`）从未被 TSX 引用。

**Source**：Code Complete · McConnell — 死代码增加认知负担，维护者需判断"这段能不能删"。

**Consequence**：新人接手时需理解 2120 行代码，其中 ~530 行（25%）是无效的。每次改 CSS 都要猜测哪些类实际生效。

**Remedy**：删除 CodeInspector.tsx、NodeTypeLegend.tsx、废弃 CSS 类。

---

### 🟡 R5 · Dependency Disorder 依赖混乱：前端混用两套 API 风格

**Symptom**：`CodeGraphPage` 管理操作走 `knowledgeApi`（Panel POST 统一信封），图谱数据走 `authFetch`（Engine GET REST）。`NexusChatPanel` 既不使用 `authFetch` prop 也不使用 `knowledgeApi`，自己写 `authHeaders()` 从错误 key 读。

**Source**：Clean Architecture · Dependency Rule — 依赖方向不一致，同一页面三种数据获取方式。

**Consequence**：改 API 契约时需确认三种方式都正确。新增开发者不知道该用哪种。

**Remedy**：统一走 `knowledgeApi`（Panel POST → KS），去掉 `authFetch` 和 `NexusChatPanel` 的自定义 fetch。

---

### 🟡 R5 · Dependency Disorder 依赖混乱：Engine 无认证但 CORS *

**Symptom**：`service.ts:83-85` 设置 `Access-Control-Allow-Origin: '*'`，且无 token/API key 校验。Engine 监听 `0.0.0.0:8443`。

**Source**：SE@Google · Least Privilege — 服务应只开放必要的最小权限。

**Consequence**：任何人能访问 8443 端口就能直接调用 Engine API，绕过 Panel 和 KS 的全部权限校验。

**Remedy**：Engine 改为监听 `127.0.0.1`，CORS 移除或限制为 `localhost`。

---

### 🟡 R4 · Accidental Complexity 偶然复杂：`engineProxy` 的 URL 构造依赖隐式假设

**Symptom**：`code-graph-routes.ts:239` 用 `new URL(c.req.url)` 取 query params，依赖 Hono Node adapter 返回绝对 URL。在其他运行时（Deno/Cloudflare Workers）会抛异常。

**Source**：Philosophy of Software Design · Deep Module — 接口应隐藏实现细节，不应暴露运行时假设。

**Consequence**：切换到非 Node 部署环境时，所有 Engine 代理端点全部 502。

**Remedy**：改用 `c.req.query()` 逐参数转发，或 `new URL(c.req.url, 'http://x')` 兼容相对 URL。

---

### 🟡 R6 · Domain Model Distortion 领域扭曲：`cancelled` 标记不持久化

**Symptom**：`code-graph-service.ts:111` 的 `cancelled` 是 `Set<string>`（内存态），服务器重启后丢失。如果 restart 发生在 `processing` 状态且 delete 发生在 restart 前，worker 会继续执行。

**Source**：DDD · Evans — 领域状态应完整建模，内存态的状态丢失会导致领域不一致。

**Consequence**：KS 重启后，已删除的 code-graph 可能被 in-flight worker 重新写入。

**Remedy**：在 `runBuild` 入口检查 `getCodeGraphById` 是否为 null（已有 `isDeleted` 双判据，但依赖 `cancelled` 标记先于 `deleteCodeGraph` 删除。改为：先软删行 → 再置 cancelled 标记 → 再 cleanup，确保重启后 `getCodeGraphById` 返回 null）。
